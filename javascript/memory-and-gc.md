# Память и сборка мусора

> **Коротко.** Память в JavaScript выделяется неявно, когда создаются значения, а освобождает её сборщик мусора (garbage collector, GC). Объект можно собрать, когда до него нельзя добраться от корней: глобального объекта, стека вызовов, очередей задач и ссылок из хоста. Циклы этому не мешают. Утечка в языке со сборкой мусора — это нежелательная достижимость: забытый слушатель, таймер, кэш или замыкание держат то, что программе уже не нужно. `WeakMap`, `WeakRef` и `FinalizationRegistry` позволяют ссылаться на объект, не удерживая его.

**Связанные темы:** [Замыкания](./closures.md), [Типы данных и приведение типов](./types-and-coercion.md), [Дескрипторы свойств, `Proxy` и `Reflect`](./property-descriptors-and-proxy.md), [Event loop](./event-loop.md), [async/await, обработка ошибок и отмена](./async-await.md)

## Теория

### Что говорит спецификация

Жизненный цикл памяти один во всех языках: выделить, использовать, освободить. В JavaScript первый и третий шаги неявные. Литерал, вызов конструктора, конкатенация строк выделяют память. Освобождает её движок.

Спецификация ECMAScript почти ничего не говорит о памяти. В ней нет стека и кучи, нет алгоритма сборки и нет обязанности что-либо собирать. Раздел 9.9 начинается словами: спецификация «не гарантирует, что какой-либо объект или символ будет собран». Недостижимый объект может прожить долго или вечно. Поэтому всё, что связано со сборкой, описано через «может» (may).

Нормативно описано только одно — **живость** (liveness). Набор объектов живой, если программа без учёта `WeakRef` ещё может наблюдать идентичность хотя бы одного из них: сравнить через `===`, использовать как ключ `Map`. Объекты, которые не живы, движок вправе собрать: очистить указывающие на них `WeakRef`, удалить записи `WeakMap` и `WeakSet`, поставить в очередь колбэки `FinalizationRegistry`.

Живость в общем случае невычислима. Спецификация прямо говорит, что движки используют консервативное приближение — **достижимость** (reachability).

> [!NOTE]
> Миф «примитивы лежат на стеке, объекты в куче» к языку отношения не имеет. Спецификация не знает ни того, ни другого. В V8 строки, `BigInt` и дробные числа — объекты в куче. Без отдельного объекта хранятся только небольшие целые (Smi) и, например, элементы плотно упакованных числовых массивов. Локальная переменная, захваченная замыканием, тоже уходит в кучу ([подробнее](./closures.md#замыкания-и-память)).

### Достижимость и корни

Сборщик начинает с **корней** (roots) и идёт по ссылкам. Всё, что он обошёл, живо. Остальное — мусор. Корни:

- глобальный объект и глобальные лексические привязки (`let`/`const` верхнего уровня скрипта);
- стек вызовов: локальные переменные и аргументы активных функций, их записи окружения;
- очереди: колбэки таймеров, микрозадачи, ожидающие продолжения `await`;
- ссылки из хоста: слушатели событий на живых DOM-узлах, сам DOM-документ, `postMessage`-порты, открытые соединения.

Следствие: объект жив, пока есть **хотя бы один** путь от корня. Обнулить одну переменную недостаточно, если объект лежит ещё в массиве, кэше или в замыкании обработчика.

### Подсчёт ссылок против mark-and-sweep

**Подсчёт ссылок** (reference counting) хранит у объекта число входящих ссылок и освобождает его при нуле. Это просто и детерминированно, но не работает с циклами: два объекта, ссылающиеся друг на друга, держат счётчики на единице даже тогда, когда до них никто не может добраться. MDN прямо пишет: ни один современный JS-движок подсчёт ссылок для сборки не использует.

**Mark-and-sweep** (пометка и очистка) сводит вопрос «нужен ли объект» к «достижим ли он». Фаза пометки обходит граф от корней, фаза очистки освобождает непомеченное. Недостижимый цикл не помечен — значит, собран. Поколения, инкрементальность, параллельность и конкурентность — это улучшения того же алгоритма.

> [!NOTE]
> Утечки старых IE на циклах «DOM-узел ↔ обработчик» объяснялись тем, что DOM жил в COM-объектах с подсчётом ссылок, а JS — в отдельной куче со своим сборщиком. Цикл через границу двух куч не видел никто. Сегодня V8 и Oilpan (сборщик C++-объектов Blink) трассируют ссылки через границу JS ↔ DOM, и такой цикл собирается.

### Как это делает V8

> [!WARNING]
> Всё в этом подразделе — детали реализации V8 (Chrome, Node, Deno), а не спецификация. Другие движки устроены похоже, но не так же.

Сборщик V8 называется **Orinoco**. Он опирается на **гипотезу поколений**: большинство объектов умирает молодыми. Поэтому куча разделена.

- **Молодое поколение** — небольшое пространство из двух полупространств (semi-space). Новые объекты выделяются в одном из них сдвигом указателя, это очень дёшево. **Scavenge** (minor GC) копирует живые объекты во второе полупространство, после чего они меняются ролями. Стоимость пропорциональна числу **выживших**, а не всех объектов: мёртвые просто не копируются. Пережившие две сборки переносятся (promotion) в старое поколение.
- **Старое поколение** собирает **Mark-Compact** (major GC): пометка от корней, очистка в free-list'ы, частичное уплотнение (compaction) фрагментированных страниц.
- **Барьер записи** (write barrier). Чтобы minor GC не обходил всё старое поколение, каждая запись ссылки из старого объекта на молодой регистрируется в remembered set. Эти ссылки становятся дополнительными корнями.

Чтобы паузы были короткими, работа распределена. **Параллельно** — несколько потоков в одной паузе (так работает Scavenge). **Инкрементально** — маленькими порциями вперемешку с JS. **Конкурентно** — в фоновых потоках, пока JS выполняется (пометка и очистка старого поколения). Chrome дополнительно запускает сборку в **idle time**, например в простое между кадрами. Короткая пауза на главном потоке всё равно остаётся: завершение пометки, уплотнение, Scavenge.

> [!NOTE]
> В V8 есть альтернативный сборщик молодого поколения — Minor Mark-Sweep (MinorMS). В V8 14.6 из Node 26 он выключен по умолчанию (`--no-minor-ms`, сверено 2026-11-12), молодое поколение собирает Scavenger.

Что из этого следует на практике:

- создавать много короткоживущих объектов дёшево, дорого — держать их долго: каждый перенос в старое поколение — копирование, а старое поколение собирается реже и дольше;
- частые крупные сборки видны в Performance-профиле как `Major GC` / `Minor GC` и складываются в long tasks;
- `delete` свойства или `arr.length = 0` память сразу не возвращают — они только делают объекты недостижимыми к следующей сборке.

### Что удерживает память

Классы причин, по которым ненужный объект остаётся достижимым:

| Причина | Путь от корня | Что делать |
| --- | --- | --- |
| Глобальная переменная, случайная глобальная (`x = 1` без объявления в sloppy mode) | глобальный объект | модули и strict mode, явная очистка |
| Слушатель на `window`, `document`, долгоживущем `EventTarget` | хост → слушатель → замыкание | `removeEventListener`, `{ signal }`, `{ once: true }` |
| `setInterval`, незавершённый `setTimeout`, `requestAnimationFrame`-цикл | очередь таймеров → колбэк | `clearInterval`, флаг остановки |
| Замыкание с большим окружением | функция → `[[Environment]]` | не держать тяжёлое в той же области, что долгоживущие функции |
| Кэш на `Map`/объекте без вытеснения | модуль → `Map` → значения | ограничение размера (LRU), `WeakMap`, TTL |
| Detached DOM: узел удалён из документа, но на него ссылается JS | переменная → узел → всё поддерево | обнулять ссылки на узлы при удалении |
| Подписки на store, шину событий, `AbortSignal` всей страницы | источник → список подписчиков | отписка при уничтожении |
| Залогированный объект при открытых DevTools | консоль | не логировать большие объекты в проде |

Последствия утечки — рост кучи, всё более долгие major GC и в итоге падение вкладки или процесса. Диагностика описана ниже в «Как измерять» и подробно — в теме «Утечки памяти» раздела «Производительность».

> [!WARNING]
> В V8 `slice`, `substring` и подобные операции на длинной плоской строке могут вернуть **sliced string** — ссылку на родителя со смещением и длиной, без копирования символов. Пока жив короткий срез, жива вся исходная строка. На Node 26 срез длиной 20 символов удерживал 19-мегабайтного родителя, а срез длиной 12 — уже нет: короткие срезы копируются.

### Слабые ссылки: `WeakMap` и `WeakSet`

`WeakMap` связывает значение с объектом, не удерживая сам объект. Если ключ больше нигде не достижим, запись исчезает вместе с ним. Запись устроена как **ephemeron**: значение живо, только пока жив ключ. Поэтому значение может ссылаться на свой ключ, и это не мешает сборке.

Отсюда ограничения API:

- **Нет обхода, `size` и `clear`.** Результат зависел бы от того, когда прошла сборка. API сделан так, чтобы GC был ненаблюдаем.
- **Ключ — только то, что может удерживаться слабо** (`CanBeHeldWeakly`): объект или символ, не зарегистрированный через `Symbol.for`. Примитив нельзя «собрать»: число `42` можно получить заново в любой момент, у него нет идентичности. С ES2023 ключом могут быть уникальные символы. `Symbol.for('a')` — нет: его можно воссоздать по строке. Хорошо известные символы (`Symbol.iterator`) допустимы, но не будут собраны никогда.

`WeakSet` — то же для множества: «помечен ли этот объект», без удержания.

Типичные применения: метаданные для чужих объектов (DOM-узлов, объектов библиотек) без мутации; кэш вычислений по объекту; прокси-кэш «сырой объект → обёртка»; приватные данные до появления `#x`; множество уже посещённых узлов при обходе графа.

### Слабые ссылки: `WeakRef` и `FinalizationRegistry`

`WeakRef` (ES2021) — объект-ссылка, которая не удерживает цель. `deref()` возвращает цель или `undefined`, если её уже собрали.

Чтобы код вида `if (ref.deref()) ref.deref().foo()` не ломался посередине, цель после `deref()` попадает в список **`[[KeptAlive]]`** агента и удерживается сильно до вызова `ClearKeptObjects`. Конструктор `new WeakRef(target)` делает то же самое. Хост вызывает `ClearKeptObjects`, когда закончился синхронный участок выполнения. В HTML это конец **microtask checkpoint**, то есть после опустошения всей очереди микрозадач, а не после одной микрозадачи.

`FinalizationRegistry` (ES2021) вызывает колбэк когда-нибудь **после** того, как зарегистрированная цель собрана.

```js
const registry = new FinalizationRegistry((heldValue) => {
  // runs later, in its own task — never in the middle of sync code
});
registry.register(target, heldValue, unregisterToken);
registry.unregister(unregisterToken); // true if something was removed
```

- `heldValue` удерживается **сильно**, пока регистрация активна. Если он ссылается на цель, цель не будет собрана никогда. Передача самой цели как `heldValue` — `TypeError`.
- `unregisterToken` удерживается слабо. Им может быть и сама цель.
- Колбэк выполняется в отдельной задаче (в HTML — global task на JavaScript engine task source), не посреди синхронного кода.
- Колбэк может не выполниться вообще: например, если реестр сам стал недостижимым или страница закрывается.

> [!TIP]
> MDN советует избегать `WeakRef` и `FinalizationRegistry`, где это возможно. Они существуют для оптимизации памяти в долгоживущих программах: кэши больших объектов, освобождение внешних ресурсов (WebAssembly-памяти, хэндлов) как страховка. Логика программы не должна зависеть от того, собран ли объект и когда. Освобождать ресурсы нужно явно: `close()`, `dispose()`, `using`.

### Vue: где здесь сборка мусора

- **Зависимости хранятся по слабым ключам.** В `@vue/reactivity` 3.5 подписки лежат в `targetMap: WeakMap<target, Map<key, Dep>>`, а кэши прокси — в `reactiveMap`, `readonlyMap` и их shallow-вариантах, тоже `WeakMap`. Поэтому `reactive(obj)` не продлевает жизнь `obj`. Пока есть сырой объект, повторный `reactive(obj)` возвращает тот же прокси.
- **Рефакторинг 3.5** уменьшил память реактивной системы на 56 % (тест «1000 ref + 2000 computed + 1000 effect»). Заодно `computed` теперь подписывается на зависимости лениво — только когда у него есть подписчики. Поэтому «висящий» computed без подписчиков собирается, в том числе на SSR.
- **Большие данные — без глубокой реактивности.** `reactive` и `ref` создают прокси для каждого вложенного объекта при чтении и держат для них записи зависимостей. Для больших неизменяемых структур — `shallowRef` (заменять целиком) или `markRaw` (ставит на объект флаг `__v_skip`).
- **Эффекты и scope.** `watch`/`watchEffect`/`computed`, созданные синхронно в `setup()`, принадлежат effect scope компонента и останавливаются при размонтировании. Watcher, созданный в асинхронном колбэке (`setTimeout`, `then`), к компоненту не привязан и остановится только вручную. Для composables вне компонента — `effectScope()` и `onScopeDispose()`.
- **`<KeepAlive>`** держит экземпляры скрытых компонентов со всем их состоянием и DOM. Проп `max` включает LRU-вытеснение: ключи хранятся в `Set` в порядке использования, при переполнении удаляется самый старый.

### Как измерять

- **Chrome DevTools → Memory.** Heap snapshot показывает объекты и для каждого — **shallow size** (память самого объекта) и **retained size** (сколько освободится, если удалить объект: всё, что достижимо только через него). Режим Comparison между двумя снимками показывает, что выросло. Панель Retainers — путь удержания до корня. Allocation timeline показывает, какие выделения пережили сборку.
- **Performance** — события GC на таймлайне и график JS heap.
- **`performance.measureUserAgentSpecificMemory()`** — экспериментальный API для мониторинга памяти в проде. Требует secure context и cross-origin isolation, результат асинхронный и сравним только с самим собой. `performance.memory` — нестандартный устаревший API Chrome.
- **Node:** `process.memoryUsage()` (`rss`, `heapUsed`, `external`, `arrayBuffers`), `v8.writeHeapSnapshot()`, `node --inspect` с теми же инструментами DevTools. `node --expose-gc` даёт `globalThis.gc()` — только для экспериментов и тестов: из языка вызвать GC нельзя.

## Примеры

Метаданные для DOM-узлов без утечки и без мутации узлов:

```js
const tooltips = new WeakMap(); // element -> tooltip state

function attachTooltip(el, text) {
  tooltips.set(el, { text, shown: false });
}

function onHover(el) {
  const state = tooltips.get(el);
  if (state) state.shown = true;
}
// when el is removed from the DOM and dropped by JS, its entry goes away too
```

Слушатель, который снимается вместе с компонентом:

```ts
export function useWindowSize() {
  const width = ref(window.innerWidth);
  const controller = new AbortController();

  window.addEventListener('resize', () => {
    width.value = window.innerWidth;
  }, { signal: controller.signal, passive: true });

  // runs on unmount, or on effectScope().stop() outside a component
  onScopeDispose(() => controller.abort());
  return { width };
}
```

Без `abort()` слушатель на `window` держит замыкание, через него — `width` и всё окружение composable, а значит, и данные компонента после размонтирования.

Кэш больших объектов, который не мешает их сборке:

```js
const images = new Map(); // url -> WeakRef<ImageBitmap>

async function getImage(url) {
  const cached = images.get(url)?.deref();
  if (cached) return cached;
  const bitmap = await createImageBitmap(await (await fetch(url)).blob());
  images.set(url, new WeakRef(bitmap));
  return bitmap;
}
// the Map itself still grows with dead WeakRefs: see task 3
```

## Вопросы с интервью

::: details Как движок понимает, что объект больше не нужен?
Никак: «не нужен» невычислимо. Движок проверяет более слабое условие — достижимость. От корней (глобальный объект, стек вызовов, очереди задач и микрозадач, ссылки из хоста вроде слушателей на DOM-узлах) сборщик обходит граф ссылок. Непомеченное — мусор. Спецификация формально говорит о живости (можно ли ещё наблюдать идентичность объекта) и прямо допускает приближение через достижимость. Она также не обязывает собирать что-либо и не говорит, когда. Отсюда «утечка» в JS: объект достижим, хотя программе не нужен.
:::

::: details Собираются ли циклические ссылки? Почему не используют подсчёт ссылок?
Собираются. Mark-and-sweep смотрит на достижимость от корней, а не на число входящих ссылок, поэтому изолированный цикл не помечается и освобождается. Подсчёт ссылок цикл не освободит: счётчики не падают до нуля. Ни один современный JS-движок не использует его как основной механизм. Исторические утечки IE на циклах «DOM ↔ обработчик» были из-за того, что DOM жил в COM с подсчётом ссылок, а JS — в другой куче. Сейчас V8 трассирует ссылки через границу с Oilpan, и такие циклы собираются.
:::

::: details Как устроена сборка мусора в V8?
Это детали реализации, не спецификация. Гипотеза поколений: большинство объектов умирает молодыми. Молодое поколение — два полупространства. Scavenge копирует выживших во второе, стоимость пропорциональна числу живых объектов. Пережившие две сборки переносятся в старое поколение, которое собирает Mark-Compact. Ссылки «старый → молодой» отслеживает барьер записи, чтобы minor GC не обходил старое поколение. Паузы сокращают параллельный Scavenge, инкрементальная и конкурентная пометка, конкурентная очистка и сборка в idle time. Вывод для кода: короткоживущие объекты дешёвые, долгоживущие и переживающие сборку — дорогие.
:::

::: details Чем WeakMap отличается от Map и почему у WeakMap нет size и обхода?
`Map` держит ключи сильно: пока жива `Map`, живы все ключи и значения. `WeakMap` держит ключ слабо, а значение — пока жив ключ (ephemeron). Значение может ссылаться на ключ, и это не мешает сборке. Обход, `size` и `clear` сделали бы сборку наблюдаемой и недетерминированной, поэтому их нет. Ключи — только объекты и незарегистрированные символы (`CanBeHeldWeakly`), не примитивы и не `Symbol.for`: их можно воссоздать, у них нет идентичности. Применение — метаданные к чужим объектам, кэш по объекту, кэш прокси (так делает Vue), множество посещённых узлов.
:::

::: details Когда оправданы WeakRef и FinalizationRegistry и почему на них нельзя полагаться?
`WeakRef` — для кэша больших объектов, которые можно пересоздать: держим ссылку, но не мешаем сборщику. `FinalizationRegistry` — подчистить побочные структуры (запись в `Map` с мёртвым `WeakRef`) или как страховка для внешнего ресурса. Полагаться нельзя: сборка может не произойти никогда, колбэк может не вызваться, время зависит от движка и нагрузки. После `deref()` и после `new WeakRef` цель живёт минимум до конца текущего синхронного участка (`[[KeptAlive]]`). `heldValue` удерживается сильно — если он ссылается на цель, цель бессмертна. Освобождение ресурсов должно быть явным (`dispose()`, `using`), а финализатор — только подстраховкой.
:::

::: details Что такое shallow size и retained size? Как найти утечку?
Shallow size — память самого объекта без того, на что он ссылается. Retained size — сколько освободится, если удалить объект: он сам плюс всё, что достижимо **только** через него (его поддерево доминаторов). Утечку ищут так: воспроизвести сценарий (открыть и закрыть экран несколько раз), снять heap snapshot до и после, сравнить в режиме Comparison, отсортировать по росту и retained size. У подозрительного объекта по панели Retainers пройти путь до корня: обычно там слушатель, таймер, `Context` замыкания, кэш или detached DOM. Сборку DevTools форсирует перед снимком, поэтому в снимке только достижимое.
:::

::: details Как Vue избегает утечек в реактивности и где ответственность на разработчике?
Vue хранит зависимости в `targetMap: WeakMap<target, Map<key, Dep>>`, а кэш прокси — в `reactiveMap` на `WeakMap`. Поэтому реактивность сама не держит объекты. Эффекты, созданные синхронно в `setup()`, принадлежат effect scope компонента и останавливаются при размонтировании. С 3.5 `computed` подписывается лениво и собирается без подписчиков. На разработчике: watcher, созданный в асинхронном колбэке (не привязан к компоненту); слушатели на `window` и внешние подписки (снимать в `onScopeDispose`/`onUnmounted`); глобальное состояние на SSR, которое живёт весь процесс; `<KeepAlive>` без `max`; глубокая реактивность для больших данных вместо `shallowRef`/`markRaw`.
:::

::: details Правда ли, что примитивы хранятся на стеке, а объекты в куче?
Для языка — нет: спецификация не определяет ни стек, ни кучу, только значения и записи окружения. Для V8 это тоже неверно. Строки, `BigInt` и обычно дробные числа — объекты в куче. Без выделения хранятся небольшие целые (Smi) прямо в слове-указателе. Переменные, захваченные замыканием, живут в heap-объекте `Context` независимо от типа. Правильная формулировка: примитивы неизменяемы и передаются по значению, объекты — по ссылке (точнее, ссылка копируется по значению). Где лежат байты — решает движок.
:::

## Задачи

### 1. Что будет собрано · легко

После каждого фрагмента прошла полная сборка. Какие объекты, созданные в нём, будут собраны?

```js
// A
let user = { name: 'Ann' };
const admins = [user];
user = null;

// B
let a = {}, b = { a };
a.b = b;
a = b = null;

// C
const map = new Map();
let k1 = {};
map.set(k1, 'x');
k1 = null;

// D
const wm = new WeakMap();
let k2 = {};
wm.set(k2, { k2 });
k2 = null;

// E
function f() { const big = new Array(1e6); return () => 1; }
const g = f();

// F
function h() {
  const big = new Array(1e6);
  const log = () => big.length;
  log();
  return () => 1;
}
const g2 = h();
```

::: details Решение и разбор
- **A — нет.** `user = null` убирает одну ссылку, массив `admins` держит объект.
- **B — да.** Цикл недостижим от корней. Mark-and-sweep его не пометит.
- **C — нет.** `Map` держит ключи сильно. Ключ уже не достать без обхода `map`, но `map.keys()` его вернёт — значит, он жив.
- **D — да.** Значение ссылается на ключ, но запись `WeakMap` — ephemeron: значение живо, только пока ключ достижим из другого места.
- **E — да.** Спецификация говорит, что `g` держит окружение `f` целиком, но `big` больше никто не может наблюдать. В V8 `big` никто не захватил, и он даже не попадает в `Context` замыкания.
- **F — в V8 нет.** `log` захватила `big`, и `big` лежит в общем для области `Context`. Возвращённая стрелка держит этот же `Context`, хотя сама `big` не использует. Подробно — в задаче «Найдите утечку» темы [«Замыкания»](./closures.md).

Проверено на Node 26 с `--expose-gc`: в A, C и F объекты живы, в B, D, E собраны.
:::

### 2. Состояние для чужих объектов · легко

Нужен трекер: сколько раз пользователь кликнул по каждому элементу. Элементы приходят из разных частей приложения, их удаляют из DOM в любой момент. Нельзя мутировать элементы. Нужно также знать общее число кликов. Реализуйте `track(el)`, `clicks(el)` и `total()`.

::: details Решение и разбор
```js
const counts = new WeakMap(); // element -> number
let totalClicks = 0;

export function track(el) {
  counts.set(el, (counts.get(el) ?? 0) + 1);
  totalClicks++;
}

export const clicks = (el) => counts.get(el) ?? 0;
export const total = () => totalClicks;
```

- `WeakMap` не удерживает удалённые элементы: вместе с узлом исчезает и счётчик. С `Map` каждый когда-либо кликнутый узел жил бы вечно — со всем поддеревом и слушателями.
- `total()` нельзя посчитать обходом: у `WeakMap` нет итерации. Агрегаты хранят отдельно. Если нужен список «живых» элементов со счётчиками — это уже другая задача: нужен явный жизненный цикл (`untrack(el)` при удалении) или `WeakRef` в обычной `Map`.
- Ключ — только объект. `track('button-1')` бросит `TypeError`. Для строковых идентификаторов `WeakMap` бессмысленна: строку нельзя «собрать».

Сложность: O(1) на операцию; память — O(число живых элементов).
:::

### 3. Кэш со слабыми значениями · средне

Пример `getImage` выше держит `Map<url, WeakRef>`: значения собираются, но сами записи с мёртвыми `WeakRef` копятся. Реализуйте `WeakValueCache` с методами `get(key)`, `set(key, value)` и `size`, который удаляет записи после сборки значений. Учтите, что значение по ключу могут перезаписать до того, как сработает очистка старого.

::: details Решение и разбор
```js
class WeakValueCache {
  #map = new Map(); // key -> WeakRef<value>
  #registry = new FinalizationRegistry((key) => {
    const ref = this.#map.get(key);
    // the key may already point to a newer, live value
    if (ref && ref.deref() === undefined) this.#map.delete(key);
  });

  get(key) {
    return this.#map.get(key)?.deref();
  }

  set(key, value) {
    this.#map.set(key, new WeakRef(value));
    this.#registry.register(value, key);
    return this;
  }

  get size() {
    return this.#map.size; // may include entries whose value is already dead
  }
}
```

- `heldValue` — ключ, а не значение. Реестр держит `heldValue` сильно: передай мы значение или объект со ссылкой на него, значение не собралось бы никогда. Передача самого значения — `TypeError`.
- Проверка `ref.deref() === undefined` защищает от гонки. Старое значение собрано, очистка встала в очередь, а тем временем `set` записал по тому же ключу новое живое значение. Без проверки колбэк удалил бы свежую запись. Сравнить сохранённый `WeakRef` с актуальным тоже работает: `heldValue` может быть `{ key, ref }`, ведь ссылка на `WeakRef` цель не удерживает.
- `size` приблизителен: между сборкой и колбэком запись ещё есть. Колбэк может не прийти никогда, поэтому для гарантий добавляют ленивую очистку в `get` (`deref() === undefined` → `delete`).
- `this` внутри стрелки в инициализаторе поля — экземпляр. Реестр держит колбэк, колбэк — кэш, кэш — реестр: обычный цикл, он собирается целиком.

Проверено на Node 26 с `--expose-gc`, включая гонку с перезаписью ключа.

Сложность: O(1) на `get` и `set`; память — O(число записей, ещё не очищенных).
:::

### 4. Почему тест не видит сборку · средне

Тест для кэша из задачи 3 запускают в Node с `--expose-gc`. Он падает: значение не собрано. Почему? Как написать тест?

```js
test('drops collected values', () => {
  const cache = new WeakValueCache();
  let value = { id: 1 };
  cache.set('a', value);
  value = null;
  gc();
  expect(cache.get('a')).toBeUndefined();
});
```

::: details Решение и разбор
`new WeakRef(value)` внутри `set` выполняет `AddToKeptObjects(value)`: цель кладётся в список `[[KeptAlive]]` и удерживается **сильно** до `ClearKeptObjects`. Тот же эффект у каждого `deref()`. Хост очищает список, только когда закончился синхронный участок выполнения — в HTML и Node это конец microtask checkpoint. Значит, `gc()` в том же синхронном коде объект не соберёт по спецификации. Это не баг движка. Даже `await null` не поможет: продолжение выполняется в той же проверке микрозадач. На Node 26 после `await null` объект был жив, после `setTimeout` — собран.

```js
const nextTask = () => new Promise((r) => setTimeout(r, 0));

test('drops collected values', async () => {
  const cache = new WeakValueCache();
  cache.set('a', { id: 1 });       // no local variable keeps it alive

  await nextTask();                // ClearKeptObjects has run
  gc();
  expect(cache.get('a')).toBeUndefined();

  await nextTask();                // the cleanup callback runs in a task
  expect(cache.size).toBe(0);
});
```

- Тест всё равно опирается на поведение конкретного движка: спецификация не обязывает `gc()` что-то собирать. Такие тесты держат отдельно и помечают как зависящие от V8.
- Надёжнее тестировать логику без сборщика: вынести создание `WeakRef` и реестра в зависимость и подменить её фейком, который «собирает» по команде.
- Для `FinalizationRegistry` одной задачи иногда мало: если колбэк не пришёл, повторяют `gc()` и ожидание в цикле с ограничением попыток.
:::

### 5. Срез держит мегабайты · сложно

Сервис на Node парсит большие ответы (десятки мегабайт строкой) и сохраняет из каждого короткий идентификатор в долгоживущий `Set`. Память растёт примерно на размер ответа с каждым запросом, хотя сами ответы нигде не хранятся. Объясните причину и исправьте `extractId`.

```js
const seen = new Set();

function extractId(body) {
  const start = body.indexOf('"id":"') + 6;
  return body.slice(start, body.indexOf('"', start)); // 20-36 chars
}

function onResponse(body) {
  seen.add(extractId(body));
}
```

::: details Решение и разбор
Деталь V8: `slice` на плоской строке возвращает **sliced string** — объект «родитель + смещение + длина» без копирования символов, если результат не короче 13 символов. Короткий идентификатор в `Set` держит весь ответ. В heap snapshot это видно как `sliced string` с retained size в мегабайты и родителем в Retainers. На Node 26 пять срезов по 20 символов удерживали около 76 МБ, срезы по 12 символов и копии — ничего.

Исправление — получить строку, которая не ссылается на родителя:

```js
function extractId(body) {
  const start = body.indexOf('"id":"') + 6;
  const id = body.slice(start, body.indexOf('"', start));
  return [...id].join(''); // builds a new flat string from code points
}
```

- В языке нет API «скопировать строку», поэтому любой способ — опора на поведение движка. `[...s].join('')` проверен на Node 26. Популярный трюк `(' ' + s).slice(1)` создаёт новую плоскую строку из конкатенации, и срез ссылается уже на неё, а не на ответ. Для идентификатора допустимо и `Buffer.from(s).toString()`.
- Лучшее исправление — не держать строку вовсе: парсить поток (`JSON.parse` создаёт новые строки для значений), хранить числовой id, хэш или ограничивать `seen` по размеру — сам по себе неограниченный `Set` тоже утечка.
- Та же ловушка у регулярных выражений: группы захвата `match` и `exec` — тоже срезы.

Сложность: O(k) на копирование среза длины k.
:::
