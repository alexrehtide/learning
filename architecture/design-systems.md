# Design system и UI-kit

> **Коротко.** UI-kit — это набор готовых компонентов. Design system шире: в неё входят токены, компоненты, правила их применения, документация и процесс выпуска версий, то есть общий язык дизайна и разработки. Основа — дизайн-токены в три уровня (primitive → semantic → component), формат DTCG и CSS custom properties: так темы и dark mode переключаются без пересборки. Поведение и доступность сложных компонентов сегодня берут из headless-библиотеки (во Vue — Reka UI), а поверх кладут свой стиль; Nuxt UI устроен именно так. Senior проектирует API компонента так, чтобы его расширяли без форка, считает доступность частью контракта и выпускает kit по semver: deprecation в minor, удаление в major, codemod для массовых правок.

**Связанные темы:** [Принципы и паттерны проектирования](principles-and-patterns.md), [Структура большого проекта и Feature-Sliced Design](large-project-structure.md), [UI-coding: базовые компоненты на Vue](../live-coding/ui-components.md), [UI-coding: автокомплит, таблица, дерево](../live-coding/ui-widgets.md), [Оптимизация загрузки](../performance/loading.md), [CSRF, clickjacking и supply chain](../security/csrf-and-clickjacking.md), [Utility, conditional и mapped types](../typescript/type-level-programming.md)

## Теория

### Design system, UI-kit, библиотека компонентов

Эти слова часто путают, и на интервью их различие проверяют первым вопросом.

| | Библиотека компонентов | UI-kit | Design system |
| --- | --- | --- | --- |
| Что это | код: `Button`, `Dialog`, `Select` | компоненты + визуальный стиль продукта (часто и макеты в Figma) | токены, компоненты, паттерны, правила, документация, процесс |
| Отвечает на вопрос | «как сделать кнопку» | «как выглядит наша кнопка» | «когда нужна кнопка, а когда ссылка, и кто решает, что добавить» |
| Владелец | команда или open source | команда продукта | отдельная команда или гильдия с процессом вклада |
| Пример | Reka UI | `shared/ui` одного продукта | Material Design, GOV.UK Design System |

Design system — это **продукт для внутренних потребителей**. У неё есть пользователи (команды), roadmap, версии, changelog и поддержка. Без процесса она за год превращается в UI-kit, который каждая команда форкнула под себя. Поэтому на senior-интервью говорят не только о компонентах, но и о том, как в систему попадает новый компонент: кто предлагает, кто ревьюит дизайн и код, как решают, что компонент общий, а не продуктовый.

### Дизайн-токены: три уровня

**Дизайн-токен** — именованное дизайн-решение: цвет, отступ, радиус, шрифт, длительность анимации. Токен отделяет **имя** решения от **значения**, и поэтому значение меняется в одном месте. Токены обычно раскладывают в три уровня:

| Уровень | Пример имени | Значение | Кто использует |
| --- | --- | --- | --- |
| Primitive (палитра, base) | `color.blue.600` | `#2563eb` | только семантические токены |
| Semantic (alias, назначение) | `color.bg.accent`, `color.text.danger` | `{color.blue.600}` | компоненты и экраны |
| Component | `button.primary.bg` | `{color.bg.accent}` | один компонент |

Главное правило: **компоненты не ссылаются на примитивы**. В кнопке пишут `var(--color-bg-accent)`, а не `var(--color-blue-600)`. Тогда тема, ребрендинг или dark mode меняют только связи semantic → primitive, а код компонентов не трогают. Компонентный уровень нужен не всегда. Он оправдан, когда кнопку перекрашивают отдельно от остальных акцентов, например под бренд партнёра. Иначе он раздувает список токенов, и сотни переменных никто не может удержать в голове.

Имена семантических токенов описывают **назначение**, а не вид: `text.muted`, а не `text.gray`. «Серый» в тёмной теме перестаёт быть серым, а «приглушённый» остаётся приглушённым.

### Формат DTCG и сборка в CSS

Design Tokens Community Group (W3C Community Group, не W3C Standard) выпустила первую стабильную версию спецификации **2025.10** 28 октября 2025 года. Она состоит из трёх модулей: Format, Color и Resolver. Файлы — JSON с расширением `.tokens` или `.tokens.json`, media type `application/design-tokens+json`. Главные правила Format:

- токен — объект со свойством `$value`, группа — объект без него;
- `$type` задают у токена или наследуют от группы, и инструменты **не должны** угадывать тип по значению;
- алиас пишется как `"{color.blue.600}"` и указывает на `$value` целого токена; JSON Pointer `"$ref": "#/…"` может указать и на часть значения;
- циклические ссылки запрещены, инструмент обязан их обнаружить;
- кроме простых типов (`color`, `dimension`, `fontFamily`, `fontWeight`, `duration`, `cubicBezier`, `number`) есть составные: `shadow`, `border`, `typography`, `transition`, `gradient`, `strokeStyle`;
- у цвета значение — объект с цветовым пространством: `{ "colorSpace": "srgb", "components": [0.15, 0.39, 0.92], "hex": "#2563eb" }`.

Модуль **Resolver** (файл `.resolver.json`) описывает токены, которые зависят от контекста: тему, плотность, бренд. В нём **sets** — наборы токенов, **modifiers** — переключатели с именованными контекстами (`light`, `dark`, `darkHighContrast`) и `resolutionOrder` — порядок наложения, где более поздний источник побеждает. На вход подаётся выбор вроде `{ "theme": "dark" }`. Число возможных результатов равно произведению числа контекстов всех модификаторов, поэтому две темы × два бренда × две плотности дают уже восемь сборок.

> [!NOTE]
> Спецификацию продолжают развивать: на designtokens.org лежит черновик от 08.09.2026 с пометкой «не реализуйте эту версию» (сверено 2026-11-14). Ссылаться и реализовывать нужно версию 2025.10. Поддержка в инструментах (Figma, Tokens Studio, Style Dictionary) появлялась постепенно, поэтому формат конкретного инструмента стоит проверить.

Источник истины — JSON, но браузер JSON не читает. Сборка превращает токены в артефакты для каждой платформы: CSS custom properties для веба, Swift и Kotlin для мобильных приложений, тему Tailwind. Для веба выбирают **CSS custom properties**, а не переменные Sass. Переменная Sass исчезает при компиляции, а custom property живёт в рантайме: её наследуют потомки, переопределяют в поддереве (`[data-theme="dark"]`, бренд в одном виджете) и читают из JS. Поэтому тема переключается сменой атрибута на `<html>`, без второго бандла CSS.

Dark mode строится на семантическом уровне. Компоненты ссылаются на семантические токены, поэтому для тёмной темы достаточно переопределить только их. Начальную тему берут из `prefers-color-scheme`, выбор пользователя хранят в cookie или `localStorage`. В SSR тему нужно знать до первой отрисовки, иначе страница мигнёт светлой темой. Поэтому Nuxt-модули ставят класс на `<html>` маленьким inline-скриптом в `<head>` (с [CSP](../security/csp.md) ему нужен nonce или hash) либо читают cookie на сервере.

### Headless против стилизованных библиотек

| | Стилизованная (Vuetify, PrimeVue в styled-режиме) | Headless (Reka UI) | Свой kit поверх headless (Nuxt UI, shadcn-vue) |
| --- | --- | --- | --- |
| Даёт | поведение + a11y + внешний вид | поведение + a11y + ARIA + фокус, без стилей | всё, при этом стиль ваш |
| Свой бренд | борьба с чужим CSS, `!important`, глубокие селекторы | полный контроль | контроль через токены и варианты |
| Цена | быстро стартовать, дорого отличаться | разметку и стили пишете сами | нужно поддерживать свой слой |
| Хорошо для | админки, внутренние инструменты | основа собственной design system | продукт с собственным дизайном |

Headless стал стандартом, потому что делит работу по реальной сложности. Сложно и одинаково для всех сделать правильный combobox: клавиатуру, roving focus, `aria-activedescendant`, typeahead, портал, позиционирование, возврат фокуса, RTL. Это пишется один раз и проверяется с экранными читалками. Внешний вид у каждого продукта свой, и чужие стили здесь только мешают. Стилизованная библиотека смешивает эти слои, поэтому ребрендинг превращается в войну с её CSS.

**Reka UI** — новое имя Radix Vue начиная с v2 (актуальная версия — 2.11, сверено 2026-11-14). По документации это «low-level UI component library» для доступных design systems. Компоненты поставляются без стилей, следуют паттернам WAI-ARIA, по умолчанию неконтролируемые, но могут быть полностью контролируемыми (`v-model:open`). Prop `asChild` отдаёт рендеринг своему дочернему элементу. Компоненты составные: `DialogRoot`, `DialogTrigger`, `DialogPortal`, `DialogOverlay`, `DialogContent`, `DialogTitle`, `DialogDescription`, `DialogClose`.

**Nuxt UI v4** — открытая (MIT) библиотека из 125+ компонентов, с которой объединили бывший платный Nuxt UI Pro. Она построена на трёх основах: Reka UI отвечает за поведение и доступность, Tailwind CSS (CSS-first, токены через `@theme`) — за стили, Tailwind Variants — за варианты. Это готовая реализация схемы «headless + токены + варианты». У неё семантические цвета (`primary`, `secondary`, `success`, `info`, `warning`, `error`, `neutral`), которые назначаются в `app.config.ts`. Тему компонента можно переопределить на четырёх уровнях, от слабого к сильному: глобально в `app.config.ts` (`ui.button.slots`, `variants`, `defaultVariants`), компонентом `<UTheme>` для поддерева, prop `ui` у экземпляра и prop `class`, который приклеивается к корневому слоту. Это и есть расширяемость без форка.

### API компонента: как не сделать «комбайн»

У компонента kit десятки потребителей, поэтому ошибку в его API исправляют через major-версию. Правила, которые на интервью ожидают услышать:

- **Варианты — объединение строк, а не набор boolean.** `variant: 'solid' | 'outline' | 'ghost'` вместо `primary`, `outline` и `ghost` как отдельных флагов. Флаги допускают бессмысленные сочетания (`primary` + `ghost`), и их число растёт как 2ⁿ. Объединение перечисляет только допустимые состояния, и TS проверяет его ([типы-объединения](../typescript/narrowing.md)).
- **Props — для данных и состояния, слоты — для содержимого.** `icon="i-lucide-plus"` подходит для простого случая. Но если в кнопку понадобится бейдж или спиннер особой формы, prop `iconColor` не поможет, а слот `#leading` поможет. Хороший компонент даёт оба варианта: prop для типового случая и слот, чтобы выйти за его пределы. Как разбирают компонент, обросший props, — в задаче «Компонент-комбайн» темы [о принципах](principles-and-patterns.md).
- **`v-model` и оба режима.** Поле ввода, переключатель или диалог работают и неконтролируемыми (своё состояние), и контролируемыми (`v-model`). Во Vue 3.4+ это одна строка `defineModel()` ([подробнее](../live-coding/ui-components.md)).
- **Составные компоненты вместо массива конфигов.** `<Tabs><TabsList><TabsTrigger>` даёт потребителю место для разметки там, где `items: [{ label, icon, badge, disabled, tooltip }]` разрастается бесконечно.
- **Атрибуты и полиморфизм.** Обычный HTML-атрибут (`aria-*`, `data-testid`, `type`) должен доходить до нужного DOM-элемента. Для этого в многокорневом или обёрнутом компоненте пишут `inheritAttrs: false` + `v-bind="$attrs"`. Кнопка-ссылка — это `as="a"`/`asChild` или отдельный `to`, а не вторая копия компонента.
- **Escape hatch** — `class` и `ui`-слоты, как в Nuxt UI. Если запасного выхода нет, потребитель скопирует компонент к себе, и такие копии kit уже не обновит.

### Доступность как контракт компонента

Kit отвечает за доступность так же, как за типы props. Поведение диалога, вкладок или combobox по [WAI-ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/) входит в публичное API. Его ломающее изменение (например, Escape больше не закрывает диалог) — breaking change, даже если TS-интерфейс не изменился. Сам APG предупреждает, что его примеры нужно проверить с вспомогательными технологиями, прежде чем брать в production. Его же принцип «No ARIA is better than bad ARIA» объясняет, почему неверная роль хуже, чем никакой.

Ответственность делится так:

| Гарантирует kit | Остаётся потребителю |
| --- | --- |
| роли, `aria-*`-связки, клавиатуру, ловушку и возврат фокуса | осмысленный текст: заголовок диалога, `aria-label` у кнопки-иконки |
| видимый `:focus-visible`, контраст пар семантических токенов | не перекрасить токены в нечитаемые сочетания |
| `prefers-reduced-motion` для анимаций | не делать кликабельный `div` вместо `Button` |

Обязательное и проверяемое kit делает обязательным в API. Если без заголовка диалог недоступен, `title` — обязательный prop или kit выдаёт предупреждение в dev-режиме. Reka UI, например, предлагает либо `DialogTitle`, либо обёртку `VisuallyHidden`, а если описание не нужно — явный `:aria-describedby="undefined"`.

### Документация и тесты: Storybook

Kit документируют живыми примерами. **Storybook** (10.x, сверено 2026-11-14) — «мастерская» для разработки компонентов в изоляции. Поддержка Vue 3 идёт через интеграцию Vue + Vite. **Story** фиксирует одно отрисованное состояние компонента, и одна и та же story служит сразу документацией, площадкой для дизайнеров и тестом:

- **render-тест** — story отрисовалась без ошибки;
- **интеракционный тест** — `play`-функция кликает, печатает и проверяет результат;
- **a11y-тест** — аддон A11y прогоняет автоматические проверки на каждой story;
- **визуальный тест** — снимок пикселей сравнивается с эталоном, это делает облачный сервис Chromatic от авторов Storybook;
- аддон Vitest превращает stories в тесты Vitest в browser mode, поэтому они идут в том же CI, что и юнит-тесты.

Визуальные тесты в kit важнее, чем в продукте. Смена токена или отступа меняет сотни экранов, и глазами такое не проверить. Цена — шум от сглаживания шрифтов и анимаций и время на ревью диффов, поэтому снимки делают в одном браузере, без анимаций и с фиксированными данными.

### Версионирование и breaking changes

Kit выпускают по [Semantic Versioning 2.0.0](https://semver.org/): MAJOR — несовместимое изменение API, MINOR — обратно совместимая функциональность, PATCH — исправления. Две детали из spec, о которых часто забывают: пометка API устаревшим (deprecated) **обязывает** поднять minor, а в `0.y.z` «anything MAY change at any time». Kit, который годами живёт в `0.x`, ничего не обещает потребителям.

Публичное API kit шире, чем props:

| Изменение | Breaking? |
| --- | --- |
| удалён или переименован prop, слот, событие, токен | да |
| сменилось значение по умолчанию (`size: 'md'` → `'sm'`) | да |
| изменилась DOM-структура, на которую потребители вешают селекторы | формально нет, фактически ломает. Поэтому заранее объявляют, что DOM — не API, и дают `ui`/`class`/`data-*` |
| изменилась клавиатура или ARIA-поведение | да |
| визуальное изменение (новый радиус) | по договорённости: обычно minor с анонсом, крупный редизайн — major |
| добавлен необязательный prop, вариант, токен | minor |

Путь удаления: в minor старый prop продолжает работать и пишет предупреждение в dev-режиме, в документации и changelog указана замена. Spec советует выпустить хотя бы один minor с deprecation до удаления в major. Массовые переименования автоматизируют **codemod**: скрипт на AST (jscodeshift, ast-grep, свой трансформ над `@vue/compiler-sfc`) правит код потребителей. Если вы просите 40 команд вручную заменить `type="primary"` на `variant="solid"`, миграция растянется на год.

**Changesets** (`@changesets/cli` 3.x) автоматизирует выпуск. Автор PR добавляет changeset — markdown-файл, где во frontmatter указаны пакеты и тип изменения, а в тексте — запись для changelog. `changeset version` поднимает версии, пишет `CHANGELOG.md` и обновляет зависимые пакеты монорепозитория, а `changeset publish` публикует их и ставит git-теги `pkg@X.Y.Z`. В CI это обычно «release PR», который копит changesets и выпускает версию при мёрже.

### Дистрибуция

| Способ | Плюсы | Цена |
| --- | --- | --- |
| Папка в продукте (`shared/ui`) | ноль инфраструктуры, правки сразу | только один продукт |
| Пакет в монорепозитории (workspace) | изменение kit и всех потребителей одним PR, без публикации | все продукты обязаны жить в одном репозитории и обновляться разом |
| npm-пакет (приватный registry) | потребители обновляются в своём темпе, работает между репозиториями | несколько версий в проде одновременно, нужны semver, changelog и codemods |
| Nuxt Layer | kit приходит вместе с `app.config`, токенами, плагинами и composables | только для Nuxt-потребителей |

Для пакета важны технические детали. `vue` объявляют в `peerDependencies`, иначе в приложении окажутся два экземпляра Vue, и `provide`/`inject` между ними сломается. ESM-сборку делают с `sideEffects` (CSS-файлы указывают как side effects), чтобы работал tree shaking ([подробнее](../performance/loading.md)). Каждый компонент — отдельная точка входа. Публикация пакета — это поставка кода чужим продуктам, поэтому на неё распространяются меры против [атак на цепочку поставок](../security/csrf-and-clickjacking.md): provenance, 2FA, lockfile.

### Когда своя design system не нужна

Своя система окупается, когда у компании несколько продуктов или команд с общим брендом и есть люди, готовые поддерживать её как продукт. Одному продукту обычно хватает готовой библиотеки (Nuxt UI) с настроенными токенами и тонкого `shared/ui` с продуктовыми обёртками. Типичная ошибка senior-кандидата — предложить свою систему с нуля там, где проблема в отсутствии токенов и правил, а не компонентов.

## Примеры

### 1. Токены в формате DTCG и сборка в CSS

```json
{
  "color": {
    "$type": "color",
    "blue": {
      "600": { "$value": { "colorSpace": "srgb", "components": [0.149, 0.388, 0.922], "hex": "#2563eb" } },
      "400": { "$value": { "colorSpace": "srgb", "components": [0.376, 0.647, 0.98], "hex": "#60a5fa" } }
    },
    "bg": {
      "accent": { "$value": "{color.blue.600}", "$description": "Primary action background" }
    }
  },
  "button": {
    "primary": {
      "bg": { "$type": "color", "$value": "{color.bg.accent}" }
    }
  }
}
```

```css
/* generated: primitives + light semantic layer */
:root {
  --color-blue-600: #2563eb;
  --color-blue-400: #60a5fa;
  --color-bg-accent: var(--color-blue-600);
  --button-primary-bg: var(--color-bg-accent);
}

/* dark context: only the semantic layer is redefined */
[data-theme='dark'] {
  --color-bg-accent: var(--color-blue-400);
}
```

Компонентный токен ссылается на семантический через `var()`, поэтому переопределения в `[data-theme='dark']` хватает, чтобы перекрасить все кнопки. Если бы генератор подставил в `--button-primary-bg` готовое значение `#2563eb`, тёмная тема его бы не изменила.

### 2. Кнопка kit: варианты, слоты, полиморфизм

```vue
<script setup lang="ts">
import { computed } from 'vue'

type Variant = 'solid' | 'outline' | 'ghost'
type Size = 'sm' | 'md' | 'lg'

const props = withDefaults(defineProps<{
  variant?: Variant
  size?: Size
  loading?: boolean
  as?: 'button' | 'a'
}>(), { variant: 'solid', size: 'md', loading: false, as: 'button' })

defineSlots<{
  default(): any
  leading?(): any
  trailing?(): any
}>()

const isButton = computed(() => props.as === 'button')
</script>

<template>
  <component
    :is="props.as"
    :type="isButton ? 'button' : undefined"
    :class="['ui-button', `ui-button--${props.variant}`, `ui-button--${props.size}`]"
    :aria-busy="props.loading || undefined"
    :data-loading="props.loading || undefined"
  >
    <span v-if="props.loading" class="ui-button__spinner" aria-hidden="true" />
    <slot v-else name="leading" />
    <slot />
    <slot name="trailing" />
  </component>
</template>

<style scoped>
.ui-button--solid {
  background: var(--button-primary-bg);
  color: var(--color-text-on-accent);
}
.ui-button:focus-visible {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}
</style>
```

`type="button"` по умолчанию защищает от случайной отправки формы. Атрибуты потребителя (`aria-label`, `href`, `data-testid`) доходят до корня через fallthrough. Стили используют только токены, и ни одного литерала цвета в компоненте нет.

### 3. Deprecation prop и changeset

```ts
// Button.vue, inside <script setup>: old `type` prop kept for one minor cycle
const props = defineProps<{
  variant?: 'solid' | 'outline' | 'ghost'
  /** @deprecated since 2.4.0, use `variant`. Removed in 3.0.0 */
  type?: 'primary' | 'secondary'
}>()

const legacy = { primary: 'solid', secondary: 'outline' } as const

if (import.meta.env.DEV && props.type) {
  console.warn('[ui] <Button type> is deprecated, use variant="' + legacy[props.type] + '"')
}

const variant = computed(() => props.variant ?? (props.type ? legacy[props.type] : 'solid'))
```

```md
---

```

## Вопросы с интервью

::: details Чем design system отличается от UI-kit и библиотеки компонентов
Библиотека компонентов — это код. UI-kit — компоненты плюс визуальный стиль конкретного продукта. Design system — общий язык дизайна и разработки: токены, компоненты, паттерны применения, принципы, документация и процесс (кто добавляет компонент, как выпускаются версии, как собирают обратную связь). Ключевое слово — процесс. Design system — внутренний продукт с пользователями, roadmap и поддержкой. Без этого она превращается в набор форков. Сильный ответ добавляет, когда своя система не нужна: одному продукту хватит готовой библиотеки и токенов.
:::

::: details Что такое дизайн-токены и зачем делить их на уровни
Токен — именованное дизайн-решение, которое отделяет имя от значения. Уровни: primitive (палитра, `blue.600`), semantic (назначение, `bg.accent`, `text.muted`) и при необходимости component (`button.primary.bg`). Компоненты ссылаются только на семантические токены. Поэтому тема, dark mode и ребрендинг меняют связи semantic → primitive, а не код компонентов. Имена описывают назначение, а не цвет. Источник истины — JSON в формате DTCG (стабильная версия 2025.10), из него сборка генерирует CSS custom properties и артефакты для других платформ. Цена — дисциплина: токены без правил и ревью размножаются до сотен, и их никто не использует правильно.
:::

::: details Как реализовать темы и dark mode в design system
Тема — это переопределение семантического слоя токенов, а не второй набор компонентов. Токены собирают в CSS custom properties, тему переключают атрибутом или классом на `<html>` (`[data-theme='dark']`), и каскад перекрашивает всё дерево без второго бандла. Это работает, только если компоненты ссылаются на семантические токены через `var()`, а не на готовые значения. Начальное значение берут из `prefers-color-scheme`, выбор пользователя хранят в cookie. Так SSR отрисует нужную тему сразу, без мигания. Если тема есть только в `localStorage`, нужен блокирующий inline-скрипт в `<head>` с nonce для CSP. Отдельно проверяют контраст пар токенов в каждой теме. В DTCG варианты описывает модуль Resolver через modifiers и contexts, и надо помнить, что число комбинаций (тема × бренд × плотность) перемножается.
:::

::: details Почему headless-компоненты стали стандартом и что бы вы выбрали для Vue-проекта
Headless-библиотека отдаёт самое трудное и одинаковое для всех — поведение, клавиатуру, фокус и ARIA по APG, — но не навязывает внешний вид. Стилизованная библиотека смешивает эти слои, поэтому свой бренд превращается в борьбу с чужим CSS. Во Vue стандарт — Reka UI (бывший Radix Vue): составные компоненты, контролируемый и неконтролируемый режимы, `asChild`. Выбор зависит от задачи. Для админки подойдёт готовая стилизованная библиотека. Продукту на Nuxt подойдёт Nuxt UI: это Reka UI + Tailwind + варианты, тема настраивается через `app.config.ts`. Для собственной design system нескольких продуктов — свой слой стилей поверх Reka UI. Цена headless: разметку и стили пишете вы, и неправильной разметкой можно сломать доступность.
:::

::: details Как спроектировать API компонента kit, чтобы его не пришлось форкать
Варианты описывают объединением строк, а не набором boolean, чтобы невозможные сочетания не проходили проверку типов. Props — для данных и состояния, слоты — для содержимого, причём для типового случая есть prop, а для нетипового — слот. Компонент поддерживает и контролируемый, и неконтролируемый режим через `defineModel`. Сложные виджеты делают составными компонентами, а не массивом конфигов. Атрибуты потребителя доходят до нужного элемента. Полиморфизм — через `as` или `asChild`, а не через копию компонента. Для крайних случаев нужен escape hatch: `class` и переопределение отдельных слотов стиля (`ui` в Nuxt UI). Последний аргумент: у kit много потребителей, поэтому каждый prop — обещание, которое потом можно отменить только major-версией. Добавлять prop стоит, когда случай встретился у нескольких команд.
:::

::: details Что считается breaking change в UI-kit и как его выпустить
Удаление или переименование prop, слота, события или токена, смена значения по умолчанию, изменение клавиатурного или ARIA-поведения. Изменение DOM-структуры тоже ломает потребителей, если они вешают на неё селекторы, поэтому заранее объявляют, что DOM — не API, и дают `class`, `ui` и `data-*`. Визуальные изменения версионируют по договорённости. Путь по semver: в minor добавляют новый API, старый помечают deprecated (это само по себе требует minor), он пишет предупреждение в dev-режиме. Удаляют его в следующем major. Для массовой замены пишут codemod. Выпуск ведут через Changesets: changeset в каждом PR, release PR собирает changelog и версии. Если kit годами сидит в `0.x`, он формально ничего не обещает.
:::

::: details Как гарантировать качество и доступность компонентов kit
Доступность — часть контракта: поведение по APG, видимый фокус, контраст токенов и `prefers-reduced-motion` гарантирует kit. Обязательное для доступности делается обязательным в API (например, заголовок диалога) или проверяется предупреждением в dev-режиме. Каждое состояние компонента — story в Storybook. Одна story служит документацией, render-тестом, интеракционным тестом через `play` и a11y-проверкой аддоном A11y, а через аддон Vitest stories идут в CI. Визуальная регрессия (Chromatic или аналог) ловит то, что не видят юнит-тесты: изменение токена меняет сотни экранов. Автоматика находит только часть проблем доступности, поэтому ключевые виджеты проверяют вручную с клавиатурой и экранной читалкой.
:::

## Задачи

### 1. Разложить цвета по токенам · легко

В проекте 40 компонентов, в стилях захардкожены `#2563eb` (кнопки, ссылки, активная вкладка), `#dc2626` (ошибки, кнопка удаления), `#6b7280` (подписи, плейсхолдеры, иконки). Нужна тёмная тема. Предложите токены и порядок миграции.

::: details Решение и разбор
Примитивы: `color.blue.600`, `color.red.600`, `color.gray.500` и пары для тёмной темы (`blue.400`, `red.400`, `gray.400`).

Семантика по назначению, а не по цвету: `bg.accent`, `text.link`, `border.accent-active` → blue; `text.danger`, `bg.danger` → red; `text.muted`, `icon.muted` → gray. Один примитив попадает в несколько семантических токенов, потому что у них разные причины меняться. Ссылки и кнопки сейчас одного цвета, но после ребрендинга могут разойтись.

Компонентные токены пока не нужны (YAGNI): ни один компонент не перекрашивается отдельно.

Миграция:
1. Сгенерировать CSS custom properties.
2. Codemod или поиск по регулярке заменяют литералы на семантические `var()`, но спорные места (серый — это подпись или граница?) решает человек.
3. Stylelint-правило запрещает литералы цвета в компонентах, чтобы они не вернулись.
4. Добавить `[data-theme='dark']`, который переопределяет только семантику, и проверить контраст каждой пары текст/фон.

Порядок важен: тёмная тема поверх захардкоженных цветов — это 40 файлов правок, а после миграции — один.
:::

### 2. API кнопки · средне

Предложен API: `<Button primary danger small large loading icon="plus" iconRight href="/x" />`. Что с ним не так и как бы вы его спроектировали?

::: details Решение и разбор
Проблемы:
- `primary`/`danger` и `small`/`large` — взаимоисключающие флаги. Сочетание `small large` проходит проверку типов, а поведение зависит от порядка проверок в коде.
- `icon` + `iconRight` — два prop на одно понятие, и всё равно нельзя поставить спиннер или бейдж.
- `href` без `as`: компонент молча становится ссылкой, а `disabled` у `<a>` не работает.

Новый API:

```ts
interface ButtonProps {
  variant?: 'solid' | 'outline' | 'ghost'
  color?: 'accent' | 'danger' | 'neutral'
  size?: 'sm' | 'md' | 'lg'
  loading?: boolean
  as?: 'button' | 'a'
}
// slots: default, leading, trailing
```

Вид (`variant`) и смысл (`color`) — разные оси. Поэтому «опасная обводка» выражается как `variant="outline" color="danger"`, и не нужен комбинаторный взрыв флагов. Иконки уходят в слоты `leading`/`trailing`, а для частого случая можно оставить сокращение `leading-icon="i-lucide-plus"`. Ссылка — это явный `as="a"` (или `to` с `NuxtLink`), а disabled-ссылки не бывает: если действие недоступно, рисуется кнопка.

Кнопка с одной иконкой без текста недоступна без подписи. Kit либо требует `aria-label` типом (отдельный компонент `IconButton` с обязательным `label`), либо предупреждает в dev-режиме.

Переход со старого API — по задаче 4: оба API живут один minor-цикл.
:::

### 3. Kit для трёх продуктов · сложно

В компании три Nuxt-приложения в трёх репозиториях, у каждого свой `components/ui` с похожими, но разными кнопками, модалками и селектами. У одного продукта другой бренд (цвета, шрифт, радиусы). Спроектируйте общий kit: основу, темизацию, дистрибуцию, процесс.

::: details Решение и разбор
**Основа.** Брать headless Reka UI, а не писать поведение с нуля: combobox и dialog по APG стоят недели работы. Если дизайн укладывается в Nuxt UI, стоит рассмотреть его и ограничиться темой: это дешевле своего слоя. Свой слой стилей нужен, если дизайн далёк от Nuxt UI.

**Токены.** Один набор токенов в DTCG, бренд — модификатор в Resolver (`brand: default | partner`), тема — второй модификатор (`light | dark`). Получается 2 × 2 = 4 сборки CSS custom properties. Компоненты знают только семантические токены, поэтому бренд партнёра — это файл значений, а не форк компонентов.

**Дистрибуция.** Репозитории разные, поэтому монорепозиторий с атомарными изменениями недоступен без переезда. Варианты:
- npm-пакет в приватном registry: продукты обновляются в своём темпе, нужны semver, Changesets, codemods;
- Nuxt Layer: тот же пакет, но приносит `app.config`, плагины и токены целиком. Это удобно, раз все потребители на Nuxt.

Разумно сделать оба слоя: Vue-пакет компонентов + тонкий Nuxt Layer с конфигурацией. `vue` и `reka-ui` — в `peerDependencies`.

**Процесс.** Владелец kit — небольшая команда или ротация из продуктовых команд. Новый компонент попадает в kit, когда он нужен минимум двум продуктам, а до этого живёт в продукте. Storybook публикуется для дизайнеров, визуальные тесты стоят в CI kit.

**Миграция.** Не «большой взрыв». Сначала токены во всех трёх продуктах, затем компоненты по одному, начиная с самых используемых (кнопка, поле ввода), а старые `components/ui` помечаются deprecated линтером. Метрика прогресса — доля импортов из `@acme/ui` против локальных компонентов.

**Цена,** которую стоит назвать: команда поддержки, медленные изменения из-за обратной совместимости и риск, что продукты застрянут на старых major-версиях. Без codemods и changelog так и происходит.
:::

### 4. Переименовать prop без поломки · средне

В kit `@acme/ui@2.3.0` у `Button` есть `type="primary" | "secondary"`, который конфликтует с нативным `type` кнопки (`submit`, `reset`). Нужно перейти на `variant`. Опишите выпуск.

::: details Решение и разбор
1. **2.4.0 (minor).** Добавить `variant`, оставить `type` со старыми значениями как deprecated: JSDoc `@deprecated`, предупреждение в dev-режиме, маппинг в `variant` (пример 3). Важно: значения `submit` и `reset` теперь должны проходить в нативный атрибут, иначе форма не отправится. Это повод сделать переход аккуратно, а не просто переименовать prop. Changeset с типом `minor` и инструкцией.
2. **Codemod.** Трансформ находит `<Button type="primary">` в SFC и `.ts`, заменяет на `variant="solid"`, а `type="submit"` не трогает. Динамические `:type="..."` он не меняет и помечает комментарием для ручной правки. Codemod прогоняют по всем репозиториям-потребителям и открывают PR.
3. **Наблюдение.** Поиск по коду или телеметрия dev-предупреждений показывает, сколько мест осталось.
4. **3.0.0 (major).** `type` в смысле варианта удалён, и `type` стал обычным нативным атрибутом. Changeset `major` и migration guide.

Ошибка, которую ждут услышать: переименовать в patch или minor «потому что это мелочь». Для потребителя после `npm update` это сломанная сборка или, хуже, молча неправильный вид.
:::
