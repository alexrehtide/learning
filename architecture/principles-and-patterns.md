# Принципы и паттерны проектирования

> **Коротко.** Принципы проектирования нужны, чтобы изменения стоили дёшево. Код, который меняется вместе, держат рядом (связность, cohesion), а между частями, которые меняются независимо, оставляют узкий контракт (зацепление, coupling). SOLID, DRY, KISS и YAGNI — эвристики вокруг этой идеи, а не законы, и у каждой есть цена: преждевременная абстракция обходится дороже дублирования. Во Vue паттерны встречаются в своих формах. Наблюдатель — это сама реактивность. Стратегия — словарь функций или `<component :is>`. Адаптер и фасад стоят на границе с API. Внедрение зависимостей делают через `provide`/`inject` и плагины. Композиция вместо наследования — это composables вместо mixins. Senior на интервью не перечисляет паттерны, а объясняет, какую проблему решает выбранный и чем за него платят.

**Связанные темы:** [EventEmitter](../live-coding/event-emitter.md), [Мини-реактивность в стиле Vue](../live-coding/mini-reactivity.md), [UI-coding: базовые компоненты на Vue](../live-coding/ui-components.md), [UI-coding: автокомплит, таблица, дерево](../live-coding/ui-widgets.md), [Функциональные приёмы и иммутабельность](../javascript/functional-programming.md), [Прототипы и классы](../javascript/prototypes-and-classes.md), [Модули: ESM и CommonJS](../javascript/modules.md), [Generics](../typescript/generics.md), [Дескрипторы свойств, Proxy и Reflect](../javascript/property-descriptors-and-proxy.md)

## Теория

### Связность и зацепление

**Связность** (cohesion) показывает, насколько части модуля относятся к одной задаче. **Зацепление** (coupling) показывает, сколько модуль знает о других модулях и насколько сильно от них зависит. Цель — высокая связность и слабое зацепление: изменение затрагивает один модуль и не расходится по проекту.

Во фронтенде зацепление бывает разной силы. Ниже виды от слабого к сильному:

| Через что связаны | Пример | Чем опасно |
| --- | --- | --- |
| Узкий явный контракт | props и события, параметры composable | почти ничем: зависимость видна в сигнатуре |
| Абстракция (порт) | компонент знает `OrdersApi`, а не `fetch` и URL | нужен слой адаптеров |
| Общий формат данных | DTO бэкенда используется прямо в шаблонах | переименование поля на сервере ломает десятки компонентов |
| Общее изменяемое состояние | несколько фич пишут в один стор | неясно, кто и почему изменил значение |
| Неявные события | глобальная шина, `window`-события | поток данных не виден по коду ([подробнее](../live-coding/event-emitter.md)) |
| Знание внутренностей | `$parent`, `ref` на ребёнка с вызовом его методов, импорт из чужой `internal/` | любой рефакторинг соседа ломает модуль |

Связность определяет, как раскладывать файлы. Раскладка по типу (`components/`, `stores/`, `utils/`) даёт низкую связность: одна фича разбросана по пяти папкам, и её изменение касается всех пяти. Раскладка по фичам держит вместе то, что меняется вместе. Как устроена такая структура в большом проекте, разбирается отдельной темой раздела.

### SOLID применительно к фронтенду

Роберт Мартин собрал SOLID для объектно-ориентированного кода, но принципы формулируются через модули и зависимости, поэтому переносятся на компоненты, composables и сторы.

| Принцип | Формулировка | Во Vue-коде | Перегиб |
| --- | --- | --- | --- |
| **S** — единственная ответственность | «Собирайте вместе то, что меняется по одним причинам, и разделяйте то, что меняется по разным» | компонент не смешивает загрузку данных, бизнес-правила и разметку, если у них разные «заказчики» | дробление на компоненты по 10 строк, где каждое изменение требует открыть пять файлов |
| **O** — открытость/закрытость | расширять поведение, не меняя существующий код | слоты, стратегии в props, реестры, плагины | точки расширения «на будущее», которыми никто не пользуется |
| **L** — подстановка Лисков | подтип можно использовать везде, где ожидается базовый тип | обёртка над `<input>` сохраняет `v-model`, атрибуты и события; все реализации порта ведут себя одинаково | — |
| **I** — разделение интерфейсов | клиент не зависит от методов, которыми не пользуется | узкие props (`name`, а не весь `user`), узкие порты, небольшие сторы | интерфейс на каждый метод |
| **D** — инверсия зависимостей | политика верхнего уровня зависит от абстракций, а не от деталей | компонент получает `OrdersApi` через `inject`, а не импортирует `axios` | абстракция над тем, что никогда не заменят и не нужно подменять в тестах |

**SRP — про людей, а не про «одну вещь».** В статье 2014 года Мартин прямо пишет: «This principle is about people». Причина изменения — это актор: дизайнер, продукт, бэкенд, юристы. Компонент формы заказа, где лежат вёрстка, правила скидок и формат запроса, меняется по трём причинам от трёх разных групп людей. Если правила скидок вынести в чистые функции, а запрос — в адаптер, каждая правка затронет одно место. Обратная ошибка — разрезать компонент на `OrderFormHeader`, `OrderFormBody`, `OrderFormFooter`, которые всегда меняются вместе. Связность от этого падает, а не растёт.

**OCP во Vue — это слоты и плагины.** Мартин называет системы плагинов высшим воплощением OCP: «Система не знает о плагинах. Плагины знают о системе». Компонент, который принимает слот `#cell-status`, расширяется без правки. Компонент, который на каждый новый случай получает булев prop и ветку `v-if`, приходится менять каждый раз. Это первый признак нарушения (задача 1).

**LSP проверяют обёртками.** `BaseInput` над нативным `<input>` должен вести себя как `<input>`: пробрасывать `$attrs` (`autocomplete`, `aria-*`, `name`), поддерживать `v-model` и не глотать `focus`/`blur`. Иначе он нарушает ожидания каждого, кто его подставил. В TypeScript совместимость структурная, поэтому компилятор проверит форму реализации порта, но не её поведение ([подробнее](../typescript/type-system.md)). Если `InMemoryOrdersApi` возвращает заказы в другом порядке или не бросает `NotFoundError`, тесты против неё ничего не доказывают.

### DRY, KISS, YAGNI и где они вредят

**DRY** в «Программисте-прагматике» сформулирован так: у каждого **знания** в системе должно быть одно авторитетное представление. Речь о знании, а не о тексте. Два одинаковых по коду валидатора, один для ИНН в форме регистрации, другой для ИНН в форме платежа, — это одно знание, и их стоит объединить. Два похожих компонента карточки товара в каталоге и в корзине — это разные знания, которые сегодня совпали случайно. Их объединение создаёт зацепление между фичами.

Сэнди Метц описывает, как растёт **ошибочная абстракция**. Разработчик выносит дублирование в общий модуль. Следующему требованию модуль «почти подходит», и в него добавляют параметр и условие. Через год у компонента 15 флагов, и каждое изменение ломает чужой экран. Отказаться жалко, потому что в абстракцию уже вложено много труда. Её вывод: «Дублирование намного дешевле ошибочной абстракции», а лечение — встроить абстракцию обратно в места вызова, удалить неиспользуемые ветки и только потом искать настоящую общую часть. Практическое правило — **правило трёх**: обобщать на третьем повторе, когда видно, что именно повторяется.

**KISS** — простейшее решение, которое решает задачу. Во фронтенде его чаще всего нарушают инфраструктурой: свой event bus, свой DI-контейнер, обёртка над Pinia, слой «сервисов», которые просто вызывают API. Каждый слой должен объяснять, что он скрывает. Если он только пробрасывает вызов дальше, это лишняя косвенность.

**YAGNI** («вам это не понадобится») — правило экстремального программирования: не строить сейчас то, что «понадобится потом». Мартин Фаулер считает цену такой функциональности так: цена разработки, цена задержки (полезное сделано позже), **цена владения** (лишняя сложность мешает каждому следующему изменению) и цена исправления, если идея верна, а реализация нет. Важная оговорка Фаулера: YAGNI не относится к тому, что делает код проще в изменении, то есть к рефакторингу, тестам и отделению адаптеров. Поэтому порт для HTTP-клиента не противоречит YAGNI: он окупается тестами уже сегодня. Плагинная система для одного экрана противоречит.

> [!TIP]
> На интервью принципы называют вместе с ценой: «Здесь я бы не выносил общий компонент: карточки совпадают сейчас, но меняются по требованиям разных команд. Дублирование в 40 строк дешевле зацепления каталога и корзины». Это отличает senior от того, кто выучил аббревиатуры.

### Композиция вместо наследования: composables против mixins

Во Vue 2 логику переиспользовали тремя способами: `mixins`, `extends` (наследование опций) и renderless-компоненты со scoped-слотом. Документация Vue 3 называет у mixins три недостатка:

1. **Неясный источник свойств.** Когда mixins несколько, по шаблону не видно, откуда взялось `this.loading`.
2. **Конфликты имён.** Два mixin разных авторов могут объявить одно и то же свойство.
3. **Неявное общение между mixins.** Mixin, которому нужны данные другого, полагается на общее имя свойства, и они оказываются скрыто зацеплены.

Composable решает все три. Результат деструктурируется, поэтому источник виден: `const { items, loading } = useOrders()`. При конфликте переменную переименовывают. Зависимость передаётся явно аргументом: `useFilter(items)`. Поэтому документация больше не рекомендует mixins во Vue 3 и сохраняет их только для миграции. Это та же идея, что «composition over inheritance» у «банды четырёх»: поведение собирают из независимых частей, а не наследуют вместе с чужим состоянием.

Composable против renderless-компонента. Документация советует composable для чистой логики, а компонент — когда переиспользуются и логика, и разметка. Renderless-компонент создаёт лишний экземпляр компонента, и на уровне всего приложения это заметные накладные расходы.

> [!NOTE]
> Composables выносят не только для переиспользования. Документация прямо предлагает дробить большой компонент на `useFeatureA`, `useFeatureB` по логическим задачам и называет их «сервисами в области видимости компонента». Это SRP внутри компонента. Соглашения composable (`use`-префикс, `toValue` для аргументов, обычный объект из `ref` на выходе, очистка эффектов, синхронный вызов в `setup`) — тема раздела «Vue».

### Паттерны, которые встречаются во Vue-коде

Из 23 паттернов «банды четырёх» на фронтенде регулярно работают несколько. Многие встроены в язык или фреймворк и не требуют классов.

| Паттерн | Какую проблему решает | Как выглядит во Vue/Nuxt |
| --- | --- | --- |
| Observer (наблюдатель) | уведомить зависимых об изменении | реактивность (`track`/`trigger`), `watch`, события компонента, `EventTarget` |
| Strategy (стратегия) | выбрать алгоритм во время выполнения | словарь функций, компаратор в props, `<component :is>` |
| Adapter (адаптер) | привести чужой интерфейс к своему | маппер DTO → модель, обёртка над SDK, реализация порта |
| Facade (фасад) | дать простой вход в сложную подсистему | composable или стор поверх нескольких API и кэша |
| Factory (фабрика) | создавать объекты без знания конкретного класса | `createApp`, `defineStore`, `createUseFetch`, `$fetch.create` |
| Proxy (заместитель) | перехватить доступ к объекту | `reactive`, `readonly` |
| Decorator (декоратор) | добавить поведение, сохранив интерфейс | компонент-обёртка, `debounce`, `memoize` вокруг функции |
| Command (команда) | превратить действие в объект | undo/redo, очередь офлайн-мутаций |
| Dependency Injection | отдать зависимость снаружи, а не создавать внутри | `provide`/`inject`, `app.provide` в плагине, `provide` в плагине Nuxt |

**Observer.** Реактивность Vue и есть наблюдатель: эффект подписывается на свойства, которые прочитал, а запись в них его уведомляет ([как устроено](../live-coding/mini-reactivity.md)). Явный emitter нужен для событий, которые не являются состоянием ([реализация и ловушки](../live-coding/event-emitter.md)). Правило выбора: если подписчику нужно текущее **значение**, это состояние и `computed`/`watch`. Если ему важен **факт** («заказ отправлен»), это событие.

**Strategy.** Цепочка `if (type === 'courier') … else if (type === 'pickup') …`, повторённая в расчёте цены, в шаблоне и в валидации, — сигнал собрать стратегии в объект с общим интерфейсом. Новый способ доставки тогда добавляется записью в реестр, а не правкой трёх файлов (задача 3). В JS стратегия — это обычно функция, а не класс. Компаратор у `sort` тоже стратегия.

**Adapter и Facade на границе с API.** Адаптер переводит ответ бэкенда в модель фронтенда: `created_at: string` в `createdAt: Date`, `status: 1` в `'paid'`, вложенный `data.items` в массив. Без него формат сервера расползается по шаблонам, и переименование одного поля бэкендом ломает весь UI. В DDD такой слой называют anti-corruption layer. Фасад собирает несколько вызовов и кэш за одним методом: `useCheckout()` скрывает корзину, расчёт доставки и создание заказа. Риск фасада — превратиться в «божественный» объект, через который проходит всё. Признак: фасад меняется при любом изменении в любой фиче.

**Factory.** Фабрика нужна, когда объект должен создаваться заново для каждого контекста. В SSR это обязательно: модульный синглтон (`export const store = reactive({})`) живёт в процессе Node и **общий для всех запросов**, поэтому данные одного пользователя утекают к другому. Поэтому `createApp`, `createPinia` и `defineStore` — фабрики, а не готовые экземпляры. Фабрики с настройками по умолчанию дают и Nuxt: `$fetch.create({ baseURL, onRequest })` и `createUseFetch` (Nuxt 4.4+) создают свой клиент или свой `useFetch` с заголовками авторизации.

**Dependency Injection.** Компонент не создаёт зависимость и не импортирует её конкретную реализацию, а получает её из контекста. Во Vue это `provide`/`inject`: значение ищется вверх по дереву, и ближайший провайдер затеняет дальних. Плагин делает `app.provide(key, value)`, и значение доступно во всём приложении. В Nuxt плагин возвращает `{ provide: { api } }`, а значение читается как `useNuxtApp().$api`. Чем это лучше импорта модуля:

- **Подмена в тестах и сторибуке** без `vi.mock` по пути файла: смонтировать компонент с `global.provide`.
- **Разные реализации в разных поддеревьях**: виджет в превью админки получает моки, а в продукте — настоящий API.
- **Изоляция запросов в SSR**: экземпляр создаётся в плагине для каждого приложения, то есть для каждого запроса.

Цена: зависимость не видна в props, а без провайдера `inject` вернёт `undefined` с предупреждением. Поэтому ключи делают `Symbol` с типом `InjectionKey<T>` ([зачем фантомный тип](../typescript/generics.md)), а доступ оборачивают в composable, который бросает понятную ошибку (пример 1). Документация советует держать мутации состояния у провайдера, наружу отдавать функции изменения, а само значение — через `readonly()`.

> [!WARNING]
> `inject` работает только синхронно в `setup` (в `<script setup>` — и после `await`, компилятор восстанавливает контекст), в функциональных компонентах и внутри `app.runWithContext`. Вызов из обработчика клика или из `setTimeout` вернёт `undefined`. Библиотечные composables проверяют это через `hasInjectionContext()` (Vue 3.3+).

### Container/presentational и headless-компоненты

**Container/presentational** — паттерн из React 2015 года (Дэн Абрамов): контейнер знает, *откуда* данные, презентационный компонент — *как* их показать, и получает всё через props. Плюсы: презентационный компонент тривиально тестировать и показывать в сторибуке. В 2019 году Абрамов дописал к статье, что больше не советует так делить компоненты: хуки позволяют вынести логику без искусственного деления. Во Vue роль контейнера играет composable. Разумный современный вариант такой: страница (или компонент фичи) вызывает `useOrders()` и передаёт данные в «глупые» компоненты UI-kit, а не каждый компонент делится надвое.

**Headless-компонент** отдаёт поведение, состояние и доступность без разметки и стилей: раскрытие, фокус, клавиатуру, ARIA. Разметку пишет потребитель через scoped-слот или composable. Так устроены Reka UI, Headless UI и TanStack Table. Это ISP и OCP вместе: дизайн меняется без форка логики, а логика доступности пишется один раз ([пример составных компонентов](../live-coding/ui-components.md)). Цена: потребитель отвечает за разметку, и сломать доступность становится проще. Поэтому поверх headless-слоя обычно строят стилизованный UI-kit.

### Инверсия зависимостей: порт и адаптер для HTTP-клиента

Алистер Кокбёрн сформулировал архитектуру **портов и адаптеров** (hexagonal): приложение должно одинаково работать, когда им управляет пользователь, тест или скрипт, и разрабатываться отдельно от реальных устройств и баз данных. **Порт** — интерфейс «осмысленного разговора» с внешним миром, описанный в терминах приложения. **Адаптер** — его реализация под конкретную технологию. Для тестов в порт вставляют адаптер в памяти.

Для фронтенда это значит: компоненты и сторы зависят от `OrdersApi` с методами `list`, `get` и `cancel` и моделями `Order`. Об URL, `fetch`, формате ошибок и snake_case знает только адаптер. Тогда:

- компонент тестируется с `createInMemoryOrdersApi()` без сети и без мока `fetch`;
- переход с REST на GraphQL или на сгенерированный клиент OpenAPI меняет один файл;
- ошибки сервера переводятся в доменные (`OrderNotFoundError`) в одном месте.

Порт оправдан на границе с внешним миром: API, `localStorage`, аналитика, платёжный SDK, время (`now()`). Внутри приложения между своими модулями он обычно лишний (KISS).

## Примеры

Порт, два адаптера и внедрение через `provide`/`inject`. Код запускается в Node 26 как `.ts` (типы удаляются при загрузке).

```ts
// orders/api.ts — the port: speaks the app's language, not the server's
export interface Order {
  id: string
  total: number
  status: 'pending' | 'paid' | 'cancelled'
  createdAt: Date
}

export class OrderNotFoundError extends Error {
  readonly orderId: string
  constructor(orderId: string) {
    super(`Order ${orderId} not found`)
    this.orderId = orderId
  }
}

export interface OrdersApi {
  list(): Promise<Order[]>
  get(id: string): Promise<Order>
  cancel(id: string): Promise<void>
}

// orders/http-adapter.ts — knows URLs, DTO shape and HTTP errors
interface OrderDto {
  id: string
  total_cents: number
  status: 0 | 1 | 2
  created_at: string
}

const STATUS = ['pending', 'paid', 'cancelled'] as const

const toOrder = (dto: OrderDto): Order => ({
  id: dto.id,
  total: dto.total_cents / 100,
  status: STATUS[dto.status],
  createdAt: new Date(dto.created_at),
})

type Fetcher = (path: string, init?: RequestInit) => Promise<Response>

export function createHttpOrdersApi(fetcher: Fetcher): OrdersApi {
  async function request<T>(path: string, init?: RequestInit, id?: string): Promise<T> {
    const res = await fetcher(path, init)
    if (res.status === 404 && id) throw new OrderNotFoundError(id)
    if (!res.ok) throw new Error(`HTTP ${res.status} for ${path}`)
    return (res.status === 204 ? undefined : await res.json()) as T
  }
  return {
    list: async () => (await request<OrderDto[]>('/orders')).map(toOrder),
    get: async (id) => toOrder(await request<OrderDto>(`/orders/${id}`, undefined, id)),
    cancel: (id) => request<void>(`/orders/${id}/cancel`, { method: 'POST' }, id),
  }
}

// orders/memory-adapter.ts — same contract, used in tests and storybook
export function createInMemoryOrdersApi(seed: Order[] = []): OrdersApi {
  const orders = new Map(seed.map((o) => [o.id, { ...o }]))
  const find = (id: string) => {
    const order = orders.get(id)
    if (!order) throw new OrderNotFoundError(id)
    return order
  }
  return {
    list: async () => [...orders.values()].map((o) => ({ ...o })),
    get: async (id) => ({ ...find(id) }),
    cancel: async (id) => {
      find(id).status = 'cancelled'
    },
  }
}
```

Внедрение. Ключ с типом, composable с понятной ошибкой и плагин, который создаёт экземпляр на каждое приложение (в SSR — на каждый запрос):

```ts
// orders/injection.ts
import { inject, type App, type InjectionKey } from 'vue'

export const ordersApiKey: InjectionKey<OrdersApi> = Symbol('OrdersApi')

export function useOrdersApi(): OrdersApi {
  const api = inject(ordersApiKey, null)
  if (!api) throw new Error('OrdersApi is not provided: install ordersPlugin')
  return api
}

export const ordersPlugin = {
  install(app: App, options: { baseURL: string }) {
    const fetcher: Fetcher = (path, init) => fetch(options.baseURL + path, init)
    app.provide(ordersApiKey, createHttpOrdersApi(fetcher))
  },
}
```

```vue
<!-- OrderList.vue: knows the port, not the transport -->
<script setup lang="ts">
import { ref } from 'vue'
import { useOrdersApi, type Order } from './orders'

const api = useOrdersApi()
const orders = ref<Order[]>([])
const error = ref<string | null>(null)

async function load() {
  try {
    orders.value = await api.list()
  } catch (e) {
    error.value = (e as Error).message
  }
}

async function cancel(id: string) {
  await api.cancel(id)
  await load()
}

load()
</script>

<template>
  <p v-if="error" role="alert">{{ error }}</p>
  <ul v-else>
    <li v-for="order in orders" :key="order.id">
      {{ order.id }} — {{ order.status }}
      <button v-if="order.status === 'pending'" @click="cancel(order.id)">Cancel</button>
    </li>
  </ul>
</template>
```

В тесте компонент монтируется с `global: { provide: { [ordersApiKey]: createInMemoryOrdersApi(seed) } }`, без сети и без мока модулей. В Nuxt тот же адаптер создаётся в плагине поверх `$fetch.create`, а данные страницы загружаются через `useAsyncData`, чтобы не запрашивать их дважды при SSR.

## Вопросы с интервью

::: details Как применить SOLID к Vue-компонентам? Приведите пример нарушения каждого принципа
SRP: компонент формы заказа содержит вёрстку, правила скидок и формат запроса — три причины изменения от трёх разных групп людей (дизайн, продукт, бэкенд). Лечится выносом правил в чистые функции, а запроса — в адаптер. OCP: таблица, которой на каждый новый вид ячейки добавляют prop и `v-if`. Её открывают для расширения слотами (`#cell-<key>`). LSP: `BaseInput`, который не пробрасывает `$attrs` и `blur`, нельзя подставить вместо `<input>`. ISP: компонент аватара принимает весь объект `user`, хотя нужны `name` и `photoUrl`. Он перерисовывается и ломается от изменений, которые его не касаются. DIP: компонент импортирует `axios` и URL напрямую, поэтому его не протестировать без мока сети. Лечится портом через `inject`. Важно добавить цену: SOLID — эвристики про стоимость изменения. Дробить компонент на части, которые всегда меняются вместе, — тоже ошибка.
:::

::: details Что такое DRY и когда дублирование лучше абстракции
DRY в исходной формулировке («Программист-прагматик») — про знание: у каждого правила одно авторитетное представление. Одинаковый текст двух мест ещё не значит одно знание. Если два компонента совпали случайно и меняются по требованиям разных команд, общая абстракция зацепит фичи. Каждое новое расхождение добавит в неё флаг и ветку, и через год её будут бояться трогать. Сэнди Метц: «Дублирование намного дешевле ошибочной абстракции». Её рецепт выхода — встроить абстракцию обратно и выделить заново то, что действительно общее. Практика: обобщать на третьем повторе (правило трёх) и спрашивать, одна ли причина изменения у копий. Валидация ИНН — одно знание и выносится сразу. Карточка товара в каталоге и в корзине — скорее нет.
:::

::: details Почему во Vue 3 composables вместо mixins
Документация Vue 3 называет у mixins три недостатка. Неясен источник свойств: при нескольких mixins по `this.loading` не понять, откуда оно. Возможны конфликты имён между mixins разных авторов. Mixins общаются неявно, через общие имена свойств, и оказываются скрыто зацеплены. Composable — обычная функция: результат деструктурируется (источник виден в коде), переменные можно переименовать, а зависимости передаются аргументами (`useFilter(items)`). Это «композиция вместо наследования»: поведение собирают из независимых частей. Против renderless-компонентов composables выигрывают тем, что не создают лишний экземпляр компонента. Компонент оставляют, когда переиспользуется и разметка. Mixins в Vue 3 оставлены только для миграции.
:::

::: details Как сделать внедрение зависимостей во Vue и Nuxt? Чем это лучше импорта модуля
Через `provide`/`inject`: плагин делает `app.provide(key, impl)` (в Nuxt плагин возвращает `{ provide: { api } }`, значение доступно как `$api`), компонент получает зависимость через `inject` в `setup`. Ключ — `Symbol` с типом `InjectionKey<T>`, доступ — через composable вроде `useOrdersApi()`, который бросает понятную ошибку, если провайдера нет. Преимущества перед импортом: подмена в тестах и сторибуке через `global.provide` без мока модулей, разные реализации в разных поддеревьях, а в SSR — экземпляр на запрос вместо модульного синглтона, общего для всех пользователей процесса. Цена: зависимость не видна в props, `inject` работает только в контексте `setup`, а DI ради DI — лишняя косвенность. Внедряют то, что нужно подменять: API, хранилище, аналитику, время.
:::

::: details Какие паттерны «банды четырёх» вы встречаете во Vue-коде
Observer — сама реактивность и события компонентов. Proxy — `reactive` и `readonly`. Strategy — словарь функций вместо `switch`, компаратор сортировки, `<component :is>`. Adapter — маппер DTO в модель на границе с API. Facade — composable или стор поверх нескольких сервисов. Factory — `createApp`, `createPinia`, `defineStore`, `$fetch.create`. Decorator — компонент-обёртка или `debounce` вокруг функции. Command — undo/redo и очередь офлайн-мутаций. В JS многие паттерны вырождаются в функции: стратегия — это функция, а не класс с интерфейсом. Хороший ответ называет проблему, которую решает паттерн, и цену, а не просто список.
:::

::: details Актуален ли паттерн container/presentational
Идея — отделить «откуда данные» от «как показать»: контейнер загружает данные и передаёт их через props в презентационный компонент без побочных эффектов. Такой компонент легко тестировать и показывать в сторибуке. Но автор паттерна Дэн Абрамов в 2019 году написал, что больше не советует делить компоненты так догматично: хуки (во Vue — composables) выносят логику без лишнего слоя компонентов. Сегодня разумно так: страница или компонент фичи вызывает composable, а компоненты UI-kit остаются «глупыми» и получают данные через props. Делить каждый компонент надвое не нужно. Близкая идея — headless-компоненты: поведение и доступность без разметки.
:::

::: details Как оценить, хорошо ли спроектирован модуль фронтенда
Смотрят на связность и зацепление. Вопросы: сколько файлов меняется при типичной доработке фичи (если пять папок — низкая связность)? Что модуль знает о соседях — публичный контракт или внутренности (`$parent`, импорт из чужого `internal/`, общий изменяемый стор)? Виден ли поток данных по коду или он идёт через глобальную шину? Можно ли протестировать модуль без сети и без моков чужих модулей? Сколько параметров и флагов у общих компонентов (много флагов — признак ошибочной абстракции)? Есть ли слои, которые только пробрасывают вызов? Метрики (циклические импорты, fan-in/fan-out) проверяют линтерами границ, но главное — цена типичного изменения.
:::

## Задачи

### 1. Компонент-комбайн · средне

`<DataTable>` за два года обзавёлся props `selectable`, `expandable`, `showActions`, `actionsPosition`, `compact`, `stickyHeader`, `showStatusBadge`, `statusColors`, `avatarColumn`, `editableCells`, `exportCsv` и ещё десятком. Каждый новый экран добавляет флаг, и правка для одного экрана ломает другой. Предложите, как перепроектировать компонент, и объясните цену.

::: details Решение и разбор
Диагноз: это ошибочная абстракция (Метц) и нарушение OCP. Компонент закрыт для расширения: любая новая ячейка требует правки общего кода. Кроме того, у него десяток причин изменения от разных фич (SRP).

Ключевые решения:

1. **Слоты вместо флагов отображения.** `#cell-<key>="{ row, value }"` заменяет `showStatusBadge`, `statusColors` и `avatarColumn`: экран рисует свою ячейку сам. `#row-actions="{ row }"` заменяет `showActions` и `actionsPosition`.
2. **Поведение — в composables.** Выбор строк (`useSelection(rows, { key })`), раскрытие и экспорт — отдельные функции, которые экран подключает, если нужно. `exportCsv` вообще не дело таблицы: экспорт работает с данными, а не с отображением.
3. **Ядро таблицы узкое.** `columns`, `rows`, `rowKey`, сортировка через `v-model:sort` и слоты. Варианты внешнего вида (`compact`, `stickyHeader`) остаются props: это действительно параметры одного компонента, а не разных фич.
4. **Headless-вариант** для сложных случаев: `useTable({ columns, rows })` возвращает состояние и обработчики, разметку пишет экран (так устроен TanStack Table).

Миграция: не переписывать всё разом, а по Метц — для самых «кривых» экранов временно отдать таблицу в копию, удалить неиспользуемые ветки, а потом выделить ядро.

Цена: экранам приходится писать больше разметки, и единообразие держится на UI-kit и ревью, а не на компоненте. Слотов больше — значит, больше контракта, который нельзя ломать. Если таблица живёт в общем пакете, имена слотов становятся публичным API с версионированием.
:::

### 2. Слой API, который можно тестировать и заменить · средне

Компоненты вызывают `axios.get('/api/v2/orders')` прямо в `setup`, в шаблонах используются поля `total_cents` и `created_at`. Нужно: тестировать компоненты без сети, а через полгода перейти на сгенерированный клиент GraphQL. Спроектируйте слой.

::: details Решение и разбор
Ключевые решения:

1. **Порт в языке приложения**: `OrdersApi` с методами `list`, `get`, `cancel` и моделью `Order` (`total: number`, `createdAt: Date`, `status` — объединение строк). Модель не повторяет DTO.
2. **Адаптер** `createHttpOrdersApi(fetcher)` знает URL, DTO, маппинг и перевод ошибок (`404` → `OrderNotFoundError`). Транспорт передаётся аргументом, поэтому адаптер можно протестировать с фейковым `fetcher`. Переход на GraphQL — новый адаптер `createGraphqlOrdersApi(client)` с тем же портом.
3. **Адаптер в памяти** с тем же контрактом для тестов и сторибука. Оба адаптера прогоняются одним набором контрактных тестов, иначе подмена ничего не доказывает (LSP).
4. **Внедрение** через `InjectionKey` и плагин (см. «Примеры»). В Nuxt — плагин поверх `$fetch.create` с `provide`, данные страниц через `useAsyncData(() => $orders.list())`.
5. **Кэш и дедупликация** — уровнем выше порта (стор, `useAsyncData` или библиотека server state), а не внутри адаптера: адаптер отвечает только за перевод.

Альтернативы: мокать `fetch` или модуль через `vi.mock`. Это дешевле на старте, но тесты зацеплены за URL и формат DTO и ломаются при смене транспорта. Если клиент генерируется из OpenAPI, тонкий адаптер всё равно нужен, чтобы модель фронтенда не повторяла схему бэкенда.

Цена: лишний слой и маппинг, который нужно поддерживать. Для маленького приложения с одним бэкендом и без тестов компонентов это может быть преждевременно. Но YAGNI, по Фаулеру, не относится к тому, что упрощает изменения, а тестируемость окупается сразу.
:::

### 3. Стратегии доставки вместо `switch` · легко

Способ доставки (`courier`, `pickup`, `post`) проверяется через `switch` в трёх местах: в расчёте стоимости, в шаблоне формы (разные поля) и в валидации. Добавление «постамата» потребовало правок в трёх файлах, и одну забыли. Перепроектируйте.

::: details Решение и разбор
```ts
// delivery/strategy.ts
import type { Component } from 'vue'

export interface DeliveryMethod<Form = unknown> {
  id: string
  label: string
  price(cart: { total: number; weightKg: number }): number
  validate(form: Form): string[] // error messages
  form: () => Promise<Component> // lazy-loaded form fields
}

export const deliveryMethods: Record<string, DeliveryMethod<any>> = {
  courier: {
    id: 'courier',
    label: 'Courier',
    price: (cart) => (cart.total >= 5000 ? 0 : 300),
    validate: (f: { address?: string }) => (f.address ? [] : ['Address is required']),
    form: () => import('./forms/CourierFields.vue').then((m) => m.default),
  },
  // pickup, post, locker: one entry each
}
```

Форма рендерит `<component :is="defineAsyncComponent(method.form)">`, расчёт и валидация вызывают `method.price` и `method.validate`. Новый способ доставки — одна запись в реестре (OCP), а TypeScript не даст забыть метод: реализация обязана соответствовать `DeliveryMethod`.

Варианты: если правила приходят с бэкенда (цены, доступность по региону), в реестре остаются только отображение и валидация, а цену считает сервер. Если способов два и новых не ожидается, `switch` с проверкой исчерпываемости через `never` проще и тоже ловит забытый случай ([подробнее](../typescript/narrowing.md)). Это KISS: стратегия окупается, когда вариантов много или их добавляют разные люди.

Цена: логика одного способа доставки собрана в одном месте (высокая связность), зато общая логика всех способов (скидки, сравнение) размазана по реализациям.
:::

### 4. Mixin в composable · средне

В проекте, мигрирующем на Vue 3, есть mixin `paginationMixin` с `data: { page, pageSize, total }`, `computed: pageCount`, `methods: next`, `prev` и хуком `watch: { page: 'fetchPage' }`, где `fetchPage` должен объявить компонент. Его используют вместе с `filterMixin`, который тоже объявляет `page` и сбрасывает его в `1` при смене фильтра. Перепишите на composables и объясните, какие проблемы ушли.

::: details Решение и разбор
```ts
import { computed, ref, watch, toValue, type MaybeRefOrGetter } from 'vue'

export function usePagination(options: {
  total: MaybeRefOrGetter<number>
  pageSize?: number
  onPageChange: (page: number) => void
}) {
  const page = ref(1)
  const pageSize = options.pageSize ?? 20
  const pageCount = computed(() => Math.max(1, Math.ceil(toValue(options.total) / pageSize)))

  watch(page, (p) => options.onPageChange(p))

  return {
    page,
    pageCount,
    next: () => { if (page.value < pageCount.value) page.value++ },
    prev: () => { if (page.value > 1) page.value-- },
    reset: () => { page.value = 1 },
  }
}

// in a component:
// const total = ref(0)
// const { page, next, prev, reset } = usePagination({ total, onPageChange: fetchPage })
// const { filters } = useFilters({ onChange: reset })
```

Что ушло:

- **Неявный контракт.** Mixin требовал, чтобы компонент объявил `fetchPage`, и узнать это можно было только из кода mixin. Теперь колбэк — явный аргумент.
- **Конфликт имён.** Оба mixins объявляли `page`, и итоговое значение зависело от правил слияния опций. Теперь `page` один, а `useFilters` получает `reset` аргументом.
- **Скрытое общение.** `filterMixin` сбрасывал `this.page`, рассчитывая, что его объявил другой mixin. Теперь связь видна в месте вызова.
- **Источник свойств** виден по деструктуризации.

Альтернатива: `useFilters` мог бы сам владеть `page`, но тогда пагинация зацеплена за фильтры. Передача `reset` оставляет оба composable независимыми.

Цена: в компоненте становится больше строк связки, и порядок вызовов имеет значение: `total` должен быть объявлен до `usePagination`.
:::
