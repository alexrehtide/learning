# Структура большого проекта и Feature-Sliced Design

> **Коротко.** Раскладка по типу файлов (`components/`, `stores/`, `utils/`) масштабируется плохо. Одна фича размазана по всему дереву, границ между модулями нет, и любой файл может импортировать любой. Большой проект раскладывают по бизнес-смыслу и вводят правило зависимостей: импорты идут только в одну сторону, а в модуль входят через его публичный API. Feature-Sliced Design (FSD) — готовый словарь для этого: слои `app → pages → widgets → features → entities → shared`, слайсы по доменам, сегменты по назначению и линтер Steiger. В Nuxt 4 FSD конфликтует с файловым роутингом и auto-imports, и это решают настройкой. Senior объясняет, что даёт структура и чем за неё платят, а маленькому проекту FSD не навязывает.

**Связанные темы:** [Принципы и паттерны проектирования](principles-and-patterns.md), [Модули: ESM и CommonJS](../javascript/modules.md), [Оптимизация загрузки](../performance/loading.md)

## Теория

### По типу или по фичам

| | По типу файлов | По фичам (доменам) |
| --- | --- | --- |
| Как выглядит | `components/`, `composables/`, `stores/`, `api/`, `types/` | `orders/`, `catalog/`, `cart/`, внутри каждой `ui/`, `model/`, `api/` |
| Где лежит одна фича | в пяти папках | в одной |
| Границы | нет: любой файл видит любой | у каждого модуля свой вход (`index.ts`) |
| Удалить фичу | искать хвосты по всему проекту | удалить папку и поправить импорты её публичного API |
| Владение кодом | «папка `components/` общая» | команда владеет `orders/` (CODEOWNERS) |
| Хорошо для | до ~20–30 компонентов, одной команды, прототипа | долгоживущего продукта, нескольких команд |

Раскладка по типу ломается не из-за количества файлов, а из-за отсутствия **границ**. Пока `components/` небольшая, все помнят, кто кого использует. Когда в ней 300 файлов, `OrderStatusBadge` импортируется из каталога, корзины и админки. Её изменение по требованию одной команды ломает экраны другой, а понять, что можно безопасно удалить, уже нельзя. Это низкая связность и неконтролируемое зацепление из [темы о принципах](principles-and-patterns.md): то, что меняется вместе, лежит врозь, а то, что должно быть независимым, связано.

### Слои и правило зависимостей

Слоистая архитектура делит код по **стабильности**. Нижние слои (UI-kit, HTTP-клиент, модели) меняются редко, и от них зависят многие. Верхние (страницы, сценарии) меняются часто, и от них не зависит никто. Правило зависимостей: **импорты идут только вниз**, к более стабильному коду. Тогда изменение верхнего слоя ничего не ломает внизу, а изменение нижнего видно по графу импортов.

Из правила следуют два свойства:

- **Граф зависимостей без циклов.** Цикл между модулями означает, что они по сути один модуль: их нельзя ни тестировать, ни выпускать, ни понимать по отдельности. В ESM циклы к тому же дают `ReferenceError` из TDZ при неудачном порядке вычисления модулей ([подробнее](../javascript/modules.md)).
- **Граница проверяется машиной.** «Не импортируй из features в entities» — это правило линтера, а не договорённость на ревью.

### Feature-Sliced Design: слои, слайсы, сегменты

FSD — методология с трёхуровневой иерархией. Актуальная версия — **v2.1** (сверено с feature-sliced.design 2026-11-14).

**Слои** — фиксированный набор папок верхнего уровня, от самого ответственного к самому стабильному:

| Слой | Что в нём | Слайсы |
| --- | --- | --- |
| `app` | инициализация, провайдеры, глобальные стили, роутер, аналитика | нет |
| `processes` | **устарел**, содержимое переносят в `features` и `app` | — |
| `pages` | экраны целиком: UI, загрузка данных, состояния ошибки и загрузки | да, обычно слайс на страницу |
| `widgets` | крупные самостоятельные блоки UI, переиспользуемые на нескольких страницах | да |
| `features` | действия пользователя с бизнес-ценностью: «добавить в корзину», «оставить отзыв» | да |
| `entities` | бизнес-сущности: `user`, `order`, `product` — модель, API, базовый UI | да |
| `shared` | основа без бизнес-домена: UI-kit, HTTP-клиент, конфиг, i18n, утилиты | нет |

**Правило импортов** в формулировке FSD: «A module (file) in a slice can only import other slices when they are located on layers strictly below». Отсюда два запрета: импорт вверх и импорт **между слайсами одного слоя** (`features/cart` не импортирует `features/favorites`). В `app` и `shared` слайсов нет, поэтому их сегменты свободно импортируют друг друга.

**Слайс** группирует код по бизнес-смыслу (`entities/order`). Идеальный слайс не зависит от соседей по слою и содержит почти весь код своей задачи. **Сегмент** группирует код внутри слайса по техническому назначению: `ui`, `api`, `model`, `lib`, `config`. Методология требует называть сегменты по **цели**, а не по сущности: `components/`, `hooks/`, `types/` — плохие имена, потому что не помогают искать код.

> [!NOTE]
> В v2.0 большая часть логики уходила в `entities` и `features`, а страницы только собирали их. Главное изменение v2.1 — подход **pages first**: код живёт в слайсе страницы, пока не понадобится на второй странице, и только тогда спускается ниже. Документация прямо говорит, что не каждый блок — виджет и не каждое действие — фича, а слои использовать не обязательно: минимум — `app`, `pages`, `shared`. Проекты на v2.0 остаются валидными.

### Публичный API слайса и cross-imports

**Публичный API** — контракт слайса с внешним миром, обычно `index.ts` с реэкспортами. Снаружи импортируют только `@/entities/order`, а не `@/entities/order/model/store`. Это даёт свободу рефакторинга внутри слайса и делает зависимость видимой.

Три правила вокруг публичного API:

- **Без `export *`.** FSD называет wildcard-реэкспорт плохой практикой: интерфейс слайса не виден, а наружу утекают внутренности. Экспортируют поимённо.
- **В `shared/ui` и `shared/lib` — индекс на компонент**, а не один общий: `@/shared/ui/button`, `@/shared/ui/text-field`. Общий barrel-файл тянет в граф модулей весь UI-kit и мешает tree shaking ([почему](../javascript/modules.md)).
- **Внутри слайса — относительные импорты**, между слайсами — абсолютные через алиас. Импорт своего же `index.ts` изнутри слайса — частый источник циклов.

**Cross-imports между entities.** Сущности ссылаются друг на друга: у заказа есть покупатель, у пользователя — заказы. Правило слоя это запрещает. v2.1 стандартизировала исключение — нотацию `@x`: файл `entities/user/@x/order.ts` — отдельный публичный API `user`, предназначенный **только** для `entities/order`. Читается «user crossed with order». Её разрешено использовать только на слое `entities`, и cross-imports должно быть минимум. Чаще всего через `@x` передают типы. Если через него нужна логика, сущности, скорее всего, нарезаны неверно.

### Типичные ошибки внедрения

1. **Всё — фича.** `features/order-list`, `features/user-avatar`, `features/header`. Слой превращается в ту же свалку, только с правилом импортов, которое мешает. Фича — это действие пользователя, а не кусок UI.
2. **`entities` как зеркало DTO бэкенда.** Слайс на каждую таблицу БД, без поведения. Сущность — понятие предметной области фронтенда со своей моделью, и маппинг DTO живёт в её сегменте `api` ([адаптер](principles-and-patterns.md)).
3. **Бизнес-логика в `shared`.** `shared/lib/calculateDiscount.ts` — это уже домен. `shared` не должен знать слов «заказ» и «скидка».
4. **Обход публичного API** через глубокие импорты и **auto-imports**, которые прячут зависимость целиком (см. ниже про Nuxt).
5. **Преждевременное дробление.** Слайс, который используется в одном месте, — лишний уровень косвенности. Steiger ловит это правилом `fsd/insignificant-slice`.
6. **Внедрение без линтера.** Через полгода правило импортов нарушено в сотне мест, и структура только мешает.
7. **Миграция одним PR.** Переезд всего проекта блокирует команды на недели. Переносят по странице, начиная со `shared` и новых экранов.

### FSD и Nuxt 4

Nuxt — фреймворк с соглашениями о каталогах, и три из них конфликтуют с FSD.

| Конфликт | Почему мешает | Решение |
| --- | --- | --- |
| `app/pages/` — файловый роутинг | FSD тоже нужен слой `pages`, но со слайсами, а не с маршрутами | `dir.pages` указывает на отдельный каталог маршрутов; файлы маршрутов тонкие и импортируют слайс страницы |
| Auto-imports компонентов и composables | `<OrderCard>` в шаблоне работает без `import`, поэтому линтер не видит зависимость, а правило импортов и публичный API обходятся незаметно | `components: { dirs: [] }`, `imports: { scan: false }`; API Vue и Nuxt (`ref`, `useFetch`) остаются автоимпортом |
| Корневой `shared/` Nuxt | это код, общий для приложения и сервера Nitro, а не слой FSD | не путать: слой FSD живёт в `app/shared/`, а в `shared/` Nuxt — только то, что нужно и серверу |

В Nuxt 4 код приложения лежит в `app/` (`srcDir`), а `server/`, `shared/` и `public/` — в корне. Эта раскладка сама подсказывает соответствие: **соглашения Nuxt в `app/` (`app.vue`, `layouts/`, `plugins/`, `middleware/`, каталог маршрутов) — это и есть слой `app` FSD**, а остальные слои кладутся рядом в `app/` (пример 1). Алиас `~` уже указывает на `app/`, генерируемый `tsconfig` для контекста приложения его покрывает, ничего дополнительно настраивать не нужно.

Официальное руководство FSD по Nuxt предлагает другой вариант: слои в `src/` в корне, алиас `@` на `src` и `dir.pages: './src/app/routes'`. Оно не указывает версию Nuxt и написано для раскладки без `app/`. В Nuxt 4 каталог вне `app/` не входит в контекст приложения сгенерированных `tsconfig`, и его придётся подключать вручную.

> [!WARNING]
> `imports.scan: false` ломает переопределение composables через Nuxt Layers: их придётся импортировать из каждого слоя явно. Если проект собран на слоях, оставьте сканирование только для `shared` или откажитесь от FSD внутри слоёв в пользу слоя-на-домен.

> [!NOTE]
> В Nuxt 3 `srcDir` по умолчанию — корень проекта, а `app/` как каталог исходников появился в Nuxt 4. Поэтому руководства по FSD для Nuxt 3 кладут слои в корень или в `src/`.

### Модульный монолит и проверка границ

FSD — частный случай более общей идеи **модульного монолита**: одно приложение, один деплой, но внутри модули с явными границами. Каждый модуль владеет своим кодом, наружу отдаёт публичный API, а зависимости между модулями объявлены и проверяются. Другой распространённый вариант для Vue/Nuxt — модуль на домен (`modules/orders`, `modules/catalog`) со своей внутренней раскладкой и общим `shared`. Он проще FSD, но не даёт готового ответа, куда класть код, нужный двум доменам.

Граница существует, только если её проверяет машина:

| Инструмент | Что проверяет | Когда брать |
| --- | --- | --- |
| Steiger + `@feature-sliced/steiger-plugin` | структуру FSD: импорты вверх и между слайсами (`fsd/forbidden-imports`), обход публичного API (`fsd/no-public-api-sidestep`), лишние слайсы (`fsd/insignificant-slice`), имена сегментов (`fsd/segments-by-purpose`) | проект на FSD; линтер в бета-версии |
| ESLint `no-restricted-imports` | запрещённые пути и шаблоны по `files` — встроенное правило, без плагинов | простые правила: «из `entities` нельзя в `features`», «без глубоких импортов» |
| `eslint-plugin-boundaries`, `import-x/no-restricted-paths` | матрицу «какой тип модуля что может импортировать» | своя модульная схема, не FSD |
| dependency-cruiser | граф целиком: циклы, сироты, правила, визуализация | аудит и CI в большом проекте |

> [!TIP]
> Линтер видит только `import`. Всё, что связывает модули в обход импортов, — auto-imports, глобальные компоненты, `provide`/`inject` по строковому ключу, глобальная шина событий — граница не ловит. Поэтому в проекте с проверкой границ auto-imports собственного кода выключают.

### Когда FSD избыточен

FSD стоит денег: на вход новичка, на споры «это feature или entity», на `index.ts` в каждом слайсе, на настройку Nuxt. Окупается он, когда над проектом работает несколько команд, проект живёт годы и в нём десятки экранов. Не окупается в лендинге, внутренней админке на пять страниц, прототипе и проекте одной команды из трёх человек. Там хватает раскладки по фичам и двух правил: вход в модуль через `index.ts` и запрет импортов между фичами. В v2.1 FSD сам движется к этому: pages first и минимум слоёв.

## Примеры

### 1. Nuxt 4 + FSD: раскладка и конфиг

```text
app/
  app.vue                 # FSD layer "app": Nuxt conventions
  layouts/default.vue
  plugins/api.ts
  middleware/auth.ts
  routes/                 # Nuxt file routing (dir.pages)
    orders/
      index.vue
      [id].vue
  pages/                  # FSD layer "pages": slices
    order-details/
      ui/OrderDetailsPage.vue
      index.ts
  widgets/order-summary/
  features/cancel-order/
  entities/
    order/
      model/types.ts
      api/order-api.ts
      ui/OrderStatusBadge.vue
      index.ts
    user/
      @x/order.ts         # public API of "user" for "order" only
      index.ts
  shared/                 # FSD layer "shared" (not Nuxt's root shared/)
    ui/button/
    api/http.ts
server/
shared/                   # Nuxt: code shared by app and Nitro
nuxt.config.ts
```

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  dir: {
    // Nuxt routes live apart from the FSD "pages" layer
    pages: 'app/routes',
  },
  // Own components and composables are imported explicitly,
  // so linters see every dependency between slices
  components: { dirs: [] },
  imports: { scan: false },
})
```

Файл маршрута — тонкий: параметры маршрута и SEO, вся логика в слайсе страницы.

```vue
<!-- app/routes/orders/[id].vue -->
<script setup lang="ts">
import { OrderDetailsPage } from '~/pages/order-details'

const route = useRoute()
const id = computed(() => String(route.params.id))
</script>

<template>
  <OrderDetailsPage :order-id="id" />
</template>
```

### 2. Публичный API и cross-import

```ts
// app/entities/user/@x/order.ts — only entities/order may import this
export type { User as OrderCustomer } from '../model/types'

// app/entities/order/model/types.ts
import type { OrderCustomer } from '~/entities/user/@x/order'

export interface Order {
  id: string
  status: 'pending' | 'paid' | 'cancelled'
  customer: OrderCustomer
}

// app/entities/order/index.ts — named re-exports, no `export *`
export type { Order } from './model/types'
export { fetchOrder } from './api/order-api'
export { default as OrderStatusBadge } from './ui/OrderStatusBadge.vue'
```

### 3. Проверка границ

```ts
// steiger.config.ts
import { defineConfig } from 'steiger'
import fsd from '@feature-sliced/steiger-plugin'

export default defineConfig([
  ...fsd.configs.recommended,
  // Nuxt conventions in the "app" layer are not FSD slices
  { ignores: ['./app/routes/**', './app/layouts/**', './app/plugins/**', './app/middleware/**'] },
])
```

```js
// eslint.config.js — the same idea with the built-in rule, no plugins
// Nuxt conventions of the "app" layer (routes, layouts, plugins)
// are not listed: they may import any layer
const layers = ['pages', 'widgets', 'features', 'entities', 'shared']
const sliced = 'pages|widgets|features|entities'

// One config object per layer: options of the same rule do not merge
// across flat-config objects, the last matching object wins
export default layers.map((layer, i) => ({
  files: [`app/${layer}/**`],
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [
        ...(i > 0 ? [{
          group: layers.slice(0, i).map((upper) => `~/${upper}/**`),
          message: `${layer} may import only from lower layers`,
        }] : []),
        {
          regex: `^~/(${sliced})/[^/]+/(ui|model|api|lib|config)/`,
          message: 'import a slice through its public API',
        },
      ],
    }],
  },
}))
```

Этот конфиг ловит импорт вверх и глубокий импорт, но не импорт между слайсами одного слоя и не различает `@x`. Для этого понадобится шаблон на каждый слайс, поэтому для FSD проще взять Steiger, а ESLint оставить для своей, более простой схемы модулей.

## Вопросы с интервью

::: details Почему раскладка по типу файлов не масштабируется
Потому что в ней нет границ, а связность низкая. Одна фича разбросана по `components/`, `stores/`, `api/`, `types/`, и каждое изменение трогает пять папок. Любой файл может импортировать любой, поэтому граф зависимостей становится сплошной сетью: неясно, что безопасно менять и удалять, а у кода нет владельца. Пока проект маленький, это незаметно и даже удобно. Ломается всё, когда появляются несколько команд и сотни компонентов. Раскладка по доменам держит вместе то, что меняется вместе, и позволяет задать границу: вход через публичный API, импорты в одну сторону, проверка линтером.
:::

::: details Как устроен Feature-Sliced Design и какое в нём правило импортов
Три уровня. Слои — фиксированные папки `app`, `pages`, `widgets`, `features`, `entities`, `shared` (плюс устаревший `processes`), упорядоченные по стабильности. Слайсы делят слой по бизнес-доменам: `entities/order`, `features/cancel-order`. Сегменты делят слайс по назначению: `ui`, `api`, `model`, `lib`, `config`. Правило: модуль слайса импортирует только слайсы с **нижних** слоёв, поэтому соседей по слою и вверх нельзя. В `app` и `shared` слайсов нет. Снаружи в слайс входят только через публичный API. Главное в v2.1 — pages first: код живёт в странице, пока не понадобится второй странице. Все слои использовать не обязательно.
:::

::: details Как отличить feature от entity и widget
Entity — существительное предметной области: заказ, пользователь, товар. Её модель, API и базовое отображение нужны многим. Feature — глагол, действие пользователя с бизнес-ценностью: «отменить заказ», «добавить в избранное». Она использует сущности, но не другие фичи. Widget — крупный самостоятельный блок UI, который собирает фичи и сущности и **переиспользуется на нескольких страницах**: шапка, корзина в сайдбаре. Практический тест из документации — переиспользование. Если блок или действие живёт на одной странице, это код этой страницы. Спор «feature или entity» обычно означает, что выделять слайс пока рано.
:::

::: details Зачем слайсу публичный API и чем опасен barrel-файл
Публичный API — контракт: снаружи видно только то, что экспортирует `index.ts`, а внутренности можно рефакторить, не ломая потребителей. Ещё он делает зависимость явной и проверяемой: линтер запрещает импорт мимо индекса. Barrel-файл с `export *` всё это портит: интерфейс не виден, наружу утекает всё подряд, а один общий индекс `shared/ui` тянет в граф модулей весь UI-kit, замедляет dev-сервер и мешает tree shaking, если пакет не помечен как свободный от побочных эффектов. Поэтому экспорты поимённые, в `shared/ui` индекс на компонент, а внутри слайса импорты относительные, чтобы не получить цикл через собственный индекс.
:::

::: details Что делать, если двум сущностям нужны друг друга
Сначала проверить, нужна ли связь в коде. Часто заказу нужен только `customerId`, а отображение покупателя собирает страница или виджет, которые стоят выше обоих слайсов. Если сущности действительно ссылаются друг на друга (обычно типами), в FSD v2.1 для этого есть нотация `@x`: `entities/user/@x/order.ts` — узкий публичный API пользователя, предназначенный только для заказа. Такие связи видны в структуре папок, а не спрятаны в обычном индексе. Если через `@x` начинает ходить логика, а не типы, сущности нарезаны неверно: возможно, это одна сущность или общая часть должна жить в отдельном слайсе.
:::

::: details Как совместить FSD с Nuxt 4
Три конфликта. Первый — `pages/`: в Nuxt это файловый роутинг, в FSD — слой. Решение: `dir.pages` переносит маршруты в отдельный каталог (`app/routes`), а файлы маршрутов тонкие и импортируют слайс страницы. Второй — auto-imports: компонент в шаблоне работает без `import`, линтер границ не видит зависимость, и правило импортов обходится незаметно. Поэтому для собственного кода их выключают (`components.dirs: []`, `imports.scan: false`), а API Vue и Nuxt оставляют. Третий — имена: корневой `shared/` Nuxt — код для приложения и сервера, а не слой FSD. Сами слои удобно класть в `app/`: соглашения Nuxt там уже играют роль слоя `app`, алиас `~` и `tsconfig` работают без настройки. Цена: `imports.scan: false` ломает переопределение composables через Nuxt Layers, и это надо учесть.
:::

::: details Когда вы бы не стали внедрять FSD
Когда его цена выше пользы: лендинг, админка на пять экранов, прототип, одна небольшая команда. FSD добавляет порог входа, `index.ts` в каждом слайсе, споры о классификации и настройку Nuxt. Он окупается при нескольких командах, долгой жизни продукта и десятках экранов: тогда правило импортов и проверка линтером экономят больше, чем стоят. Для середины хватает раскладки по фичам с двумя правилами — вход через `index.ts` и запрет импортов между фичами, проверяемые `no-restricted-imports`. В существующий проект FSD вносят постепенно: `shared`, потом новые страницы, потом перенос старых по одной, с линтером в CI с первого дня.
:::

## Задачи

### 1. Разложить файлы по слоям · легко

Проект интернет-магазина на Nuxt 4 переезжает на FSD. Куда положить: `Button.vue`, `http.ts` (обёртка над `$fetch`), тип `Product` и `fetchProduct`, `ProductCard.vue`, кнопку «В корзину» с логикой добавления, `CartSidebar.vue` (показывается на каталоге и на странице товара), экран каталога с фильтрами, плагин аналитики, `formatPrice`?

::: details Решение и разбор
| Файл | Куда | Почему |
| --- | --- | --- |
| `Button.vue` | `shared/ui/button` | без бизнес-домена |
| `http.ts` | `shared/api` | инфраструктура |
| `Product`, `fetchProduct` | `entities/product/model`, `entities/product/api` | бизнес-сущность |
| `ProductCard.vue` | `entities/product/ui` | базовое отображение сущности; кнопку действия получает через слот |
| «В корзину» | `features/add-to-cart` | действие пользователя, нужно в карточке и на странице товара |
| `CartSidebar.vue` | `widgets/cart-sidebar` | крупный блок на нескольких страницах |
| экран каталога | `pages/catalog`, фильтры там же | фильтры нужны одной странице — pages first |
| плагин аналитики | `app` (в Nuxt — `app/plugins/`) | инициализация приложения |
| `formatPrice` | `shared/lib/format` | если это чистое форматирование валюты; если в нём правила скидок — это уже домен и место в `entities` |

Тонкое место — `ProductCard`. Сущность не может импортировать фичу «В корзину», поэтому карточка принимает кнопку через слот, а собирает их вместе страница или виджет. Это и есть композиция сверху вниз, которой требует правило импортов.
:::

### 2. Найти нарушения · средне

Найдите нарушения FSD и предложите исправление.

```ts
// app/entities/order/model/store.ts
import { useCartStore } from '~/features/add-to-cart/model/store'

// app/features/cancel-order/ui/CancelButton.vue (script)
import { refundPayment } from '~/features/refund/api'

// app/shared/lib/discount.ts
import type { Order } from '~/entities/order'
export const discountFor = (o: Order) => (o.items.length > 5 ? 0.1 : 0)

// app/widgets/header/ui/Header.vue (template only)
// <UserAvatar /> rendered without any import
```

::: details Решение и разбор
1. **Сущность импортирует фичу** — импорт вверх, да ещё и мимо публичного API. Заказу не нужен стор корзины. Если связь есть в сценарии («повторить заказ» кладёт товары в корзину), это отдельная фича `features/repeat-order`, которая использует обе сущности.
2. **Фича импортирует фичу** — запрещено между слайсами одного слоя. Варианты: возврат денег — часть сценария отмены, и тогда `refundPayment` переезжает в `cancel-order`. Либо это операция над платежом, и тогда она в `entities/payment/api`. Либо две фичи оркестрирует виджет или страница уровнем выше.
3. **Бизнес-логика в `shared`**, да ещё с импортом вверх из `entities`. Правило скидки — домен: `entities/order/lib/discount.ts`.
4. **Зависимость спрятана auto-import**: Steiger и ESLint её не видят. Выключить автоимпорт компонентов и импортировать `UserAvatar` из `~/entities/user`.

Общий вывод для интервью: три из четырёх нарушений — это вопрос «кто оркестрирует». Ответ всегда один: слой выше обоих участников.
:::

### 3. Циклическая зависимость сущностей · средне

`entities/order` импортирует `User` из `entities/user`, а `entities/user` импортирует `fetchOrdersByUser` и `Order` из `entities/order`, чтобы показать в профиле «последние заказы». Сборка проходит, но в тестах иногда `ReferenceError: Cannot access 'X' before initialization`. Что происходит и как разорвать цикл?

::: details Решение и разбор
Цикл модулей: при загрузке одного из них второй вычисляется раньше, чем объявлены нужные первому привязки, и обращение попадает в TDZ. В тестах порядок входа другой, чем в приложении, поэтому ошибка «плавает».

Разрыв по шагам:

1. **«Последние заказы пользователя» — не свойство пользователя**, а блок профиля. Запрос `fetchOrdersByUser` остаётся в `entities/order`, а список собирает `pages/profile` (или `widgets/recent-orders`, если он нужен на двух страницах). Зависимость `user → order` исчезает.
2. **`order → user` нужен только тип покупателя.** Он идёт через `entities/user/@x/order.ts` и `import type`. Импорт только типа удаляется при компиляции и в рантайме цикла не создаёт.
3. **Закрепить линтером**: Steiger запрещает обычные импорты между сущностями, а dependency-cruiser или `import-x/no-cycle` ловят циклы на CI.

Альтернатива «вынести общее в `shared`» здесь неверна: `shared` не должен знать о заказах и пользователях.
:::

### 4. План миграции legacy-проекта · сложно

Nuxt 3-проект на 4 года: 400 компонентов в `components/` (автоимпорт с префиксами путей), 60 composables, 25 сторов Pinia, три команды. Релизы каждую неделю, заморозить разработку нельзя. Предложите план перехода на структуру с проверяемыми границами.

::: details Решение и разбор
Ключевые решения:

1. **Сначала цель, потом методология.** Проблема — нет границ и владельцев, а не «нет FSD». Спросить, нужна ли полная FSD или хватит доменных модулей. Для трёх команд и сотен компонентов FSD оправдан: он даёт общий словарь и готовый линтер.
2. **Обновление до Nuxt 4 — отдельный шаг** до миграции структуры: переезд в `app/` меняет все пути, и смешивать два переезда в одном потоке PR — гарантированные конфликты.
3. **Каркас без переноса кода.** Создать `app/shared`, `app/entities` и остальные слои, настроить `dir.pages`, Steiger и ESLint **только на новые каталоги**. Старый `components/` живёт как есть.
4. **Остановить рост долга.** Новый код — только в слоях. Линтер в CI блокирует импорт из новых слоёв в старый `components/`, иначе миграция никогда не закончится.
5. **Переносить по вертикали:** страница целиком вместе с тем, что нужно только ей (pages first), а общее спускать в `entities` и `shared` при втором использовании. Порядок — по частоте изменений: сначала то, что команды трогают каждый спринт.
6. **Auto-imports выключать постепенно.** Сначала `imports.scan: false` и `components.dirs: []` для новых каталогов (старые остаются в `dirs`), а когда `components/` опустеет — удалить совсем. Явные импорты в старом коде можно сгенерировать codemod-ом.
7. **Владение.** CODEOWNERS по слайсам, а не по слоям: команда заказов владеет `entities/order`, `features/*-order`, `pages/orders-*`.

Цена: месяцы двух структур одновременно и правило «новое — по-новому», которое нужно защищать на ревью. Альтернатива «большой переезд за две недели» дешевле в теории, но на практике это блокировка релизов и конфликты слияния у всех трёх команд.
:::
