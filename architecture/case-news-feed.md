# Разбор: новостная лента

> **Коротко.** Новостная лента — самая частая задача раунда «спроектируйте приложение». В ней сходятся почти все темы раздела: cursor-пагинация, нормализованный кэш, optimistic updates, стратегия рендеринга, real-time и производительность длинного списка. Senior проектирует её по RADIO: требования (персональная ли лента, какие медиа, нужны ли новые посты без перезагрузки) → части (лента, карточка, композер, стор, слой API) → нормализованная модель постов и авторов → cursor-API и мутации → углубление: бесконечная прокрутка, виртуализация и возврат на позицию, медиа, первый экран, новые посты без прыжка, доступность по паттерну `feed`. Каждое решение привязывают к требованиям и называют цену.

**Связанные темы:** [Frontend System Design: фреймворк RADIO](system-design-framework.md), [Данные и сеть в System Design](data-and-network.md), [Нефункциональные требования: рендеринг, офлайн, i18n, наблюдаемость](non-functional.md), [Разбор: автокомплит](case-autocomplete.md), [DOM API и observers](../browser/dom.md), [Real-time: polling, SSE, WebSocket](../network/realtime.md), [Хранилища браузера](../network/browser-storage.md), [Оптимизация загрузки](../performance/loading.md), [Оптимизация runtime и профилирование](../performance/runtime.md), [Производительность Vue и Nuxt](../performance/vue-performance.md), [Core Web Vitals и измерение](../performance/web-vitals.md), [Утечки памяти](../performance/memory-leaks.md), [XSS и безопасный вывод во Vue](../security/xss.md)

## Теория

Здесь — применение уже разобранных механизмов к одной задаче. Порядок разговора и тайминг — в [теме про RADIO](system-design-framework.md). Пагинация, нормализация, optimistic updates и real-time в общем виде — в [«Данных и сети»](data-and-network.md), там же задачи «Лайк с откатом и быстрыми кликами» и «Лента с курсором и новыми постами». Выбор стратегии рендеринга и офлайн — в [нефункциональных требованиях](non-functional.md). Ниже — какие из этих решений принимаются для ленты и почему.

Условие на интервью: «Спроектируйте новостную ленту, как в Facebook» (вариации: Twitter/X, лента LinkedIn, Instagram). Задача уровня приложения, поэтому в ней есть сетевой API, клиентский кэш, стратегия рендеринга и real-time.

### R — требования: что спрашивать

| Вопрос | Что решает |
| --- | --- |
| Лента персональная и за логином или публичная? | Нужен ли SSR ради SEO и можно ли кэшировать HTML на CDN (персональный — нельзя) |
| Какие типы контента: текст, фото, видео, ссылки с превью? | Модель вложений, стратегия загрузки медиа, высота карточек (переменная) |
| Какие действия: публикация, лайки, комментарии, репост? | Мутации, optimistic updates, нужна ли нормализация |
| Нужны ли новые посты без перезагрузки? Насколько срочно? | Polling, SSE или ничего; плашка «новые посты» |
| Сколько постов листают за сессию? | Нужна ли виртуализация и выгрузка далёких страниц |
| Основные устройства и сеть? | Размер медиа, объём JS, порог предзагрузки |
| Порядок: хронологический или ранжированный? | Курсор по `(createdAt, id)` или по позиции в выдаче ранжирования |

На «решите сами» записывают допущения: «Лента за логином; текст и фото, видео — вторым приоритетом; публикация, лайки, комментарии; новые посты появляются без перезагрузки, задержка в минуту допустима; за сессию — сотни постов; 60 % мобильный веб; порядок ранжирует сервер».

**Функциональные требования**: бесконечная лента; публикация поста; лайк и комментарий; фото и видео в постах. **Нефункциональные**: быстрый первый экран (LCP), плавная прокрутка без прыжков (CLS, INP), экономия трафика на мобильных, возврат на ту же позицию после перехода в пост, доступность с клавиатуры и скринридером. **Вне рамок**: алгоритм ранжирования, модерация, загрузка и транскодирование видео на сервере.

### A — архитектура

```text
 ┌──────────────────────────── Client ────────────────────────────┐
 │  FeedPage                                                      │
 │   ├─ Composer ──────── createPost ──┐                          │
 │   ├─ NewPostsBanner ◀── "N new" ──┐ │                          │
 │   └─ FeedList ── PostCard × N     │ │                          │
 │        ▲  reads by id             │ ▼                          │
 │   Entity store ◀─────── Feed controller ◀──▶ API client ───────┼──▶ Server
 │   (posts, users)         (pages, cursors,     (fetch, retries, │    (black box)
 │                           pending mutations)   SSE / polling)  │
 └────────────────────────────────────────────────────────────────┘
```

- **FeedList** — список карточек, триггер подгрузки, виртуализация, роли `feed`/`article`.
- **PostCard** — получает `id` поста и читает его из стора. Лайк, комментарии и медиа — внутри карточки.
- **Composer** — форма нового поста: черновик, вложения, отправка.
- **NewPostsBanner** — плашка «12 новых постов», копит сигналы, по клику вставляет их наверх.
- **Feed controller** — порядок постов в ленте, курсоры, загрузка страниц, ожидающие мутации. Во Vue это composable поверх кэша запросов или стор.
- **Entity store** — посты и авторы по `id`. Одна копия сущности на всё приложение.
- **API client** — запросы, повторы, транспорт новых постов.

Данные идут в одну сторону: сервер → контроллер → стор → карточки. Карточка не держит копию поста, поэтому лайк на странице поста виден в ленте без синхронизации.

### D — модель данных

| Данные | Вид | Где живёт |
| --- | --- | --- |
| Посты, авторы, вложения | server state | нормализованный стор: `posts by id`, `users by id` |
| Порядок ленты: `ids`, `nextCursor`, `newestCursor` | server state | контроллер ленты |
| Новые посты, ещё не показанные | server state, буфер | контроллер ленты, отдельно от `ids` |
| Черновик поста | persistent client state | `localStorage` или IndexedDB, переживает перезагрузку |
| Ожидающие мутации (`pending`) | client state | контроллер: для показа «отправляется…» и отката |
| Раскрыт ли «читать дальше», открыты ли комментарии | ephemeral client state | компонент карточки |
| Относительное время («5 мин назад») | derived | `computed` от `createdAt` и общего таймера |

**Почему здесь нормализация окупается**, хотя в [автокомплите](case-autocomplete.md) — нет. Один автор виден в десятках постов, один пост — в ленте, на своей странице, в профиле и в уведомлениях. Пост меняется часто: лайки, число комментариев, правка текста. Это ровно случай «одна сущность во многих местах, частые мелкие правки» из [«Данных и сети»](data-and-network.md). GreatFrontEnd отмечает, что Facebook (Relay) и Twitter (Redux) используют нормализованный клиентский стор. Цена: схема, слияние частичных объектов и ручная вставка новых постов в `ids`, потому что нормализация не решает списки.

Чтобы старый ответ не затёр свежие данные, у поста есть `version` (или `updatedAt`): при слиянии запись заменяется, только если версия не старше.

### I — интерфейс

```text
GET  /feed?cursor=<opaque>&limit=10
→ 200 { posts: Post[], users: User[], nextCursor: string | null }

GET  /feed/new?since=<newestCursor>      → { count, posts?, users? }
POST /posts            { clientId, text, attachments }   Idempotency-Key: <uuid>
PUT  /posts/:id/like   |  DELETE /posts/:id/like
GET  /posts/:id/comments?cursor=…&limit=20
```

Решения в контракте и их цена:

- **Cursor, а не offset.** В ленту постоянно добавляются посты, offset даёт дубли и пропуски. При ранжированной ленте курсор указывает не на дату, а на позицию в **снимке выдачи** на сервере: иначе ранжирование между запросами перемешает страницы. Цена снимка — память сервера и его время жизни: после часа простоя ленту проще загрузить заново.
- **Авторы отдельным массивом** (sideloading), а не вложенным объектом в каждом посте. Ответ меньше, а клиенту не нужно извлекать сущности из вложенной структуры. В GraphQL то же даёт нормализация по `__typename` и `id`.
- **Размеры вложений в ответе**: `width`, `height`, `blurhash` или доминантный цвет. Без них карточка не знает свою высоту до загрузки картинки: прыгает лента (CLS) и ломается оценка высоты в виртуализации.
- **Маленькая первая страница** (5–10 постов): она нужна для первого экрана, следующие грузятся заранее.
- **Лайк — итоговое состояние** (`PUT`/`DELETE`), а не переключение: идемпотентно, повтор безопасен.
- **Пост с `clientId` и ключом идемпотентности**: повтор после обрыва не создаст второй пост, а оптимистичную запись легко сопоставить с ответом сервера.

**Интерфейс компонентов** короткий. `PostCard` принимает `postId`, а не объект поста: карточка читает актуальные данные из стора. `FeedList` принимает `ids`, `hasMore`, `loading` и испускает `loadMore`.

### O — углубление: что выбрать за 15 минут

Всё ниже за раунд не обсудить. Обычно ждут производительность длинного списка и новые посты. Дальше выбирают по требованиям: медиа, первый экран, доступность или мутации.

#### Первый экран: SSR или оболочка

Лента за логином, SEO ей не нужен. Это аргумент против SSR «по привычке» ([как выбирать](non-functional.md)). Аргумент за — LCP: без SSR цепочка выглядит как HTML → бандл → `/feed` → картинка первого поста. Варианты:

- **CSR с оболочкой**: статичный HTML, скелетоны, данные после загрузки JS. Дёшево для сервера, но LCP поздний.
- **SSR первой страницы**: в HTML 3–5 постов, картинка первого — с `fetchpriority="high"` и без `loading="lazy"` ([LCP-изображение](../performance/loading.md)). Данные уходят в payload и второй раз не запрашиваются. Цена — сервер на каждый запрос, кэшировать HTML нельзя (он персональный), а кнопки «мёртвые» до гидрации.
- **SSR + отложенная гидрация** карточек ниже первого экрана (`hydrate-on-visible` в Nuxt, `hydrateOnVisible()` во Vue 3.5). Первый экран гидрируется сразу, иначе первый лайк уйдёт в негидрированный HTML ([подробнее](../performance/vue-performance.md)).

Выбор при наших допущениях: SSR первой страницы в Nuxt, остальные страницы — на клиенте. Если лента публичная (профиль, хэштег), добавляется SEO, и SSR становится обязательным.

#### Бесконечная прокрутка

Триггер — `IntersectionObserver` на элементе-«сторожке» (sentinel) после последнего поста, а не обработчик `scroll` с `getBoundingClientRect()`: наблюдатель не нагружает главный поток и не вызывает принудительный layout ([как он работает](../browser/dom.md)). Решения:

- **Предзагрузка следующей страницы** заранее: `rootMargin: '0px 0px 1500px 0px'` — запрос уходит за 1–2 экрана до конца. На медленной сети порог больше.
- **Один запрос в полёте**: пока страница грузится, новые срабатывания игнорируются.
- **Повторная проверка после загрузки.** Наблюдатель сообщает только о пересечении порога. Если после загрузки короткой страницы sentinel всё ещё в зоне, нового уведомления не будет, и лента застрянет. Помогает `unobserve` + `observe`: после `observe()` первое уведомление приходит всегда.
- **Кнопка «Показать ещё»** рядом с автоподгрузкой: для клавиатуры, при ошибке загрузки и чтобы добраться до подвала. Без неё подвал недостижим.
- **Ошибка страницы**: состояние «Не удалось загрузить» с повтором, а не бесконечный спиннер.

#### Длинный список: `content-visibility` или виртуализация

| | `content-visibility: auto` | Виртуализация |
| --- | --- | --- |
| Что экономит | layout и paint карточек за экраном | число узлов DOM и компонентов Vue |
| Поиск браузера, якоря, скринридер | работают, узлы в DOM | не видят карточек вне окна |
| Сложность | две строки CSS | измерение высот, оценка, перерасчёт позиций |
| Когда хватает | сотни постов | тысячи постов или тяжёлые карточки (видео, iframe) |

Карточки ленты разной высоты, поэтому виртуализация требует измерять их после рендера (`ResizeObserver`) и считать позиции префиксными суммами ([окно с переменной высотой](../performance/runtime.md)). Цена: прыжки прокрутки, когда оценка сменяется измерением; потерянный фокус, когда карточка с фокусом уходит из DOM. Выбор при «сотнях постов за сессию»: `content-visibility: auto` с `contain-intrinsic-size: auto 600px`. Значение `auto` запоминает измеренную высоту, поэтому полоса прокрутки не прыгает. На web.dev такая правка сократила рендеринг страницы блога с 232 до 30 мс. Виртуализация — когда за сессию тысячи постов, тогда же далёкие страницы выгружают из памяти, сохраняя курсоры.

#### Возврат на позицию

Пользователь открыл пост, нажал «Назад» — и должен оказаться у того же поста. Для этого нужны две вещи:

1. **Данные живы**: кэш ленты не удаляется при уходе со страницы (`gcTime`, стор, `KeepAlive` для страницы ленты). Иначе после «Назад» загрузится одна первая страница, и прокручивать будет некуда.
2. **Позиция**. Nuxt по умолчанию возвращает `savedPosition` при навигации «назад» после хука `page:loading:end`. Это работает, если высота ленты восстановилась до прокрутки. С виртуализацией или изменившимися высотами пиксельный `scrollY` не надёжен. Надёжнее хранить **якорь**: `id` верхнего видимого поста и его смещение от верха, а при возврате прокручивать к нему.

#### Новые посты без прыжка

Сигнал о новых постах копится в буфере, в ленту их не вставляют без действия пользователя ([механика](data-and-network.md)). Транспорт — polling `/feed/new` раз в 30–60 секунд или SSE «есть новые» ([как выбрать](../network/realtime.md)). Для ленты с допустимой задержкой в минуту polling проще: обычный HTTP и нет долгих соединений на сервере. Паузу делают при `document.visibilityState === 'hidden'`, а при возврате на вкладку после долгого отсутствия — проверку сразу.

Прыжки бывают и без новых постов: картинка без размеров, раскрытый «читать дальше», догрузившееся превью ссылки над читаемым местом. Против этого работает **scroll anchoring** браузера: при изменении высоты выше видимой области он корректирует прокрутку. `overflow-anchor: auto` по умолчанию, по MDN — Baseline 2026. Но это страховка, а не замена размерам медиа в API.

#### Мутации: лайк, комментарий, публикация

- **Лайк** — optimistic update с одной мутацией в полёте на пост и откатом к подтверждённому сервером состоянию (задача «Лайк с откатом и быстрыми кликами» в [«Данных и сети»](data-and-network.md)). В нормализованном сторе патч одного поста виден везде.
- **Свой пост** — оптимистично наверх ленты со статусом «Публикуется…» и `clientId`. После ответа запись заменяется серверной по `clientId`. При ошибке пост остаётся с кнопкой «Повторить», текст не теряется. Инвалидировать всю ленту ради своего поста дорого: перезагрузятся все страницы.
- **Счётчики** (лайки, комментарии) в real-time обычно не нужны: обновляются при следующем чтении поста. Live-счётчик для одного открытого поста — отдельное решение.

#### Медиа

- **Фото**: `srcset`/`sizes` под ширину колонки, AVIF/WebP, `loading="lazy"` для всех, кроме первого экрана, `width`/`height` из API ([изображения](../performance/loading.md)). Пока картинка грузится, место занимает плейсхолдер цвета или `blurhash`.
- **Видео**: `preload="none"` и постер. Автовоспроизведение только `muted` и только когда видео видно больше чем наполовину (`IntersectionObserver` с `threshold: 0.5`). Одновременно играет одно видео, ушедшее с экрана — пауза. На мобильном и при `Save-Data` автовоспроизведение выключают.
- **Превью ссылок** и встраивания (iframe) — лениво и с зарезервированной высотой.

#### Доступность: паттерн `feed`

По APG «Feed»: контейнер с `role="feed"`, каждый пост — `role="article"` с `aria-labelledby` (автор и время) и, по желанию, `aria-describedby` (текст). У статьи `aria-posinset` и `aria-setsize`: число загруженных или общее, `-1`, если общее неизвестно. Пока добавляются статьи, на ленте `aria-busy="true"`, после — `false`. Клавиатура: Page Down/Page Up — фокус на следующую/предыдущую статью, Ctrl+End/Ctrl+Home — на первый фокусируемый элемент после/перед лентой. Поэтому у статьи `tabindex="0"`. Новые посты объявляет live region: «Доступно 12 новых постов», без автоматической вставки.

#### Безопасность

Текст поста, имена и комментарии — пользовательские данные. Ссылки, упоминания и хэштеги собирают из токенов в компоненты, а не склеивают HTML для `v-html`. Ссылки из постов проверяют по схеме (`javascript:` — XSS) и открывают с `rel="noopener noreferrer ugc"` ([XSS](../security/xss.md)).

## Примеры

### 1. Доска к 25-й минуте

```text
DESIGN: News feed (logged-in, ranked, web desktop + mobile)

R  Functional: infinite feed · create post · like / comment · photos, video (P2)
   Non-functional: fast first screen (LCP) · no jumps (CLS) · smooth scroll (INP)
                   back → same position · mobile data · a11y (feed pattern)
   Out of scope: ranking, moderation, video transcoding

A  FeedPage: Composer · NewPostsBanner · FeedList → PostCard(id)
   Feed controller (ids, cursors, pending) ↔ Entity store (posts, users) ↔ API

D  Post {id, authorId, text, media[{url, w, h, blurhash}], likeCount, liked, version}
   User {id, name, avatar} → normalized by id
   Feed {ids, nextCursor, newestCursor, buffered new} · Draft → localStorage

I  GET /feed?cursor&limit=10 → {posts, users, nextCursor}
   GET /feed/new?since · POST /posts {clientId} + Idempotency-Key · PUT|DELETE like

O  1) SSR first page, lazy hydration below the fold, LCP image fetchpriority=high
   2) sentinel + IntersectionObserver, prefetch 1–2 screens ahead, "Show more"
   3) content-visibility for hundreds; virtualization for thousands; restore by anchor
   4) new posts: polling 60s → banner, no auto insert
```

### 2. Нормализованный стор ленты

Сущности хранятся один раз, лента — только упорядоченные `id`. Дубли между страницами отбрасываются, устаревший ответ не затирает более новую версию.

```ts
interface User { id: string; name: string }
interface Post { id: string; authorId: string; text: string; likeCount: number; version: number }
interface FeedPage { posts: Post[]; users: User[]; nextCursor: string | null }

class FeedStore {
  posts = new Map<string, Post>();
  users = new Map<string, User>();
  ids: string[] = [];
  nextCursor: string | null = null;
  private inFeed = new Set<string>();

  appendPage(page: FeedPage): void {
    this.merge(page);
    for (const post of page.posts) {
      if (this.inFeed.has(post.id)) continue; // already shown on an earlier page
      this.inFeed.add(post.id);
      this.ids.push(post.id);
    }
    this.nextCursor = page.nextCursor;
  }

  prependNew(page: FeedPage): void {
    this.merge(page);
    const fresh = page.posts.map((p) => p.id).filter((id) => !this.inFeed.has(id));
    for (const id of fresh) this.inFeed.add(id);
    this.ids.unshift(...fresh);
  }

  view(id: string) {
    const post = this.posts.get(id)!;
    return { ...post, author: this.users.get(post.authorId)! };
  }

  private merge(page: FeedPage): void {
    for (const user of page.users) this.users.set(user.id, user);
    for (const post of page.posts) {
      const known = this.posts.get(post.id);
      if (!known || post.version >= known.version) this.posts.set(post.id, post); // stale data never wins
    }
  }
}

const ann = { id: 'u1', name: 'Ann' };
const post = (id: string, version = 1, likeCount = 0) => ({ id, authorId: 'u1', text: `post ${id}`, likeCount, version });

const store = new FeedStore();
store.appendPage({ posts: [post('3'), post('2')], users: [ann], nextCursor: 'c1' });
store.appendPage({ posts: [post('2'), post('1')], users: [ann], nextCursor: null }); // '2' repeats
console.log(store.ids); // [ '3', '2', '1' ]

store.prependNew({ posts: [post('4')], users: [ann], nextCursor: null });
console.log(store.ids); // [ '4', '3', '2', '1' ]

store.posts.set('3', post('3', 2, 10)); // a like confirmed by the server, version 2
store.appendPage({ posts: [post('3', 1, 9)], users: [], nextCursor: null }); // a late, older response
console.log(store.view('3').likeCount); // 10

store.users.set('u1', { id: 'u1', name: 'Ann Lee' }); // renamed once, visible in every post
console.log(store.view('1').author.name, store.view('4').author.name); // Ann Lee Ann Lee
```

### 3. Лента с подгрузкой и ролями `feed`

Шаблон показывает решения, а не готовый компонент: сторожок с запасом, повторная проверка после загрузки, кнопка-альтернатива, роли и `content-visibility`. `PostCard` рендерит `<article>`, атрибуты попадают на него через fallthrough.

```vue
<script setup lang="ts">
import { onBeforeUnmount, onMounted, useTemplateRef, watch } from 'vue';

const props = defineProps<{ ids: string[]; hasMore: boolean; loading: boolean }>();
const emit = defineEmits<{ loadMore: [] }>();
const sentinel = useTemplateRef<HTMLElement>('sentinel');
let observer: IntersectionObserver | undefined;

onMounted(() => {
  observer = new IntersectionObserver(
    ([entry]) => {
      if (entry.isIntersecting && props.hasMore && !props.loading) emit('loadMore');
    },
    { rootMargin: '0px 0px 1500px 0px' }, // ask for the next page 1–2 screens ahead
  );
  if (sentinel.value) observer.observe(sentinel.value);
});

// The observer reports only threshold crossings: re-observe to get a fresh check after a short page.
watch(() => props.loading, (loading) => {
  if (!loading && observer && sentinel.value) {
    observer.unobserve(sentinel.value);
    observer.observe(sentinel.value);
  }
});

onBeforeUnmount(() => observer?.disconnect());
</script>

<template>
  <div role="feed" :aria-busy="loading" aria-label="News feed">
    <PostCard
      v-for="(id, index) in ids"
      :key="id"
      :post-id="id"
      tabindex="0"
      :aria-posinset="index + 1"
      :aria-setsize="hasMore ? -1 : ids.length"
      class="post"
    />
  </div>
  <div ref="sentinel" aria-hidden="true"></div>
  <button v-if="hasMore" type="button" :disabled="loading" @click="emit('loadMore')">
    Show more
  </button>
</template>

<style scoped>
.post {
  content-visibility: auto;
  contain-intrinsic-size: auto 600px;
}
</style>
```

## Вопросы с интервью

::: details С каких вопросов вы начнёте, если просят спроектировать новостную ленту
С тех, что меняют дизайн. Персональная ли лента и за логином ли она: от этого зависит, нужен ли SSR ради SEO и можно ли кэшировать HTML. Какие типы контента: текст, фото, видео. Это модель вложений и стратегия загрузки медиа. Какие действия: публикация, лайки, комментарии. Нужны ли новые посты без перезагрузки и с какой задержкой. Сколько постов листают за сессию: от этого зависит, нужна ли виртуализация. Устройства и сеть. Порядок хронологический или ранжированный. Ранжирование, модерацию и обработку видео сразу отношу к серверу и вне рамок. На «решите сами» записываю допущения с числами.
:::

::: details Нужен ли ленте нормализованный кэш и чем вы за него платите
Да, это один из немногих случаев, когда он окупается. Автор виден в десятках постов, пост — в ленте, на своей странице и в профиле, и меняется он часто: лайки, комментарии, правки. В нормализованном сторе пост хранится один раз, патч лайка виден везде без перезапросов. Цена: схема с `id` у каждой сущности, слияние частичных объектов, защита от устаревших ответов через версию. Новые посты в ленту всё равно вставляются вручную в массив `ids`: нормализация не знает, в какой список попадает сущность. Для автокомплита или каталога я бы её не взял.
:::

::: details Как реализовать бесконечную прокрутку и какие у неё ловушки
`IntersectionObserver` на элементе после последнего поста, с `rootMargin` на 1–2 экрана вперёд, чтобы следующая страница пришла до того, как пользователь доскроллит. Не больше одного запроса в полёте. Наблюдатель сообщает только о пересечении порога. Если после короткой страницы сторожок всё ещё виден, уведомления не будет, поэтому после загрузки делаю `unobserve` и `observe`. Ловушки самой прокрутки: недостижимый подвал, клавиатура и ошибки загрузки. Поэтому рядом остаётся кнопка «Показать ещё» и состояние ошибки с повтором. Плюс память и DOM растут с каждой страницей, это отдельное решение.
:::

::: details Виртуализация или content-visibility для ленты
Зависит от длины сессии. `content-visibility: auto` с `contain-intrinsic-size: auto 600px` пропускает layout и paint карточек за экраном, но узлы остаются в DOM. Поиск браузера, якоря и скринридер работают, а цена — две строки CSS. Для сотен постов этого хватает. Виртуализация убирает узлы и компоненты, поэтому нужна на тысячах постов или тяжёлых карточках. Цена у неё выше: переменная высота требует измерения и префиксных сумм, прокрутка прыгает при смене оценки на измерение, фокус теряется, поиск браузера не находит посты вне окна. При виртуализации ещё выгружаю далёкие страницы из памяти, сохраняя курсоры.
:::

::: details Как показать новые посты, чтобы лента не прыгала
Не вставлять их автоматически. Сигнал о новых постах — polling раз в 30–60 секунд или SSE — копится в буфере, а наверху появляется плашка «12 новых постов». По клику вставляю их и прокручиваю к началу. Если пользователь и так в самом верху, можно вставить сразу. Для скринридера то же объявляет live region. Polling выбираю, когда минута задержки допустима: это обычный HTTP без долгих соединений. На скрытой вкладке опрос ставлю на паузу, при возврате проверяю сразу. Против прыжков от картинок и раскрытого текста нужны размеры медиа в API, а scroll anchoring браузера — страховка.
:::

::: details Нужен ли SSR ленте за логином
SEO ей не нужен, поэтому «SSR, потому что Nuxt» — не аргумент. Аргумент — LCP: без SSR первый пост виден только после цепочки HTML → бандл → API → картинка. Я бы рендерил на сервере первую страницу из 3–5 постов, картинку первого грузил с `fetchpriority="high"`, а карточки ниже первого экрана гидрировал при появлении. Цена: сервер на каждый запрос, HTML нельзя кэшировать на CDN, ведь он персональный, и кнопки не отвечают до гидрации. Если команда не хочет держать SSR, CSR с оболочкой и скелетонами — приемлемый выбор, но тогда LCP надо измерять и бороться за него по-другому: маленькая первая страница, ранний запрос данных.
:::

::: details Как сделать ленту доступной
По паттерну APG «Feed». Контейнер `role="feed"`, каждый пост — `article` с `aria-labelledby` на автора и время, с `aria-posinset` и `aria-setsize`. Если общее число неизвестно, `aria-setsize="-1"`. Пока подгружается страница, на ленте `aria-busy="true"`. Клавиатура: Page Down и Page Up переводят фокус между статьями, Ctrl+End и Ctrl+Home выводят из ленты. Поэтому статьи фокусируемы. Новые посты объявляю через live region, а не вставляю молча. Плюс кнопка «Показать ещё» вместо обязательной автоподгрузки. При виртуализации нельзя удалять из DOM статью с фокусом.
:::

## Задачи

### 1. Лента без сети · средне

Продолжение разбора: «А если пользователь в метро без сети?». Что увидит человек, открывший ленту офлайн, и что произойдёт с лайком и постом, сделанными без сети?

::: details Решение и разбор
Уровни по возрастанию цены ([офлайн в общем виде](non-functional.md)):

1. **Честное состояние.** Уже загруженная лента остаётся на экране, подгрузка показывает «Нет подключения» с повтором, а не бесконечный спиннер. Почти бесплатно.
2. **Последняя лента после перезагрузки.** Первые 2–3 страницы и их сущности — в IndexedDB, медиа первого экрана — в Cache API через Service Worker. Открыл приложение без сети — видит ленту часовой давности с пометкой «обновлено в 8:40». Цена: место на устройстве (лимит записей и возраста), очистка при выходе из аккаунта: лента персональная ([Хранилища браузера](../network/browser-storage.md)).
3. **Очередь мутаций.** Лайк и пост без сети записываются в очередь и отправляются при `online`. Лайк идемпотентен (`PUT`), повтор безопасен. Пост отправляется с `clientId` и ключом идемпотентности, созданным при нажатии «Опубликовать», а не при отправке. Иначе повтор после потерянного ответа создаст дубль. В UI пост помечен «Ожидает сети».

Выбор: 1 и 2 — почти всегда, это главный выигрыш для мобильных. Очередь — для лайков и постов. Комментарии офлайн я бы не делал: их контекст (ветка) устаревает, а конфликтов больше. Медиа в очереди — только с ограничением размера: видео на 200 МБ в IndexedDB не кладут.
:::

### 2. В 10 раз больше пользователей · средне

Аудитория выросла в 10 раз. Бэкенд не справляется с `/feed` и `/feed/new` в час пик, CDN медиа дорожает. Что может сделать фронтенд и чем заплатит?

::: details Решение и разбор
Меньше запросов на ленту:

- **Polling реже и адаптивно**: 60 с вместо 30, пауза на скрытой вкладке, увеличение интервала, если новых постов нет, и jitter, чтобы клиенты не били в сервер одновременно после деплоя или сбоя. Цена — новые посты позже.
- **`/feed/new` возвращает только `count`**, а посты — по клику на плашку. Большинство клиентов плашку не нажмёт.
- **Предзагрузка следующей страницы ближе к концу**: порог 1 экран вместо 3. Цена — чаще видно спиннер.
- **Не перезагружать ленту при возврате** на вкладку, если она свежая (`staleTime` десятки секунд).
- **Переход на SSE** для сигнала «есть новые»: один долгий ответ вместо опроса. Это меняет нагрузку на сервер, а не убирает её: тысячи открытых соединений требуют другой инфраструктуры ([масштабирование real-time](../network/realtime.md)). Решение принимают вместе с бэкендом.

Меньше трафика медиа:

- `srcset` под реальную ширину колонки, AVIF, `preload="none"` для видео, без автовоспроизведения на мобильных.
- Сравнить порог ленивой загрузки браузера с реальной глубиной прокрутки: картинки, до которых пользователь не доскроллил, не должны грузиться.

Деградация: если `/feed` медленный, показывать ленту из кэша с пометкой и обновлять в фоне. Если `/feed/new` отвечает `429` или `503`, клиент увеличивает интервал, а не повторяет сразу. Порядок: сначала `count` вместо постов и адаптивный polling (максимум эффекта, почти без вреда UX), потом остальное.
:::

### 3. Лента на мобильном · средне

70 % трафика — мобильный веб на средних Android. Жалобы: «лента дёргается при прокрутке», «съедает трафик», «после возврата из поста — снова наверху». Разберите причины и решения.

::: details Решение и разбор
- **«Дёргается»** — это долгие задачи и сдвиги. Сдвиги (CLS): картинки без размеров, превью ссылок без зарезервированной высоты. Лечат размеры из API и плейсхолдеры. Долгие задачи: рендер страницы из 10 тяжёлых карточек одной задачей, гидрация, тяжёлые обработчики `scroll`. Лечат `IntersectionObserver` вместо `scroll`, `content-visibility: auto` и рендер новой страницы частями ([разбиение работы](../performance/runtime.md)). Подтвердить профилем на реальном устройстве с замедлением CPU, а не на ноутбуке.
- **«Съедает трафик»**: автовоспроизведение видео и картинки под десктоп. Видео только по нажатию или при `Save-Data`/медленной сети не играть, `srcset` под ширину экрана, меньшая первая страница. Предзагрузку следующей страницы оставить, но без медиа: картинки грузит `loading="lazy"`.
- **«Снова наверху»**: страница ленты размонтировалась, кэш умер, и после «Назад» загрузилась одна первая страница. Нужны кэш ленты, переживающий навигацию, и восстановление позиции по якорю (задача 4).

Дополнительно для мобильных: цели касания 44–48 px у лайка и меню, композер на весь экран при фокусе (клавиатура закрывает половину экрана), pull-to-refresh — только если он не конфликтует с жестом браузера.
:::

### 4. Возврат на позицию после поста · сложно

Пользователь пролистал 80 постов, открыл 81-й, вернулся «Назад». Ожидание: он снова видит 81-й пост на том же месте. Карточки разной высоты, медиа догружаются, лента может быть виртуализирована. Спроектируйте решение.

::: details Решение и разбор
Две части.

**1. Данные должны пережить навигацию.** Если кэш ленты удалён при уходе, после «Назад» придёт одна первая страница, и 81-го поста просто нет. Варианты: кэш запросов с достаточным `gcTime` и тем же ключом, стор ленты или `KeepAlive` для страницы ленты. С `KeepAlive` сохраняются и DOM, и состояние компонентов, но его цена — память, а таймеры и подписки надо ставить на паузу в `onDeactivated`. Если вкладку перезагрузили, данные теряются. Тогда честный вариант — начать сверху: курсоры могли устареть.

**2. Позиция.** Пиксельный `scrollY` ненадёжен: высоты карточек до загрузки медиа и после различаются, а при виртуализации полная высота — оценка. Надёжнее якорь:

```ts
interface ScrollAnchor { postId: string; offsetTop: number } // top of the post relative to the viewport

function captureAnchor(cards: HTMLElement[]): ScrollAnchor | null {
  const first = cards.find((el) => el.getBoundingClientRect().bottom > 0); // first card still visible
  return first ? { postId: first.dataset.id!, offsetTop: first.getBoundingClientRect().top } : null;
}

function restoreAnchor(anchor: ScrollAnchor, findCard: (id: string) => HTMLElement | null): void {
  const el = findCard(anchor.postId);
  if (el) window.scrollBy(0, el.getBoundingClientRect().top - anchor.offsetTop);
}
```

- **Когда сохранять**: в `onBeforeRouteLeave` или по событию прокрутки с throttle, вместе с ключом записи истории (`history.state`), чтобы «Назад» на ленту из разных мест восстанавливал свою позицию.
- **Когда восстанавливать**: после рендера ленты. При виртуализации сначала сказать виртуализатору прокрутить к индексу поста (`scrollToIndex`), чтобы карточка оказалась в DOM, затем поправить смещение. Nuxt по умолчанию возвращает `savedPosition` после `page:loading:end`. Это конфликтует с якорем, поэтому для маршрута ленты стандартное поведение переопределяют в `app/router.options.ts`.
- **Медиа выше якоря** догружаются после восстановления и сдвигают его. Помогают размеры из API, scroll anchoring браузера и повторная коррекция после загрузки картинок выше якоря.

Альтернатива — открывать пост в модальном окне поверх ленты с изменением URL. Лента не размонтируется вовсе, и проблемы нет. Цена: два режима маршрута (прямой заход по URL открывает полноценную страницу) и управление фокусом в модалке.

Сложность: O(n) по числу карточек в DOM для поиска якоря, а при виртуализации их в DOM несколько десятков.
:::
