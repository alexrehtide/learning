# Разбор: автокомплит

> **Коротко.** Автокомплит — самая частая задача раунда «спроектируйте компонент». Он выглядит как поле со списком, а на деле это конвейер запроса: нормализация и минимальная длина, кэш, debounce, отмена устаревших запросов, проверка актуальности ответа. Senior проектирует его по RADIO: требования (откуда подсказки, сколько данных, мобильные) → четыре части (поле, список, кэш, контроллер) → модель данных с флагом «ответ полный» → API компонента и сервера → углубление в кэш и его вытеснение, гонки, виртуализацию, доступность по паттерну combobox и безопасную подсветку. Правильного ответа нет: каждое решение привязывают к требованиям и называют его цену.

**Связанные темы:** [Frontend System Design: фреймворк RADIO](system-design-framework.md), [Данные и сеть в System Design](data-and-network.md), [Нефункциональные требования: рендеринг, офлайн, i18n, наблюдаемость](non-functional.md), [Design system и UI-kit](design-systems.md), [UI-coding: автокомплит, таблица, дерево](../live-coding/ui-widgets.md), [debounce и throttle](../live-coding/debounce-throttle.md), [async/await, обработка ошибок и отмена](../javascript/async-await.md), [Стеки и очереди](../algorithms/stacks-and-queues.md), [HTTP-кэширование и CDN](../network/caching.md), [Хранилища браузера](../network/browser-storage.md), [Оптимизация runtime и профилирование](../performance/runtime.md), [XSS и безопасный вывод во Vue](../security/xss.md)

## Теория

Здесь — проектирование, а не код. Реализация компонента на Vue (`useSearch`, combobox, подсветка) — в теме [«UI-coding: автокомплит, таблица, дерево»](../live-coding/ui-widgets.md). Порядок разговора и тайминг — в [теме про RADIO](system-design-framework.md), решения о кэше и сети в общем виде — в [«Данных и сети»](data-and-network.md). Ниже — как они применяются к одной задаче.

Условие на интервью звучит так: «Спроектируйте компонент автокомплита для поиска на сайте» (вариации: поиск в Facebook, Google, выбор города в форме бронирования). Задача компонентная, но с сетью, поэтому в ней есть и API компонента, и API сервера.

### R — требования: что спрашивать

Вопросы, ответ на которые меняет дизайн:

| Вопрос | Что решает |
| --- | --- |
| Откуда подсказки: локальный массив, сервер или оба? | Есть ли сетевой слой, кэш и отмена. Локальные 200 городов фильтруются в памяти без debounce |
| Сколько записей в источнике, сколько показывать? | Серверный или клиентский поиск; нужна ли виртуализация (обычно 5–10 подсказок — нет) |
| Какие типы результатов: текст, с картинкой, разнородные (люди, страницы, группы)? | Модель данных и кастомизация рендеринга (слоты) |
| Что происходит при выборе: подставить текст, перейти на страницу, выбрать значение формы? | Событие `select` и что хранит компонент |
| С какой длины запроса искать? | Число запросов и размер ответа на короткие префиксы |
| Мобильные устройства? | Экранная клавиатура, высота видимой области, размер целей касания, медленная сеть |
| Это компонент UI-kit для многих продуктов или одно поле? | Насколько широк API: слоты, источники данных, тема |
| Языки, IME, RTL? | Нормализация запроса, композиция ввода, направление списка |

Если интервьюер говорит «решите сами», формулируют допущение: «Компонент UI-kit; подсказки с сервера, база — миллионы записей; показываем до 8; ищем с 2 символов; десктоп и мобильный веб; несколько языков, включая японский».

**Функциональные требования**: подсказки по мере ввода; выбор мышью, касанием и клавиатурой; состояния «загрузка», «ничего не найдено», «ошибка»; подсветка совпадения. **Нефункциональные**: подсказки появляются быстро (ориентир — до 100–200 мс после паузы в наборе, ввод не тормозит, см. INP), лишних запросов нет, доступность по паттерну combobox, мобильные, i18n. **Вне рамок**: устройство поискового индекса и ранжирования на сервере, исправление опечаток (это задача сервера; клиент только передаёт запрос).

### A — архитектура: четыре части

```text
                   ┌─────────────────────────────── Autocomplete ───┐
  user types ────▶ │ Input ──query──▶ Controller ──fetch──▶ Server   │
                   │   ▲                │   ▲                (black   │
                   │   │ activeIndex,   │   │ hit/miss        box)    │
                   │   │ expanded       ▼   │                         │
                   │ ResultsList ◀──results── Cache                   │
                   └──────────────────────────────────────────────────┘
```

- **Input** — текстовое поле. Отдаёт контроллеру введённый текст и клавиши, получает `aria-*` и состояние раскрытия.
- **ResultsList** (popup) — список подсказок. Рендерит результаты через слот потребителя, сообщает о выборе.
- **Cache** — ответы сервера по нормализованному запросу. Живёт в экземпляре компонента или общий на страницу (см. ниже).
- **Controller** — мозг компонента: нормализует запрос, решает, идти ли в кэш или в сеть, держит таймер debounce и `AbortController`, отбрасывает устаревшие ответы, хранит активный индекс. Во Vue это composable, который используют поле и список.

Данные текут в одну сторону: ввод → контроллер → кэш или сервер → результаты → список. Поле и список не общаются напрямую, обе части читают состояние контроллера. Это и делает компонент тестируемым: контроллер проверяется без DOM, с подменённым fetcher-ом.

> [!NOTE]
> Стратегия рендеринга для компонента почти не обсуждается. Достаточно сказать, что подсказки — чисто клиентская часть, поле при SSR рендерится пустым и интерактивно после гидратации. Если поле стоит на первом экране, пользователь может начать печатать до гидратации. Введённое значение надо прочитать из DOM при монтировании, а не затереть пустым `ref`.

### D — модель данных

| Данные | Вид | Где живёт |
| --- | --- | --- |
| Подсказки (`Suggestion`) | server state | кэш контроллера |
| Флаг «ответ полный» у записи кэша | server state, метаданные | там же |
| Текст в поле, активный индекс, раскрыт ли список, статус запроса | ephemeral client state | контроллер экземпляра |
| Недавние запросы пользователя | persistent client state | `localStorage` или сервер (если нужны на всех устройствах) |
| Нормализованный запрос, «пусто», видимые сегменты подсветки | derived | `computed` |

Две детали отличают проработанную модель:

- **`complete` у ответа.** Если сервер вернул все совпадения для `vu` (их меньше `limit`), то ответ на `vue` — подмножество, и его можно отфильтровать на клиенте без запроса. Если ответ обрезан по `limit`, так делать нельзя: нужные подсказки могли не попасть в первые 8.
- **`id` у подсказки.** Нужен для `key` в списке, для `aria-activedescendant` и для события выбора: подпись может повторяться (два «Санкт-Петербурга» в разных странах).

### I — интерфейс: компонент и сервер

**API компонента** — то, что увидит потребитель UI-kit:

- `source: (query, { signal }) => Promise<Suggestion[]>` — функция данных, а не URL. Так компонент не знает о REST, авторизации и формате ответа, а локальный источник — та же функция над массивом.
- `minLength` (по умолчанию 1–2), `debounce` (200–300 мс), `limit`.
- `v-model` для текста и событие `select` с выбранной подсказкой. Выбор и текст разделены: пользователь может набрать текст и не выбрать ничего.
- Слоты: опция (`{ item, active, segments }`), «пусто», «загрузка», «ошибка». Так продукт рисует аватары и типы результатов, не форкая компонент ([паттерн headless](design-systems.md)).

**API сервера**:

```text
GET /suggest?q=vue&limit=8&locale=ru
→ 200 { query: "vue", items: [{ id, type, label, matches: [[0, 3]] }], complete: false }
Cache-Control: public, max-age=60   (only if results are not personalized)
```

Решения в контракте и их цена:

- **`query` в ответе** позволяет проверить актуальность ответа и без `AbortController`: ответ не к последнему запросу — отбросить.
- **`locale` в параметрах** (или в ключе кэша): иначе ответ на одном языке ляжет в запись другого.
- **`GET`, а не `POST`**: его кэширует браузер и CDN. Для общих подсказок (города, товары) это снимает нагрузку с сервера. Персональные подсказки (друзья, история) — `private` или `no-store`, иначе CDN покажет одному пользователю чужие результаты ([подробнее](../network/caching.md)).
- **Подсветка: диапазоны с сервера или вычисление на клиенте.** Сервер знает, что совпало при нечётком поиске и стемминге (`бег` → `бегать`), клиентская подсветка — только буквальное совпадение. Цена серверных диапазонов: индексы в UTF-16 или в кодовых точках надо оговорить в контракте. В обоих случаях на клиенте строку режут на сегменты и выводят как текст, а не HTML.

### O — углубление: что выбрать за 15 минут

Все темы ниже за раунд не обсудить. Обычно берут сеть и кэш (их ждут всегда), плюс одну-две по требованиям: доступность, мобильные, большой список.

#### Сеть: меньше запросов и никаких гонок

Конвейер на каждое изменение текста: нормализация → минимальная длина → кэш → debounce → запрос с отменой предыдущего → проверка актуальности → запись в кэш. Механика debounce — в [отдельной теме](../live-coding/debounce-throttle.md), отмены и гонок — в [async/await](../javascript/async-await.md). В дизайне важно назвать, что каждый шаг решает:

- **Debounce** уменьшает число запросов, но не устраняет гонку: два запроса с паузой больше `wait` уходят оба, и ответ на старый может прийти позже.
- **Отмена** (`AbortController`, `signal` в `fetch`) экономит сеть и снимает гонку, если fetcher её уважает. Отменённый `fetch` отклоняется с `DOMException` `AbortError`, её не показывают как ошибку.
- **Проверка актуальности** (последний запрос или `query` в ответе) — страховка, если источник игнорирует `signal`.
- **Throttle вместо debounce** — когда подсказки должны появляться **во время** набора, а не после паузы (поиск в Google обновляется на ходу). Цена — больше запросов, поэтому так делают, когда сервер дешёвый и быстрый.
- **Повторы** при ошибке сети для подсказок обычно не нужны: следующий символ всё равно запустит новый запрос. Достаточно состояния «ошибка» и повтора при следующем вводе.

Пока идёт загрузка, старые результаты остаются на экране: список, который мигает пустотой на каждом символе, хуже слегка устаревшего.

#### Кэш: структура, префиксы, вытеснение

Варианты структуры:

| Структура | Плюсы | Цена |
| --- | --- | --- |
| `Map<query, Suggestion[]>` | просто, мгновенный ответ на повторный запрос (стёр символ — список сразу) | дубли: «Vue» лежит в записях `v`, `vu`, `vue` |
| То же + фильтрация по полному префиксу | меньше запросов при наборе | клиентский фильтр должен повторять правило сервера (префикс, подстрока, без диакритики) |
| Нормализованный: `results by id` + `query → ids` | одна копия подсказки | сложнее; окупается, только если подсказки тяжёлые (картинки, вложенные данные) или их редактируют |

Для большинства случаев хватает первого, с фильтрацией по `complete` как оптимизацией. Нормализованный кэш здесь редко окупается: подсказки маленькие и не редактируются ([когда нормализация оправдана](data-and-network.md)).

**Вытеснение.** Неограниченный `Map` растёт всю сессию: в долгоживущем SPA с поиском в шапке это тысячи записей. Нужны оба ограничения:

- **Размер** — LRU: при переполнении удаляется давно не использованная запись. На `Map` это O(1), так как `Map` хранит порядок вставки ([LRU на `Map`](../algorithms/stacks-and-queues.md)).
- **Время жизни** зависит от данных: список городов — часы или весь сеанс, люди и группы — минуты, котировки акций — секунды или без кэша. Это та же настройка, что `staleTime` у кэша запросов.

**Где живёт кэш.** В экземпляре компонента он умирает при размонтировании: закрыли и открыли модалку с поиском — запросы заново. Общий кэш на страницу (модуль или стор, ключ по источнику и локали) переживает это, но его надо сбрасывать при смене пользователя, иначе следующий увидит подсказки прошлого. Переживать перезагрузку (IndexedDB) стоит только **начальным** результатам, которые показывают при фокусе в пустом поле: недавние запросы, популярное.

#### Рендеринг: длинный список

При 5–10 подсказках виртуализация не нужна, и это стоит сказать вслух. Она нужна, когда автокомплит превращается в выбор из большого списка без серверного поиска («выберите один из 5 000 товаров»). Тогда рендерят только видимые опции ([как устроено окно](../performance/runtime.md)), и это ломает две вещи из a11y: опции вне окна отсутствуют в DOM, поэтому `aria-activedescendant` не может на них указывать, а скринридер не знает их число. Решения: при движении стрелками сначала сдвинуть окно, потом выставить `aria-activedescendant`; у опций указать `aria-setsize` и `aria-posinset`.

Фильтрация 5 000 записей на каждый символ — несколько миллисекунд. Для 100 000 записей поиск переносят в Web Worker или на сервер, чтобы ввод не ждал фильтрации.

#### Доступность: паттерн combobox

По APG «Combobox»: у поля `role="combobox"`, `aria-expanded`, `aria-controls` (id списка), `aria-autocomplete="list"` и `aria-activedescendant`; у списка `role="listbox"`; у опций `role="option"` и `aria-selected` у активной. DOM-фокус всегда в поле, иначе пользователь не сможет печатать, а стрелки меняют только `aria-activedescendant`. Клавиши: ↓/↑ — по опциям, Enter — выбрать, Esc — закрыть, а если список уже закрыт — по желанию очистить поле. Число результатов и «ничего не найдено» объявляют через live region (`role="status"`). Подробности и ловушки (`mousedown.prevent`, прокрутка к активной опции, `isComposing`) — в [реализации](../live-coding/ui-widgets.md).

Почему это проектное решение, а не деталь: если доступность заложена в API (компонент сам ставит роли и id, потребитель только рендерит содержимое опции в слоте), её нельзя сломать в продукте. Если компонент отдаёт «сырой» список, каждый продукт сделает её по-своему.

#### Мобильные

- **Экранная клавиатура** закрывает нижнюю половину экрана. Список ограничивают по высоте видимой области (`visualViewport`), поле при фокусе прокручивают вверх; на маленьких экранах поиск часто открывают на весь экран.
- **Атрибуты поля**: `type="search"` или `enterkeyhint="search"` (кнопка «Найти» на клавиатуре), `autocapitalize="off"` и `spellcheck="false"` для названий, `autocomplete="off"`, чтобы подсказки браузера не легли поверх ваших.
- **Цели касания** не меньше 24×24 CSS px (WCAG 2.2, 2.5.8), на практике 44–48 px в высоту.
- **Медленная сеть**: debounce длиннее, меньший `limit`, без картинок в подсказках или с маленькими.

#### Безопасность и i18n

- **Подсветка без HTML.** Подсказки — пользовательские данные (имена, названия групп). Собрать строку с `<mark>` и вывести через `v-html` — XSS. Строку режут на сегменты и выводят интерполяцией ([XSS и безопасный вывод во Vue](../security/xss.md)).
- **Нормализация запроса** — та же, что у сервера: `trim`, регистр, Unicode-нормализация (`normalize('NFC')`), при необходимости `е`/`ё` и диакритика. Иначе ключ кэша и подсветка расходятся с тем, что нашёл сервер.
- **IME.** Во время композиции (японский, китайский) Enter подтверждает ввод, а не выбирает подсказку, и запрос по промежуточному тексту не нужен.

### 2. Кэш с префиксами, LRU и временем жизни

Запись знает, полный ли ответ. Полный ответ на короткий префикс отвечает и на длинный запрос без сети. `Map` хранит порядок вставки, поэтому «переложить в конец» — это LRU.

```ts
interface Suggestion { id: string; label: string }
interface Entry { items: Suggestion[]; complete: boolean; expiresAt: number }

// Results by normalized query: LRU by the insertion order of Map, TTL per entry.
class SuggestCache {
  private entries = new Map<string, Entry>();
  private maxEntries: number;
  private ttlMs: number;
  private now: () => number;

  constructor(maxEntries = 100, ttlMs = 60_000, now = () => Date.now()) {
    this.maxEntries = maxEntries;
    this.ttlMs = ttlMs;
    this.now = now;
  }

  set(query: string, items: Suggestion[], complete: boolean): void {
    this.entries.delete(query); // re-insert to mark as most recent
    this.entries.set(query, { items, complete, expiresAt: this.now() + this.ttlMs });
    if (this.entries.size > this.maxEntries) {
      this.entries.delete(this.entries.keys().next().value!); // the oldest one
    }
  }

  get(query: string): Suggestion[] | undefined {
    const exact = this.fresh(query);
    if (exact) return exact.items;
    // A complete answer for a shorter prefix already contains every match for the longer query.
    for (let len = query.length - 1; len > 0; len--) {
      const prefix = this.fresh(query.slice(0, len));
      if (prefix?.complete) {
        return prefix.items.filter((s) => s.label.toLowerCase().includes(query));
      }
    }
    return undefined;
  }

  private fresh(query: string): Entry | undefined {
    const entry = this.entries.get(query);
    if (!entry) return undefined;
    if (entry.expiresAt <= this.now()) {
      this.entries.delete(query);
      return undefined;
    }
    this.entries.delete(query); // touch: move to the end of the LRU order
    this.entries.set(query, entry);
    return entry;
  }
}

let time = 0;
const cache = new SuggestCache(2, 1000, () => time);
cache.set('vu', [{ id: '1', label: 'Vue' }, { id: '2', label: 'Vuex' }, { id: '3', label: 'Vuetify' }], true);
console.log(cache.get('vue')?.map((s) => s.label)); // [ 'Vue', 'Vuex', 'Vuetify' ], no request
cache.set('re', [{ id: '4', label: 'React' }], false); // limit hit: not complete
console.log(cache.get('rea')); // undefined: must go to the server
cache.set('ang', [], true);
console.log(cache.get('vu')); // undefined: evicted as least recently used
time = 2000;
console.log(cache.get('ang')); // undefined: expired
```

Фильтр `includes` здесь повторяет правило сервера «совпадение по подстроке». Если сервер ищет нечётко или со стеммингом, клиентский фильтр выбросит то, что сервер бы нашёл, и префиксную оптимизацию надо отключить. Это компромисс, который стоит проговорить: меньше запросов ценой связи клиента с алгоритмом поиска.

## Вопросы с интервью

::: details С каких вопросов вы начнёте, если просят спроектировать автокомплит
С тех, что меняют дизайн. Откуда подсказки: локальный список или сервер, сколько записей и сколько показываем. Это решает, нужны ли сеть, кэш, отмена и виртуализация. Что происходит при выборе: подстановка текста, переход или значение формы. С какой длины искать. Нужны ли мобильные, какие языки и есть ли IME. Это компонент UI-kit или одно поле: от этого зависит ширина API. Ранжирование и исправление опечаток сразу отношу к серверу и вне рамок. На «решите сами» записываю допущения с числами: «сервер, миллионы записей, до 8 подсказок, с 2 символов, десктоп и мобильный».
:::

::: details Почему debounce не решает проблему гонки ответов и что решает
Debounce только откладывает запрос до паузы в наборе. Если пауз было две, ушли два запроса, и ответ на `vu` может прийти после ответа на `vue` и затереть его. Гонку снимают отмена предыдущего запроса через `AbortController` и проверка актуальности перед записью результата: сравнить с последним запросом или с полем `query` в ответе. Проверка нужна как страховка, потому что не каждый источник уважает `signal`. Кэш по ключу тоже помогает: ответ ложится в запись своего запроса, а список показывает запись текущего.
:::

::: details Как вы устроите кэш подсказок и когда его чистить
По умолчанию — `Map` от нормализованного запроса к результатам. Повторный запрос и стирание символа отвечают мгновенно. Если сервер помечает ответ как полный (совпадений меньше лимита), длинный запрос фильтрую из ответа на префикс без сети, но только когда клиентский фильтр повторяет правило сервера. Чистить нужно по двум признакам: размер (LRU, на `Map` это O(1)) и время жизни, которое зависит от данных: города — часы, люди — минуты, котировки — без кэша. Если кэш общий на страницу, его сбрасываю при смене пользователя. Нормализованный кэш по `id` здесь обычно не окупается: подсказки маленькие и не редактируются.
:::

::: details Что в API компонента вы оставите потребителю, а что спрячете внутри
Потребителю — источник данных функцией `source(query, { signal })`, а не URL, чтобы компонент не знал про REST и авторизацию. Ещё ему остаются настройки `minLength`, `debounce`, `limit`, `v-model` для текста, событие `select` и слоты для опции, «пусто», «загрузка», «ошибка». Внутри — то, что каждый продукт сделал бы с ошибками: конвейер запроса с отменой и проверкой актуальности, роли и `aria-*`, клавиатура, live region, позиционирование списка. Слот опции получает сегменты подсветки, а не HTML, поэтому потребитель не может случайно открыть XSS.
:::

::: details Как подсветить совпадение и кто должен вычислять позиции
Если поиск буквальный, позиции можно найти на клиенте регулярным выражением с экранированием. Если сервер ищет нечётко или со стеммингом, только он знает, что совпало, и отдаёт диапазоны. Тогда в контракте надо оговорить, в каких единицах индексы: UTF-16 или кодовые точки. В обоих случаях строку режут на сегменты «совпало / не совпало» и выводят интерполяцией, совпавшие — в `<mark>`. Склеивать HTML и выводить через `v-html` нельзя: подсказки — пользовательские данные, это XSS.
:::

::: details Как сделать автокомплит доступным и почему фокус не уходит в список
По паттерну APG «Combobox»: поле с `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-autocomplete="list"`, список `listbox`, опции `option`. Фокус остаётся в поле, чтобы можно было печатать дальше, а активную опцию сообщает `aria-activedescendant`. Стрелки двигают активную опцию, Enter выбирает, Esc закрывает. Число результатов и «ничего не найдено» читает скринридер через live region. Отсюда обязанности кода: прокручивать список к активной опции и не терять фокус при клике мышью. В виртуализированном списке ещё нужно сдвигать окно до смены `aria-activedescendant` и ставить `aria-setsize` и `aria-posinset`.
:::

::: details Что изменится, если подсказки не с сервера, а из локального массива
Сеть уходит, а вместе с ней отмена, гонки и большая часть кэша. Debounce на сотнях записей не нужен: фильтрация в памяти занимает доли миллисекунды, а задержка только ухудшит отклик. Остаются нормализация, подсветка, доступность и, если записей тысячи, виртуализация списка. Если записей сотни тысяч, фильтрацию переношу в Web Worker или всё-таки на сервер, чтобы ввод не ждал. Потребителю ничего не меняется: локальный источник — та же функция `source`, просто синхронная внутри.
:::

## Задачи

### 1. Подсказки офлайн · средне

Продолжение разбора: интервьюер спрашивает: «А если пользователь потерял сеть?». Это поиск по городам в приложении бронирования, которое работает как PWA. Что покажет поле без сети и что вы для этого сделаете?

::: details Решение и разбор
Сначала уточнить, что значит «работать офлайн» для этого поля. Варианты по возрастанию цены:

1. **Честное состояние.** Без сети запросы падают сразу, поле показывает «Нет подключения» вместо бесконечного спиннера. Ответы, которые уже в кэше памяти, по-прежнему работают. Стоит почти ничего: обработать ошибку `fetch` и событие `offline`.
2. **Кэш, переживающий перезагрузку.** Недавние запросы пользователя и популярные города — в IndexedDB. При фокусе в пустом поле они показываются и без сети ([Хранилища браузера](../network/browser-storage.md)).
3. **Локальный индекс.** Список городов не так велик: 50 000 записей — несколько мегабайт, а в сжатом виде меньше. Его скачивают в фоне (Service Worker, Cache API) и ищут локально, в Web Worker. Цена: трафик и место на устройстве, обновление индекса, два правила поиска, которые должны давать одинаковые результаты.

Выбор: для бронирования — пункты 1 и 2. Офлайн-бронирование всё равно невозможно, а подсказки по истории помогают заполнить форму заранее. Пункт 3 выбрал бы для приложения, где поиск по справочнику — основной сценарий без сети, например офлайн-карты. Подробнее об уровнях офлайна — в [нефункциональных требованиях](non-functional.md).
:::

### 2. В 10 раз больше пользователей · средне

Сервис подсказок не справляется: после роста аудитории в 10 раз он отвечает 800 мс в час пик. Бэкенд-команда просит у фронтенда снизить нагрузку. Что вы можете сделать на клиенте и в контракте и чем заплатите за каждое решение?

::: details Решение и разбор
Меньше запросов на одного пользователя:

- **Минимальная длина** 2–3 символа вместо 1. Самые дорогие запросы — однобуквенные. Цена: на коротких запросах подсказок нет, а для китайского и японского один символ — уже слово, поэтому порог зависит от языка.
- **Debounce длиннее** (300 мс вместо 150). Цена: подсказки появляются позже.
- **Префиксный кэш** по флагу `complete`: дописывание символов к уже полному ответу не идёт в сеть.
- **Отмена** экономит клиенту сеть, но не всегда серверу: запрос может уже обрабатываться. Её стоит сочетать с остальным, а не считать решением.

Ответы переиспользуются между пользователями:

- **HTTP-кэш и CDN для неперсональных подсказок**: `GET /suggest?q=моск&locale=ru` с `Cache-Control: public, max-age=300`. Популярные префиксы почти у всех одинаковы, и CDN отвечает без бэкенда. Цена: подсказки устаревают на время `max-age`, а нормализовать `q` надо одинаково, иначе `Моск` и `моск` — разные записи CDN ([ключ кэша](../network/caching.md)). Персональную часть (друзья, история) отделяют в отдельный запрос или добавляют на клиенте.
- **Предзагрузка популярного**: топ-1000 запросов отдаётся одним статическим файлом и ищется локально, сеть — только для остального.

Деградация: если сервер не ответил за 300–500 мс, показываем то, что есть (кэш, недавнее), а не ждём. Выбор порядка: сначала кэш на CDN и минимальная длина (максимальный эффект, почти без вреда для UX), потом остальное.
:::

### 3. Автокомплит на мобильном · средне

Аналитика: 70 % поиска — мобильный веб, и пользователи жалуются, что «подсказки прячутся» и «промахиваюсь по подсказке». Опишите изменения в дизайне компонента для мобильных и что из этого влияет на API.

::: details Решение и разбор
Причины жалоб:

- **«Подсказки прячутся»**: список открывается вниз под экранную клавиатуру. Решения: высота списка из `visualViewport.height` (а не `100vh`), прокрутка поля к верху экрана при фокусе. На узких экранах — полноэкранный режим поиска: поле вверху, список под ним на всю оставшуюся высоту. Цена полноэкранного режима: отдельная разметка, управление фокусом и кнопка «Назад», которая должна закрывать поиск, а не уводить со страницы.
- **«Промахиваюсь»**: строки подсказок по 32 px. Высота 44–48 px, вся строка — цель касания, отступы между строками. Минимум WCAG 2.2 — 24×24 CSS px (критерий 2.5.8).

Остальное: `enterkeyhint="search"`, отключённые автоисправление и автозаглавные буквы для названий; меньший `limit` (на экране всё равно помещается 5–6 строк) и более длинный debounce на медленной сети; подсказки без тяжёлых картинок. Выбор по касанию — на `click`, а не на `touchstart`: иначе прокрутка списка пальцем выберет первую строку, которой коснулись.

Влияние на API: проп `mode: 'popup' | 'fullscreen' | 'auto'` (по умолчанию `auto` по ширине экрана) и событие закрытия полноэкранного режима, чтобы продукт мог синхронизировать историю. Остальное компонент делает сам, потребитель ничего не настраивает.
:::

### 4. Локальные и серверные подсказки вместе · сложно

Поиск в шапке соцсети. При фокусе в пустом поле — 5 недавних запросов пользователя. При вводе — сначала совпадения среди друзей (они уже загружены на клиент, их около 1 000), затем результаты сервера (люди, группы, страницы). Спроектируйте модель данных и поток: как объединять источники, что показывать, пока сервер не ответил, как избежать прыжков списка.

::: details Решение и разбор
```ts
type SuggestionType = 'recent' | 'friend' | 'person' | 'group' | 'page';

interface Suggestion {
  id: string; // unique across sources: `${type}:${entityId}`
  type: SuggestionType;
  label: string;
  matches?: [start: number, end: number][];
}

interface Source {
  type: 'local' | 'remote';
  search(query: string, opts: { signal: AbortSignal }): Promise<Suggestion[]> | Suggestion[];
}
```

Поток на каждый ввод:

1. **Локальные источники** (недавние, друзья) отвечают синхронно, без debounce: результаты видны на первом же символе.
2. **Серверный источник** проходит обычный конвейер: debounce, отмена, кэш, проверка актуальности.
3. **Слияние** по фиксированному порядку групп: друзья, затем серверные. Дедупликация по сущности: друг, найденный и сервером, показывается один раз, в группе друзей. Поэтому `id` строится от сущности, а не от источника.

Прыжки списка — главная UX-проблема. Если серверные результаты вставлять выше локальных или пересортировывать всё по релевантности, то строка, на которую пользователь уже нацелился (мышью или стрелками), уедет из-под него. Решения: серверные результаты только **добавляются ниже** локальных; на время ожидания под группой друзей держать место или тонкий индикатор; активная опция сохраняется по `id`, а не по индексу. Цена: лучший серверный результат может оказаться ниже среднего друга. Альтернатива — общее ранжирование на сервере (клиент отправляет id друзей или сервер знает их сам), тогда локальные результаты — лишь быстрый предварительный показ, который заменяется одним разом.

Доступность групп: заголовки групп — `role="group"` с `aria-label` внутри `listbox` (или опции с описанием типа), чтобы скринридер говорил «Друзья, Анна». Live region объявляет итог, когда пришли серверные результаты, а не на каждый промежуточный шаг.
:::

### 5. Inline-дополнение, как в адресной строке · сложно

Продакт просит: «Пусть в поле сразу дописывается первая подсказка, как в адресной строке браузера». Какие решения меняются в модели, интерфейсе и доступности? Когда вы бы от этого отказались?

::: details Решение и разбор
Модель: у поля теперь два текста. **Введённый** (`typed`) — то, что набрал пользователь, по нему идут запросы и кэш. **Отображаемый** — `typed` плюс выделенный остаток первой подсказки. Смешать их — значит запрашивать сервер по дописанному тексту, то есть по собственной подсказке.

Поведение:

- Дописывать только если подсказка **начинается** с введённого текста. Иначе это не дополнение, а замена.
- Backspace удаляет выделенный остаток, а не последний символ пользователя. Повторное дописывание до следующего печатного символа не делать, иначе стереть ничего нельзя.
- Ответ сервера, пришедший позже, не должен менять текст под курсором, если пользователь уже напечатал дальше: та же проверка актуальности.
- IME: во время композиции не дописывать вообще.

Доступность: `aria-autocomplete="both"`. APG описывает это значение: подсказки в списке плюс невведённая часть выбранной подсказки появляется в поле после курсора выделенной. Скринридер прочитает изменение значения поля, поэтому live region не должен дублировать его.

Когда отказаться: если первая подсказка часто не та (поиск по людям, где «Анна» — сотни людей), дописывание мешает больше, чем помогает. Пользователь вынужден стирать чужой текст. Ещё отказаться стоит в многоязычном поле с IME. Оно уместно, когда первая подсказка почти всегда верная: адреса, уже посещённые URL, команды.
:::
