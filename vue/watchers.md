# `watch` и `watchEffect`

> **Коротко.** Watcher — реактивный эффект, который выполняет побочное действие в ответ на изменение данных. `watch(source, cb)` следит за явно указанным источником (ref, геттер, `reactive`, массив) и вызывает колбэк с новым и старым значением. `watchEffect(fn)` сам собирает зависимости при выполнении, но только до первого `await`. Колбэк по умолчанию выполняется пакетно, перед рендером компонента (`flush: 'pre'`). Перед каждым перезапуском и при остановке Vue вызывает очистку (`onWatcherCleanup`): так отменяют запросы и устраняют гонки. Watcher, созданный синхронно в `setup()`, останавливается при размонтировании сам, созданный асинхронно — течёт.

**Связанные темы:** [Реактивность: `ref`, `reactive`, `computed`](./reactivity.md), [Мини-реактивность в стиле Vue](../live-coding/mini-reactivity.md), [Event loop](../javascript/event-loop.md), [async/await](../javascript/async-await.md), [Утечки памяти](../performance/memory-leaks.md), [Производительность Vue и Nuxt](../performance/vue-performance.md), [Компоненты и шаблоны](./components-and-templates.md)

## Теория

Все проверки в теме выполнены на Vue 3.5.45 в Node 26.13.1: поведение — запуском `vue`, DOM-сценарии — с happy-dom, SSR — через `@vue/server-renderer`, вывод компилятора — через `@vue/compiler-sfc`. Те же сценарии повторены на `3.6.0-rc.15`, расхождение одно, оно описано во врезке в конце теории.

### Из чего состоит watcher

С 3.5 базовый `watch` живёт в `@vue/reactivity`, а `runtime-core` добавляет к нему планировщик и обработку ошибок. Внутри — три части:

- **геттер**: источник, приведённый к функции. Для ref это `() => source.value`, для `reactive` — обход объекта, для массива — `source.map(...)`;
- **эффект** `ReactiveEffect(getter)`: выполняет геттер под трекингом и подписывается на всё, что тот прочитал;
- **задание** (job): при изменении зависимостей эффект не перезапускается сам, а отдаёт задание планировщику. Задание заново вычисляет геттер, сравнивает результат со старым значением через `Object.is` и, если оно изменилось, вызывает колбэк.

Колбэк выполняется **без трекинга** (`pauseTracking()` в исходнике): чтения внутри него новых зависимостей не создают. У `watchEffect` колбэка нет, поэтому зависимости собирает сама функция. Как устроены `track`, `trigger` и планировщик, показано с реализацией с нуля в [«Мини-реактивности»](../live-coding/mini-reactivity.md#планировщик-пакетирование-и-watch).

### Источники `watch`

| Источник | Что отслеживается | Когда вызывается колбэк |
| --- | --- | --- |
| `ref` | `.value` | значение изменилось по `Object.is`; у `shallowRef` — и после `triggerRef`, когда ссылка та же |
| геттер `() => state.x` | всё, что прочитал геттер | **результат** геттера изменился |
| `reactive`-объект | весь объект, глубоко | при любой мутации внутри |
| массив `[a, () => b.value]` | каждый элемент по правилам выше | изменился хотя бы один элемент |

Всё остальное — не источник. `watch(state.n, cb)` передаёт **число**: `state.n` прочитано один раз при вызове, следить не за чем. Vue предупреждает: `Invalid watch source: 1 A watch source can only be a getter/effect function, a ref, a reactive object, or an array of these types`. Геттером становится пустая функция: без `immediate` колбэк не вызовется никогда, с `immediate` — один раз, с `undefined` вместо значения.

Отсюда главная ошибка с props: `watch(props.id, cb)` — то же самое, `props.id` — уже значение. Правильно — геттер `watch(() => props.id, cb)`. С деструктурированными props в 3.5 ошибку ловит компилятор:

```js
const { count } = defineProps(['count'])
watch(count, () => {})
// [@vue/compiler-sfc] "count" is a destructured prop and should not be passed
// directly to watch(). Pass a getter () => count instead.
```

`watch(() => count, ...)` компилятор переписывает в `watch(() => __props.count, ...)`: деструктуризация props реактивна, потому что обращения превращаются в доступ к свойству ([подробнее](./components-and-templates.md)).

> [!WARNING]
> `watch(props.user, cb)` с объектом **работает наполовину**. Объект из props — реактивный прокси, и мутации `user.name` колбэк видит. Но после того как родитель передал **новый** объект, watcher продолжает следить за старым. Проверено: мутация — вызов, замена — тишина, мутация нового объекта — тишина. Геттер `() => props.user` реагирует на замену.

### Глубина

- **`reactive` как источник** — неявно глубокий: Vue обходит объект целиком (`traverse`) и подписывается на каждое свойство.
- **Геттер** — не глубокий. `watch(() => state.list, cb)` сработает только при `state.list = [...]`, а `push` не заметит. Нужен `{ deep: true }`.
- **`deep: number`** (3.5) ограничивает глубину обхода. Для `s = reactive({ a: { b: { c: 1 } } })` с `deep: 1` проверено: `s.a.b.c++` и `s.a.b = {}` не вызывают колбэк, `s.a = {}` вызывает. С `deep: 2` срабатывает и замена `s.a.b`.
- **`deep: false`** у `reactive`-источника оставляет только верхний уровень.

При мутации на месте колбэк получает `newValue === oldValue`: это один и тот же объект, «старой версии» Vue не хранит. Если нужен diff, снимок делают вручную: `watch(() => [...state.list], cb)` или `structuredClone(toRaw(...))`.

Глубокий обход стоит O(размер объекта) **на каждое срабатывание** и создаёт зависимость на каждое свойство. Для большой формы или списка дешевле следить за конкретными полями геттером или менять данные иммутабельно и следить за ссылкой ([модель стоимости](../performance/vue-performance.md#большие-данные-меньше-реактивности)).

### `immediate` и `once`

- `immediate: true` вызывает колбэк сразу при создании. `oldValue` в первом вызове — `undefined`, для массива источников — `[]`.
- `once: true` (3.4+) после первого вызова колбэка останавливает watcher. С `immediate` колбэк выполнится один раз — при создании.

Обе опции имеют смысл только у `watch`: если передать их `watchEffect`, Vue в dev предупредит, что `"immediate" option is only respected when using the watch(source, callback, options?) signature`.

### `watchEffect`: зависимости собираются при выполнении

`watchEffect(fn)` выполняет `fn` сразу и подписывается на всё, что она прочитала. При изменении любой зависимости `fn` выполняется заново, набор зависимостей пересобирается: ветка `if`, которая не выполнилась, не отслеживается.

Отслеживается только **синхронная** часть. Трекинг привязан к глобальному «текущему эффекту», а продолжение после `await` выполняется в другой микрозадаче, когда эффект уже снят. Проверено: изменение зависимости, прочитанной после `await`, эффект не перезапускает (задача 3). Всё, что должно отслеживаться, читают до первого `await`.

| | `watch` | `watchEffect` |
| --- | --- | --- |
| Зависимости | явный источник | всё, что прочитано синхронно |
| Первый запуск | лениво (или `immediate`) | сразу |
| `oldValue` | есть | нет |
| Колбэк меняет свой источник | перезапустится (до лимита рекурсии) | изменение во время своего выполнения игнорируется |

`watch` выбирают, когда важно, **на что** реагировать: нужен `oldValue`, источник один, а в колбэке читается много лишнего. `watchEffect` удобен, когда эффект читает несколько значений и их список легко устареет, если перечислять его вручную.

### `flush` и планировщик

Изменение состояния не запускает колбэк сразу: задание встаёт в очередь планировщика, которую Vue сбрасывает одной микрозадачей. Как устроены очередь и `nextTick`, разобрано в [«Event loop»](../javascript/event-loop.md#vue-пакетные-обновления-и-nexttick). Здесь — что выбирает `flush`:

- **`'pre'`** (по умолчанию). Задание помечено флагом `PRE` и получает `id` своего компонента, поэтому выполняется **перед** рендером этого компонента. DOM ещё старый, зато изменения состояния в колбэке попадают в тот же рендер. Проверено: watcher, который по `q` пишет `upper`, даёт один перерендер на изменение. Три присваивания подряд — один вызов колбэка с последним значением.
- **`'post'`** (`watchPostEffect`) — через `queuePostRenderEffect`, после обновления DOM. Нужен, чтобы прочитать размеры, проскроллить, передать узел сторонней библиотеке. Изменение состояния в таком колбэке стоит лишнего рендера: тот же пример с `flush: 'post'` дал два перерендера вместо одного.
- **`'sync'`** (`watchSyncEffect`) — синхронно, в момент `trigger`, без очереди. Три присваивания — три вызова. Исключение — операции, которые Vue сам пакетирует: `list.push(1, 2, 3)` у реактивного массива вызывает sync-колбэк один раз. Документация предупреждает о цене: никакого пакетирования, а колбэк видит промежуточные состояния. Порядок всех трёх в одном компоненте разобран в задаче 4.

> [!NOTE]
> Колбэк `watch` может менять собственный источник: заданию с колбэком разрешена рекурсия (`ALLOW_RECURSE`), и он будет перезапускаться, пока значение меняется. Защита от бесконечного цикла в dev — `RECURSION_LIMIT = 100`: watcher, который на каждый вызов меняет источник, обрывается ошибкой `Maximum recursive updates exceeded` (проверено). `watchEffect`, который пишет в то, что сам читает, рекурсии не даёт: запись во время собственного выполнения игнорируется.

### Очистка и гонки

Асинхронный колбэк может завершиться, когда источник уже изменился: ответ на старый запрос перезапишет новый. Механика гонки и общие решения — в [«async/await»](../javascript/async-await.md#vue-очистка-в-watch). Во Vue для этого есть очистка: функция, которую Vue вызовет **перед следующим запуском** колбэка и **при остановке** watcher'а, в том числе при размонтировании компонента.

- **`onWatcherCleanup(fn)`** (3.5) импортируется из `vue` и вызывается внутри колбэка `watch` или функции `watchEffect`. Его удобно вызывать из вспомогательных функций и composables.
- **`onCleanup`** — третий аргумент колбэка `watch` или первый аргумент функции `watchEffect`. Работает и до 3.5.

Обе регистрируют очистку в одном и том же списке, порядок вызова — порядок регистрации. Ограничение у них разное. `onWatcherCleanup` находит watcher через глобальный «текущий watcher», который выставлен только во время синхронной части колбэка. После `await` вызов даёт предупреждение `onWatcherCleanup() was called when there was no active watcher to associate with`, и очистка не регистрируется. `onCleanup` привязан к своему watcher'у замыканием и работает и после `await`, но регистрировать очистку позже, чем начался запрос, всё равно бессмысленно.

### `WatchHandle`: `stop`, `pause`, `resume`

`watch` и `watchEffect` возвращают `WatchHandle` (3.5). Это функция — вызов останавливает watcher — со свойствами `stop`, `pause` и `resume`.

- `stop()` снимает подписки и вызывает очистку. Повторно запустить watcher нельзя.
- `pause()` сохраняет подписки, но не выполняет задания. Изменения во время паузы запоминаются.
- `resume()` возобновляет работу. Если за паузу источник изменился, задание ставится в очередь, и колбэк вызывается **один раз** со значением на момент паузы как `oldValue`: после `pause(); a.value = 1; a.value = 2; resume()` колбэк получил `0 → 2` в следующем сбросе. Если изменений не было, ничего не происходит. Пауза полезна, когда watcher временно не нужен, а пересоздавать его дорого или неудобно: вкладка скрыта, идёт массовый импорт, который синхронизируется один раз в конце.

### Время жизни

У каждого компонента есть effect scope. Watcher, созданный **синхронно** в `setup()`, попадает в него и останавливается при размонтировании. Watcher, созданный асинхронно (в `setTimeout`, `then`, вложенной `async`-функции), к компоненту не привязан и живёт, пока его не остановят вручную. Проверено: после размонтирования синхронный watcher молчит, а созданный в `setTimeout` срабатывает.

`await` верхнего уровня в `<script setup>` безопасен: компилятор превращает `await fetch('x')` в `([__temp, __restore] = _withAsyncContext(() => fetch('x'))), await __temp, __restore()`, и `__restore()` возвращает текущий экземпляр до следующей строки. В обычном `async setup()` без компилятора такой обёртки нет. Подробности и проверка с `<Suspense>` — в [«Утечках памяти»](../performance/memory-leaks.md#vue-что-останавливается-само-а-что-нет). Вне компонента watchers собирают в `effectScope()` и останавливают его `stop()`.

> [!WARNING]
> **SSR.** На сервере компонент не размонтируется, поэтому Vue не создаёт там ленивых watchers. `watch` без `immediate` возвращает пустой `WatchHandle` и не вызывается никогда. `watch` с `immediate` и `watchEffect` выполняются один раз и сразу останавливаются. Проверено `renderToString`: из трёх watchers отработали только `immediate` и `watchEffect`, каждый по разу. Исключение — `flush: 'sync'`: такие watchers живут до конца рендера, после чего `renderToString` останавливает их сам. Загрузку данных для SSR поэтому делают не в watcher, а через `await` в `setup` или `useAsyncData`/`useFetch` в Nuxt.

### `watch` против `computed`

Частая ошибка — «вычислять» значение через watcher:

```js
const fullName = ref('')
watch([first, last], ([f, l]) => { fullName.value = `${f} ${l}` }, { immediate: true })
```

Это два источника истины и окно рассинхрона. Проверено: сразу после `first.value = 'C'` `fullName` ещё `'A B'`, а значение обновится только в следующем сбросе. Кроме того, это лишний `ref` и лишний перерендер, если watcher `post`. `computed` синхронен при чтении, ленив и кэширует ([подробнее](./reactivity.md#computed-ленивость-и-кэш)). Правило: если результат — **значение**, которое можно вычислить из состояния, это `computed`. Если результат — **действие** (запрос, `localStorage`, DOM, аналитика, навигация), это watcher.

> [!NOTE]
> В Options API watchers объявляют опцией: `watch: { 'user.name'(v, old) {}, list: { handler, deep: true, immediate: true } }`. Строка с точкой — путь от `this`. Императивный вариант — `this.$watch(source, cb, options)`. Он возвращает `WatchHandle` и тоже останавливается вместе с компонентом. Механика та же: под капотом `instanceWatch` вызывает тот же `doWatch`.

> [!NOTE]
> Во Vue 3.6 (RC, `3.6.0-rc.15`, сверено 2026-11-16) публичный API watchers не меняется: все проверки темы дали тот же вывод, кроме одного крайнего случая. Ядро реактивности 3.6 проверяет «грязность» по значениям (push-pull по образцу alien-signals), а 3.5 — по счётчикам версий. Поэтому если зависимость изменили и вернули к прежнему значению до сброса очереди, геттер `() => [a.value, b.value]` в 3.5 вычисляется заново и вызывает колбэк (новый массив не равен старому), а в 3.6 не вычисляется вовсе. Стабильного 3.6 пока нет.

## Примеры

### Поиск с отменой устаревших запросов

```ts
import { ref, watch, onWatcherCleanup } from 'vue'

const query = ref('')
const results = ref<Item[]>([])
const error = ref<unknown>(null)

watch(query, async (q) => {
  if (!q) { results.value = []; return }
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort()) // before the first await
  try {
    results.value = await api.search(q, { signal: controller.signal })
    error.value = null
  } catch (e) {
    if (!controller.signal.aborted) error.value = e
  }
}, { immediate: true })
```

Очистка срабатывает и при следующем изменении `query`, и при размонтировании: запрос, который ушёл со страницы, тоже отменяется.

### Скролл к последнему сообщению после рендера

```vue
<script setup lang="ts">
import { useTemplateRef, watch } from 'vue'

const props = defineProps<{ messages: Message[] }>()
const list = useTemplateRef<HTMLElement>('list')

// 'post': the new message is already in the DOM when the callback runs
watch(() => props.messages.length, () => {
  list.value?.lastElementChild?.scrollIntoView({ block: 'end' })
}, { flush: 'post' })
</script>

<template>
  <ul ref="list"><li v-for="m in messages" :key="m.id">{{ m.text }}</li></ul>
</template>
```

С `flush: 'pre'` колбэк увидел бы список без нового элемента и проскроллил бы к предпоследнему.

## Вопросы с интервью

::: details Чем watch отличается от watchEffect
`watch(source, cb)` следит за явно указанным источником: ref, геттером, `reactive`-объектом или массивом из них. Он ленив по умолчанию и передаёт в колбэк новое и старое значение, а сам колбэк выполняется без трекинга. `watchEffect(fn)` выполняется сразу, подписывается на всё, что `fn` прочитала синхронно, и пересобирает зависимости при каждом запуске. Старого значения у него нет, а всё, что прочитано после первого `await`, не отслеживается. `watch` выбирают, когда нужен `oldValue` или важно точно контролировать, на что реагировать. `watchEffect` — когда эффект читает несколько значений и перечислять их вручную неудобно. Оба возвращают `WatchHandle` со `stop`, `pause` и `resume` и поддерживают очистку.
:::

::: details Почему watch(props.id) не срабатывает и как правильно
`props.id` вычисляется в момент вызова `watch`, поэтому передаётся просто значение, например число. Источником могут быть только ref, геттер, `reactive`-объект или массив из них. Для числа Vue выводит `Invalid watch source`, и колбэк не вызывается никогда (с `immediate` — один раз, с `undefined`). Правильно — геттер `() => props.id`: он читает свойство реактивного объекта props при каждом вычислении. С деструктурированными props в 3.5 `watch(id)` — ошибка компиляции: компилятор подсказывает передать `() => id` и сам переписывает его в `() => __props.id`. Отдельный подвох — `watch(props.user)` с объектом: мутации видны, а замену объекта родителем watcher пропустит, потому что держит старый прокси.
:::

::: details Когда watcher глубокий и чем это опасно
`reactive`-объект как источник — неявно глубокий: Vue обходит его целиком и подписывается на каждое свойство. Геттер и ref по умолчанию не глубокие: `watch(() => state.list, cb)` не заметит `push`, нужен `{ deep: true }`. С 3.5 `deep` может быть числом — глубиной обхода. Цена: обход O(размер объекта) на каждое срабатывание и зависимость на каждое свойство. Кроме того, при мутации на месте `newValue === oldValue`: старой копии нет. Для больших структур лучше следить за конкретными полями геттером или обновлять данные иммутабельно и следить за ссылкой.
:::

::: details Что такое flush и когда нужны post и sync
`flush` задаёт, когда выполняется колбэк относительно рендера. `'pre'` (по умолчанию) — в том же сбросе очереди, перед рендером своего компонента. Несколько изменений дают один вызов, DOM ещё старый, а изменения состояния в колбэке попадают в тот же рендер. `'post'` — после обновления DOM: чтобы измерить, проскроллить, передать узел библиотеке. Изменение состояния в нём стоит лишнего рендера. `'sync'` — сразу при каждом `trigger`, без пакетирования: колбэк видит промежуточные состояния и вызывается на каждое присваивание. Он нужен редко, например для синхронной интеграции с внешним стором или отладки. Все три живут в одном планировщике, который сбрасывается микрозадачей, — поэтому `await nextTick()` дожидается и pre-, и post-колбэков.
:::

::: details Как избежать гонки запросов в watcher
Гонка: пользователь ввёл «ab», ушли два запроса, ответ на «a» пришёл последним и перезаписал результат. Решение — очистка. `onWatcherCleanup(fn)` (3.5) или аргумент `onCleanup` регистрирует функцию, которую Vue вызовет перед следующим запуском колбэка и при остановке watcher'а, в том числе при размонтировании. В ней вызывают `abort()` у `AbortController`, а в колбэке проверяют `signal.aborted` или ловят `AbortError`. `onWatcherCleanup` нужно вызвать до первого `await`: он ищет текущий watcher через глобальную переменную, которая после `await` уже сброшена, и Vue выдаёт предупреждение. Debounce сокращает число запросов, но гонку не устраняет.
:::

::: details Когда watcher не останавливается сам
Сам останавливается watcher, созданный синхронно в `setup()`: он попадает в effect scope компонента. Это верно и после `await` верхнего уровня в `<script setup>`: компилятор оборачивает его в `withAsyncContext`, который восстанавливает экземпляр. Не останавливаются watchers из `setTimeout`, `then`, вложенной `async`-функции и обычного `async setup()` без компилятора. Они держат замыкание с данными компонента и продолжают срабатывать. Такие останавливают вызовом `WatchHandle` или собирают в `effectScope()`. На сервере ленивые watchers не создаются вовсе, а `watchEffect` и `immediate` выполняются один раз: компонент там не размонтируется, и иначе каждый запрос оставлял бы живые эффекты.
:::

::: details Когда использовать computed, а когда watch
`computed` — для значения, которое выводится из состояния: он синхронен при чтении, ленив, кэширует и не создаёт второго источника истины. `watch` — для побочного действия: запроса, записи в `localStorage`, работы с DOM, аналитики, навигации. Антипаттерн — `watch` с присваиванием в `ref`: значение отстаёт до следующего сброса очереди, появляется лишний `ref` и возможен лишний рендер. Признак — колбэк watcher'а, который только присваивает. Обратный антипаттерн — побочные эффекты в геттере `computed`: неизвестно, когда и сколько раз он выполнится.
:::

::: details Зачем нужны pause и resume, если есть stop
`stop()` необратим: подписки сняты, очистка вызвана, вернуть watcher можно только созданием нового. `pause()` (3.5) сохраняет подписки и только перестаёт выполнять задания. `resume()` возобновляет работу и, если за паузу источник изменился, один раз вызывает колбэк с итоговым значением и значением до паузы как `oldValue`. Это удобно для временно ненужных эффектов: скрытая вкладка, неактивный экран под `KeepAlive`, массовая операция, после которой нужна одна синхронизация, а не сотня. Такие же методы есть у `effectScope`.
:::

## Задачи

### 1. Что выведет · легко

```js
import { reactive, watch, nextTick } from 'vue'

const state = reactive({ user: { name: 'Ann' }, list: [1] })
const log = []
watch(state, () => log.push('state'))
watch(() => state.user, () => log.push('user'))
watch(() => state.user, () => log.push('user deep'), { deep: true })
watch(() => state.list, () => log.push('list'))
watch(() => state.list.length, () => log.push('length'))

state.user.name = 'Bob'
state.list.push(2)
await nextTick()
console.log(log.join(', '))

state.list = [3]
await nextTick()
console.log(log.join(', '))
```

::: details Решение и разбор
```
state, user deep, length
state, user deep, length, state, list, length
```

- `state` — `reactive`-источник, он неявно глубокий. Две мутации в одном синхронном куске — **один** вызов: задание дедуплицируется в очереди.
- Геттер `() => state.user` не глубокий: ссылка на `user` не изменилась, колбэка нет. С `deep: true` Vue обходит результат и видит `name`.
- `() => state.list` возвращает тот же массив после `push`, поэтому вызова нет. А `length` — примитив, он изменился с 1 на 2.
- Замена `state.list = [3]` меняет ссылку, поэтому срабатывают `list` и `length` (2 → 1), а также `state`: он подписан на каждое свойство. Порядок вызовов — порядок создания watchers.
:::

### 2. Найдите баг · легко

При переходе с `/users/1` на `/users/2` компонент переиспользуется, но профиль не перезагружается.

```vue
<script setup>
import { ref, watch } from 'vue'

const props = defineProps({ userId: Number })
const user = ref(null)

watch(props.userId, async (id) => {
  user.value = await api.getUser(id)
}, { immediate: true })
</script>
```

::: details Решение и разбор
```js
watch(() => props.userId, async (id) => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())
  user.value = await api.getUser(id, { signal: controller.signal })
}, { immediate: true })
```

`props.userId` прочитан один раз, и в `watch` ушло число `1`. Число — не источник: Vue выводит `Invalid watch source` и подставляет пустой геттер. Из-за `immediate` колбэк вызывается один раз, но с `id === undefined`, то есть уходит запрос `getUser(undefined)`. Потом колбэк не вызывается никогда. Проверено: после смены `userId` список вызовов — `[undefined]`. Геттер читает `props.userId` при каждом вычислении и подписывается на свойство реактивного объекта props.

Попутно исправлена гонка: при быстром переключении 1 → 2 → 3 ответ на `2` мог прийти последним. С деструктуризацией `const { userId } = defineProps(...)` исходный код вообще не скомпилировался бы: компилятор 3.5 требует `() => userId`.
:::

### 3. Что выведет · средне

```js
import { ref, watchEffect } from 'vue'

const tick = () => new Promise((r) => setTimeout(r))
const a = ref(1)
const b = ref(1)
let runs = 0

watchEffect(async () => {
  runs++
  a.value
  await tick()
  b.value
})

await tick(); await tick()
b.value++
await tick()
console.log(runs)
a.value++
await tick()
console.log(runs)
```

::: details Решение и разбор
```
1
2
```

`watchEffect` отслеживает только то, что прочитано синхронно, до первого `await`. Во время чтения `b.value` текущего эффекта уже нет: продолжение выполняется в другой задаче, а эффект снял себя с «текущего» сразу после того, как функция вернула промис. Поэтому `b` — не зависимость, и его изменение ничего не запускает. Изменение `a` перезапускает эффект.

Исправление — прочитать всё нужное до `await`: `const [x, y] = [a.value, b.value]`. Или перейти на `watch([a, b], ...)` с явными источниками.
:::

### 4. Что выведет · средне

```js
import { ref, watch, h, createApp, nextTick } from 'vue'

const el = document.createElement('div')
const n = ref(0)

createApp({
  setup() {
    watch(n, (v) => console.log('pre', v, el.textContent))
    watch(n, (v) => console.log('post', v, el.textContent), { flush: 'post' })
    watch(n, (v) => console.log('sync', v, el.textContent), { flush: 'sync' })
    return () => h('span', n.value)
  }
}).mount(el)

n.value = 1
n.value = 2
console.log('after set', el.textContent)
await nextTick()
```

::: details Решение и разбор
```
sync 1 0
sync 2 0
after set 0
pre 2 0
post 2 2
```

- `sync` вызывается в момент каждой записи, без очереди: два присваивания — два вызова, DOM ещё не обновлён.
- `pre` и `post` ставят задания в очередь планировщика. Сброс происходит в микрозадаче, поэтому `after set` печатается раньше них.
- В сбросе `pre`-задание с `id` компонента выполняется перед его рендером: значение уже `2`, DOM ещё `0`. Вызов один — изменения схлопнулись.
- `post`-колбэк выполняется после обновления DOM и видит `2`.
:::

### 5. Найдите баг · средне

Поиск иногда показывает результаты для предыдущего запроса, а в консоли — предупреждение Vue.

```js
watch(query, async (q) => {
  const controller = new AbortController()
  const data = await api.search(q, { signal: controller.signal })
  onWatcherCleanup(() => controller.abort())
  results.value = data
})
```

::: details Решение и разбор
```js
watch(query, async (q) => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort()) // synchronously, before await
  try {
    results.value = await api.search(q, { signal: controller.signal })
  } catch (e) {
    if (!controller.signal.aborted) throw e
  }
})
```

`onWatcherCleanup` находит watcher через глобальный «текущий watcher», а он выставлен только на время синхронной части колбэка. После `await` его нет: Vue выводит `onWatcherCleanup() was called when there was no active watcher to associate with`, и очистка не регистрируется. Даже если бы регистрация сработала, отменять уже завершённый запрос бессмысленно. Значит, гонка остаётся: медленный ответ на старый `q` перезаписывает новый. Проверено: без очистки при ответах за 30 и 5 мс остаётся результат первого запроса, с очисткой до `await` — второго.

Альтернатива для API без отмены — проверка актуальности: `let stale = false; onWatcherCleanup(() => { stale = true })` и `if (!stale) results.value = data`. Аргумент `onCleanup` работал бы и после `await`, но смысл тот же: регистрировать очистку нужно до начала запроса. Промис, отклонённый из-за `abort()`, — не настоящая ошибка, и показывать её пользователю не нужно: отсюда проверка `signal.aborted`.
:::

### 6. Что выведет · сложно

```js
import { ref, watch, nextTick } from 'vue'

const a = ref(1)
const log = []

watch(() => [a.value % 2], () => log.push('getter'))
watch([() => a.value % 2], () => log.push('array'))
const h = watch(a, (v, old) => log.push(`a ${old}->${v}`))

a.value = 3
await nextTick()
console.log(log.join(', '))

h.pause()
a.value = 4
a.value = 5
await nextTick()
console.log(log.join(', '))

h.resume()
console.log(log.length)
await nextTick()
console.log(log.join(', '))
```

::: details Решение и разбор
```
getter, a 1->3
getter, a 1->3, getter
3
getter, a 1->3, getter, a 3->5
```

- Геттер `() => [a.value % 2]` при каждом вычислении возвращает **новый** массив, а `Object.is` сравнивает ссылки. Поэтому колбэк вызывается на каждое изменение `a`, даже когда содержимое то же (`[1]` → `[1]`). Это типичная ловушка с геттером, который собирает объект или массив.
- Массив источников сравнивается **поэлементно**. Остаток от деления оставался `1` и при 1 → 3, и при 3 → 4 → 5, поэтому `array` не вызвался ни разу.
- Записи `4` и `5` идут в одном синхронном куске. Задания встают в очередь один раз и выполняются в сбросе, когда `a` уже `5`. Поэтому `getter` во втором блоке вызван один раз: значение `4` watcher не увидел вовсе.
- Пока `h` на паузе, его задание не выполняется, но изменение запоминается. `resume()` ставит задание в очередь, а не вызывает колбэк синхронно, поэтому сразу после него длина лога — `3`. В следующем сбросе колбэк вызывается один раз: `oldValue` — значение до паузы (`3`), `newValue` — текущее (`5`).

Исправление ловушки с геттером: вернуть примитив (`() => a.value % 2`), передать массив источников или, если нужен составной ключ, сравнивать по содержимому вручную. `deep: true` здесь не помогает: с ним колбэк вызывается на каждое срабатывание без сравнения.
:::
