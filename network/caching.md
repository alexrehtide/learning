# HTTP-кэширование и CDN

> **Коротко.** Кэш вправе отдать сохранённый ответ без сервера, пока тот **свежий**. Срок свежести задаёт `Cache-Control: max-age` (для общих кэшей — `s-maxage`), а без него браузер вычисляет срок эвристикой. Устаревший ответ не выбрасывается, а **валидируется**: условный запрос с `If-None-Match` и ответ `304` без тела. `no-cache` значит «храни, но проверяй каждый раз», а `no-store` — «не храни». Рабочая стратегия: хэш в имени файла плюс год и `immutable` для ассетов, валидация на каждый запрос для HTML. CDN — это общий кэш у пользователя. Его надо научить ключу кэша и уметь сбрасывать.

**Связанные темы:** [HTTP: методы, статусы, заголовки, версии](./http.md), [От ввода URL до отображения страницы](../browser/from-url-to-pixels.md), [Web Workers, Service Workers и PWA](../browser/workers.md)

## Теория

### Кто кэширует: private и shared

RFC 9111 различает два вида кэшей:

- **Private** (частный) — кэш одного пользователя, в первую очередь HTTP-кэш браузера. В нём можно хранить персональные ответы.
- **Shared** (общий) — кэш, который обслуживает многих: CDN, обратный прокси (nginx, Varnish), корпоративный прокси. Ответ, сохранённый здесь, получат **все** пользователи.

Отсюда главная опасность: персональный ответ в общем кэше — это утечка данных. Поэтому RFC запрещает общему кэшу хранить ответ на запрос с `Authorization`, если сервер явно не разрешил (`public`, `s-maxage` или `must-revalidate`). Cookies такой защиты **не дают**: ответ на запрос с сессионной cookie общий кэш сохранит как обычный, если заголовки ответа разрешают. Персональные ответы помечают `private` или `no-store`.

На практике кэшируются ответы на `GET` и `HEAD`: ответ на `POST` RFC разрешает хранить только с явным сроком свежести и `Content-Location`, и браузеры этого не делают. Ключ кэша — это метод плюс URL (с query-строкой), а также заголовки из `Vary`.

### Свежесть и возраст

Ответ **свежий** (fresh), пока его возраст меньше срока свежести (freshness lifetime). Свежий ответ кэш отдаёт сам, без сервера. Срок свежести берётся по приоритету:

1. `s-maxage` — только для общих кэшей;
2. `max-age`;
3. `Expires` минус `Date` (абсолютная дата, зависит от часов; при наличии `max-age` игнорируется);
4. **эвристика** — если явного срока нет.

**Возраст** (age) учитывает, сколько ответ уже пролежал в кэшах по пути. CDN сообщает его заголовком `Age`, и браузер прибавляет его к своему времени хранения. Ответ с `max-age=600, Age: 590` в браузере свеж ещё только 10 секунд.

**Эвристика.** Без `max-age` и `Expires` кэш вправе сам назначить срок свежести ответам с эвристически кэшируемыми статусами: `200`, `203`, `204`, `206`, `300`, `301`, `308`, `404`, `405`, `410`, `414`, `501`. RFC предлагает типичное значение — **10% от времени с `Last-Modified`**. Файл, изменённый 10 дней назад, браузер сочтёт свежим ещё сутки и не пойдёт на сервер.

> [!WARNING]
> Эвристика — главный источник «после деплоя у пользователя старая версия». HTML без `Cache-Control`, но с `Last-Modified` (его ставит почти любой статический сервер) браузер закэширует сам. Проверено в Chromium 157: ответ с `Last-Modified` десятидневной давности и без `Cache-Control` повторный `fetch` берёт из кэша без запроса. То же происходит с ответом, где есть **только** `s-maxage`: к браузеру эта директива не относится, явного срока для него нет — и включается эвристика.

### Директивы Cache-Control

| Директива | В ответе означает |
| --- | --- |
| `max-age=N` | свежий N секунд с момента генерации |
| `s-maxage=N` | то же для общих кэшей, перекрывает `max-age`; после истечения общий кэш обязан валидировать |
| `no-cache` | хранить можно, но **перед каждым** использованием валидировать |
| `no-store` | не сохранять нигде |
| `private` | только частный кэш (браузер), не CDN |
| `public` | можно хранить и в общем кэше, даже если обычно нельзя (ответ на запрос с `Authorization`) |
| `must-revalidate` | устаревший ответ нельзя отдавать без успешной валидации, даже при недоступном сервере |
| `immutable` (RFC 8246) | пока свежий, не изменится: не валидировать даже при перезагрузке |
| `stale-while-revalidate=N` (RFC 5861) | N секунд после устаревания можно отдавать старое, обновляя в фоне |
| `stale-if-error=N` (RFC 5861) | N секунд после устаревания можно отдавать старое, если сервер ответил 5xx или недоступен |

Частая путаница:

- **`no-cache` ≠ «не кэшировать».** Ответ хранится и переиспользуется, но только после `304` от сервера. Экономится тело, а не запрос. `max-age=0, must-revalidate` даёт почти то же.
- **`no-store` — единственная директива «не хранить».** Она для по-настоящему чувствительных данных: банковская выписка, персональный документ. Цена — нет ни кэша, ни дешёвой валидации, а в части браузеров страница с `no-store` не попадает в bfcache.
- **`private` не секретность.** Это запрет общему кэшу, браузер ответ сохранит. От чужих глаз на общем компьютере защищает только `no-store`.
- `Pragma: no-cache` — пережиток HTTP/1.0, в RFC 9111 устарел. `Expires` работает, но `max-age` надёжнее: не зависит от часов клиента.

### Валидация: ETag, Last-Modified и 304

Устаревший ответ (stale) не удаляется: кэш задаёт серверу **условный запрос**, «изменилось ли с этой версии?».

- **`ETag`** — идентификатор версии представления: хэш содержимого или номер ревизии. Кэш отправляет `If-None-Match: "<etag>"`.
- **`Last-Modified`** — дата изменения. Кэш отправляет `If-Modified-Since`. Точность — секунда, и дата не всегда совпадает с изменением содержимого (пересборка без изменений меняет дату).

Если версия совпала, сервер отвечает **`304 Not Modified`** без тела, но с заголовками, которые были бы в `200`: `Cache-Control`, `ETag`, `Expires`, `Vary`. Кэш обновляет по ним свою запись и отдаёт сохранённое тело. При наличии `If-None-Match` сервер `If-Modified-Since` игнорирует: `ETag` точнее.

**Сильный и слабый ETag.** `"abc"` — сильный: байт в байт то же представление. `W/"abc"` — слабый: семантически эквивалентное (например, тот же JSON с другим форматированием или другим сжатием). Для `If-None-Match` используется **слабое сравнение** (`W/"abc"` совпадает с `"abc"`), для `Range` и `If-Match` нужен сильный.

> [!WARNING]
> Классическая ловушка — ETag, зависящий от сервера. Apache и nginx исторически строили ETag из inode, размера и времени изменения файла. За балансировщиком у каждого сервера свой ETag, и валидация почти никогда не даёт 304. Если ETag не хэш содержимого, проверьте, что он одинаков на всех узлах.

Для JavaScript валидация прозрачна: если кэш получил `304`, `fetch` вернёт сохранённый ответ со статусом `200` (проверено в Chromium 157). Увидеть `304` в коде можно, только если сам отправить условный запрос с `cache: 'no-store'`.

### Устаревший ответ и stale-while-revalidate

`Cache-Control: max-age=60, stale-while-revalidate=600` значит: минуту ответ свежий; следующие 10 минут кэш отдаёт его **сразу** и параллельно идёт за новой версией; после этого — обычная валидация. Пользователь не ждёт сервер, а данные отстают не больше чем на один запрос. Проверено в Chromium 157: после истечения `max-age` `fetch` мгновенно вернул старое тело, сервер получил фоновый запрос, и следующий `fetch` вернул новое.

`stale-if-error` — страховка от падения origin: CDN продолжит отдавать последнюю удачную версию вместо 502. Обе директивы — разрешения, не обязанности: кэш может их игнорировать. `must-revalidate` запрещает отдавать устаревшее совсем.

### Vary и ключ кэша

`Vary` перечисляет заголовки запроса, от которых зависит ответ: `Vary: Accept-Encoding, Accept-Language`. Кэш отдаёт сохранённый ответ, только если эти заголовки в новом запросе совпадают с сохранёнными. `Vary: *` не совпадает никогда.

- **Слишком узкий `Vary`** — ошибка корректности: CDN отдаст английскую страницу русскому пользователю или WebP браузеру без его поддержки.
- **Слишком широкий `Vary`** — кэш бесполезен. `Vary: User-Agent` даёт тысячи вариантов, `Vary: Cookie` — по варианту на пользователя.

> [!WARNING]
> HTTP-кэш Chromium хранит **один** вариант на URL. Проверено в Chromium 157: запросы с `Accept-Language: ru`, `en`, `ru` к ресурсу с `Vary: Accept-Language` дали три сетевых запроса — вариант `en` вытеснил `ru`. Если ответ часто меняется по заголовку, надёжнее разные URL (`/ru/…`, `/en/…`).

### Стратегия для фронтенда: хэш в имени и валидация HTML

Цель противоречива: ассеты должны кэшироваться навсегда, а новая версия сайта — появляться сразу после деплоя. Решение — разделить ресурсы:

- **Ассеты с хэшем содержимого в имени** (`app.3f9a1c.js`, `/_nuxt/BXk2f.js`): `Cache-Control: public, max-age=31536000, immutable`. Новое содержимое — новое имя, а значит, новый URL. Старый файл не нужно инвалидировать: на него просто никто больше не ссылается.
- **HTML и всё, что ссылается на ассеты по имени** (`index.html`, `sw.js`, `manifest.webmanifest`): `Cache-Control: no-cache` с `ETag`. Каждый заход — дешёвая валидация, после деплоя — сразу новый HTML с новыми именами ассетов.
- **Файлы без хэша** (`/favicon.ico`, `/logo.svg`, `/robots.txt`): короткий `max-age` (часы) или `no-cache`.
- **API**: зависит от данных. Персональные — `private, no-cache` или `no-store`. Общие справочники — `public, max-age=60, stale-while-revalidate=600`.

Важная деталь при деплое: **не удаляйте старые чанки сразу**. Пользователь с открытой вкладкой держит старый HTML, и ленивая загрузка `import()` запросит чанк, которого нет. Получится `404` и ошибка загрузки модуля. Старые ассеты оставляют на несколько дней или версий.

### Кэши браузера: memory, disk, bfcache

- **Memory cache** — в Chromium кэш процесса рендеринга. Повторное использование ресурса в той же странице (то же изображение дважды, повторный `<script>` с тем же URL) обходится без HTTP-кэша. Живёт, пока жив документ.
- **HTTP-кэш (disk cache)** — тот, о котором вся тема: подчиняется `Cache-Control`, переживает перезапуск браузера.
- **bfcache** — снимок **всей страницы** с JS-кучей при навигации «Назад/Вперёд». Это не HTTP-кэш: страница восстанавливается без запросов и без выполнения скриптов (событие `pageshow` с `persisted: true`). Мешают ему `unload`-обработчики, открытые соединения и исторически `Cache-Control: no-store` на документе.
- **Service Worker и Cache API** — программный слой поверх, см. [Web Workers, Service Workers и PWA](../browser/workers.md#cache-api-против-http-кэша).

> [!NOTE]
> Chrome с версии 116 постепенно разрешает bfcache для страниц с `Cache-Control: no-store`, но с ограничениями: страница вытесняется при изменении cookies, срок жизни в bfcache — 3 минуты вместо 10. Другие браузеры такие страницы в bfcache не кладут (сверено 2026-11-12). Если данные не секретные, а нужна просто актуальность, используйте `no-cache`: оно на bfcache не влияет.

**Разделение кэша (cache partitioning).** С Chrome 86 и Firefox 85 (в Safari раньше) ключ HTTP-кэша включает сайт верхнего уровня. `jquery.min.js` с общего CDN, загруженный на `a.com`, на `b.com` скачается заново. Это закрывает атаки, которые по скорости загрузки определяют, на каких сайтах был пользователь. Аргумент «возьмём библиотеку с публичного CDN — она уже в кэше» больше не работает.

**Перезагрузка.** Обычный reload в Chromium валидирует **только документ**: подресурсы со свежим `max-age` берутся из кэша без запроса (проверено в Chromium 157). Поэтому `immutable` в Chromium не реализован — он почти ничего бы не дал. Firefox и Safari поддерживают `immutable` (MDN BCD 8.1.8). Жёсткая перезагрузка (Ctrl+Shift+R) идёт мимо кэша для всего.

У `fetch` есть опция `cache` — режим работы с HTTP-кэшем для одного запроса: `default`, `no-store` (мимо кэша и без записи), `reload` (мимо кэша, но с записью), `no-cache` (всегда валидировать), `force-cache` (взять даже устаревшее), `only-if-cached`.

### CDN: edge, ключ кэша, инвалидация

CDN — сеть общих кэшей (**edge**, точек присутствия) рядом с пользователями. Запрос приходит на ближайший edge. При промахе edge идёт в **origin**, часто через промежуточный слой (**origin shield**), чтобы промахи всех edge не били в origin одновременно. Что важно знать фронтенду:

- **Ключ кэша.** По умолчанию — хост, путь и query. `?utm_source=…` и `?fbclid=…` дробят кэш на тысячи копий одной страницы, поэтому лишние параметры убирают из ключа, а порядок параметров нормализуют. `Vary` и cookies в ключе — осознанное решение, не умолчание.
- **Свой срок для CDN.** `s-maxage` задаёт срок общим кэшам отдельно от браузера: `Cache-Control: max-age=0, s-maxage=3600` — CDN держит час, браузер валидирует каждый раз. RFC 9213 добавил `CDN-Cache-Control` — те же директивы только для CDN. Многие CDN ещё понимают свои заголовки (`Surrogate-Control`).
- **Request collapsing.** На популярный, но промахнувшийся URL edge отправляет в origin **один** запрос, а остальных ждущих обслуживает его ответом. Иначе истечение кэша главной страницы — это тысяча одновременных рендеров (cache stampede). `stale-while-revalidate` помогает с той же проблемой.
- **Инвалидация (purge).** Сброс по URL, по префиксу или по **тегам** (`Surrogate-Key` у Fastly, `Cache-Tag` у Cloudflare): ответ помечается тегами `product-42 catalog`, правка товара сбрасывает всё с тегом `product-42`. Purge сбрасывает только CDN, **не браузеры**: если браузер получил `max-age=86400`, он сутки не спросит. Поэтому лучшая инвалидация — новый URL (хэш в имени), а для HTML — короткий браузерный срок и долгий на CDN с purge при публикации.

### Nuxt: routeRules как кэш-политика

Nuxt задаёт кэш по маршрутам через `routeRules` (гибридный рендеринг). Поведение сверено по исходникам Nuxt 4.6.4 и Nitro 2.13.6:

- **`/_nuxt/**`** (ассеты сборки с хэшем) Nitro по умолчанию отдаёт с `public, max-age=31536000, immutable`.
- **`swr: N`** — Nitro рендерит страницу, кладёт ответ в серверное хранилище и отдаёт его N секунд. После этого отдаёт устаревший и перерендеривает в фоне. В ответ ставится `Cache-Control: s-maxage=N, stale-while-revalidate`, слабый `ETag` по хэшу тела и `Last-Modified`, на условный запрос — `304`. `swr: true` — без срока, только `stale-while-revalidate`.
- **`isr: N`** — то же, но кэширует сама платформа на CDN (Netlify, Vercel). `isr: true` — до следующего деплоя.
- **`headers`** — заголовки как есть, например свой `cache-control` для API.

> [!WARNING]
> Кэш Nitro пропускает ответ с `Set-Cookie`, с `private`/`no-store`/`no-cache` в `Cache-Control` и с `Vary` по заголовкам, которых нет в его ключе. Ключ — путь с query и метод, **cookies в нём нет**. Страница с `swr`, которая читает сессию из cookie, но сама cookie не ставит, будет закэширована с данными первого пользователя и показана всем.

## Примеры

```js
// server.mjs — headers for a Vite/Nuxt-like build output on a plain Node server
import { createServer } from 'node:http';

function cacheControlFor(pathname) {
  if (/\/assets\/.+\.[0-9a-z]{8}\.(js|css|woff2|avif)$/.test(pathname)) {
    return 'public, max-age=31536000, immutable'; // content hash in the name
  }
  if (pathname === '/' || pathname.endsWith('.html') || pathname === '/sw.js') {
    return 'no-cache'; // revalidate on every use, ETag makes it cheap
  }
  if (pathname.startsWith('/api/me')) return 'private, no-cache';
  if (pathname.startsWith('/api/catalog')) {
    return 'public, max-age=60, s-maxage=300, stale-while-revalidate=600';
  }
  return 'public, max-age=3600'; // unhashed public files
}
```

```ts
// nuxt.config.ts — caching policy per route
export default defineNuxtConfig({
  routeRules: {
    '/': { swr: 60 },                 // s-maxage=60, stale-while-revalidate
    '/blog/**': { isr: 3600 },        // CDN cache on Netlify/Vercel
    '/account/**': { ssr: false },    // personal: never in a shared cache
    '/api/catalog/**': {
      headers: { 'cache-control': 'public, max-age=60, stale-while-revalidate=600' },
    },
  },
})
```

```js
// Explicit cache mode for one request: bypass a stale entry after a mutation
await fetch('/api/cart', { method: 'POST', body: JSON.stringify(item) });
const cart = await fetch('/api/cart', { cache: 'no-cache' }).then((r) => r.json());
```

## Вопросы с интервью

::: details Чем no-cache отличается от no-store и max-age=0
`no-store` запрещает сохранять ответ где-либо: каждый запрос — полный ответ с сервера. `no-cache` разрешает хранить, но требует валидировать перед каждым использованием: кэш отправит `If-None-Match`, и при `304` тело не передаётся. `max-age=0` делает ответ сразу устаревшим, что на практике тоже ведёт к валидации, но формально кэш может отдать устаревшее при недоступном сервере. `max-age=0, must-revalidate` это запрещает и почти равно `no-cache`. Для HTML и `sw.js` нужен `no-cache`, `no-store` — только для чувствительных данных: он лишает и кэша, и дешёвой валидации, а в части браузеров и bfcache.
:::

::: details Что делает браузер, если в ответе нет Cache-Control
Если нет ни `Cache-Control`, ни `Expires`, а статус эвристически кэшируемый (`200`, `301`, `404` и другие), браузер вправе сам назначить срок свежести. Обычно это 10% от времени с `Last-Modified`: файл, изменённый 10 дней назад, считается свежим сутки. Всё это время браузер не ходит на сервер. Отсюда «после деплоя у части пользователей старая версия»: статический сервер отдал `index.html` с `Last-Modified`, но без `Cache-Control`. Вывод — явно задавать политику для каждого типа ресурса, особенно `no-cache` для HTML.
:::

::: details Как работает валидация и чем ETag лучше Last-Modified
Когда ответ устарел, кэш отправляет условный запрос: `If-None-Match` с сохранённым `ETag` или `If-Modified-Since` с `Last-Modified`. Если ресурс не изменился, сервер отвечает `304` без тела, но с актуальными `Cache-Control` и `ETag`. Кэш продлевает запись и отдаёт сохранённое тело. `ETag` точнее: он зависит от содержимого, а не от даты с точностью до секунды, и не меняется от пересборки без изменений. Поэтому при обоих заголовках сервер смотрит на `If-None-Match`. Слабый `ETag` (`W/"…"`) означает семантическую эквивалентность, и для `If-None-Match` его достаточно. Ловушка — ETag из inode и времени файла: за балансировщиком он разный на каждом узле, и 304 почти не бывает.
:::

::: details Как раздавать статику SPA, чтобы и кэш работал, и деплой применялся сразу
Разделить ресурсы. Сборщик кладёт хэш содержимого в имя ассета, и такие файлы отдаются с `max-age=31536000, immutable`: изменение = новое имя, инвалидировать ничего не нужно. HTML, `sw.js` и манифест отдаются с `no-cache` и `ETag`: каждый заход — дешёвая валидация, и после деплоя пользователь сразу получает новый HTML со ссылками на новые ассеты. Файлы без хэша — короткий срок. Старые чанки после деплоя не удаляют сразу: открытые вкладки со старым HTML ещё будут их запрашивать при ленивой загрузке. На ошибку загрузки чанка приложение реагирует перезагрузкой — в Nuxt это встроено (`emitRouteChunkError: 'automatic'` перезагружает страницу при следующей навигации).
:::

::: details Что делает Vary и чем опасны ошибки в нём
`Vary` перечисляет заголовки запроса, от которых зависит ответ, и кэш отдаёт сохранённый ответ только при их совпадении. Забытый `Vary` — ошибка корректности: CDN отдаст вариант не тому клиенту, например русскую страницу английскому пользователю или AVIF старому браузеру. Слишком широкий `Vary` (`User-Agent`, `Cookie`) дробит кэш до бесполезности. К тому же браузеры хранят немного вариантов: Chromium — один на URL, следующий вытесняет предыдущий. Поэтому для языка и персонализации надёжнее разные URL или отказ от общего кэша, а `Vary: Accept-Encoding` CDN обычно нормализует сам.
:::

::: details Что такое stale-while-revalidate и чем swr в Nuxt отличается от isr
`stale-while-revalidate=N` разрешает кэшу N секунд после устаревания отдавать старый ответ сразу, параллельно обновляя его в фоне. Пользователь не ждёт сервер, а свежесть отстаёт на один запрос; на CDN это ещё и защита от лавины запросов в origin при истечении кэша. В Nuxt `swr: N` кэширует отрендеренную страницу на сервере Nitro (в его хранилище) и ставит `Cache-Control: s-maxage=N, stale-while-revalidate`, чтобы её мог держать и CDN. `isr: N` передаёт кэширование платформе (Netlify, Vercel): страница хранится на её CDN, `isr: true` — до следующего деплоя. Оба режима опасны для персональных страниц: ключ кэша — URL, не пользователь.
:::

::: details Как инвалидировать кэш на CDN и почему лучше этого избегать
Средства CDN: purge по URL, по префиксу, по тегам (ответ помечается `Surrogate-Key`/`Cache-Tag`, сброс по тегу затрагивает все связанные страницы), soft purge — пометить устаревшим вместо удаления. Но purge сбрасывает только CDN: браузеры, получившие долгий `max-age`, его не узнают, а сам purge распространяется по сети не мгновенно. Поэтому основная стратегия — сделать инвалидацию ненужной. Ассеты получают новые URL через хэш в имени. HTML получает короткий срок для браузера и долгий для CDN (`max-age=0, s-maxage=…` или `CDN-Cache-Control`), а purge по тегу запускается при публикации контента.
:::

::: details Почему общий CDN для популярных библиотек больше не ускоряет загрузку
Раньше идея была такой: `jquery.min.js` с публичного CDN уже лежит в кэше от других сайтов. С Chrome 86, Firefox 85 и раньше в Safari HTTP-кэш **разделён** по сайту верхнего уровня: ключ включает сайт, на котором ресурс загружен. Закэшированное на `a.com` на `b.com` не используется. Сделано это для приватности: по времени загрузки ресурса другой сайт мог понять, где пользователь бывал. Теперь сторонний CDN для библиотек — только лишние DNS, TCP и TLS к чужому хосту и ещё одна точка отказа. Ассеты выгоднее раздавать со своего домена через свой CDN.
:::

## Задачи

### 1. Политика кэширования для ресурсов · легко

Задайте `Cache-Control` для каждого ответа приложения на CDN и объясните выбор:

1. `/index.html`
2. `/assets/app.3f9a1c7b.js`
3. `/sw.js`
4. `/logo.svg` (без хэша, меняется раз в год)
5. `GET /api/me` — профиль текущего пользователя
6. `GET /api/products?category=shoes` — публичный каталог, обновляется раз в несколько минут
7. `GET /api/statements/2026-10.pdf` — банковская выписка

::: details Решение и разбор
1. `no-cache` (+ `ETag`). Каждый заход — валидация, новый деплой виден сразу. Если CDN должен держать HTML: `max-age=0, s-maxage=3600` и purge при деплое.
2. `public, max-age=31536000, immutable`. Изменение даст новое имя.
3. `no-cache`. Браузер проверяет `sw.js` мимо HTTP-кэша (`updateViaCache: 'imports'`), но CDN проверку не обходит: долгий срок на CDN задержит обновление Service Worker.
4. `public, max-age=86400` или `no-cache`. Без хэша любой долгий срок — риск старой версии.
5. `private, no-cache`. CDN не хранит, браузер хранит и валидирует. `Vary: Cookie` здесь не нужен: в общий кэш ответ не попадает.
6. `public, max-age=60, stale-while-revalidate=600`. Ключ на CDN — с `category`, но без `utm_*`.
7. `no-store`. Чувствительные данные: ни CDN, ни диск браузера.
:::

### 2. Свежий или устаревший · легко

Браузер получил ответ в 12:00:00 по своим часам:

```http
HTTP/1.1 200 OK
Date: Thu, 12 Nov 2026 12:00:00 GMT
Age: 1800
Cache-Control: max-age=3600, stale-while-revalidate=600
ETag: "v7"
```

Что произойдёт при запросах в 12:20, 12:35 и 12:50? А если бы вместо `Cache-Control` был только `Last-Modified: Thu, 02 Nov 2026 12:00:00 GMT`?

::: details Решение и разбор
`Age: 1800` — ответ уже полчаса пролежал на CDN, поэтому в браузере он свеж только 3600 − 1800 = 1800 секунд, до 12:30.

- **12:20** — возраст 3000 < 3600: свежий, ответ из кэша без запроса.
- **12:35** — возраст 3900: устарел, но в окне `stale-while-revalidate` (до 4200). Ответ из кэша сразу, в фоне — условный запрос `If-None-Match: "v7"`.
- **12:50** — возраст 4800, окно прошло (если фоновой валидации не было): обычный условный запрос, ответ ждёт сервер. При `304` запись обновляется, и отсчёт идёт заново.

Без `Cache-Control` срок задаёт эвристика: 10% от `Date − Last-Modified` = 10% от 10 суток = 1 сутки, минус `Age`. Все три запроса браузер обслужил бы из кэша, не спрашивая сервер. Именно так «застревает» `index.html` без явной политики.
:::

### 3. Условные запросы на сервере · средне

Напишите `sendWithEtag(req, res, body, cacheControl)` для `node:http`:

- вычисляет сильный `ETag` как хэш тела;
- поддерживает `If-None-Match` со списком значений, слабыми тегами и `*`;
- при совпадении отвечает `304` без тела, но с `ETag` и `Cache-Control`;
- учитывает только `GET` и `HEAD`.

::: details Решение и разбор
```js
import { createHash } from 'node:crypto';

const strip = (tag) => tag.trim().replace(/^W\//, ''); // weak comparison

export function sendWithEtag(req, res, body, cacheControl = 'no-cache') {
  const etag = `"${createHash('sha256').update(body).digest('base64url').slice(0, 27)}"`;
  res.setHeader('ETag', etag);
  res.setHeader('Cache-Control', cacheControl);

  const inm = req.headers['if-none-match'];
  const conditional = req.method === 'GET' || req.method === 'HEAD';
  const matches =
    inm !== undefined &&
    (inm.trim() === '*' || inm.split(',').some((t) => strip(t) === strip(etag)));

  if (conditional && matches) {
    res.statusCode = 304; // no body, but validators and Cache-Control are sent
    return res.end();
  }

  res.setHeader('Content-Length', Buffer.byteLength(body));
  res.end(req.method === 'HEAD' ? undefined : body);
}
```

- Для `If-None-Match` RFC 9110 требует **слабое** сравнение: `W/"x"` совпадает с `"x"`. Поэтому `W/` снимается с обеих сторон.
- `*` совпадает с любой текущей версией. Значение имеет смысл в `If-None-Match: *` при `PUT` («создать, только если ещё нет»), но для `GET` тоже корректно даёт `304`.
- Для `POST` и других методов несовпадение условия означает `412 Precondition Failed`, а не `304`. Здесь они просто отвечают полным телом.
- Хэш считается от готового тела, значит, сервер всё равно рендерит ответ: экономится сеть, а не CPU. Чтобы не рендерить, ETag строят из версии данных (`updated_at`, номер ревизии) и сравнивают до рендера.
- `If-Modified-Since` при наличии `If-None-Match` игнорируется.

Сложность: O(n) по размеру тела на хэш, O(k) по числу тегов в заголовке.
:::

### 4. Чужое имя на странице товара · средне

В Nuxt-магазине включили кэширование:

```ts
export default defineNuxtConfig({
  routeRules: { '/products/**': { swr: 600 } },
})
```

В шапке страницы товара — приветствие с именем пользователя. Пользователь берётся из `useCookie('session')` и запроса к API на сервере. Через час поддержка получает два вида жалоб: одни видят на странице чужое имя, у других кэш «не работает», и страницы рендерятся каждый раз. Объясните оба эффекта и исправьте.

::: details Решение и разбор
**Чужое имя.** Nitro кэширует отрендеренный HTML по ключу «путь + query», cookies в ключ не входят. Первый, кто открыл `/products/42` после истечения кэша, оставил в HTML своё имя, и 10 минут его видят все. CDN по заголовку `s-maxage=600` делает то же самое на своём уровне.

**Кэш «не работает».** Nitro не сохраняет ответ с `Set-Cookie`. Если при рендере сессия продлевается (`useCookie` с записью значения, обновление токена), ответ некэшируемый, и каждый запрос рендерится заново. То есть кэш работает или нет в зависимости от того, кто первым пришёл.

**Исправление** — разделить общее и персональное:

```ts
export default defineNuxtConfig({
  routeRules: {
    '/products/**': { swr: 600 },            // shared HTML without user data
    '/api/me': { headers: { 'cache-control': 'private, no-cache' } },
  },
})
```

```vue
<script setup lang="ts">
// User data is loaded on the client only, so it never ends up in cached HTML.
const { data: user } = await useFetch('/api/me', { server: false })
</script>

<template>
  <ClientOnly>
    <span v-if="user">Привет, {{ user.name }}</span>
  </ClientOnly>
</template>
```

Альтернативы: персональные разделы на маршрутах без кэша (`ssr: false` или без `swr`), либо ключ кэша по cookie через `cache: { varies: [...] }` / `getKey` — но это вариант на каждого пользователя, кэш теряет смысл. Обязательная проверка после включения кэша — `curl -I` под двумя разными пользователями.
:::

### 5. Деплой, после которого «всё сломалось» · сложно

SPA на Vite раздаётся через CDN. Заголовки не настраивались: CDN кэширует всё на 1 час по умолчанию, origin ставит только `Last-Modified`. После деплоя:

- часть пользователей ещё несколько часов видит старую версию;
- у пользователей с открытой вкладкой при переходе по разделам падает «Failed to fetch dynamically imported module»;
- после ручного purge на CDN жалобы на старую версию продолжаются.

Найдите причины и предложите конфигурацию.

::: details Решение и разбор
**Старая версия.** У `index.html` нет `Cache-Control`. CDN держит его час, а браузер применяет эвристику: 10% от возраста `Last-Modified`. HTML, не менявшийся месяц, браузер считает свежим около трёх суток. Purge сбрасывает только CDN, браузеры не узнают о нём до истечения своего эвристического срока. Поэтому жалобы и продолжаются.

**Ошибки чанков.** Открытая вкладка держит старый HTML и старый граф модулей. Деплой удалил старые чанки, ленивый `import()` получает `404` (или, хуже, HTML-страницу SPA-fallback с `200` и MIME `text/html`), модуль не загружается.

**Конфигурация:**

```txt
/index.html, /                   Cache-Control: no-cache                      (ETag on)
/assets/*  (hashed)              Cache-Control: public, max-age=31536000, immutable
/sw.js, /manifest.webmanifest    Cache-Control: no-cache
everything else                  Cache-Control: public, max-age=3600
CDN: HTML via CDN-Cache-Control: max-age=600 + purge on deploy
```

- **Деплой без удаления.** Новые ассеты загружаются **до** переключения HTML, старые хранятся несколько версий (у хэшированных файлов нет конфликтов имён).
- **SPA-fallback не для ассетов.** Запрос к `/assets/*`, которого нет, должен отвечать `404`, а не `index.html`.
- **Восстановление на клиенте.** Событие `vite:preloadError` или `catch` у `import()` — перезагрузка страницы один раз (с защитой от цикла через `sessionStorage`). В Nuxt это поведение по умолчанию: `app:chunkError` и перезагрузка при следующей навигации.
- **Уже застрявшим пользователям** помочь сервером нельзя: их браузер не идёт на сервер. Остаётся ждать окончания эвристического срока. Для экстренных случаев есть `Clear-Site-Data: "cache"` — но его браузер получит, только когда всё-таки сделает запрос, например к API.
:::
