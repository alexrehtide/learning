# HTTP: методы, статусы, заголовки, версии

> **Коротко.** HTTP — это две разные вещи: **семантика** (методы, статусы, заголовки — RFC 9110, одинаковы во всех версиях) и **передача** (как сообщения едут по сети — HTTP/1.1, HTTP/2, HTTP/3). Свойства методов — **безопасность** и **идемпотентность** — не формальность: на них держатся повторы запросов, prefetch и кэш. Статус говорит клиенту, *что делать дальше*, поэтому спорные пары (301/308, 302/307/303, 401/403) различаются именно поведением клиента. HTTP/2 убрал head-of-line blocking на уровне HTTP, но оставил его в TCP. HTTP/3 переносит потоки в QUIC поверх UDP и убирает его совсем.

**Связанные темы:** [От ввода URL до отображения страницы](../browser/from-url-to-pixels.md), [async/await, обработка ошибок и отмена](../javascript/async-await.md), [Web Workers, Service Workers и PWA](../browser/workers.md), [HTTP-кэширование и CDN](./caching.md), [Same-origin policy, CORS и cookies](./cors-and-cookies.md), [Real-time: polling, SSE, WebSocket](./realtime.md)

## Теория

### Семантика отдельно от передачи

С 2022 года HTTP описан набором RFC, и это разделение — лучший ответ на вопрос «чем отличаются версии»:

- **RFC 9110 (HTTP Semantics)** — методы, статусы, заголовки, content negotiation, условные запросы. Общие для всех версий. Кэширование — RFC 9111.
- **RFC 9112 / 9113 / 9114** — «проводка» HTTP/1.1, HTTP/2 и HTTP/3: как сообщение превращается в байты.

Сообщение в любой версии — это метод и цель запроса (или статус ответа), **поля** (заголовки), содержимое (content, раньше «тело») и, возможно, трейлеры. HTTP **не хранит состояния** между запросами: сессию строят поверх него cookies и токены.

### Методы: безопасные и идемпотентные

- **Безопасный** (safe) метод по смыслу только читает: клиент не просит и не ждёт изменений на сервере. По RFC 9110 безопасны `GET`, `HEAD`, `OPTIONS`, `TRACE`.
- **Идемпотентный** метод: эффект N одинаковых запросов равен эффекту одного. Это безопасные методы, а также `PUT` и `DELETE`.

| Метод | Безопасный | Идемпотентный | Типичное назначение |
| --- | --- | --- | --- |
| `GET` | да | да | получить представление ресурса |
| `HEAD` | да | да | то же без содержимого (размер, `ETag`) |
| `OPTIONS` | да | да | возможности ресурса, [CORS preflight](./cors-and-cookies.md#простые-запросы-и-preflight) |
| `POST` | нет | нет | обработать данные: создать, выполнить действие |
| `PUT` | нет | да | заменить ресурс целиком по известному URL |
| `PATCH` | нет | не гарантирует | частичное изменение (RFC 5789) |
| `DELETE` | нет | да | удалить |
| `QUERY` | да | да | запрос с телом (поиск со сложным фильтром) |

Зачем это фронтендеру:

- **Повторы.** Клиент, прокси и браузер вправе автоматически повторить идемпотентный запрос после обрыва соединения: непонятно, дошёл ли он, но повтор ничего не испортит. `POST` так повторять нельзя — двойной заказ. Отсюда **ключ идемпотентности** (`Idempotency-Key`) для мутаций, которые нужно повторять.
- **Prefetch и краулеры.** Speculative prefetch, сканеры ссылок в почте и поисковые боты ходят по `GET`-ссылкам. `GET /unsubscribe?id=1` или `GET /items/1/delete` выполнятся без пользователя. RFC прямо требует запрещать небезопасное действие на безопасном методе.
- **Тело у `GET`.** Синтаксически возможно, но не имеет семантики: прокси и серверы вправе отклонить такой запрос как попытку request smuggling. `fetch` вообще бросает `TypeError` на `GET` с `body`. Для «поиска с JSON-фильтром» был выбор между `POST` (теряем кэш и повторы) и длинной query-строкой. Его закрывает `QUERY`.

> [!NOTE]
> Метод `QUERY` стандартизирован в RFC 10008 (Proposed Standard, июнь 2026, сверено 2026-11-12): безопасный и идемпотентный, с телом, ответ кэшируемый с учётом тела. Сервер может объявить поддержку заголовком `Accept-Query`. Для браузера это просто имя метода: `fetch` его отправит, но cross-origin запрос пойдёт через CORS preflight.

### Статусы: что клиент должен сделать

Класс — первая цифра, и клиент, не знающий конкретного кода, обязан понимать его как `x00` своего класса:

- **1xx** — промежуточные: `100 Continue` (сервер готов принять большое тело), `101 Switching Protocols` (переход на WebSocket в HTTP/1.1), `103 Early Hints` (подсказки `Link: preload` до финального ответа).
- **2xx** — успех: `200`, `201 Created` (+ `Location` нового ресурса), `202 Accepted` (принято в обработку), `204 No Content`, `206 Partial Content` (ответ на `Range`, видео и докачка).
- **3xx** — дальнейшее действие: редиректы и `304 Not Modified` (условный запрос, кэш свежий).
- **4xx** — ошибка клиента: **повторять тот же запрос бесполезно**, кроме `408`, `425` и `429`.
- **5xx** — ошибка сервера: повтор может помочь. `502 Bad Gateway` — прокси получил плохой ответ, `503 Service Unavailable` — перегрузка или обслуживание (часто с `Retry-After`), `504 Gateway Timeout` — прокси не дождался.

**Редиректы** различаются по двум осям: постоянный или временный (можно ли кэшировать и запоминать новый URL) и можно ли менять метод.

| | Метод может смениться на `GET` | Метод сохраняется |
| --- | --- | --- |
| **Постоянный** | `301 Moved Permanently` | `308 Permanent Redirect` |
| **Временный** | `302 Found` | `307 Temporary Redirect` |
| **«Смотри другое»** | `303 See Other` — всегда `GET` | — |

У 301 и 302 смена `POST` → `GET` — исторический баг браузеров, который RFC узаконил словами «for historical reasons, a user agent MAY». Fetch Standard делает это обязательным: на 301/302 `POST` превращается в `GET` без тела, на 303 — любой метод, кроме `GET`/`HEAD`. 307 и 308 появились, чтобы сказать «повтори **тот же** запрос там». Для навигации (`GET`) 301 и 308 эквивалентны. Для API, принимающего `POST`, переезд — только 308.

**Ошибки доступа:**

- `401 Unauthorized` — на самом деле «не аутентифицирован»: нет учётных данных или они недействительны. Сервер **обязан** прислать `WWW-Authenticate` с вызовом. На фронте 401 — сигнал обновить токен или отправить на логин.
- `403 Forbidden` — «понял, кто вы, но нельзя». Повтор с теми же данными бесполезен. Сервер, который хочет скрыть само существование ресурса, может ответить `404`.

**Ошибки данных:**

- `400 Bad Request` — запрос синтаксически испорчен: невалидный JSON, нет обязательного параметра.
- `422 Unprocessable Content` — синтаксис и тип верны, но смысл нет: валидация бизнес-правил (email занят? нет — это уже 409; «дата окончания раньше начала» — 422).
- `409 Conflict` — конфликт с **текущим состоянием** ресурса: оптимистичная блокировка, уникальность, устаревшая версия. Пользователь может разрешить конфликт и повторить.

Не менее важно, чего статусы **не** делают в браузере: `fetch` выполняет промис на любом HTTP-ответе, включая 404 и 500. Отклоняет он только сетевую ошибку, отмену и CORS-отказ. Проверка `response.ok` (статус 200–299) — работа клиента.

### Заголовки и content negotiation

Имена полей регистронезависимы, в HTTP/2 и HTTP/3 передаются строчными. Полезно держать в голове группы:

- **Метаданные представления:** `Content-Type` (с `charset`), `Content-Length`, `Content-Encoding`, `Content-Language`.
- **Согласование:** `Accept`, `Accept-Language`, `Accept-Encoding` — что клиент готов принять, с весами `q` от 0 до 1. Ответ — `Vary`: какие заголовки запроса повлияли на выбор.
- **Условные запросы:** `If-None-Match`/`ETag`, `If-Modified-Since`/`Last-Modified`, `If-Match` — подробно в теме [HTTP-кэширование и CDN](./caching.md#валидация-etag-last-modified-и-304).
- **Аутентификация:** `Authorization`, `WWW-Authenticate`.
- **Контекст:** `Host` (в HTTP/2+ — псевдозаголовок `:authority`), `Origin`, `Referer`, `User-Agent` и client hints `Sec-CH-*`.

**Content negotiation** (proactive) — сервер выбирает вариант по заголовкам запроса: `Accept: image/avif,image/webp,*/*` → AVIF по тому же URL. Цена — `Vary`. Если сервер выбирает формат по `Accept`, но не отдал `Vary: Accept`, CDN закэширует AVIF и раздаст его браузеру, который его не умеет. Обратная крайность — `Vary: User-Agent` — дробит кэш почти до нуля.

> [!WARNING]
> Часть заголовков браузер не даёт выставить из JavaScript — Fetch Standard называет их **forbidden request-headers**: `Accept-Encoding`, `Cookie`, `Host`, `Origin`, `Referer`, `Connection`, `Content-Length`, всё с префиксами `Sec-` и `Proxy-` и другие. `fetch` молча их отбрасывает. Пользовательский агент должен оставаться их единственным хозяином: иначе скрипт мог бы подделать `Origin` и обойти CORS.

### Сжатие

Клиент объявляет `Accept-Encoding`, сервер сжимает и пишет `Content-Encoding`. Это свойство **представления**: `ETag` и кэш относятся к сжатым байтам, поэтому нужен `Vary: Accept-Encoding`. `Transfer-Encoding: chunked` — другое: способ передачи в HTTP/1.1, в HTTP/2 и HTTP/3 его нет (там свои кадры).

| Кодировка | Что это | Поддержка |
| --- | --- | --- |
| `gzip` | DEFLATE, повсеместно | все |
| `br` | Brotli: встроенный словарь частых веб-строк, на тексте заметно меньше gzip | все с 2016–2017 |
| `zstd` | Zstandard: сжатие как у Brotli, но заметно быстрее на сервере | Chromium 123, Firefox 126, Safari 26.3 |
| `dcb`, `dcz` | Brotli/Zstandard со **словарём** — предыдущей версией файла (RFC 9842) | Chromium 130; Firefox — за флагом, Safari — нет |

Поддержка — по MDN BCD, сверено 2026-11-12.

Практика: сжимать текст (HTML, CSS, JS, JSON, SVG), не сжимать уже сжатое (JPEG, AVIF, WOFF2, видео) — только CPU впустую. Статику сжимать при сборке максимальным уровнем, динамику — на лету быстрым. **Compression dictionary transport** решает проблему деплоев: новый бандл, отличающийся от старого на пару функций, передаётся как разница с закэшированной версией — десятки байт вместо сотен килобайт.

### HTTP/1.1: текст и очередь

Сообщение — текст: строка запроса, заголовки, пустая строка, тело. Соединение по умолчанию **persistent** (keep-alive) и переиспользуется, но в каждый момент по нему идёт **один** запрос: следующий ждёт полного ответа. Pipelining (отправить несколько запросов подряд) есть в стандарте, но ответы всё равно возвращаются по порядку, и браузеры его так и не включили. Это **head-of-line blocking на уровне HTTP**: медленный ответ держит очередь.

Браузеры обходят его параллельными соединениями — в Chromium до **6 на хост**. Отсюда весь «фольклор» оптимизации эпохи HTTP/1.1: склейка файлов в бандл, CSS-спрайты, инлайн картинок в base64, **domain sharding** (`static1.`, `static2.` — по 6 соединений на каждый). Плюс заголовки повторяются в каждом запросе без сжатия: cookie на 2 КБ уходит с каждой иконкой.

### HTTP/2: мультиплексирование и HPACK

HTTP/2 (RFC 9113) меняет только проводку, семантика та же:

- **Бинарные кадры** (frames). Каждый запрос — **поток** (stream) со своим id. Кадры разных потоков перемешиваются в **одном** TCP-соединении: сотня запросов идёт параллельно, медленный ответ не держит остальные.
- **HPACK** (RFC 7541) сжимает заголовки: статическая таблица частых полей, динамическая таблица уже отправленных в этом соединении, коды Хаффмана. Повторная cookie стоит пару байт.
- **Псевдозаголовки** `:method`, `:scheme`, `:authority`, `:path`, `:status`. Имена полей обязаны быть строчными, connection-специфичные поля (`Connection`, `Keep-Alive`, `Transfer-Encoding`) запрещены.
- Браузеры поддерживают HTTP/2 **только поверх TLS** (договорённость через ALPN `h2`).

Что стало хуже, чем ожидали:

- **Head-of-line blocking переехал в TCP.** TCP — один упорядоченный поток байт. Потерялся один пакет — ядро ОС не отдаст приложению ничего, что пришло после него, пока пакет не переслан, даже если это кадры *других* потоков. На сети с потерями (мобильная, Wi-Fi) одно соединение HTTP/2 может проиграть шести соединениям HTTP/1.1.
- **Приоритеты** из первой версии (дерево зависимостей) почти никто не реализовал правильно; RFC 9113 их объявил устаревшими. На смену пришли Extensible Priorities (RFC 9218): заголовок `Priority: u=1, i` — срочность 0–7 и инкрементальность. Браузер выставляет приоритеты сам, `fetchpriority` на элементе влияет на них.
- **Server push** — сервер присылает ресурсы до запроса. На практике пушил то, что уже в кэше, и тормозил основной ответ. Chromium убрал его в версии 106. Замена — `103 Early Hints`: сервер только *подсказывает*, а браузер решает, грузить ли.

Оптимизации HTTP/1.1 при HTTP/2 становятся вредными: шардинг ломает одно общее соединение (лишние DNS, TCP и TLS) и приоритизацию, гигантский бандл и спрайты мешают кэшировать гранулярно. Склейка не умерла — сотни мелких модулей всё ещё дороже десятка чанков (накладные на запрос, хуже сжатие), но «всё в один файл» больше не нужно.

### HTTP/3: QUIC поверх UDP

HTTP/3 (RFC 9114) — та же семантика поверх **QUIC** (RFC 9000), транспорта, построенного на UDP в пространстве пользователя:

- **Потоки на уровне транспорта.** QUIC знает о потоках сам: потеря пакета задерживает только тот поток, чьи данные в нём были. Head-of-line blocking между запросами исчезает. Сжатие заголовков — **QPACK**, переделанный HPACK: тот предполагал строгий порядок доставки.
- **TLS 1.3 встроен в рукопожатие.** Новое соединение — 1 RTT вместо TCP + TLS (2 RTT). При повторном подключении — **0-RTT**: запрос уходит в первом же пакете.
- **Connection migration.** Соединение определяется connection ID, а не четвёркой IP/порт. Переход с Wi-Fi на мобильную сеть не рвёт загрузку.
- **Почему UDP.** TCP реализован в ядрах ОС и в бесчисленных middlebox (NAT, файрволы), поэтому изменить его поведение на практике нельзя — это **окостенение** (ossification). UDP пропускают все, а QUIC шифрует почти всё, включая собственные заголовки, чтобы промежуточные узлы не закостенели снова. Цена — больше CPU на шифрование и разбор в userspace и сети, где UDP режут: там браузер откатывается на HTTP/2.

**0-RTT небезопасен для неидемпотентных запросов:** злоумышленник может записать пакет с early data и **воспроизвести** его (replay). Поэтому в 0-RTT разумно отправлять только безопасные запросы, а сервер, не готовый рисковать, отвечает `425 Too Early` — клиент повторит запрос после рукопожатия (RFC 8470).

Как браузер узнаёт, что сервер умеет HTTP/3: заголовок `Alt-Svc: h3=":443"` в ответе по HTTP/2 (поэтому первый визит часто идёт по HTTP/2) или DNS-запись `HTTPS` (RFC 9460), которая сообщает о `h3` ещё до первого соединения.

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| Формат | текст | бинарные кадры | бинарные кадры |
| Транспорт | TCP (+TLS) | TCP + TLS | QUIC (UDP), TLS 1.3 внутри |
| Параллельность | ~6 соединений на хост | потоки в одном соединении | потоки в одном соединении |
| HOL blocking | HTTP и TCP | только TCP | нет между потоками |
| Заголовки | текст, без сжатия | HPACK | QPACK |
| Рукопожатие (новое, TLS 1.3) | 2 RTT: TCP + TLS | 2 RTT: TCP + TLS | 1 RTT, повтор — 0-RTT |

### Vue и Nuxt: где это видно

- **`fetch` против `$fetch`.** Нативный `fetch` выполняет промис на 404. `$fetch` в Nuxt (библиотека ofetch) бросает `FetchError` на любой статус вне 2xx, а тело ошибки разбирает в `error.data`. Перенося код между ними, легко потерять или задвоить обработку ошибок.
- **Редирект в Nuxt.** `navigateTo` на сервере отвечает `302` по умолчанию. Для переехавших страниц — `navigateTo(url, { redirectCode: 301 })`: поисковики перенесут вес на новый URL. На клиенте редирект — смена маршрута в роутере, HTTP-статуса нет вовсе.
- **Статус ошибки.** `createError({ status: 404, statusText: 'Not Found' })` на сервере задаёт HTTP-статус ответа: страница «не найдено» должна отвечать 404, а не 200 (иначе получится soft 404 для поисковиков).

> [!NOTE]
> В Nuxt 4 до 4.3 и в Nuxt 3 поля назывались `statusCode` и `statusMessage`. С 4.3 рекомендуются `status` и `statusText` по образцу Web API (подготовка к H3 v2 и Nitro v3), старые имена работают, но помечены устаревшими (сверено 2026-11-12).

## Примеры

```js
// Status handling with native fetch: the promise resolves on 4xx/5xx too.
async function getJson(url, init) {
  const response = await fetch(url, {
    ...init,
    headers: { Accept: 'application/json', ...init?.headers },
  });

  if (response.status === 204) return null;
  if (response.ok) return response.json();

  const problem = response.headers.get('Content-Type')?.includes('json')
    ? await response.json()
    : { title: await response.text() };

  throw Object.assign(new Error(`HTTP ${response.status}`), {
    status: response.status,
    problem,
  });
}
```

```ts
// app/middleware/legacy-blog.global.ts — permanent redirect for moved pages
export default defineNuxtRouteMiddleware((to) => {
  if (to.path.startsWith('/blog/')) {
    return navigateTo(to.fullPath.replace('/blog/', '/articles/'), {
      redirectCode: 301, // server side only; default is 302
    })
  }
})
```

```ts
// server/api/orders/[id].get.ts — a real 404, not "200 with an empty body"
export default defineEventHandler(async (event) => {
  const order = await findOrder(getRouterParam(event, 'id'))
  if (!order) {
    throw createError({ status: 404, statusText: 'Order Not Found' })
  }
  return order
})
```

## Вопросы с интервью

::: details Чем безопасный метод отличается от идемпотентного и почему это важно на фронтенде
Безопасный метод по смыслу не меняет состояние сервера (`GET`, `HEAD`, `OPTIONS`, `TRACE`). Идемпотентный — повтор даёт тот же эффект, что и один запрос: все безопасные плюс `PUT` и `DELETE`. Все безопасные идемпотентны, но не наоборот: `DELETE` меняет состояние, но повторный `DELETE` ничего нового не сделает (статус может быть другим — 404, эффект тот же). На этих свойствах держится инфраструктура: клиенты и прокси повторяют идемпотентные запросы после обрыва, prefetch и краулеры ходят только по безопасным, 0-RTT в HTTP/3 безопасен только для них. На фронтенде отсюда два правила: никаких действий на `GET`-ссылках и никаких автоматических повторов `POST` без ключа идемпотентности.
:::

::: details Чем отличаются PUT, PATCH и POST
`PUT` заменяет ресурс по известному клиенту URL целиком и идемпотентен: два одинаковых `PUT` дают одно состояние. Им же можно создать ресурс, если URL выбирает клиент. `PATCH` применяет частичное изменение; идемпотентность зависит от формата: merge-patch с присваиванием полей идемпотентен, JSON Patch с `add` в массив — нет. `POST` — «обработай эти данные» по правилам ресурса: создание в коллекции, где URL выбирает сервер (ответ `201` с `Location`), или любое действие, которое не ложится в другие методы. Он ни безопасен, ни идемпотентен.
:::

::: details Чем отличаются 301, 302, 303, 307 и 308
Две оси: постоянство и сохранение метода. 301 и 308 — постоянные: браузер и поисковики запоминают новый URL, ответ кэшируется. 302 и 307 — временные. На 301 и 302 браузер по историческим причинам меняет `POST` на `GET` и теряет тело — так требует Fetch Standard. 307 и 308 запрещают менять метод: «повтори тот же запрос там». 303 явно говорит «результат смотри по этому адресу через `GET`» — это паттерн Post/Redirect/Get после отправки формы, чтобы F5 не отправил заказ повторно. Для страниц (`GET`) 301 и 308 равнозначны, для переезда API с `POST` — только 308.
:::

::: details Чем 401 отличается от 403, а 409 от 422
401 — «не аутентифицирован»: нет учётных данных или они недействительны; сервер обязан прислать `WWW-Authenticate`, клиент может обновить токен и повторить. 403 — «аутентифицирован, но нельзя»: повтор с теми же данными бесполезен, нужно другое право доступа. Если ресурс нужно скрыть, отвечают 404. 422 — данные синтаксически верны, но не проходят правила обработки: валидация полей. 409 — запрос противоречит текущему состоянию ресурса: устаревшая версия при оптимистичной блокировке, занятый уникальный ключ. Практическое различие для UI: 422 показываем у полей формы, 409 — как «данные изменились, обновите и повторите».
:::

::: details Что такое content negotiation и зачем нужен Vary
Content negotiation — выбор варианта ответа по заголовкам запроса: формат по `Accept` (AVIF или JPEG), язык по `Accept-Language`, сжатие по `Accept-Encoding`. URL один, а представлений несколько, поэтому кэшам нужно знать, по каким заголовкам ответ различается. Это сообщает `Vary`: `Vary: Accept-Encoding, Accept`. Без него CDN отдаст закэшированный вариант не тому клиенту — AVIF старому браузеру или сжатое Brotli тому, кто его не объявлял. Слишком широкий `Vary` (`User-Agent`, `Cookie`) делает кэш почти бесполезным, поэтому для языка чаще используют разные URL (`/en/`, `/ru/`).
:::

::: details Что дал HTTP/2 по сравнению с HTTP/1.1 и какие старые оптимизации стали вредными
HTTP/1.1 обрабатывает один запрос за раз на соединение, браузеры открывают около шести соединений на хост, заголовки повторяются текстом. HTTP/2 мультиплексирует потоки в одном TCP-соединении бинарными кадрами и сжимает заголовки HPACK. Вредными стали domain sharding (лишние рукопожатия, ломает приоритеты и единое соединение), спрайты и инлайн base64 (портят кэширование и приоритизацию), склейка всего в один файл (одна правка инвалидирует весь бандл). Но HTTP/2 не убрал head-of-line blocking в TCP: потеря пакета останавливает все потоки, и на плохой сети одно соединение может уступить шести. Server push на практике не взлетел и удалён из Chromium — его заменил `103 Early Hints`.
:::

::: details Почему HTTP/3 работает поверх UDP и чем опасен 0-RTT
TCP живёт в ядрах ОС и в промежуточных устройствах, которые ожидают его конкретного поведения, поэтому новый транспорт поверх IP или изменённый TCP массово не развернуть. UDP проходит везде, и QUIC реализует поверх него надёжную доставку с независимыми потоками, встроенным TLS 1.3 и миграцией соединения, а почти всё шифрует, чтобы сеть снова не окостенела. Потеря пакета задерживает только свой поток. 0-RTT позволяет отправить запрос в первом пакете повторного соединения, но early data можно перехватить и воспроизвести. Поэтому в 0-RTT отправляют только идемпотентные запросы, а сервер может ответить `425 Too Early`, и клиент повторит запрос после рукопожатия.
:::

::: details Почему fetch не отклоняет промис на 404 и 500
Для `fetch` любой полученный HTTP-ответ — успешно выполненный сетевой запрос: сервер ответил, и ответ можно прочитать. Промис отклоняется только при сетевой ошибке, отмене через `AbortSignal` или отказе CORS (для JavaScript это та же сетевая ошибка, без подробностей). Это разумно: у 404 и 422 есть полезное тело, а решать, что считать ошибкой, должна прикладная логика. Поэтому нужна проверка `response.ok` или `status`. Обёртки вроде `$fetch` в Nuxt (ofetch) или axios делают наоборот и бросают на не-2xx — при смене клиента это меняет поток ошибок.
:::

## Задачи

### 1. Метод и статус для API · легко

Выберите метод и статус успешного ответа или ошибки для каждой операции API заказов:

1. Создать заказ; сервер назначает id.
2. Повторная отправка того же создания с тем же `Idempotency-Key`.
3. Сменить адрес доставки (изменение одного поля).
4. Отменить заказ, который уже отправлен курьеру.
5. Отправить форму с `quantity: -3`.
6. Запросить чужой заказ под своим токеном.
7. Запросить заказ с истёкшим токеном.

::: details Решение и разбор
1. `POST /orders` → `201 Created` с `Location: /orders/1042` и телом созданного заказа.
2. Тот же `POST` → сервер находит ключ и возвращает **сохранённый** ответ первого запроса (`201` с тем же заказом). Если первый запрос ещё обрабатывается — `409 Conflict`. Если ключ пришёл с другим телом — `422` (так советует черновик IETF о `Idempotency-Key`).
3. `PATCH /orders/1042` с `{ "address": … }` → `200` с заказом или `204`. `PUT` потребовал бы прислать заказ целиком.
4. `POST /orders/1042/cancel` (действие) или `PATCH` со статусом → `409 Conflict`: запрос верный, но противоречит текущему состоянию.
5. `422 Unprocessable Content` с описанием ошибок по полям (например, `application/problem+json`, RFC 9457). `400` — если тело вообще не разобралось как JSON.
6. `403`, или `404`, чтобы не раскрывать существование чужого заказа.
7. `401` с `WWW-Authenticate: Bearer error="invalid_token"` — клиент обновит токен и повторит.
:::

### 2. Повтор только там, где можно · средне

Напишите `fetchWithRetry(url, init, options)`:

- повторяет запрос при сетевой ошибке и статусах `408`, `429`, `502`, `503`, `504`;
- повторяет только идемпотентные методы или запросы с заголовком `Idempotency-Key`;
- уважает `Retry-After` (секунды или HTTP-дата), иначе — экспоненциальная задержка с jitter;
- поддерживает отмену через `init.signal`, в том числе во время ожидания.

::: details Решение и разбор
```js
const IDEMPOTENT = new Set(['GET', 'HEAD', 'OPTIONS', 'TRACE', 'PUT', 'DELETE']);
const RETRYABLE = new Set([408, 429, 502, 503, 504]);

export async function fetchWithRetry(url, init = {}, { retries = 3, baseDelay = 300, maxDelay = 10_000 } = {}) {
  const method = (init.method ?? 'GET').toUpperCase();
  const canRetry = IDEMPOTENT.has(method) || new Headers(init.headers).has('Idempotency-Key');

  for (let attempt = 0; ; attempt++) {
    let response;
    try {
      response = await fetch(url, init);
    } catch (error) {
      // Aborts are not retried; neither are non-idempotent requests.
      if (!canRetry || attempt >= retries || init.signal?.aborted) throw error;
      await sleep(backoff(attempt, baseDelay, maxDelay), init.signal);
      continue;
    }

    if (!canRetry || attempt >= retries || !RETRYABLE.has(response.status)) return response;

    const delay = retryAfter(response) ?? backoff(attempt, baseDelay, maxDelay);
    await response.body?.cancel(); // release the connection, we won't read it
    await sleep(Math.min(delay, maxDelay), init.signal);
  }
}

function backoff(attempt, base, max) {
  // "Full jitter": spreads clients out so they don't retry in lockstep.
  return Math.random() * Math.min(max, base * 2 ** attempt);
}

function retryAfter(response) {
  const value = response.headers.get('Retry-After')?.trim();
  if (!value) return null;
  if (/^\d+$/.test(value)) return Number(value) * 1000;
  const date = Date.parse(value);
  return Number.isNaN(date) ? null : Math.max(0, date - Date.now());
}

function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) return reject(signal.reason);
    const onAbort = () => {
      clearTimeout(timer);
      reject(signal.reason);
    };
    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}
```

Ключевые решения:

- **`POST` без ключа не повторяется ни при каких ошибках.** Сетевая ошибка не значит, что сервер ничего не сделал: ответ мог потеряться после выполнения.
- **Тело отброшенного ответа отменяется** (`body.cancel()`): иначе соединение в HTTP/1.1 остаётся занятым до сборки мусора, а в Node поток висит.
- **Jitter** обязателен: без него тысяча клиентов после падения сервера вернётся одновременно и положит его снова (thundering herd).
- Ограничение: `init.body` как `ReadableStream` читается один раз, повторить такой запрос нельзя. Строка, `Blob`, `FormData` и `URLSearchParams` повторяются без проблем.

Сложность: O(retries) попыток; задержка в худшем случае ограничена `retries · maxDelay`.
:::

### 3. Форма заказа и кнопка «Назад» · средне

Обработчик формы `POST /checkout` создаёт заказ и отвечает `302 Found` с `Location: /orders/1042`. Один разработчик предлагает заменить 302 на 307 «потому что 302 устарел», другой — на 303. Что произойдёт в каждом варианте и какой выбрать? Что будет, если вместо редиректа сразу отдать `200` с HTML страницы заказа?

::: details Решение и разбор
- **302** — браузер, следуя Fetch Standard, сменит `POST` на `GET` и откроет `/orders/1042`. Работает, но благодаря историческому исключению, а не смыслу статуса.
- **307** — браузер повторит **`POST`** с тем же телом на `/orders/1042`. Ресурс заказа `POST` не принимает (`405`) или, хуже, примет: «оптимизация» ломает поток.
- **303 See Other** — правильный выбор: явно «результат — по этому адресу через `GET`». Это паттерн **Post/Redirect/Get**: в истории остаётся `GET /orders/1042`, и F5 или «Назад/Вперёд» не переотправляют форму.
- **`200` сразу** — в истории остаётся запись `POST /checkout`. F5 покажет диалог «отправить данные повторно?», и пользователь создаст второй заказ. Защита от этого на сервере всё равно нужна (ключ идемпотентности в скрытом поле формы), но PRG убирает сам повод.

В SPA этой проблемы нет: `fetch` отправляет `POST`, а навигацию делает роутер. Но `fetch` по умолчанию сам следует редиректам (`redirect: 'follow'`) с теми же правилами смены метода. Поэтому 307/308 от API на `POST` приведут к повторному `POST` по новому адресу.
:::

### 4. Шесть соединений и потерянный пакет · средне

Страница грузит 30 небольших файлов с одного хоста. RTT — 100 мс, каждый файл помещается в один RTT, соединение уже открыто, пропускная способность не ограничивает. Оцените время загрузки:

1. по HTTP/1.1 с шестью соединениями;
2. по HTTP/2;
3. по HTTP/2, если в начале потерялся один пакет с данными файла №1 (повторная отправка — ещё 1 RTT);
4. по HTTP/3 в той же ситуации.

::: details Решение и разбор
1. **HTTP/1.1:** на каждом соединении файлы идут по очереди: ⌈30 / 6⌉ = 5 волн × 100 мс ≈ **500 мс**. Domain sharding на 2 хоста дал бы 3 волны (~300 мс) ценой лишних DNS, TCP и TLS.
2. **HTTP/2:** все 30 запросов уходят сразу в одном соединении, ответы приходят вперемешку ≈ **100 мс**.
3. **HTTP/2 с потерей:** TCP не отдаёт приложению байты после «дыры», пока пакет не пришёл повторно. Застрянут не только файл №1, но и все кадры, пришедшие после потерянного пакета, — практически все 30 файлов ≈ **200 мс**. Плюс TCP уменьшит окно перегрузки для **всего** соединения.
4. **HTTP/3:** потеря задержит только поток файла №1. Остальные 29 файлов готовы через ~100 мс, файл №1 — через ~200 мс. Реакция на перегрузку в QUIC тоже есть, но доставка других потоков не стоит.

Вывод для интервью: HTTP/2 выигрывает у HTTP/1.1 на хорошей сети почти всегда, но на сети с потерями единое TCP-соединение — единая точка торможения. Именно эту проблему решает HTTP/3.
:::

### 5. Выбор языка по Accept-Language · средне

Напишите `negotiateLanguage(header, available)`: по заголовку `Accept-Language` выбрать язык из `available` (например, `['en', 'ru', 'pt-BR']`). Учитывать веса `q`, порядок при равных весах, `q=0` (язык запрещён), `*`, а также совпадение по префиксу в обе стороны: `en-US` → `en`, `pt` → `pt-BR`. Если ничего не подошло, вернуть первый из `available`.

```js
negotiateLanguage('ru-RU,ru;q=0.9,en-US;q=0.8,en;q=0.7', ['en', 'ru']); // 'ru'
negotiateLanguage('de-CH, fr;q=0.9, *;q=0.5', ['en', 'ru']);           // 'en'
negotiateLanguage('pt', ['en', 'pt-BR']);                                // 'pt-BR'
```

::: details Решение и разбор
```js
export function negotiateLanguage(header, available) {
  const fallback = available[0];
  if (!header) return fallback;

  const ranges = header
    .split(',')
    .map((part) => {
      const [tag, ...params] = part.trim().split(';');
      const qParam = params.map((p) => p.trim()).find((p) => p.startsWith('q='));
      return { tag: tag.trim().toLowerCase(), q: qParam ? Number(qParam.slice(2)) : 1 };
    })
    .filter((range) => range.tag && range.q > 0) // drops q=0 and NaN
    .sort((a, b) => b.q - a.q); // Array#sort is stable: equal q keep header order

  const lower = available.map((lang) => lang.toLowerCase());

  for (const { tag } of ranges) {
    if (tag === '*') return fallback;

    // 1. Exact match.
    let index = lower.indexOf(tag);
    // 2. Range is a prefix of an available tag: "pt" -> "pt-BR".
    if (index === -1) index = lower.findIndex((lang) => lang.startsWith(`${tag}-`));
    // 3. Lookup: drop subtags from the range: "en-US" -> "en".
    for (let t = tag; index === -1 && t.includes('-'); ) {
      t = t.slice(0, t.lastIndexOf('-'));
      index = lower.indexOf(t);
    }
    if (index !== -1) return available[index];
  }
  return fallback;
}
```

Разбор:

- `q=0` — явный запрет, такой диапазон отбрасывается. Невалидный `q` (`q=abc` → `NaN`) — тоже: `NaN > 0` ложно.
- Шаги 2 и 3 — это два алгоритма RFC 4647: basic filtering (диапазон `pt` подходит к `pt-BR`) и lookup (усечение `en-US` до `en`). Строгая реализация выбирает один из них, на практике полезны оба.
- Ответ с выбором по `Accept-Language` обязан содержать `Vary: Accept-Language`. Лучше редиректить на URL с языком (`/ru/`), а выбор запоминать в cookie.

Сложность: O(r log r + r · a · L) по времени, где r — число диапазонов, a — число доступных языков, L — длина тега; O(r) по памяти.
:::
