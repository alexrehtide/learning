# Стеки и очереди

> **Коротко.** Стек (stack) — LIFO: последним положили, первым достали. Очередь (queue) — FIFO: первым положили, первым достали. Дек (deque) умеет оба конца, приоритетная очередь отдаёт минимальный элемент. В JS стек — это массив с `push`/`pop` за амортизированное O(1). Очереди, дека и кучи во встроенной библиотеке нет. Очередь на `shift` формально стоит O(n) за операцию, и в V8 на больших массивах это действительно так. Поэтому очередь делают на указателе головы, кольцевом буфере или двух стеках, а приоритетную очередь — на бинарной куче. На интервью стек и очередь всплывают в задачах на скобки, монотонный стек, BFS, top-K, слияние k списков и LRU-кэш.

**Связанные темы:** [Оценка сложности](./complexity.md), [Массивы, строки и хеш-таблицы](./arrays-strings-hashing.md), [Event loop](../javascript/event-loop.md), [Функции и `this`](../javascript/functions-and-this.md), [Память и сборка мусора](../javascript/memory-and-gc.md), [Утечки памяти](../performance/memory-leaks.md), [Рекурсия и динамическое программирование](./recursion-and-dp.md), [curry, compose, memoize, once](../live-coding/function-utilities.md)

## Теория

### Абстрактный тип и реализация

Стек и очередь — **абстрактные типы данных**: они задают операции и их порядок, а не устройство в памяти. Одну и ту же очередь можно сделать на массиве, связном списке или кольцевом буфере, и сложность операций будет разной.

| Структура | Операции | Порядок | В JS | Типичные задачи |
| --- | --- | --- | --- | --- |
| Стек | `push`, `pop`, `peek` | LIFO | массив: `push`/`pop`/`at(-1)` | скобки, отмена (undo), DFS, монотонный стек, разбор выражений |
| Очередь | `enqueue`, `dequeue` | FIFO | нет: указатель головы, кольцевой буфер, два стека | BFS, планировщик задач, буфер событий, rate limiting |
| Дек | вставка и удаление с обоих концов | любой | нет: кольцевой буфер | максимум в скользящем окне, палиндромы, work stealing |
| Приоритетная очередь | `push`, `pop` минимума, `peek` | по приоритету | нет: бинарная куча | top-K, слияние k списков, Дейкстра, планирование по дедлайну |

**Почему массив хорош как стек.** `push` и `pop` работают с концом массива и ничего не сдвигают. `push` при заполнении буфера перевыделяет его с запасом, поэтому он амортизированно O(1) ([подробнее](./complexity.md)). Спецификация ECMAScript описывает `pop` как чтение и удаление элемента `length − 1`, а `push` — как запись по индексу `length`. `pop` на пустом массиве возвращает `undefined`, а не бросает ошибку: это удобно в задаче про скобки, но опасно, если в стеке могут лежать сами `undefined`.

### Стек вызовов — тоже стек

Каждый вызов функции кладёт на **стек вызовов** (call stack) запись: контекст исполнения с локальными переменными и адресом возврата ([подробнее](../javascript/functions-and-this.md)). Возврат снимает её. Поэтому рекурсия — это неявный стек, а глубина рекурсии — его размер. Стек вызовов ограничен: в Node 26 пустая рекурсивная функция падает с `RangeError: Maximum call stack size exceeded` примерно на 12 500 кадрах. Чем больше локальных переменных, тем меньше кадров. Хвостовые вызовы в V8 стек не экономят ([подробнее](./complexity.md)).

Отсюда приём: обход глубины, неизвестной заранее, — вложенные комментарии, JSON с сервера, DOM — переписывают на **явный стек**. Массив живёт в куче и ограничен только памятью. Порядок обработки при этом сохраняется, если класть детей в обратном порядке ([подробнее](./trees-and-graphs.md)).

### Очередь: почему не `shift`

По спецификации `shift` удаляет нулевой элемент и переписывает все остальные на позицию влево: O(n) шагов. Цикл `while (q.length) q.shift()` — Θ(n²). В V8 есть оптимизация left-trimming: для небольших массивов движок переносит начало объекта вместо сдвига, но после порога (буфер больше 128 КБ) этого нет ([подробнее](./complexity.md)).

> [!WARNING]
> Замер в Node 26: разобрать очередь из 100 000 чисел `shift`-ом — около 9 с, указателем головы — около 1 мс, двумя стеками — около 2 мс. BFS-подобный цикл «один `shift`, два `push`» на 300 000 элементов занял 20 с. Это деталь V8, а не гарантия: на 10 000 элементах `shift` быстрый, и тесты на маленьких данных проблему не покажут.

Три замены:

1. **Указатель головы.** Массив растёт только в конец, `dequeue` двигает индекс `head`. Когда мёртвый префикс занимает половину массива, массив сжимают через `slice(head)`. Это O(n) раз на ~n операций, то есть амортизированно O(1). Без сжатия массив растёт бесконечно, а прочитанные элементы удерживаются от сборщика мусора ([подробнее](../javascript/memory-and-gc.md)). Реализация — в [«Оценке сложности»](./complexity.md).
2. **Кольцевой буфер** (ring buffer). Массив фиксированной ёмкости, `head` и `size`, индексы берутся по модулю ёмкости. При заполнении буфер удваивают и переписывают элементы по порядку. Это лучший вариант для дека: обе стороны O(1). Ёмкость-степень двойки позволяет заменить `%` на `& (cap − 1)`.
3. **Два стека.** `enqueue` кладёт во входной стек. `dequeue` берёт из выходного, а если он пуст — перекладывает туда весь входной (порядок переворачивается). Каждый элемент перекладывается ровно один раз, поэтому амортизированно O(1), но отдельный `dequeue` может стоить O(n). Это классический вопрос на интервью и основа персистентных очередей в функциональных языках.

Связный список тоже даёт O(1) на обоих концах, но в JS он проигрывает массиву по константам: объект-узел на каждый элемент, указатели, промахи кэша. Его выбирают, когда нужно удаление из середины по ссылке на узел — как в LRU-кэше с гарантированным O(1).

### Монотонный стек

**Монотонный стек** хранит индексы так, что значения по ним строго убывают (или возрастают). Новый элемент выталкивает с вершины всё, что меньше его, и для каждого вытолкнутого он и есть «следующий больший». Это решает семейство задач «для каждого элемента найти ближайший больший или меньший справа или слева»: следующий тёплый день, акции (stock span), наибольший прямоугольник в гистограмме, вода между столбцами.

Вложенный `while` не делает алгоритм квадратичным: каждый индекс кладётся на стек один раз и снимается не больше одного раза. Всего 2n операций — O(n) времени и O(n) памяти в худшем случае (монотонно убывающий вход). Это та же амортизация, что у скользящего окна ([подробнее](./arrays-strings-hashing.md)).

**Монотонный дек** — то же, но с удалением с головы. Он даёт максимум в скользящем окне за O(n): голова — индекс максимума, хвост выталкивает меньшие элементы, а голова уходит, когда выпадает из окна (задача 3).

### Бинарная куча и приоритетная очередь

**Бинарная куча** (binary heap) — полное двоичное дерево, где каждый родитель не больше своих детей (min-heap). Дерево хранится в массиве без указателей: у узла `i` дети — `2i + 1` и `2i + 2`, родитель — `(i − 1) >> 1`. Минимум всегда в `a[0]`.

- **`push`**: положить в конец и **всплыть** (sift up) — менять местами с родителем, пока он больше. O(log n).
- **`pop`**: забрать корень, на его место поставить последний элемент и **погрузить** (sift down) — менять с меньшим из детей. O(log n).
- **`peek`**: O(1).
- **Построение из массива** (heapify): sift down для всех узлов от `⌊n/2⌋ − 1` до 0. Это O(n), а не O(n log n): большинство узлов — у листьев, и погружаются они на одну-две ступени. Сумма высот всех узлов — O(n) (CLRS, гл. 6).

Куча **не упорядочена целиком**: обход массива не даёт сортировку, а поиск произвольного элемента — O(n). Она **не стабильна**: элементы с равным приоритетом выходят в произвольном порядке. Если нужен FIFO среди равных (задачи планировщика), в ключ добавляют порядковый номер вставки: `(a, b) => a.p - b.p || a.seq - b.seq`.

Альтернатива «отсортировать массив после каждой вставки» стоит O(n log n) на операцию, а вставка бинарным поиском со `splice` — O(n) ([подробнее](./sorting-and-searching.md)). Это приемлемо для десятков элементов, но не для потока.

**Top-K за O(n log k).** Чтобы найти k наибольших из n, держат **min**-кучу размера k: её корень — наименьший из лучших k. Новый элемент больше корня — заменяет его. Память O(k), а данные можно читать потоком. Сортировка всего массива — O(n log n) и O(n) памяти.

### LRU-кэш на `Map`

**LRU** (least recently used) вытесняет запись, к которой дольше всего не обращались. Классическая реализация — хеш-таблица плюс двусвязный список: таблица находит узел за O(1), список переносит его в «свежий» конец и отдаёт «старый» конец за O(1).

В JS список не нужен: `Map` обходится в **порядке вставки** ([подробнее](./arrays-strings-hashing.md)). Самая старая запись — первая в `map.keys()`. Чтобы «освежить» ключ, его удаляют и вставляют заново. Только `set` недостаточно: по спецификации `Map.prototype.set` для существующего ключа меняет значение **на месте**, позиция не меняется.

> [!WARNING]
> В V8 удалённая запись `Map` оставляет «дырку» до перестройки таблицы, а новый итератор начинает обход с начала и перешагивает все дырки. LRU удаляет как раз из начала, поэтому `map.keys().next()` дорожает с ростом ёмкости. В Node 26 вытеснение при ёмкости 1000 стоило ~0,3 мкс, при 10 000 — ~4,7 мкс, при 100 000 — ~35 мкс на операцию. Для небольших кэшей это неважно. Для больших помогает **один долгоживущий итератор**: итераторы `Map` «живые», и удалённые записи до его позиции он больше не перешагивает — ~0,07 мкс независимо от ёмкости. Гарантированное O(1) даёт только своя реализация на двусвязном списке.

Это не учебный пример: `<KeepAlive max>` во Vue 3.5 хранит ключи закэшированных компонентов в `Set`. Обращение делает `keys.delete(key)` и `keys.add(key)`, а при переполнении вытесняется `keys.values().next().value` — ровно этот приём. Так же ограничивают кэш мемоизации — см. тему [curry, compose, memoize, once](../live-coding/function-utilities.md).

### Очереди в event loop и во Vue

Event loop — набор очередей ([подробнее](../javascript/event-loop.md)). Очередь микрозадач — честная FIFO: промис, поставленный в микрозадаче, выполнится в этом же цикле, после уже стоящих. Очередей задач несколько, и между ними браузер выбирает сам, поэтому порядок `setTimeout` и события ввода не гарантирован. Внутри одной очереди задач порядок FIFO.

Планировщик Vue — тоже очередь, но **упорядоченная**. `queueJob` кладёт задачу в конец, если её `id` не меньше последнего, иначе вставляет бинарным поиском (`findInsertionIndex`) и `splice`. Так родительский компонент обновляется раньше дочернего. А `flushJobs` разбирает очередь не `shift`-ом, а индексом `flushIndex` — указателем головы — и в конце обнуляет массив. Повторная постановка одной задачи отсекается флагом: очередь работает как множество с порядком.

## Примеры

```js
// Recursion -> explicit stack: pre-order DFS without call stack limits
function* walk(root) {
  const stack = [root];
  while (stack.length) {
    const node = stack.pop();
    yield node;
    // push children reversed so the first child is processed first
    for (let i = node.children.length - 1; i >= 0; i--) stack.push(node.children[i]);
  }
}
```

```js
// Queue on two stacks: each element moves from `in` to `out` once — O(1) amortized
class StackQueue {
  #in = [];
  #out = [];

  enqueue(value) {
    this.#in.push(value);
  }

  dequeue() {
    if (this.#out.length === 0) {
      while (this.#in.length) this.#out.push(this.#in.pop());
    }
    return this.#out.pop(); // undefined when empty
  }

  get size() {
    return this.#in.length + this.#out.length;
  }
}
```

```js
// Deque on a ring buffer: O(1) at both ends, O(n) only on growth
class Deque {
  #buf = new Array(8); // capacity is a power of two
  #head = 0;
  #size = 0;

  get size() {
    return this.#size;
  }

  #index(i) {
    return (this.#head + i) & (this.#buf.length - 1);
  }

  #grow() {
    const next = new Array(this.#buf.length * 2);
    for (let i = 0; i < this.#size; i++) next[i] = this.#buf[this.#index(i)];
    this.#buf = next;
    this.#head = 0;
  }

  pushBack(value) {
    if (this.#size === this.#buf.length) this.#grow();
    this.#buf[this.#index(this.#size++)] = value;
  }

  pushFront(value) {
    if (this.#size === this.#buf.length) this.#grow();
    this.#head = this.#index(-1);
    this.#buf[this.#head] = value;
    this.#size++;
  }

  popFront() {
    if (this.#size === 0) return undefined;
    const value = this.#buf[this.#head];
    this.#buf[this.#head] = undefined; // let GC collect the value
    this.#head = this.#index(1);
    this.#size--;
    return value;
  }

  popBack() {
    if (this.#size === 0) return undefined;
    const i = this.#index(--this.#size);
    const value = this.#buf[i];
    this.#buf[i] = undefined;
    return value;
  }
}
```

```js
// Min-heap with a custom comparator: push/pop O(log n), peek O(1)
class MinHeap {
  #a = [];
  #less;

  constructor(less = (x, y) => x < y) {
    this.#less = less;
  }

  get size() {
    return this.#a.length;
  }

  peek() {
    return this.#a[0];
  }

  push(value) {
    const a = this.#a;
    a.push(value);
    let i = a.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (!this.#less(a[i], a[parent])) break;
      [a[i], a[parent]] = [a[parent], a[i]];
      i = parent;
    }
  }

  pop() {
    const a = this.#a;
    if (a.length === 0) return undefined;
    const top = a[0];
    const last = a.pop();
    if (a.length > 0) {
      a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1;
        const r = l + 1;
        let min = i;
        if (l < a.length && this.#less(a[l], a[min])) min = l;
        if (r < a.length && this.#less(a[r], a[min])) min = r;
        if (min === i) break;
        [a[i], a[min]] = [a[min], a[i]];
        i = min;
      }
    }
    return top;
  }
}

// Top-K largest: min-heap of size k — O(n log k) time, O(k) memory
function topK(nums, k) {
  const heap = new MinHeap();
  for (const x of nums) {
    if (heap.size < k) heap.push(x);
    else if (x > heap.peek()) {
      heap.pop();
      heap.push(x);
    }
  }
  const result = [];
  while (heap.size) result.push(heap.pop());
  return result.reverse();
}
topK([3, 1, 5, 12, 2, 11], 3); // [12, 11, 5]
```

## Вопросы с интервью

::: details Почему очередь на shift — плохая идея и что использовать вместо неё
По спецификации `shift` сдвигает все оставшиеся элементы: O(n) за вызов, Θ(n²) за разбор очереди. В V8 маленькие массивы спасает left-trimming, но после порога в 128 КБ буфера `shift` честно линейный: в Node 26 очередь из 100 000 элементов разбирается около 9 с против миллисекунды у альтернатив. На тестах с маленькими данными этого не видно. Замены: указатель головы со сжатием мёртвого префикса (амортизированно O(1)), кольцевой буфер (O(1), подходит и для дека), два стека (амортизированно O(1), каждый элемент перекладывается один раз). Для BFS на интервью достаточно массива и индекса `head`.
:::

::: details Как сделать очередь на двух стеках и какая у неё сложность
Входной стек принимает `enqueue`. `dequeue` берёт из выходного, а когда он пуст — перекладывает в него весь входной, переворачивая порядок. Отдельный `dequeue` может стоить O(n), но каждый элемент за свою жизнь проходит три шага: `push` во входной, перекладку, `pop` из выходного. Поэтому n операций стоят O(n) — амортизированно O(1) на операцию. Амортизация — не среднее по случайным входам, а гарантия для любой последовательности. Но она не защищает отдельную операцию от задержки, и в системе реального времени это может быть важно.
:::

::: details Как связаны рекурсия и стек и когда рекурсию переписывают на явный стек
Каждый вызов кладёт кадр на стек вызовов, и рекурсия использует его как неявный стек. Стек вызовов мал: в Node 26 примерно 12 500 кадров для пустой функции, дальше `RangeError: Maximum call stack size exceeded`. V8 не оптимизирует хвостовые вызовы, так что хвостовая рекурсия не спасает. Если глубина зависит от данных — дерево комментариев, вложенный JSON, длинный связный список, — DFS переписывают на массив-стек в куче. Для pre-order детей кладут в обратном порядке, для post-order нужен флаг «дети уже обработаны» или второй стек.
:::

::: details Что такое монотонный стек и почему он работает за O(n)
Стек индексов, значения по которым строго монотонны. Новый элемент выталкивает с вершины все меньшие (для «следующего большего»), и для каждого вытолкнутого ответ — текущий индекс. Остальные ждут на стеке: для них больший ещё не встретился. Вложенный `while` не даёт O(n²): каждый индекс входит в стек один раз и выходит не больше одного раза, всего 2n операций. Сигнал в условии: «для каждого элемента ближайший больший или меньший слева или справа», «сколько дней до…», «площадь под гистограммой».
:::

::: details Как устроена бинарная куча и почему heapify работает за O(n)
Полное двоичное дерево в массиве: дети узла `i` — `2i + 1` и `2i + 2`, родитель — `(i − 1) >> 1`, каждый родитель не больше детей. `push` добавляет в конец и всплывает, `pop` ставит последний элемент в корень и погружает его, обе операции O(log n). Построение из готового массива погружает узлы снизу вверх. Высота узла, а значит и цена погружения, мала у большинства узлов: половина узлов — листья (0 шагов), четверть — 1 шаг и так далее. Сумма даёт O(n). Куча не стабильна и не поддерживает поиск: для FIFO среди равных приоритетов добавляют порядковый номер, для изменения приоритета хранят `Map` «элемент → индекс».
:::

::: details Как найти k наибольших элементов из миллиона и почему min-кучей
Min-куча размера k хранит текущих лучших k, а её корень — худший из них. Элемент больше корня вытесняет корень. Итого O(n log k) времени и O(k) памяти, и вход можно читать потоком, не держа в памяти. Max-куча на всех n элементах дала бы O(n + k log n) времени, но O(n) памяти. Сортировка — O(n log n) и O(n). Если k близко к n, проще сортировка. Если нужен только k-й элемент на массиве в памяти, есть quickselect — O(n) в среднем.
:::

::: details Как реализовать LRU-кэш в JavaScript и в чём подвох Map
`Map` хранит порядок вставки, поэтому старейшая запись — первая в `keys()`. `get` переставляет ключ в конец через `delete` и `set`: просто `set` для существующего ключа позицию не меняет. `set` при переполнении удаляет `keys().next().value`. Подвох в V8: удалённые записи оставляют дырки до перестройки таблицы, а новый итератор перешагивает их с начала, так что вытеснение дорожает с ёмкостью (~35 мкс при 100 000 записей в Node 26). Лечится одним долгоживущим итератором или своей реализацией на `Map` плюс двусвязный список с гарантированным O(1). Пример из жизни — `<KeepAlive max>` во Vue: `Set` ключей и `keys.values().next()` для вытеснения.
:::

## Задачи

### 1. Правильная скобочная последовательность · легко

Дана строка из скобок `()[]{}` и других символов. Проверьте, что скобки сбалансированы и правильно вложены: `'{[()]}'` и `'a(b)c'` — да, `'([)]'`, `'('` и `']'` — нет.

::: details Решение и разбор
Открывающая скобка кладётся на стек. Закрывающая должна совпасть с вершиной: последняя открытая закрывается первой — это и есть LIFO. В конце стек должен быть пуст.

```js
function isValid(s) {
  const pairs = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if (ch === '(' || ch === '[' || ch === '{') stack.push(ch);
    else if (ch in pairs && stack.pop() !== pairs[ch]) return false;
  }
  return stack.length === 0;
}
```

Крайние случаи: пустая строка — `true`. Закрывающая скобка на пустом стеке — `pop` вернёт `undefined`, сравнение с открывающей даст `false`. Незакрытая открывающая — стек не пуст в конце. `ch in pairs` безопасен для символов вроде `'t'`, но для пользовательских ключей вроде `'constructor'` объект с прототипом соврал бы ([подробнее](./arrays-strings-hashing.md)). Здесь ключи — одиночные символы, и унаследованных имён длиной в один символ нет. Надёжнее `Map` или `Object.hasOwn`. Если скобка одного вида, стек вырождается в счётчик: O(1) памяти.

Сложность: O(n) времени, O(n) памяти.
:::

### 2. Сколько дней до потепления · средне

Дан массив температур по дням. Для каждого дня верните, через сколько дней станет строго теплее, или 0, если не станет: `[73, 74, 75, 71, 69, 72, 76, 73]` → `[1, 1, 4, 2, 1, 1, 0, 0]`.

::: details Решение и разбор
Наивно — для каждого дня искать вправо: O(n²) на убывающем входе. Монотонный стек хранит индексы дней, для которых тёплый день ещё не найден. Температуры по ним не возрастают снизу вверх. Новый день выталкивает все более холодные дни с вершины и записывает им ответ.

```js
function daysUntilWarmer(temps) {
  const result = new Array(temps.length).fill(0);
  const stack = []; // indices of days still waiting for a warmer day
  for (let i = 0; i < temps.length; i++) {
    while (stack.length && temps[stack.at(-1)] < temps[i]) {
      const j = stack.pop();
      result[j] = i - j;
    }
    stack.push(i);
  }
  return result; // days left on the stack keep 0
}
```

Строгое `<` важно: равная температура «теплее» не считается, и `[5, 5, 5]` даёт нули. Хранить на стеке нужно индексы, а не значения: по индексу видны и температура, и расстояние. Каждый индекс входит и выходит один раз — O(n), хотя циклы вложены.

Сложность: O(n) времени, O(n) памяти.
:::

### 3. Максимум в скользящем окне · сложно

Дан массив `nums` и размер окна `k`. Верните максимум каждого окна длины `k`: `[1, 3, -1, -3, 5, 3, 6, 7]`, `k = 3` → `[3, 3, 5, 5, 6, 7]`.

::: details Решение и разбор
`Math.max(...window)` на каждом шаге — O(n·k). Куча с ленивым удалением — O(n log n). Монотонный дек даёт O(n): в нём индексы с убывающими значениями. Голова — индекс максимума окна. Новый элемент выталкивает с хвоста все не большие себя: они старше и меньше, так что максимумом уже не станут. Голова уходит, когда выпадает за левую границу окна.

```js
function maxSlidingWindow(nums, k) {
  const result = [];
  const deque = new Array(nums.length); // indices; values strictly decrease head -> tail
  let head = 0;
  let tail = 0;
  for (let i = 0; i < nums.length; i++) {
    if (head < tail && deque[head] <= i - k) head++; // left the window
    while (head < tail && nums[deque[tail - 1]] <= nums[i]) tail--;
    deque[tail++] = i;
    if (i >= k - 1) result.push(nums[deque[head]]);
  }
  return result;
}
```

Дек сделан на массиве с двумя индексами: каждый индекс попадает в него один раз, так что `head` и `tail` не перегоняют `nums.length`, и кольцевой буфер не нужен. Голова уходит не больше чем на одну позицию за шаг, потому что окно сдвигается на один элемент. При `k > nums.length` результат пуст, при `k = 1` — копия входа. Равные значения выталкиваются (`<=`), чтобы в деке оставался более свежий индекс. Решение проверено на случайных массивах против перебора.

Сложность: O(n) времени, O(k) памяти под живую часть дека (массив выделен на n для простоты).
:::

### 4. Слияние k отсортированных массивов · сложно

Даны k отсортированных по возрастанию массивов общей длиной n. Слейте их в один отсортированный: `[[1, 4, 5], [1, 3, 4], [2, 6]]` → `[1, 1, 2, 3, 4, 4, 5, 6]`. Это ядро внешней сортировки и слияния логов из нескольких источников.

::: details Решение и разбор
`lists.flat().sort()` — O(n log n) и игнорирует, что массивы уже отсортированы. Попарное слияние подряд — O(n·k). Куча хранит по одному «текущему» элементу из каждого массива. Минимум кучи — следующий элемент результата. После его извлечения в кучу кладётся следующий элемент из того же массива. Используется `MinHeap` из примеров.

```js
function mergeK(lists) {
  const heap = new MinHeap((a, b) => a.value < b.value);
  lists.forEach((list, li) => {
    if (list.length) heap.push({ value: list[0], li, i: 0 });
  });
  const result = [];
  while (heap.size) {
    const { value, li, i } = heap.pop();
    result.push(value);
    if (i + 1 < lists[li].length) heap.push({ value: lists[li][i + 1], li, i: i + 1 });
  }
  return result;
}
```

В куче не больше k элементов, поэтому каждая из n операций стоит O(log k). Пустые массивы и пустой список массивов отсекаются условием `list.length`. Компаратор `<` не гарантирует порядок равных из разных массивов. Если он важен (стабильное слияние), сравнивайте `a.value - b.value || a.li - b.li`. Альтернатива без кучи — слияние «турниром» попарно: тоже O(n log k), но O(n) дополнительной памяти на промежуточные массивы.

Сложность: O(n log k) времени, O(k) памяти без учёта результата.
:::

### 5. LRU-кэш · средне

Реализуйте `LRUCache(capacity)` с методами `get(key)` и `set(key, value)` за O(1). При переполнении вытесняется запись, к которой дольше всего не обращались. `get` тоже считается обращением.

::: details Решение и разбор
`Map` хранит порядок вставки, поэтому первая запись — самая давняя. Обращение переставляет ключ в конец: `delete`, затем `set`.

```js
class LRUCache {
  #map = new Map();
  #capacity;

  constructor(capacity) {
    this.#capacity = capacity;
  }

  get(key) {
    if (!this.#map.has(key)) return undefined;
    const value = this.#map.get(key);
    this.#map.delete(key); // re-insert to move the key to the "fresh" end
    this.#map.set(key, value);
    return value;
  }

  set(key, value) {
    this.#map.delete(key); // set() alone would keep the old position
    this.#map.set(key, value);
    if (this.#map.size > this.#capacity) {
      this.#map.delete(this.#map.keys().next().value); // the oldest key
    }
    return this;
  }
}
```

Проверка через `has`, а не `get(key) !== undefined`: иначе закэшированный `undefined` неотличим от промаха. На интервью обычно спрашивают продолжение. Первое — «а если `Map` без порядка?»: тогда `Map` ключ → узел двусвязного списка, `get` переносит узел в голову, вытеснение снимает хвост, всё O(1) без оговорок. Второе — «а TTL?»: хранить время записи и проверять его в `get`. Третье — подвох V8 из теории: при большой ёмкости `keys().next()` перешагивает дырки от удалённых записей, и вытеснение замедляется. Это лечится долгоживущим итератором `#oldest = this.#map.keys()`: удалённые ключи до его позиции он больше не посещает, а переставленные ключи уходят в конец, за его позицию.

Сложность: O(1) в среднем на операцию (хеш-таблица), O(capacity) памяти.
:::
