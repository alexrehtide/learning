# Сортировки и бинарный поиск

> **Коротко.** `Array.prototype.sort` без компаратора сравнивает **строки**, поэтому числа сортируют компаратором `(a, b) => a - b`. Компаратор обязан быть согласованным, иначе порядок не определён спецификацией. С ES2019 сортировка стабильна, с ES2023 есть немутирующий `toSorted`. В V8 под капотом TimSort: O(n log n) в худшем случае и O(n) на уже упорядоченных данных. Быстрее O(n log n) сортировку сравнениями не сделать, обойти оценку можно только без сравнений (counting, radix). Бинарный поиск находит границу монотонного условия за O(log n): lower/upper bound, точка вставки, «поиск по ответу». Встроенного бинарного поиска в JS нет, `indexOf` и `find` — линейные.

**Связанные темы:** [Оценка сложности](./complexity.md), [Массивы, строки и хеш-таблицы](./arrays-strings-hashing.md), [Стеки и очереди](./stacks-and-queues.md), [Функциональные приёмы и иммутабельность](../javascript/functional-programming.md), [Оптимизация runtime и профилирование](../performance/runtime.md), [Производительность Vue и Nuxt](../performance/vue-performance.md), [Рекурсия и динамическое программирование](./recursion-and-dp.md)

## Теория

### Контракт `Array.prototype.sort`

Спецификация описывает не алгоритм, а наблюдаемое поведение:

1. Если `comparefn` не `undefined` и не функция — `TypeError` (`[].sort(null)` тоже бросает).
2. Из массива собираются **существующие** элементы, дырки пропускаются ([подробнее](./arrays-strings-hashing.md)).
3. `undefined` всегда уходят в конец, **компаратор для них не вызывается**: `[3, undefined, 1].sort(cmp)` передаст в `cmp` только пару `1` и `3`.
4. Остальные упорядочиваются вызовами `SortCompare`. Без компаратора оба значения приводятся `ToString` и сравниваются по code units: `[10, 9, 1, 2].sort()` — `[1, 10, 2, 9]`. С компаратором результат приводится `ToNumber`: отрицательное — `a` раньше, положительное — `b` раньше, `0` и `NaN` — равны.
5. Отсортированное записывается обратно в начало массива, хвост на месте бывших дырок **удаляется**: `[3, undefined, , 1].sort()` — `[1, 3, undefined, <1 empty item>]`. Возвращается тот же массив.

**Стабильность** обязательна с ES2019: элементы, равные по компаратору, сохраняют исходный порядок. Благодаря этому сортировка таблицы сначала по городу, потом по фамилии даёт «по фамилии, внутри — по городу».

**Согласованный компаратор** (consistent comparator) — одинаковый ответ для одной пары, антисимметрия (`cmp(a, b) < 0` ⇔ `cmp(b, a) > 0`) и транзитивность, в том числе транзитивность равенства. Если компаратор не согласован, спецификация не бросает ошибку: **порядок определяется реализацией**. Три частых нарушения:

- **`(a, b) => a > b`** возвращает `true`/`false`, то есть `1`/`0`, и никогда не отрицательное. В Node 26 такие массивы остаются как были: `[3, 1, 2]` → `[3, 1, 2]`.
- **`a - b` с `NaN`.** `NaN - x` — `NaN`, а он читается как «равны». `NaN` оказывается «равен» и 1, и 3, хотя 1 < 3 — транзитивность сломана: `[3, NaN, 1, 2].sort((a, b) => a - b)` в Node 26 не меняет массив. Числа с `NaN` сначала фильтруют или явно отправляют в конец.
- **Перемешивание через `() => Math.random() - 0.5`.** Это не случайная перестановка. В Node 26 на 600 000 запусков `[1, 2, 3]` порядки `123` и `213` выпадают вдвое чаще остальных, а в массиве из 10 элементов `0` остаётся первым в 19,5 % случаев вместо 10 %. Правильно — тасование Фишера — Йетса за O(n).

`toSorted` (ES2023) — то же, но без мутации: возвращает новый **плотный** массив, дырки в нём становятся `undefined` и тоже уходят в конец. Это то, что нужно в `computed` над реактивным массивом ([подробнее](../javascript/functional-programming.md)). У типизированных массивов `sort` без компаратора — **числовой**: `-0` перед `+0`, `NaN` в конце.

### Строки для пользователя: `Intl.Collator`

Сравнение по code units пользователю не подходит: `'Яблоко'` встаёт раньше `'апельсин'`, `'ё'` — после `'ж'`, а `'file10'` — раньше `'file2'` ([подробнее](./arrays-strings-hashing.md)). Языковое сравнение даёт `localeCompare` или `Intl.Collator` (ECMA-402):

- **`new Intl.Collator('ru')`** — `ё` между `е` и `ж`, кириллица и латиница по правилам локали, регистр учитывается в последнюю очередь.
- **`numeric: true`** — числа в строке сравниваются как числа: `file2` раньше `file10`.
- **`sensitivity: 'base'`** — `'а'`, `'А'` и `'á'` равны. В CLDR `ё` — вариант `е`, поэтому `'е'` и `'ё'` при `base` тоже равны. Для фильтра это хорошо, а для сортировки равные значения упорядочит стабильность.
- **`caseFirst: 'upper'`** — заглавные раньше строчных при прочих равных.

> [!TIP]
> Создавайте `Intl.Collator` **один раз** и передавайте `collator.compare` в `sort`. `localeCompare` с локалью и опциями каждый раз заново разрешает их. Замер в Node 26 на 100 000 строк: без компаратора — 20 мс, `collator.compare` — 100 мс, `a.localeCompare(b)` — 140 мс, `a.localeCompare(b, 'ru')` — 240 мс.

### Дорогой ключ: decorate-sort-undecorate

Компаратор вызывается O(n log n) раз, и всё, что он вычисляет, — тоже. Сортировка 1000 строк компаратором с `toLowerCase()` внутри в Node 26 вызвала ключ 25 600 раз. Если ключ дорогой (нормализация, парсинг даты, `getBoundingClientRect`), его считают заранее: `map` в пары `[key, value]`, сортировка пар, `map` обратно. Это **decorate-sort-undecorate** (преобразование Шварца): 1000 вызовов ключа вместо 25 600 за счёт O(n) памяти.

### Что внутри V8: TimSort

> [!WARNING]
> Алгоритм — деталь реализации. До V8 7.0 (Chrome 70, 2018) `sort` был quick sort для массивов длиннее 10 элементов и сортировкой вставками для коротких. Quick sort нестабилен, и это было видно на практике. С 7.0 V8 использует **TimSort**, написанный на Torque. Другие движки тоже стабильны, но алгоритмы у них свои.

TimSort (Тим Питерс, Python, 2002) рассчитан на реальные данные, которые часто частично упорядочены:

1. Массив режется на **runs** — уже отсортированные отрезки. Строго убывающий run разворачивается на месте (нестрого убывающий развернуть нельзя: сломается стабильность).
2. Короткие runs дополняются до `minrun` (32–64 элемента) **бинарными вставками**: на малых n вставки быстрее слияния за счёт констант.
3. Runs сливаются попарно со стеком, инварианты которого держат слияния сбалансированными. При слиянии работает **galloping**: если один run много раз подряд «выигрывает», граница ищется экспоненциальным и бинарным поиском, а не по одному элементу.

Итог: O(n log n) в худшем случае, O(n) на отсортированном или развёрнутом массиве, стабильно, до n/2 дополнительной памяти. Замер числа вызовов компаратора в Node 26 на 1000 элементах: отсортированный — 999, развёрнутый — 999, две отсортированные половины — 1998, 10 случайных замен — около 1600, случайный — около 8600. Нижняя граница для случайного входа — log₂(1000!) ≈ 8530, так что TimSort почти оптимален и по сравнениям.

### Нижняя оценка O(n log n)

Сортировка **сравнениями** узнаёт о порядке только из ответов «меньше/больше». Её работу можно нарисовать **деревом решений**: узел — сравнение, лист — одна из перестановок входа. Листьев не меньше n!, иначе две разные перестановки получат одинаковый ответ. Двоичное дерево с n! листьями имеет высоту не меньше log₂(n!), а по формуле Стирлинга log₂(n!) = Θ(n log n). Значит, в худшем случае нужно Ω(n log n) сравнений (CLRS, 8.1).

Обойти оценку можно, если **не сравнивать**, а использовать структуру ключа:

- **Counting sort** — ключи — целые числа из `[0, k)`: посчитать вхождения, префиксные суммы дают начальные позиции, затем раскладка. O(n + k), стабильна. Хороша для статусов, приоритетов, оценок от 1 до 5.
- **Radix sort** — counting sort по разрядам, от младшего к старшему. O(d · (n + b)) для d разрядов по основанию b. Корректность держится на стабильности каждого прохода.
- **Bucket sort** — для равномерно распределённых чисел: разложить по n корзинам, корзины отсортировать вставками. В среднем O(n), в худшем как сортировка внутри корзины.

### Merge sort и quick sort

| | Merge sort | Quick sort |
| --- | --- | --- |
| Время | Θ(n log n) всегда | O(n log n) в среднем, O(n²) в худшем |
| Память | O(n) на слияние | O(log n) стека при рекурсии в меньшую часть |
| Стабильность | да, если при равенстве брать из левой половины | нет |
| Сильные стороны | предсказуемость, связные списки, внешняя сортировка | на месте, кэш-дружелюбна, малые константы |

Худший случай quick sort — неудачный опорный элемент (pivot). С pivot «первый элемент» на уже отсортированном массиве каждое разбиение отщепляет один элемент: n уровней рекурсии и n²/2 сравнений. В Node 26 такая реализация на отсортированном массиве из 10 000 чисел падает с `RangeError: Maximum call stack size exceeded`. Защита: **случайный pivot** (или медиана трёх), **трёхчастное разбиение** Дейкстры (`< pivot`, `= pivot`, `> pivot`) — иначе массив одинаковых значений снова даёт O(n²), и **рекурсия только в меньшую часть**, а большую — циклом, что ограничивает стек O(log n).

Та же идея разбиения даёт **quickselect** — k-й по величине элемент за O(n) в среднем: рекурсия идёт только в ту часть, где лежит k ([подробнее](./stacks-and-queues.md)).

### Бинарный поиск: инвариант, а не формула

Бинарный поиск работает не только для «найти x в отсортированном массиве». Он находит **границу монотонного условия**: если `pred(a[i])` истинно на префиксе массива и ложно на суффиксе, то первую позицию, где оно ложно, можно найти за ⌈log₂(n + 1)⌉ проверок.

Надёжный шаблон — **полуинтервал** `[lo, hi)` и инвариант: всё левее `lo` удовлетворяет условию, всё начиная с `hi` — нет. Шаг сохраняет инвариант (`lo = mid + 1` или `hi = mid`) и строго сужает интервал, поэтому цикл завершается, когда `lo === hi`, и это ответ. Из него получаются все варианты:

- **lower bound** — первая позиция с `a[i] >= x`, условие `v < x`. Это место вставки `x` перед равными и первое вхождение, если `a[i] === x`.
- **upper bound** — первая позиция с `a[i] > x`, условие `v <= x`. Вставка после равных, число вхождений — `upper − lower`.

Типичные ошибки: смешать закрытый `[lo, hi]` и полуоткрытый интервалы, написать `lo = mid` при `mid`, округлённом вниз (бесконечный цикл на двух элементах), вернуть `-1` там, где нужна точка вставки.

> [!NOTE]
> Знаменитое переполнение `(lo + hi) / 2` в Java и C (Джошуа Блох, 2006) в JS не возникает: числа — double, сумма индексов точна до 2⁵³. Но `(lo + hi) >> 1` приводит к int32 и ломается, начиная с суммы 2³¹: `(2 ** 31 + 2) >> 1` — `-1073741823`. `>>> 1` корректен до 2³², а длина массива не больше 2³² − 1, так что его и используют. `Math.floor((lo + hi) / 2)` безопасен всегда.

### Бинарный поиск по ответу

Если ответ — число в диапазоне `[lo, hi]`, а проверка «подходит ли значение v» **монотонна** (если подходит v, подходит и любое большее), то минимальное подходящее v находится бинарным поиском по значениям, а не по индексам. Цена — O(log(hi − lo)) проверок.

Сигналы в условии: «минимальная вместимость, чтобы успеть за D дней», «максимальный размер, при котором влезает», «минимизировать максимум». Фронтенд-примеры:

- **Подгонка текста под контейнер.** Самый крупный `font-size`, при котором заголовок не переносится. Каждая проверка — замер с layout, поэтому 7 проверок по диапазону 8–128 px вместо 120 подряд.
- **`git bisect`** — бинарный поиск первого плохого коммита: условие «баг есть» монотонно по истории.
- **Разбиение на колонки** с минимальной высотой самой высокой (задача 5).

Для вещественного ответа цикл гоняют фиксированное число итераций (50–60 для double) или до нужной точности, а не до `lo === hi`.

### Фронтенд-кейсы

**Вставка в отсортированный массив.** Бинарный поиск находит место за O(log n), но `splice` сдвигает хвост — вставка всё равно O(n). Это дешевле пересортировки (O(n log n)) и годится для сотен элементов. Для потока вставок с извлечением минимума берут кучу ([подробнее](./stacks-and-queues.md)). Пример из жизни — планировщик Vue 3.5: `queueJob` кладёт задачу в конец, если её `id` не меньше последнего, иначе `queue.splice(findInsertionIndex(id), 0, job)`. `findInsertionIndex` — полуинтервал `[flushIndex + 1, queue.length)`, `middle = (start + end) >>> 1`. По сути это lower bound по `id` с одним исключением: задачи с тем же `id`, помеченные как pre-flush (`watch` с `flush: 'pre'`), остаются впереди новой.

**Виртуальный список.** При фиксированной высоте строки индекс первой видимой — `Math.floor(scrollTop / rowHeight)`. При переменной высоте строят **префиксные суммы** смещений, и строка на высоте `y` — бинарный поиск по ним за O(log n) на событие `scroll` (реализация — [задача 3 в «Оптимизации runtime»](../performance/runtime.md)).

> [!WARNING]
> `useVirtualList` из VueUse 12.8.2 при `itemHeight`-функции на каждый `scroll` ищет первую видимую строку линейным проходом с начала списка, а отступ окна сверху и цель `scrollTo` считает через `slice` и `reduce` — всё O(n). На 100 000 строк переменной высоты это заметно. `@tanstack/vue-virtual` использует бинарный поиск по кэшу измерений.

## Примеры

```js
// Comparators: numbers, several keys, empty values last, locale-aware strings
const byNumber = (a, b) => a - b; // NaN-free input only
const byNumberDesc = (a, b) => b - a;
const collator = new Intl.Collator('ru', { numeric: true });

users.toSorted(
  (a, b) =>
    collator.compare(a.lastName, b.lastName) || // primary key
    b.age - a.age, // secondary key: `||` falls through only on 0
);

// Expensive key: compute it once per element, not once per comparison
const byDate = items
  .map((item) => [Date.parse(item.createdAt), item])
  .sort((a, b) => a[0] - b[0])
  .map(([, item]) => item);
```

```js
// Merge sort: stable, Θ(n log n), O(n) extra memory
function mergeSort(a, cmp = (x, y) => x - y) {
  if (a.length <= 1) return a.slice();
  const mid = a.length >>> 1;
  const left = mergeSort(a.slice(0, mid), cmp);
  const right = mergeSort(a.slice(mid), cmp);
  const out = [];
  let i = 0;
  let j = 0;
  while (i < left.length && j < right.length) {
    // `<= 0` takes from the left on ties: this is what makes it stable
    out.push(cmp(left[i], right[j]) <= 0 ? left[i++] : right[j++]);
  }
  while (i < left.length) out.push(left[i++]);
  while (j < right.length) out.push(right[j++]);
  return out;
}
```

```js
// Quick sort in place: random pivot, 3-way partition, recursion into the smaller part
function quickSort(a, lo = 0, hi = a.length - 1) {
  while (lo < hi) {
    const pivot = a[lo + Math.floor(Math.random() * (hi - lo + 1))];
    let lt = lo; // a[lo..lt) < pivot
    let i = lo; // a[lt..i) === pivot
    let gt = hi; // a(gt..hi] > pivot
    while (i <= gt) {
      if (a[i] < pivot) [a[lt++], a[i++]] = [a[i], a[lt]];
      else if (a[i] > pivot) [a[i], a[gt--]] = [a[gt], a[i]];
      else i++;
    }
    if (lt - lo < hi - gt) {
      quickSort(a, lo, lt - 1);
      lo = gt + 1;
    } else {
      quickSort(a, gt + 1, hi);
      hi = lt - 1;
    }
  }
  return a;
}
```

```js
// Counting sort by a small integer key in [0, k): O(n + k), stable
function countingSort(items, key, k) {
  const start = new Array(k + 1).fill(0);
  for (const item of items) start[key(item) + 1]++;
  for (let i = 1; i <= k; i++) start[i] += start[i - 1]; // first slot of each key
  const out = new Array(items.length);
  for (const item of items) out[start[key(item)]++] = item;
  return out;
}

countingSort(tasks, (t) => t.priority, 5); // priorities 0..4
```

```js
// Binary search as a partition point: first index where `pred` is false
function partitionPoint(a, pred) {
  let lo = 0;
  let hi = a.length; // invariant: pred holds before lo, fails from hi on
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (pred(a[mid])) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

const lowerBound = (a, x) => partitionPoint(a, (v) => v < x); // first a[i] >= x
const upperBound = (a, x) => partitionPoint(a, (v) => v <= x); // first a[i] > x

// Keep an array sorted: O(log n) to find the place, O(n) to shift the tail
const insertSorted = (a, x) => a.splice(upperBound(a, x), 0, x);
```

## Вопросы с интервью

::: details Почему числа без компаратора сортируются неправильно и что не так с компаратором a > b
Без компаратора `sort` приводит элементы к строкам и сравнивает code units: `'10' < '9'`, поэтому `[10, 9, 1, 2].sort()` — `[1, 10, 2, 9]`. Нужен `(a, b) => a - b`. Компаратор должен вернуть число: отрицательное, ноль или положительное. `a > b` возвращает булево, то есть 1 или 0, и никогда «меньше». Это несогласованный компаратор, и спецификация в таком случае оставляет порядок на усмотрение реализации: в Node 26 массив просто не меняется. Та же беда у `a - b` при `NaN` в данных: `NaN` «равен» всему, и транзитивность ломается. Ещё два подвоха: `sort` мутирует массив (в `computed` нужен `toSorted`), а `undefined` уходят в конец без вызова компаратора.
:::

::: details Что такое стабильная сортировка и зачем она нужна на фронтенде
Стабильная сортировка сохраняет исходный порядок элементов, равных по ключу. В JS она гарантирована с ES2019, а в V8 появилась в 7.0 вместе с TimSort. До этого массивы длиннее 10 элементов сортировались нестабильным quick sort. Практический смысл: клик по колонке «Город» в таблице, уже отсортированной по фамилии, оставляет фамилии упорядоченными внутри города. Многоуровневую сортировку можно делать проходами от младшего ключа к старшему, а пагинация по отсортированным данным не перемешивает равные записи между страницами. Куча и quick sort нестабильны. Стабильность из них получают, добавив исходный индекс последним ключом.
:::

::: details Как правильно сортировать строки для пользователя
Через `Intl.Collator` или `localeCompare`, а не через `sort()` без аргументов и не через `<`. Сравнение по code units ставит заглавные раньше строчных, `ё` после `я`, а `file10` раньше `file2`. Коллатор с локалью `ru` знает алфавит, `numeric: true` сравнивает числа в строках как числа, `sensitivity` решает, различать ли регистр и диакритику. Коллатор создают один раз и передают `collator.compare`. `localeCompare` с локалью в каждом вызове заново разрешает опции: в Node 26 на 100 000 строк — 240 мс против 100 мс у коллатора. Для серверного рендеринга локаль указывают явно: иначе сервер и браузер отсортируют по-разному, и гидрация разойдётся.
:::

::: details Какой алгоритм сортировки использует V8 и почему именно его
TimSort, с V8 7.0 (2018), на Torque. Спецификация требует только стабильности и сложность не задаёт. TimSort ищет во входе готовые возрастающие и строго убывающие отрезки (runs), короткие дополняет бинарными вставками до 32–64 элементов и сливает их стеком со сбалансированными слияниями и galloping. Реальные данные часто почти упорядочены: добавили запись в конец, отсортировали по другой колонке. На них TimSort работает за O(n): в Node 26 отсортированный массив из 1000 элементов — 999 сравнений. В худшем случае — O(n log n), стабилен, память — до n/2. Quick sort на месте экономнее по памяти, но нестабилен и имеет худший случай O(n²).
:::

::: details Почему сортировка сравнениями не может быть быстрее n log n
Любой алгоритм, который узнаёт о порядке только сравнениями, можно представить деревом решений: каждое сравнение — развилка, каждый лист — одна перестановка входа. Различимых перестановок n!, значит, листьев не меньше n!, а высота двоичного дерева — не меньше log₂(n!) = Θ(n log n) по Стирлингу. Высота — это число сравнений в худшем случае. Оценку обходят, когда ключ можно использовать как индекс: counting sort за O(n + k) для целых ключей из небольшого диапазона, radix sort по разрядам, bucket sort для равномерно распределённых чисел. На фронтенде это сортировка по статусу, приоритету или дню недели.
:::

::: details Чем quick sort отличается от merge sort и когда что выбирать
Merge sort делит пополам без условий и делает работу при слиянии: всегда Θ(n log n), стабилен, но нужен O(n) буфер. Quick sort делает работу при разбиении относительно pivot: на месте, малые константы, хорошая локальность, O(n log n) в среднем. Но он нестабилен, а при плохом pivot деградирует до O(n²) и рекурсии глубиной n. Наивная реализация с первым элементом в качестве pivot на отсортированных 10 000 числах в Node 26 падает с переполнением стека. Лечение — случайный pivot, трёхчастное разбиение для повторов и рекурсия в меньшую часть. Merge sort выбирают, когда нужны стабильность, гарантия худшего случая, связные списки или внешняя сортировка. Quick sort — для сортировки на месте примитивов. Гибриды берут лучшее: TimSort и introsort.
:::

::: details Как написать бинарный поиск, который не зацикливается и не теряет границы
Думать не о «найти x», а о границе монотонного условия, и держать инвариант. Полуинтервал `[lo, hi)`: левее `lo` условие истинно, начиная с `hi` — ложно. `mid = (lo + hi) >>> 1`. Если условие истинно на `mid`, то `lo = mid + 1`, иначе `hi = mid`. Интервал строго сужается, цикл кончается при `lo === hi`, и это первая позиция, где условие ложно. Условие `v < x` даёт lower bound, `v <= x` — upper bound. Ошибки обычно в смешении стилей: `lo = mid` при округлении вниз зацикливает на двух элементах, `hi = mid - 1` в полуинтервале теряет ответ. Переполнения `mid`, как в Java, в JS нет, но `>> 1` ломается после 2³¹ — поэтому `>>> 1`.
:::

::: details Что такое бинарный поиск по ответу и как его распознать в условии
Это бинарный поиск по значениям ответа, а не по индексам массива. Он применим, если есть проверка «подходит ли значение v», которая монотонна: подходит v — подходит и любое большее (или меньшее). Тогда минимальное подходящее значение находится за O(log диапазона) проверок, и общая сложность — O(n log диапазона), если проверка линейная. Сигналы: «минимальная вместимость», «максимальный размер, при котором влезает», «минимизировать максимальную нагрузку», «за сколько минимум дней». Сама проверка обычно жадная и простая, а трудная часть — увидеть монотонность. Фронтенд-пример — подбор максимального `font-size`, при котором текст не переносится: каждая проверка стоит layout, и log₂ проверок вместо линейного перебора заметно дешевле.
:::

## Задачи

### 1. Первое и последнее вхождение · легко

Дан отсортированный по возрастанию массив с повторами и число `target`. Верните `[first, last]` — индексы первого и последнего вхождения или `[-1, -1]`: `[1, 2, 2, 2, 5]`, `2` → `[1, 3]`. Требование — O(log n).

::: details Решение и разбор
Два бинарных поиска: lower bound даёт первое вхождение, upper bound — позицию сразу за последним. Используется `partitionPoint` из примеров.

```js
function searchRange(a, target) {
  const first = partitionPoint(a, (v) => v < target);
  if (first === a.length || a[first] !== target) return [-1, -1];
  const end = partitionPoint(a, (v) => v <= target);
  return [first, end - 1];
}
```

Проверка `first === a.length` описывает случай, когда `target` больше всех элементов. Формально хватило бы и сравнения (`a[a.length]` — `undefined`), но явная граница читается лучше. Решение «найти любое вхождение и расшириться линейно» вырождается в O(n) на массиве из одинаковых элементов. Число вхождений — `end − first`, и это частый следующий вопрос. Решение проверено против `indexOf`/`lastIndexOf` на 3000 случайных массивов, включая пустой.

Сложность: O(log n) времени, O(1) памяти.
:::

### 2. Объединение пересекающихся интервалов · средне

Даны интервалы `[start, end]` — например, занятые слоты календаря. Объедините пересекающиеся и касающиеся: `[[9, 12], [1, 3], [2, 6], [8, 10], [15, 18]]` → `[[1, 6], [8, 12], [15, 18]]`, `[[1, 4], [4, 5]]` → `[[1, 5]]`. Входной массив менять нельзя.

::: details Решение и разбор
После сортировки по началу пересекающиеся интервалы идут подряд. Текущий интервал либо продлевает последний в результате, либо открывает новый.

```js
function mergeIntervals(intervals) {
  const sorted = intervals.toSorted((a, b) => a[0] - b[0]);
  const result = [];
  for (const [start, end] of sorted) {
    const last = result.at(-1);
    if (last && start <= last[1]) last[1] = Math.max(last[1], end);
    else result.push([start, end]);
  }
  return result;
}
```

`Math.max` обязателен: `[1, 10]` поглощает `[2, 3]`, и конец не должен уменьшиться. `<=` склеивает касающиеся интервалы. Если `[1, 4]` и `[4, 5]` — разные встречи подряд, нужно `<`. `toSorted` и деструктуризация в новые пары защищают вход: `last[1] = …` меняет только массивы результата. Пустой вход даёт `[]`. Решение проверено на 2000 случайных наборах сравнением покрытых точек и проверкой, что результат не пересекается.

Сложность: O(n log n) времени из-за сортировки, O(n) памяти.
:::

### 3. Сортировка таблицы по нескольким колонкам · средне

Реализуйте `sortRows(rows, sortBy)`, где `sortBy` — список `{ key, dir: 'asc' | 'desc' }` в порядке приоритета. Строки сравниваются по правилам русской локали, `file2` раньше `file10`, без учёта регистра. Пустые значения (`null`, `undefined`, `NaN`) всегда внизу, при любом направлении. Равные по всем ключам строки сохраняют исходный порядок. Вход не мутировать.

::: details Решение и разбор
```js
const collator = new Intl.Collator('ru', { numeric: true, sensitivity: 'base' });

function compareValues(a, b) {
  if (typeof a === 'string' && typeof b === 'string') return collator.compare(a, b);
  return a < b ? -1 : a > b ? 1 : 0;
}

const isEmpty = (v) => v == null || Number.isNaN(v);

function sortRows(rows, sortBy) {
  return rows.toSorted((x, y) => {
    for (const { key, dir } of sortBy) {
      const a = x[key];
      const b = y[key];
      if (isEmpty(a) || isEmpty(b)) {
        if (isEmpty(a) && isEmpty(b)) continue;
        return isEmpty(a) ? 1 : -1; // empty values go last in both directions
      }
      const order = compareValues(a, b);
      if (order !== 0) return dir === 'desc' ? -order : order;
    }
    return 0; // equal by all keys: stability keeps the original order
  });
}
```

Главное — чтобы компаратор был согласованным. Пустые значения обрабатываются **до** инверсии направления: если просто умножить общий результат на `-1`, при `desc` они всплывут наверх. `NaN` выделен явно: через `<`/`>` он «равен» всему и ломает транзитивность. `compareValues` вместо `a - b` работает и для дат, и для чисел. Явная проверка `0` вместо `||` позволяет вернуть результат с нужным знаком. Стабильность `toSorted` закрывает последнее требование, а `sensitivity: 'base'` делает `Ёлкин` и `елкин` равными, и их порядок решает исходный. Коллатор создаётся один раз на модуль. Во Vue это `computed(() => sortRows(rows.value, sortBy.value))`: `toSorted` не мутирует реактивный массив, а `sortBy` — тоже зависимость. Проверено в Node 26 на случайных строках с пустыми значениями обоих видов.

Сложность: O(n log n · m) времени, где m — число ключей; O(n) памяти на копию.
:::

### 4. Поиск в повёрнутом отсортированном массиве · средне

Отсортированный массив различных чисел повернули: `[0, 1, 2, 4, 5, 6, 7]` → `[4, 5, 6, 7, 0, 1, 2]`. Найдите индекс `target` за O(log n) или верните `-1`: `0` → `4`, `3` → `-1`.

::: details Решение и разбор
Одна из половин относительно `mid` всегда отсортирована. Если `target` лежит в её диапазоне, ищем там, иначе — в другой.

```js
function searchRotated(a, target) {
  let lo = 0;
  let hi = a.length - 1; // closed interval [lo, hi]
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    if (a[mid] === target) return mid;
    if (a[lo] <= a[mid]) {
      // left half [lo, mid] is sorted
      if (a[lo] <= target && target < a[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {
      // right half [mid, hi] is sorted
      if (a[mid] < target && target <= a[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}
```

Здесь закрытый интервал оправдан: ищем конкретное значение и выходим по равенству. `<=` в `a[lo] <= a[mid]` нужен для случая `lo === mid` (два элемента). Неповёрнутый массив, массив из одного элемента и пустой обрабатываются без особых веток. С **повторами** (`[1, 1, 1, 0, 1]`) задача ломается: при `a[lo] === a[mid] === a[hi]` нельзя понять, какая половина отсортирована. Тогда сдвигают `lo++`, и худший случай — O(n). Это стоит сказать вслух. Решение проверено на 5000 случайных поворотах против `indexOf`.

Сложность: O(log n) времени, O(1) памяти.
:::

### 5. Раскладка карточек по колонкам · сложно

Карточки ленты с высотами `heights` раскладываются в `k` колонок **по порядку**: каждая колонка — непрерывный отрезок списка. Найдите минимально возможную высоту самой высокой колонки: `[7, 2, 5, 10, 8]`, `k = 2` → `18` (`[7, 2, 5] | [10, 8]`).

::: details Решение и разбор
Перебор разбиений экспоненциален. Поиск по ответу: высота `H` подходит, если жадная раскладка «добавлять в колонку, пока влезает» укладывается в `k` колонок. Если подходит `H`, подходит и любая бо́льшая — проверка монотонна. Ответ лежит между самой высокой карточкой и суммой всех.

```js
function minColumnHeight(heights, k) {
  const fits = (limit) => {
    let columns = 1;
    let current = 0;
    for (const h of heights) {
      if (current + h > limit) {
        columns++;
        current = 0;
      }
      current += h;
    }
    return columns <= k;
  };

  let lo = Math.max(0, ...heights); // a column must hold the tallest card
  let hi = heights.reduce((sum, h) => sum + h, 0); // one column holds everything
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (fits(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}
```

Это тот же шаблон «первое значение, где условие истинно»: `hi = mid` сохраняет подходящий кандидат. Жадность корректна: забивать колонку до предела никогда не хуже, чем начать новую раньше. Нижняя граница `max(heights)` гарантирует, что `fits` не попытается положить карточку выше лимита в пустую колонку. `Math.max(0, ...)` даёт 0 на пустом входе, но спред передаёт элементы аргументами и в Node 26 падает с `RangeError` уже на 200 000 элементах — тогда нужен `reduce`. Альтернатива — динамическое программирование за O(k·n²). Решение проверено против полного перебора разбиений на 2000 случайных наборах.

Сложность: O(n log S) времени, где S — сумма высот; O(1) дополнительной памяти.
:::
