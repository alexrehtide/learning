# Оценка сложности

> **Коротко.** Асимптотическая сложность показывает, как растёт число операций (или объём памяти) при росте входа n. Константы и младшие члены отбрасываются. O — верхняя граница, Ω — нижняя, Θ — точная, а на интервью под «O(n)» обычно имеют в виду именно точную оценку худшего случая. Senior-уровень — это умение видеть скрытую стоимость: `shift`, `includes` в цикле, spread аккумулятора в `reduce`. А ещё — отличать гарантии спецификации от поведения V8 и называть сложность и по времени, и по памяти, включая стек рекурсии.

**Связанные темы:** [Функциональные приёмы и иммутабельность](../javascript/functional-programming.md), [Память и сборка мусора](../javascript/memory-and-gc.md), [Конвейер рендеринга: layout, paint, composite](../browser/rendering-pipeline.md), [Оптимизация runtime и профилирование](../performance/runtime.md), [Производительность Vue и Nuxt](../performance/vue-performance.md), [Массивы, строки и хеш-таблицы](./arrays-strings-hashing.md)

## Теория

### Что именно считают

Модель простая: элементарные операции (сравнение, присваивание, арифметика, доступ по индексу) стоят O(1). Сложность алгоритма — число таких операций как функция размера входа. Секунды не считают: они зависят от машины, движка и прогрева JIT. Считают **порядок роста**: что станет со временем работы, если n увеличить в 10 раз.

Поэтому константы и младшие члены отбрасываются: 3n² + 100n + 7 → O(n²). При больших n слагаемое n² доминирует, а множитель 3 — свойство реализации, не алгоритма. Входов может быть несколько, и тогда их не склеивают в один: обход двух массивов — O(n + m), вложенный цикл по ним — O(n · m), и это не O(n²).

### Нотации O, Ω, Θ

Определения из CLRS для функции f(n):

- **O(g)** — верхняя граница: f(n) ≤ c · g(n) для всех n ≥ n₀ при некоторых c > 0 и n₀. Линейный поиск — O(n), и формально также O(n²): верхняя граница может быть грубой.
- **Ω(g)** — нижняя граница: f(n) ≥ c · g(n). Любая сортировка сравнениями — Ω(n log n) в худшем случае: дерево решений с n! листьями имеет высоту log₂(n!) ≈ n log n.
- **Θ(g)** — точная граница: одновременно O(g) и Ω(g).

На интервью пишут «O», а подразумевают Θ: «сортировка слиянием — O(n log n)» значит «ровно порядка n log n». Ответ «O(n³)» про линейный поиск формально верен, но засчитан не будет.

> [!NOTE]
> Нотация и **случай** — разные оси. O/Θ/Ω описывают функцию, а лучший/худший/средний случай выбирают, какую функцию описываем. «Худший случай quicksort — Θ(n²)» и «лучший случай — Θ(n log n)» — обе фразы точны.

### Лучший, средний, худший и амортизированный случай

- **Худший случай** (worst case) — гарантия на любом входе. Его спрашивают по умолчанию.
- **Лучший случай** (best case) почти бесполезен: линейный поиск находит элемент первым шагом, но опираться на это нельзя.
- **Средний случай** (average case) — матожидание по распределению входов. Хеш-таблица в среднем отвечает за O(1), но при массовых коллизиях — за O(n). Распределение входов подбирает атакующий (HashDoS), поэтому движки рандомизируют хеш-функции.
- **Амортизированная оценка** (amortized) — средняя стоимость операции в **любой** последовательности из n операций. Вероятности здесь нет, это гарантия на всю последовательность: дорогие операции редки и оплачены дешёвыми.

Классический пример — `push` в динамический массив. Когда ёмкость исчерпана, движок выделяет больший буфер и копирует элементы за O(n). Если ёмкость растёт **геометрически** (в k раз), то копирований за n вставок не больше n · k/(k − 1), то есть O(n), а одна вставка в среднем стоит O(1). При росте на **константу** вышло бы O(n²) (см. задачу 3).

> [!WARNING]
> В V8 новая ёмкость — `old + (old >> 1) + 16`, то есть рост в 1,5 раза плюс 16 (`JSObject::NewElementsCapacity`). Хеш-таблицы `Map` и `Set` при заполнении перестраиваются с удвоением. Это детали движка, спецификация их не задаёт.

### Сложность по памяти

Различают **вспомогательную память** (auxiliary space — сколько алгоритм выделяет сверх входа) и полную, вместе со входом. На интервью обычно спрашивают вспомогательную, и это стоит проговорить. Результат, который функция обязана вернуть, иногда не считают. Например, «`map` — O(1) дополнительной памяти, не считая результата».

**Стек рекурсии — тоже память.** Каждый незавершённый вызов держит кадр: O(глубина). Рекурсивный обход сбалансированного дерева — O(log n) памяти, вырожденного (списка) — O(n). Стек ограничен: в Node 26 пустая рекурсивная функция падала с `RangeError: Maximum call stack size exceeded` на глубине около 12 500, а функция с пятью аргументами и локальными переменными — около 5 400. Предел задан в байтах, поэтому глубина зависит от размера кадра.

> [!WARNING]
> В ES2015 есть proper tail calls: хвостовой вызов в strict mode не должен расти стеком. Реализован он только в JavaScriptCore (Safari). V8 и SpiderMonkey его не поддерживают, поэтому хвостовая рекурсия в Chrome и Node всё равно расходует O(n) стека. Глубокую рекурсию переписывают на явный стек (см. задачу 5).

Встроенные методы тоже бывают рекурсивными. В Node 26 на массиве с вложенностью 100 000 `arr.flat(Infinity)` и `structuredClone(arr)` падают с `RangeError`, а `JSON.stringify` справляется.

### Что гарантирует спецификация ECMAScript

Почти ничего. Алгоритмы в спецификации описывают наблюдаемое поведение, а не реализацию. Сложность `sort`, `indexOf` или `+` для строк в ней не задана.

Исключение — коллекции. Про `Map`, `Set`, `WeakMap` и `WeakSet` сказано: они «должны быть реализованы хеш-таблицами или другими механизмами, которые в среднем обеспечивают доступ за время, **сублинейное** от числа элементов». Сублинейное — не обязательно O(1): дерево с O(log n) тоже подходит. На практике все движки используют хеш-таблицы, и `has`/`get`/`set`/`delete` в среднем стоят O(1).

Для `sort` спецификация с ES2019 требует **стабильности**: равные элементы сохраняют исходный порядок. В V8 с версии 7.0 (Chrome 70) работает TimSort: O(n log n) в худшем случае, почти O(n) на частично упорядоченных данных. Короткие отрезки он досортировывает вставками. Без компаратора `sort` сравнивает **строки**: `[10, 9, 1, 2].sort()` даёт `[1, 10, 2, 9]`. Компаратор должен быть согласованным: `(a, b) => a > b` возвращает `true`/`false` (то есть 1/0) и никогда не возвращает отрицательное число. Порядок при таком компараторе зависит от реализации, и в V8 массив часто остаётся несортированным.

### Цена встроенных операций в V8

| Операция | Время | Комментарий |
| --- | --- | --- |
| `arr[i]`, `arr.length`, `push`, `pop` | O(1) | `push` — амортизированно |
| `shift`, `unshift`, `splice(i, …)` | O(n) | сдвигаются все элементы после `i` |
| `indexOf`, `includes`, `find`, `some` | O(n) | линейный поиск |
| `slice`, spread `[...a]`, `concat`, `Array.from` | O(k) | k — размер копии |
| `sort` | O(n log n) | TimSort в V8; спецификация сложность не задаёт |
| `Set.has`, `Map.get`/`set`/`delete` | O(1) в среднем | спецификация: «сублинейно» |
| `Object.keys`, `JSON.stringify`, `structuredClone` | O(размер) | обходят всё |
| `str.length`, `str[i]` | O(1) | для «плоской» строки |
| `s += x` | O(1) амортизированно в V8 | см. ниже про ropes |

Две особенности V8 ломают учебные ожидания:

1. **`shift` бывает O(1).** Для массива с буфером до 128 КБ V8 не сдвигает элементы, а переносит начало объекта в куче (left-trimming). В Node 26 очередь из 16 380 элементов разбирается `shift`-ом за ~1 мс, а из 16 400 — за ~290 мс: буфер больше 128 КБ живёт в large object space, и там остаётся честный O(n) на каждый вызов. Это деталь реализации, а не гарантия, поэтому очередь на `shift` — антипаттерн (см. «Стеки и очереди»).
2. **Конкатенация строк — ropes.** `s += x` в V8 создаёт не копию, а `ConsString` — узел дерева из двух половин. Поэтому 10 млн дописываний занимают ~0,4 с, а не часы. Но индексирование, `indexOf`, регулярные выражения и многие другие операции требуют плоской строки, и V8 её «сплющивает» (flatten) за O(n). Цикл «дописать и прочитать» снова становится квадратичным: 100 000 итераций — 0,3 с, 200 000 — 4,7 с.

Отдельно — `str.slice` и `substring`. Для длинных строк V8 создаёт `SlicedString`, ссылку на родителя за O(1), которая держит в памяти весь исходник ([подробнее](../javascript/memory-and-gc.md)).

### Скрытые квадраты

Чаще всего O(n²) появляется в коде, который выглядит линейным:

- `reduce((acc, x) => ({ ...acc, [x.id]: x }), {})` и `reduce((acc, x) => [...acc, x], [])` копируют аккумулятор на каждом шаге. Получается 1 + 2 + … + n = Θ(n²) ([подробнее](../javascript/functional-programming.md)).
- `includes`/`indexOf`/`find` внутри цикла или `filter`. Дедупликация `arr.filter((x, i) => arr.indexOf(x) === i)` — Θ(n²). Замена — `new Set(arr)`.
- `shift`/`unshift`/`splice(0, 1)` в цикле на большом массиве.
- Поиск в шаблоне Vue: `v-for="row in rows"` с `users.find(u => u.id === row.userId)` — это O(n · m) на **каждый рендер**. Лечится `computed`-индексом `new Map(users.map(u => [u.id, u]))`.
- Чтение layout в цикле с записью стилей: алгоритмически O(n), но каждый шаг вызывает layout всей страницы ([подробнее](../browser/rendering-pipeline.md)).

### Ограничения на n подсказывают алгоритм

Простой цикл в JIT-компилированном JavaScript делает порядка 10⁷–10⁸ операций в секунду. Отсюда грубая таблица того, что помещается в секунду:

| n | Допустимая сложность | Типичный приём |
| --- | --- | --- |
| ≤ 10–12 | O(n!) | перебор перестановок |
| ≤ 20–25 | O(2ⁿ) | перебор подмножеств, битовые маски |
| ≤ 500 | O(n³) | тройной цикл, DP по отрезкам |
| ≤ 5 000 | O(n²) | двойной цикл, DP по парам |
| ≤ 10⁶ | O(n log n) | сортировка, бинарный поиск, куча |
| ≤ 10⁸ | O(n) | один проход, хеш-таблица, два указателя |
| больше | O(log n), O(1) | формула, бинарный поиск по ответу |

На фронтенде бюджет жёстче: задача на главном потоке дольше 50 мс уже долгая ([подробнее](../performance/runtime.md)). O(n²) на 10 000 строк таблицы — это 10⁸ операций, то есть заметное зависание интерфейса.

### Как рассуждать о сложности вслух

1. **Назовите переменные.** «n — число заказов, m — число VIP-клиентов». Если не разделить n и m, ответ получится неверным.
2. **Начните с наивного решения** и сразу оцените его: «вложенный цикл — O(n · m), памяти O(1)».
3. **Найдите узкое место.** «Каждую итерацию ищем по массиву — это и есть множитель m».
4. **Предложите размен.** «Положим VIP в `Set`: O(n + m) времени, O(m) памяти».
5. **Назовите оба ответа и допущения.** «Время O(n + m) в среднем: хеш-таблица, худший случай при коллизиях хуже. Память O(m)».
6. **Вспомните о константах, когда это честно.** При n ≤ 20 линейный поиск по массиву быстрее `Set`: нет хеширования и аллокаций. TimSort по той же причине сортирует короткие отрезки вставками.

## Примеры

```js
// O(n · m): includes scans vipIds for every order
const vipOrders = orders.filter((o) => vipIds.includes(o.customerId));

// O(n + m) time, O(m) memory: one pass to build the Set, one to filter
const vip = new Set(vipIds);
const vipOrdersFast = orders.filter((o) => vip.has(o.customerId));
```

```js
// Amortized O(1): a queue with a head index instead of shift()
class Queue {
  #items = [];
  #head = 0;

  enqueue(value) {
    this.#items.push(value);
  }

  dequeue() {
    if (this.#head === this.#items.length) return undefined;
    const value = this.#items[this.#head];
    this.#items[this.#head++] = undefined; // let GC collect the value
    // Compact when the dead prefix dominates: O(n) once per ~n dequeues
    if (this.#head * 2 >= this.#items.length) {
      this.#items = this.#items.slice(this.#head);
      this.#head = 0;
    }
    return value;
  }
}
```

```js
// Ropes in V8: appending is cheap, reading forces flattening
let s = '';
for (let i = 0; i < n; i++) s += 'x'; // ~O(n) total in V8

let t = '';
for (let i = 0; i < n; i++) {
  t += 'x';
  t.charCodeAt(t.length - 1); // flattens t every time: O(n²) total
}
// Fix: collect parts in an array and join once
const parts = [];
for (let i = 0; i < n; i++) parts.push('x');
const joined = parts.join('');
```

```js
// Recursion depth is memory: O(depth) stack frames
function depth(node) {
  if (!node) return 0;
  return 1 + Math.max(depth(node.left), depth(node.right));
}
// Balanced tree: O(log n) stack. Degenerate tree (a list): O(n) and RangeError
```

## Вопросы с интервью

::: details Чем O отличается от Θ и Ω и что имеют в виду на интервью
O — верхняя граница роста (не быстрее, чем), Ω — нижняя (не медленнее, чем), Θ — точная (и то и другое). Формально линейный поиск — и O(n), и O(n²). На интервью «O» используют в смысле Θ худшего случая и ждут самую точную оценку. Нотацию не путают со случаем: «худший случай quicksort — Θ(n²)» — корректная фраза, нотация и случай здесь независимы. Ω встречается в нижних границах задач: сортировка сравнениями — Ω(n log n), потому что дерево решений с n! листьями имеет высоту log₂ n!.
:::

::: details Чем амортизированная сложность отличается от средней
Средняя сложность — матожидание по распределению входов. Она верна «в среднем по входам» и может быть сломана неудачным или враждебным входом: коллизии в хеш-таблице дают O(n) на операцию. Амортизированная — гарантия на любую последовательность из n операций: суммарная стоимость O(n · f), даже если отдельные операции дорогие. `push` с геометрическим ростом — амортизированно O(1): переаллокация с копированием случается всё реже, и её стоимость раскладывается на предыдущие вставки. `Map.set` — O(1) и амортизированно (рехеширование при росте), и в среднем (коллизии).
:::

::: details Что спецификация ECMAScript говорит о сложности Map, Set и методов массива
Для методов массива и строк — ничего: спецификация задаёт наблюдаемое поведение, а не алгоритм. Для `sort` она требует только стабильности (с ES2019) и оставляет порядок на совести реализации, если компаратор несогласован. Исключение — коллекции: `Map`, `Set`, `WeakMap` и `WeakSet` должны давать доступ в среднем за сублинейное время. Это допускает и O(log n), но все движки используют хеш-таблицы с O(1) в среднем. Поэтому оценки вроде «`sort` — O(n log n)» на senior-интервью стоит сопровождать словами «в V8, TimSort».
:::

::: details Сколько стоит shift и почему очередь на массиве — плохая идея
По модели — O(n): все элементы сдвигаются на одну позицию, и цикл с `shift` становится Θ(n²). В V8 есть оптимизация left-trimming: для буфера до 128 КБ движок переносит начало объекта в куче, и `shift` стоит O(1). В Node 26 это массивы примерно до 16 тысяч элементов, дальше скачок в сотни раз. Полагаться на это нельзя: порог зависит от движка, размера элемента и того, где лежит буфер. Очередь делают на индексе головы с периодической компакцией (амортизированно O(1)) или на кольцевом буфере.
:::

::: details Конкатенация строк в цикле — это O(n²)
В учебной модели — да: строки иммутабельны, и каждое `s += x` копирует s. В V8 — нет: `+` создаёт `ConsString` (rope), узел из двух ссылок за O(1). Квадрат возвращается, если между дописываниями строку читают: индексирование, `indexOf`, regex и передача во многие API требуют плоской строки, и V8 сплющивает её за O(n). Поэтому надёжный вариант для больших объёмов — собрать части в массив и вызвать `join` один раз. Он линеен без допущений о движке.
:::

::: details Как по ограничениям задачи понять, какую сложность от вас ждут
Нужно прикинуть число операций: простой цикл в JS — порядка 10⁷–10⁸ операций в секунду. n ≤ 20 разрешает перебор подмножеств O(2ⁿ). n ≤ 5 000 — O(n²). n до 10⁵–10⁶ требует O(n log n) или O(n): сортировки, хеш-таблицы, два указателя. n до 10⁹ — только O(log n) или формула. На фронтенде добавляется бюджет кадра: задача дольше 50 мс блокирует ввод, поэтому O(n²) на нескольких тысячах элементов уже ощутим.
:::

::: details Учитывается ли стек рекурсии в сложности по памяти
Да. Каждый незавершённый вызов держит кадр, поэтому рекурсия глубины d — это O(d) памяти, даже если функция не выделяет ни одного массива. Обход сбалансированного дерева — O(log n), вырожденного — O(n). В V8 нет оптимизации хвостовых вызовов, так что хвостовая рекурсия не спасает. Практический предел в Node — порядка 10⁴ кадров, дальше `RangeError: Maximum call stack size exceeded`. Входные данные в вспомогательную память обычно не включают, а результат — по договорённости. Это стоит проговорить.
:::

::: details Когда алгоритм с худшей асимптотикой быстрее
При малых n и больших константах. Асимптотика описывает рост, а не абсолютное время. Вставки на 10–30 элементах быстрее слияния: нет рекурсии, аллокаций, кэш-промахов. Поэтому TimSort досортировывает короткие отрезки вставками. Линейный поиск по массиву из 10 элементов быстрее `Set.has`, особенно с учётом создания `Set`. Ещё фактор — локальность памяти: проход по плотному массиву быстрее прыжков по указателям в дереве той же сложности. Правильный ответ на интервью: выбрать асимптотически лучший алгоритм для неизвестного n и упомянуть, где константы важнее.
:::

## Задачи

### 1. Найдите скрытые квадраты · легко

Функция оставляет первые вхождения заказов по `id`, выбирает заказы VIP-клиентов и строит словарь `id → total`. Оцените сложность и перепишите на линейную.

```js
function summarize(orders, vipIds) {
  const unique = orders.filter((o, i) => orders.findIndex((x) => x.id === o.id) === i);
  const vip = unique.filter((o) => vipIds.includes(o.customerId));
  return vip.reduce((acc, o) => ({ ...acc, [o.id]: o.total }), {});
}
```

::: details Решение и разбор
Три квадрата: `findIndex` внутри `filter` — Θ(n²), `includes` внутри `filter` — O(n · m), spread аккумулятора в `reduce` — Θ(n²) копирований. Итого O(n² + n · m).

```js
function summarize(orders, vipIds) {
  const vip = new Set(vipIds);
  const seen = new Set();
  const result = {};
  for (const o of orders) {
    if (seen.has(o.id)) continue; // keep the first occurrence, like findIndex
    seen.add(o.id);
    if (vip.has(o.customerId)) result[o.id] = o.total;
  }
  return result;
}
```

Поведение совпадает с исходным, включая пустые входы и порядок ключей (целочисленные ключи объекта всё равно идут первыми по возрастанию). На 20 000 заказов исходная версия работала 611 мс, новая — 2 мс. Если ключи `id` могут быть разных типов (`3` и `'3'`), `Set` их различает, а ключи объекта — нет. Тогда результатом лучше сделать `Map`.

Сложность: O(n + m) по времени в среднем, O(n + m) по памяти.
:::

### 2. Оцените сложность фрагментов · средне

Назовите сложность по времени каждого фрагмента, `work()` — O(1). Для `f` и `g` назовите и память.

```js
// a
for (let i = 0; i < n; i++) for (let j = i + 1; j < n; j++) work();
// b
for (let i = 1; i < n; i *= 2) for (let j = 0; j < i; j++) work();
// c
for (let i = 1; i <= n; i++) for (let j = i; j <= n; j += i) work();
// d
function f(n) {
  if (n <= 1) return 1;
  return f(n - 1) + f(n - 1);
}
// e
function g(arr) {
  if (arr.length <= 1) return arr;
  const mid = arr.length >> 1;
  return [...g(arr.slice(0, mid)), ...g(arr.slice(mid))];
}
```

::: details Решение и разбор
- **a** — n(n − 1)/2 итераций: Θ(n²). Половина квадрата — всё ещё квадрат.
- **b** — ловушка: два цикла, а не n log n. Внутренний делает 1 + 2 + 4 + … < 2n итераций. Итого Θ(n). При n = 1024 — 1023 вызова `work`.
- **c** — n/1 + n/2 + … + n/n = n · Hₙ, где Hₙ — гармоническое число ≈ ln n. Итого Θ(n log n). При n = 1024 — 7262 итерации против n · ln n ≈ 7098. Так же устроено решето Эратосфена.
- **d** — каждый вызов порождает два: 2ⁿ − 1 вызовов, Θ(2ⁿ) по времени. При `f(20)` — 1 048 575 вызовов. Память — O(n): одновременно живёт только одна ветка стека. Результат равен `2^(n-1)`, а мемоизация или один вызов `2 * f(n - 1)` дают O(n).
- **e** — рекуррентность T(n) = 2T(n/2) + O(n): `slice` и spread линейны. По основной теореме (master theorem) Θ(n log n). Память: стек O(log n) плюс копии на текущем пути n + n/2 + n/4 + … = O(n).

Метод для рекурсии: нарисовать дерево вызовов, посчитать работу на уровне и число уровней. В **e** на каждом из log n уровней суммарно O(n) работы.
:::

### 3. Почему рост ёмкости должен быть геометрическим · средне

Смоделируйте динамический массив: при заполнении выделяется новый буфер ёмкости `grow(capacity)`, старые элементы копируются. Посчитайте копирования за n вставок для `c * 2`, стратегии V8 `c + (c >> 1) + 16` и `c + 16`. Объясните результат.

::: details Решение и разбор
```js
function countCopies(n, grow) {
  let capacity = 0;
  let size = 0;
  let copies = 0;
  for (let i = 0; i < n; i++) {
    if (size === capacity) {
      copies += size; // move every element into the new buffer
      capacity = grow(capacity);
    }
    size++;
  }
  return copies;
}

countCopies(1e6, (c) => c * 2 || 1); // 1 048 575
countCopies(1e6, (c) => c + (c >> 1) + 16); // 2 418 566
countCopies(1e6, (c) => c + 16); // 31 249 500 000
```

При росте в k раз копирования образуют геометрическую прогрессию, сумма которой ограничена последним членом, умноженным на k/(k − 1). Для удвоения это < 2n, для 1,5 — < 3n. Значит, на вставку приходится O(1) амортизированно. При росте на константу c переаллокация случается каждые c вставок, а копирований n²/(2c) — Θ(n²). При n = 10⁶ это в 13 000 раз больше, чем у V8.

Почему V8 выбирает 1,5, а не 2: меньший множитель тратит меньше памяти на запас (в худшем случае треть буфера пуста, а не половина). Слагаемое +16 убирает частые переаллокации на маленьких массивах.

Сложность: O(n) суммарно, O(1) амортизированно на вставку для геометрического роста; Θ(n²) для арифметического.
:::

### 4. Пересечение двух списков: три решения · средне

Даны массивы id `a` (длина n) и `b` (длина m), возможны повторы. Верните уникальные общие id. Предложите решения с разными компромиссами и скажите, когда какое выбрать.

::: details Решение и разбор
Наивное — `a.filter((x) => b.includes(x))` плюс дедупликация: O(n · m), памяти O(1) сверх результата. Годится, только если один из массивов из единиц элементов.

Через хеш-таблицу — `Set` строится по **меньшему** массиву, чтобы память была O(min(n, m)):

```js
function intersect(a, b) {
  if (a.length > b.length) [a, b] = [b, a];
  const small = new Set(a);
  const result = new Set();
  for (const x of b) if (small.has(x)) result.add(x);
  return [...result];
}
```

Время O(n + m) в среднем, память O(min(n, m)).

Через сортировку и два указателя — когда массивы уже отсортированы (пришли с сервера по возрастанию id) или память ограничена:

```js
// a and b are sorted ascending
function intersectSorted(a, b) {
  const result = [];
  let i = 0;
  let j = 0;
  while (i < a.length && j < b.length) {
    if (a[i] < b[j]) i++;
    else if (a[i] > b[j]) j++;
    else {
      if (result.length === 0 || result[result.length - 1] !== a[i]) result.push(a[i]);
      i++;
      j++;
    }
  }
  return result;
}
```

На уже отсортированных данных — O(n + m) по времени и O(1) дополнительной памяти. Если сортировать самим — O(n log n + m log m), и `sort` мутирует входы (нужен `toSorted`, а это O(n + m) памяти). Проверено на пустых массивах, повторах (`[0, 0]` и `[0]` → `[0]`) и несортированном входе для `Set`-версии.

Сложность: `Set` — O(n + m) по времени, O(min(n, m)) по памяти; два указателя — O(n + m) по времени, O(1) по памяти при отсортированном входе.
:::

### 5. Глубокая вложенность без переполнения стека · средне

`flatDeep` разворачивает массив произвольной вложенности. На вложенности 100 000 рекурсивная версия падает с `RangeError`. Перепишите без рекурсии, сохранив порядок элементов, и оцените память.

```js
function flatDeep(arr) {
  const out = [];
  for (const x of arr) {
    if (Array.isArray(x)) out.push(...flatDeep(x));
    else out.push(x);
  }
  return out;
}
```

::: details Решение и разбор
У рекурсивной версии две проблемы. Стек растёт на кадр с каждым уровнем вложенности. А `out.push(...flatDeep(x))` ещё и копирует результат на каждом уровне: на глубине d это O(N · d), а spread большого массива в аргументы сам по себе может упереться в лимит стека.

Явный стек хранит пары «массив и позиция в нём», поэтому порядок сохраняется:

```js
function flatDeep(input) {
  const result = [];
  const stack = [[input, 0]];
  while (stack.length > 0) {
    const top = stack[stack.length - 1];
    const [arr, i] = top;
    if (i === arr.length) {
      stack.pop(); // this level is done, resume the parent
      continue;
    }
    top[1] = i + 1;
    const item = arr[i];
    if (Array.isArray(item)) stack.push([item, 0]);
    else result.push(item);
  }
  return result;
}

flatDeep([1, [2, [3, [4]], 5], [], [[6]]]); // [1, 2, 3, 4, 5, 6]
flatDeep([[[]]]); // []
```

Стек теперь — обычный массив в куче, его предел — память, а не ~10⁴ кадров. Вложенность 100 000 отрабатывает без ошибок. Встроенный `arr.flat(Infinity)` в Node 26 на той же глубине падает с `RangeError`, как и `structuredClone`, так что «есть встроенный метод» — не ответ для недоверенных данных. Циклическая ссылка (`a.push(a)`) зациклит обе версии. Защита — `Set` массивов на текущем пути стека.

Сложность: O(N) по времени, где N — суммарное число элементов и вложенных массивов; O(d) дополнительной памяти на стек, где d — глубина, плюс O(N) на результат.
:::
