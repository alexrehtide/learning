# curry, compose, memoize, once

> **Коротко.** Четыре функции высшего порядка: каждая принимает функцию и возвращает обёртку, у которой есть состояние в замыкании. `curry` собирает аргументы по частям, пока их не наберётся `fn.length`. `compose` и `pipe` склеивают функции в конвейер. `memoize` кэширует результат по ключу из аргументов. `once` выполняет функцию один раз и дальше возвращает первый результат. Написать каждую — 5–10 строк. На интервью проверяют контракт: арность и `this`, порядок композиции, выбор ключа кэша и его границы, асинхронность, поведение при исключении и что обёртка держит в памяти.

**Связанные темы:** [Замыкания](../javascript/closures.md), [Функции и `this`](../javascript/functions-and-this.md), [Функциональные приёмы и иммутабельность](../javascript/functional-programming.md), [Память и сборка мусора](../javascript/memory-and-gc.md), [Промисы](../javascript/promises.md), [Стеки и очереди](../algorithms/stacks-and-queues.md), [Рекурсия и динамическое программирование](../algorithms/recursion-and-dp.md), [Generics](../typescript/generics.md), [debounce и throttle](./debounce-throttle.md), [Утилиты промисов: `Promise.all` и компания, пул, retry](./promise-utilities.md), [Полифилы: методы `Array`, `bind`/`call`/`apply`](./polyfills.md)

## Теория

### Арность и `fn.length`

Автоматическое каррирование узнаёт число аргументов из `fn.length`. Спецификация задаёт его как **ExpectedArgumentCount**: число формальных параметров **до первого** параметра со значением по умолчанию или rest. Деструктуризация без значения по умолчанию считается обычным параметром. У функции из `bind` длина равна `max(0, длина цели − число привязанных аргументов)`.

| Функция | `length` |
| --- | --- |
| `(a, b) => {}` | 2 |
| `(a, b = 1, c) => {}` | 1 — `c` после параметра по умолчанию тоже не считается |
| `(a, ...rest) => {}` | 1 |
| `({ a }, [b]) => {}` | 2 |
| `((a, b, c) => {}).bind(null, 1)` | 2 |
| `function () { return arguments }` | 0 |

Отсюда граница автоматического каррирования: функции с параметрами по умолчанию, с rest и через `arguments` каррируют только с **явной арностью**: `curry(fn, 3)`. Так делают и lodash (`_.curry(func, arity)`), и Ramda (`R.curryN(n, fn)`).

### Контракт curry

Каррирование превращает `f(a, b, c)` в `f(a)(b)(c)`. Чем оно отличается от частичного применения, разобрано в теме [Функциональные приёмы и иммутабельность](../javascript/functional-programming.md). Практичный JS-вариант (lodash, Ramda) шире математического:

- **Несколько аргументов за раз:** `c(1)(2)(3)`, `c(1, 2)(3)` и `c(1, 2, 3)` равноценны.
- **Промежуточная функция переиспользуется.** `const add1 = c(1)` можно вызывать сколько угодно раз с разными продолжениями. Значит, накопленные аргументы нельзя хранить в общем массиве и мутировать `push`: каждый шаг создаёт новый массив. Это самая частая ошибка на интервью.
- **Лишние аргументы передаются.** Когда аргументов набралось не меньше арности, функция вызывается со **всеми**. В исходниках lodash 4.18.1 (`createCurry`) и Ramda 0.32.0 (`_curryN`) так и сделано.
- **Вызов без аргументов** возвращает новую каррированную функцию и ничего не меняет.
- **`this`** берётся из вызова, на котором набралась арность. Метод `obj.m(1, 2)` его получит, а сохранённая промежуточная `obj.m(1)` — уже нет.
- **`length` результата.** У Ramda каррированная функция сообщает, сколько аргументов ей осталось (`_arity`, до 10 параметров). У lodash `length` обёртки — 0, и документация это оговаривает.
- **Плейсхолдеры.** `_.curry.placeholder` (по умолчанию сам `_`) и `R.__` пропускают позицию: `f(_, 2)(1, 3)` — это `f(1, 2, 3)`. На интервью их просят как продолжение задачи (задача 2).

> [!NOTE]
> Типизировать `curry` для произвольной арности в TypeScript можно рекурсивным условным типом над кортежем параметров. Но вывод ломается на перегрузках и generic-функциях ([подробнее](../typescript/generics.md)). Поэтому в библиотечных типах чаще пишут перегрузки на фиксированное число аргументов. Каррирование в TS-коде встречается редко, частичное применение через стрелку типизируется само.

### compose и pipe

`compose(f, g, h)(x) === f(g(h(x)))` — справа налево, как в математике. `pipe(h, g, f)` — то же самое слева направо и читается как конвейер. В lodash это `_.flowRight` и `_.flow`, в Ramda — `R.compose` и `R.pipe`.

Детали контракта:

- **Первая функция конвейера** (у `compose` — последняя) может принимать несколько аргументов, остальные — унарные: каждая получает результат предыдущей. Ramda переносит `length` первой функции на результат, lodash — нет.
- **Пустой конвейер.** `_.flow()` возвращает первый аргумент, то есть ведёт себя как `identity`. `R.pipe()` и `R.compose()` бросают `Error('pipe requires at least one argument')`. На интервью выберите поведение и проговорите его. `identity` удобнее: конвейер из массива функций не падает на пустом массиве.
- **`this`** обе библиотеки передают всем функциям (`apply(this, args)` и `call(this, result)`).
- **Ошибка** в шаге обрывает конвейер. Обрабатывать её внутри `pipe` — не его задача.

**Асинхронный pipe** нужен, когда шаги возвращают промисы. Обычный `pipe` передал бы следующему шагу промис вместо значения. Решение — свёртка через `then`. Начинать её стоит с `Promise.resolve().then(...)`, а не с прямого вызова первой функции: тогда синхронное исключение первого шага превращается в отклонённый промис, а не вылетает из вызова. В Ramda это `R.pipeWith(R.andThen)`. Стоимость — минимум одна микрозадача на шаг: `then` откладывает даже синхронный шаг ([подробнее](../javascript/event-loop.md)).

### Контракт memoize

`memoize(fn)` возвращает обёртку, которая для уже встречавшегося ключа отдаёт сохранённый результат. Корректна она только для **чистой** функции: результат зависит лишь от аргументов, побочных эффектов нет. Главные решения — ключ, хранилище и граница кэша.

**Ключ по умолчанию у lodash — первый аргумент.** `_.memoize(fn)` строит ключ как `args[0]`, поэтому `m(1, 2)` и `m(1, 100)` вернут одно и то же. Для нескольких аргументов нужен `resolver`: `_.memoize(fn, (a, b) => `${a}|${b}`)`. Кэш — `memoized.cache` (по умолчанию `MapCache` с `get`/`set`/`has`/`delete`/`clear`), класс можно заменить через `_.memoize.Cache`. В Ramda ключ задаётся всегда: `R.memoizeWith(keyFn, fn)`, кэш — обычный объект, поэтому ключ приводится к строке, и `1` совпадает с `'1'`.

**Ключ через `JSON.stringify` — популярный и опасный.** Он сериализует только то, что видит JSON, поэтому разные аргументы сливаются в один ключ (проверено в Node 26):

| Аргументы | Что получается |
| --- | --- |
| `undefined`, `NaN`, `Infinity`, функция | в массиве — `null`, совпадают с `null` |
| `-0` и `0` | оба `0` |
| `{ a: undefined }` и `{}` | одинаковые |
| `new Map(...)`, `new Set(...)` | `{}` — содержимое теряется |
| `new Date(0)` и строка `'1970-01-01T00:00:00.000Z'` | одинаковые |
| `{ a: 1, b: 2 }` и `{ b: 2, a: 1 }` | **разные** — порядок ключей важен |
| `1n`, циклическая ссылка | `TypeError` |

Кроме коллизий, сериализация стоит O(размер аргумента) на **каждый** вызов, даже на попадание в кэш. Для больших объектов кэш может оказаться дороже вычисления.

**Объекты — по ссылке, через `WeakMap`.** Если аргумент — объект, естественный ключ — его идентичность. `Map` удерживал бы объект вечно, а `WeakMap` не мешает сборщику: когда объект больше никому не нужен, запись исчезает вместе с ним ([подробнее](../javascript/memory-and-gc.md)). Для нескольких аргументов строят **дерево** (trie): на каждом уровне `Map` для примитивов и `WeakMap` для объектов (задача 4). Кэш по ссылке корректен, только если аргументы не мутируют. Изменённый на месте объект вернёт старый результат. На этом и держится связка мемоизации с иммутабельностью: новое значение — новая ссылка.

**Граница кэша.** Неограниченный кэш — это утечка памяти, растущая с числом разных аргументов ([подробнее](../javascript/closures.md)). Варианты: ограничить размер с вытеснением LRU — `Map` в порядке вставки, разобран в теме [Стеки и очереди](../algorithms/stacks-and-queues.md); задать TTL; дать ручной `cache.clear()`; держать кэш в области жизни потребителя (компонента, запроса), а не модуля.

**Мелочи, которые проверяют:** результат `undefined` тоже должен кэшироваться, поэтому проверка — `cache.has(key)`, а не `cache.get(key) !== undefined`. Исключение не кэшируется: функция бросила — следующий вызов попробует снова. `Map` сравнивает ключи по SameValueZero, поэтому `NaN` находит сам себя, а `0` и `-0` совпадают.

### memoize асинхронной функции

Кэшировать надо **промис**, а не результат. Тогда второй вызов, пришедший до ответа, получит тот же промис, и запрос не уйдёт дважды (in-flight deduplication). Если кэшировать значение после `await`, параллельные вызовы до первого ответа отправят каждый свой запрос.

Отклонённый промис из кэша **удаляют**, иначе одна сетевая ошибка «запомнится» до перезагрузки. Удалять нужно только свою запись: пока запрос шёл, она могла истечь по TTL и быть заменена новой (задача 5). Для данных с сервера добавляют TTL, а инвалидацию после мутаций делают явной. Это уже кэш запросов. Готовые решения — `useAsyncData` с ключом в Nuxt и Pinia Colada / TanStack Query во Vue.

### Контракт once

`once(fn)` вызывает `fn` при первом вызове обёртки и возвращает этот результат при всех следующих. Аргументы следующих вызовов игнорируются.

- **`this`** передаётся из первого вызова. Обёртка — обычная функция, а не стрелка.
- **Флаг ставится до вызова `fn`.** Если `fn` рекурсивно вызовет обёртку или бросит исключение, второго выполнения не будет.
- **Исключение.** И lodash, и Ramda не повторяют вызов: исключение пробрасывается, а дальше обёртка возвращает `undefined`. В lodash `once` — это `_.before(2, func)`: счётчик уменьшается до вызова. В Ramda флаг `called` ставится до `fn.apply`. Альтернатива — «повторять до первого успеха». Для синхронной функции она редко нужна, а для асинхронной инициализации это обычное требование (задача 6).
- **Освобождение замыкания.** После вызова `fn` больше не нужна, но обёртка её держит, а вместе с ней — всё, что `fn` захватила. lodash присваивает `func = undefined` после выполнения. Ramda не освобождает.

> [!NOTE]
> `Function.prototype.once` и `Function.prototype.memo` — предложения TC39 на stage 1 с 2022 года, `Function.pipe` и `flow` отклонены, а оператор `|>` — на stage 2 (сверено 2026-11-13). В языке этих утилит пока нет.

### Во Vue

- **`computed` — мемоизация по реактивным зависимостям, а не по аргументам.** Пересчёт происходит, когда изменилась прочитанная зависимость. «`computed` с параметром» (`computed(() => (id) => ...)`) возвращает функцию, и её вызовы из шаблона не кэшируются: каждый рендер считает заново. Если нужен кэш по аргументу, вычисляют целиком `Map` в `computed` (`id → результат`) или используют `memoize` над чистой функцией.
- **Сам Vue мемоизирует строки.** В `@vue/shared` 3.5.45 есть `cacheStringFunction`: кэш — `Object.create(null)`, без прототипа, поэтому ключ `'constructor'` не попадает в `Object.prototype`. Через него сделаны `camelize`, `hyphenate`, `capitalize`, `toHandlerKey`. Кэш не ограничен: множество имён props и событий в приложении конечно. Проверка `hit || (cache[str] = fn(str))` пересчитывает «ложный» результат: `toHandlerKey('')` возвращает `''` и не кэшируется. Здесь это неважно, а в общей утилите — ошибка.
- **`app.use` — это `once` по плагину.** В runtime-core 3.5.45 установленные плагины лежат в `WeakSet`, повторный `use` того же плагина выдаёт предупреждение `Plugin has already been applied to target app.` и не вызывает `install`. Плагин добавляется в набор **до** вызова `install`: если тот бросил, повторный `use` его не установит.
- **SSR и кэш в модуле.** На сервере модуль загружается один раз на процесс, поэтому кэш `memoize` на уровне модуля общий для всех запросов. Для чистых функций от публичных данных это допустимо. Для данных пользователя это утечка между запросами (cross-request state pollution): кэш держат в состоянии запроса (`useState`, `event.context`) или не мемоизируют.

> [!TIP]
> Директивы `v-once` и `v-memo` мемоизируют не функции, а **поддерево шаблона**: `v-once` рендерит его один раз, `v-memo="[deps]"` пропускает обновление, пока массив зависимостей поэлементно не изменился. Подробно — в теме [Производительность Vue и Nuxt](../performance/vue-performance.md).

## Примеры

```js
const toSlug = pipe(
  (s) => s.trim().toLowerCase(),
  (s) => s.normalize('NFKD').replace(/[̀-ͯ]/g, ''),
  (s) => s.replace(/[^a-z0-9]+/g, '-'),
  (s) => s.replace(/^-|-$/g, ''),
);
toSlug('  Crème Brûlée! '); // 'creme-brulee'

// Partial application via curry: a configurable validator
const inRange = curry((min, max, value) => value >= min && value <= max);
const isPercent = inRange(0, 100);
[5, 120, 42].filter(isPercent); // [5, 42]

// One request per user id, even for parallel callers; failures are retried
const fetchUser = memoizeAsync((id) => fetch(`/api/users/${id}`).then((r) => r.json()), {
  maxSize: 100,
  ttl: 60_000,
});

// Lazy singleton
const getWorker = once(() => new Worker(new URL('./heavy.js', import.meta.url), { type: 'module' }));
```

## Вопросы с интервью

::: details Почему автоматический curry опирается на длину функции и когда это ломается
Каррированной функции нужно знать, сколько аргументов собрать, прежде чем вызвать оригинал, а единственный источник — `fn.length`. По спецификации это число параметров до первого со значением по умолчанию или rest. Поэтому `(a, b = 1) => …` имеет длину 1 и вызовется на первом же аргументе, `(...args) => …` — длину 0, а функция через `arguments` — 0. Для таких функций арность задают явно: `curry(fn, 3)`, `_.curry(fn, 3)`, `R.curryN(3, fn)`. Отдельная ловушка — промежуточные функции переиспользуются, поэтому накопленные аргументы нельзя мутировать: каждый шаг создаёт новый массив.
:::

::: details Чем compose отличается от pipe и какие требования к функциям конвейера
Порядком: `compose(f, g)(x)` — это `f(g(x))`, справа налево; `pipe(g, f)(x)` — то же слева направо. Первая выполняемая функция может принимать несколько аргументов, остальные должны быть унарными: каждая получает результат предыдущей. Пустой конвейер разумно делать `identity` (так `_.flow`), Ramda на нём бросает ошибку. Если шаги асинхронные, нужен отдельный `pipeAsync` со свёрткой через `then`: обычный `pipe` передаст следующему шагу промис.
:::

::: details Как lodash memoize строит ключ и как выбрать ключ правильно
По умолчанию ключ — первый аргумент, поэтому `m(1, 2)` и `m(1, 100)` дают один результат. Для нескольких аргументов передают `resolver`. Ключ выбирают по типам аргументов: примитивы можно склеить в строку с разделителем, которого нет в данных; объекты — по ссылке через `WeakMap`; для нескольких аргументов — дерево из `Map`/`WeakMap`. `JSON.stringify` как ключ даёт коллизии (`undefined` и `null`, `Map` и `{}`), ломается на `BigInt` и циклах, зависит от порядка ключей и стоит O(размер) на каждый вызов.
:::

::: details Почему мемоизация по ссылке требует иммутабельности
Кэш по ссылке отвечает на вопрос «тот же ли это объект», а не «те же ли в нём данные». Если объект изменили на месте, ссылка та же, и `memoize` вернёт результат для старого содержимого. При иммутабельных обновлениях изменение данных означает новую ссылку, поэтому сравнение ссылок становится корректной и дешёвой проверкой. На том же держатся `shallowRef` во Vue и `v-memo`.
:::

::: details Как мемоизировать асинхронную функцию
Кэшировать промис, а не результат: тогда параллельные вызовы до ответа получат один промис, и запрос уйдёт один раз. При отклонении запись удаляют, но только свою, если её уже не заменили, иначе ошибка закэшируется навсегда. Добавляют TTL и ограничение размера, для данных с сервера — явную инвалидацию после мутаций. Синхронное исключение функции стоит превратить в отклонённый промис, чтобы контракт был единым. Дальше это уже кэш запросов, и в приложении берут готовый: `useAsyncData` в Nuxt, Pinia Colada или TanStack Query.
:::

::: details Когда мемоизация вредна
Когда функция нечистая: зависит от времени, случайности, внешнего изменяемого состояния или мутирует аргументы. Когда вычисление дешевле построения ключа, например сериализации большого объекта. Когда аргументы почти не повторяются: кэш только растёт. Когда кэш не ограничен и живёт в модуле: это утечка памяти, а на SSR ещё и общий для всех запросов кэш, через который данные одного пользователя могут попасть к другому. И когда результат — изменяемый объект, который вызывающий код потом меняет: он портит кэш для всех.
:::

::: details Что должен делать once, если функция бросила исключение
Это решение контракта, и его надо проговорить. lodash и Ramda помечают функцию вызванной до выполнения: исключение пробрасывается, а дальше обёртка возвращает `undefined` и функцию больше не вызывает. Это защищает от повторных побочных эффектов, но скрывает, что инициализация не удалась. Для асинхронной инициализации (подключение, загрузка SDK) обычно нужен обратный вариант: кэшировать промис и сбрасывать его при отклонении, чтобы следующий вызов попробовал снова.
:::

## Задачи

### 1. curry · легко

Напишите `curry(fn, arity = fn.length)`: вызовы `c(1)(2)(3)`, `c(1, 2)(3)`, `c(1, 2, 3)` равноценны, промежуточные функции переиспользуются, `this` передаётся.

::: details Решение и разбор
```js
function curry(fn, arity = fn.length) {
  return function curried(...args) {
    if (args.length >= arity) return fn.apply(this, args);
    return function (...more) {
      return curried.apply(this, [...args, ...more]); // new array on every step
    };
  };
}

const add = curry((a, b, c) => a + b + c);
const add1 = add(1);
add1(2)(3); // 6
add1(10, 10); // 21 — add1 is reusable
```

Проверено в Node 26: все формы вызова, повторное использование `add1`, `c()` без аргументов, лишние аргументы доходят до `fn` (`arguments.length === 3`), `curry((a, b = 10) => a + b)(1) === 11`, а с явной арностью `curry(fn, 2)(1)(2) === 3`. Типичные ошибки: общий массив аргументов с `push` (второй вызов `add1` видит аргументы первого), проверка `===` вместо `>=` (лишние аргументы ломают вызов), стрелочные обёртки (теряется `this`). Что спросят дальше: плейсхолдеры (задача 2), `length` результата (обернуть в функцию с нужным числом параметров, как `_arity` в Ramda), типизация.

Сложность: O(k) по времени и памяти на шаг, где k — число накопленных аргументов.
:::

### 2. curry с плейсхолдерами · средне

Добавьте плейсхолдер `_`: `f(_, 2)(1, 3)` и `f(_, _, 3)(1)(2)` равны `f(1, 2, 3)`. Новые аргументы сначала заполняют дырки слева направо, остаток дописывается в конец.

::: details Решение и разбор
```js
const _ = Symbol('placeholder');

function curry(fn, arity = fn.length) {
  return function curried(...args) {
    const head = args.slice(0, arity);
    if (head.length >= arity && !head.includes(_)) return fn.apply(this, args);
    return function (...more) {
      const merged = args.map((a) => (a === _ && more.length ? more.shift() : a));
      return curried.apply(this, [...merged, ...more]);
    };
  };
}
```

Плейсхолдер — уникальное значение (`Symbol`), иначе его не отличить от настоящего аргумента. Готовность проверяется по первым `arity` позициям: дырок там нет и аргументов достаточно. `more` копируется rest-параметром на каждый вызов, поэтому `shift` не портит чужие данные. Проверено в Node 26 на `f(_, 2)(1, 3)`, `f(_, _, 3)(_, 2)(1)`, `f(1)(_, 3)(2)`. В lodash плейсхолдер — сам объект `_` (`_.curry.placeholder`), в Ramda — `R.__`.

Сложность: O(k) на шаг.
:::

### 3. compose, pipe и pipeAsync · легко

Напишите `pipe(...fns)` и `compose(...fns)`: первая функция получает все аргументы, `this` передаётся, пустой конвейер — `identity`. Затем `pipeAsync`, где шаги могут возвращать промисы, а любое исключение превращается в отклонённый промис.

::: details Решение и разбор
```js
const pipe = (...fns) => function (...args) {
  if (fns.length === 0) return args[0];
  let result = fns[0].apply(this, args);
  for (let i = 1; i < fns.length; i++) result = fns[i].call(this, result);
  return result;
};

const compose = (...fns) => pipe(...fns.reverse()); // fns is a fresh array

const pipeAsync = (...fns) => (...args) =>
  fns.slice(1).reduce(
    (promise, fn) => promise.then(fn),
    Promise.resolve().then(() => fns[0](...args)),
  );
```

`fns.reverse()` мутирует массив, но rest-параметр создаёт новый, поэтому массив вызывающего не меняется. Если бы `compose` принимал массив, понадобился бы `toReversed()`. В `pipeAsync` первый шаг вызывается внутри `then`: синхронный `throw` становится отклонением, а после ошибки следующие шаги не выполняются (проверено в Node 26). Через `reduce` пишут и синхронный `pipe`: `fns.reduce((acc, fn) => fn(acc), x)`. Это компактно, но теряет многоаргументную первую функцию и `this`. Что спросят дальше: `pipeAsync` с отменой через `AbortSignal` (проверять `signal.throwIfAborted()` между шагами), логирование шагов, композиция middleware — `compose` в стиле Koa, где каждый шаг получает `next`.

Сложность: O(n) по времени на вызов, n — число функций.
:::

### 4. memoize: resolver и несколько аргументов · средне

Напишите `memoize(fn, resolver)` с контрактом lodash: ключ — `resolver(...args)` или первый аргумент, кэш доступен как `memoized.cache`. Затем `memoizeArgs(fn)` без resolver: ключ — все аргументы, примитивы сравниваются по значению, объекты — по ссылке и не удерживаются кэшем.

::: details Решение и разбор
```js
function memoize(fn, resolver) {
  const memoized = function (...args) {
    const key = resolver ? resolver.apply(this, args) : args[0];
    if (memoized.cache.has(key)) return memoized.cache.get(key);
    const result = fn.apply(this, args);
    memoized.cache.set(key, result);
    return result;
  };
  memoized.cache = new Map();
  return memoized;
}

function memoizeArgs(fn) {
  const isObject = (v) => (typeof v === 'object' && v !== null) || typeof v === 'function';
  const node = () => ({ map: null, weak: null, hasValue: false, value: undefined });
  const root = node();
  return function (...args) {
    let current = root;
    for (const arg of args) {
      const store = isObject(arg) ? (current.weak ??= new WeakMap()) : (current.map ??= new Map());
      let next = store.get(arg);
      if (!next) store.set(arg, (next = node()));
      current = next;
    }
    if (!current.hasValue) {
      current.value = fn.apply(this, args);
      current.hasValue = true;
    }
    return current.value;
  };
}
```

`has` вместо проверки `get` на `undefined` — чтобы кэшировался и результат `undefined`. Исключение не кэшируется: `set` не выполняется. В `memoizeArgs` путь по дереву — последовательность аргументов, поэтому `f(1)` и `f(1, undefined)` различаются, `1` и `'1'` тоже, а `NaN` находит сам себя. Объекты на уровне хранятся в `WeakMap`: в Node 26 с `--expose-gc` `FinalizationRegistry` подтвердил, что объект-ключ собирается после того, как на него не осталось ссылок. Но промежуточные узлы для примитивов (`Map`) растут без ограничений — это та же утечка, если аргументы не повторяются. Что спросят дальше: ограничение размера с LRU (вытеснять первый ключ `Map`, «освежать» удалением и повторной вставкой), TTL, `cache.clear()`, почему `WeakMap` нельзя обойти и узнать размер.

Сложность: O(k) по времени на вызов, k — число аргументов (плюс стоимость `resolver`); память — O(число разных наборов аргументов).
:::

### 5. memoizeAsync: дедупликация, ошибки, TTL, размер · сложно

Напишите `memoizeAsync(fn, { key, maxSize, ttl })`: параллельные вызовы с одним ключом получают один промис, отклонение удаляет запись, запись живёт `ttl` мс, при переполнении вытесняется самая давно использованная.

::: details Решение и разбор
```js
function memoizeAsync(fn, { key = (x) => x, maxSize = Infinity, ttl = Infinity, now = Date.now } = {}) {
  const cache = new Map(); // key -> { promise, expires }, in LRU order
  return function (...args) {
    const k = key(...args);
    const hit = cache.get(k);
    if (hit && hit.expires > now()) {
      cache.delete(k); // refresh: Map.set keeps the old position
      cache.set(k, hit);
      return hit.promise;
    }
    const promise = Promise.resolve().then(() => fn.apply(this, args));
    const entry = { promise, expires: now() + ttl };
    cache.delete(k);
    cache.set(k, entry);
    if (cache.size > maxSize) cache.delete(cache.keys().next().value);
    promise.catch(() => {
      if (cache.get(k) === entry) cache.delete(k); // only our own entry
    });
    return promise;
  };
}
```

Проверено в Node 26 с фейковыми часами (`now` внедряется ради тестов): два синхронных вызова получают один промис и один запрос; после отклонения следующий вызов идёт в сеть заново; на `ttl` запись истекает; при `maxSize: 2` последовательность `a, b, a, c` вытесняет `b`, а не `a`. Проверка `cache.get(k) === entry` закрывает гонку: запрос истёк по TTL, ушёл новый, а потом старый отклонился. Без проверки он удалил бы свежую запись. `promise.catch` — отдельная ветка, которая не глушит ошибку для вызывающего, а лишь гарантирует, что отклонение не останется необработанным. Что спросят дальше: отсчитывать TTL от ответа, а не от запроса; `stale-while-revalidate` (отдать старое, обновить в фоне); отмена — когда можно прервать общий запрос, если вызывающих несколько (только когда отказались все, иначе один отменит запрос для всех).

Сложность: O(1) амортизированно на вызов (не считая `key`), O(maxSize) по памяти.
:::

### 6. once и onceAsync · легко

Напишите `once(fn)`: `this` первого вызова, повторного выполнения нет ни при исключении, ни при рекурсивном вызове, `fn` освобождается после выполнения. Затем `onceAsync(fn)` для инициализации: параллельные вызовы ждут одну попытку, после отклонения следующий вызов пробует снова.

::: details Решение и разбор
```js
function once(fn) {
  let done = false;
  let result;
  return function (...args) {
    if (done) return result;
    done = true; // before the call: covers throw and re-entrancy
    try {
      result = fn.apply(this, args);
    } finally {
      fn = null; // release fn and everything it captured
    }
    return result;
  };
}

function onceAsync(fn) {
  let promise = null;
  return function (...args) {
    if (!promise) {
      promise = Promise.resolve().then(() => fn.apply(this, args));
      promise.catch(() => { promise = null; }); // allow a retry
    }
    return promise;
  };
}
```

Проверено в Node 26: после исключения `once` возвращает `undefined` и не вызывает `fn` повторно (как lodash и Ramda); рекурсивный вызов изнутри `fn` получает `undefined`, а не второе выполнение; `onceAsync` отдаёт параллельным вызовам один промис, а после отклонения выполняет `fn` ещё раз. Частые ошибки: флаг ставится после вызова (исключение или рекурсия выполнят `fn` дважды), проверка `if (result)` вместо флага (ложный результат вызывает функцию снова — как в `cacheStringFunction` Vue), стрелочная обёртка. Что спросят дальше: `before(n, fn)` и `after(n, fn)` из lodash, `once` для метода класса — на экземпляр, а не на прототип (тот же урок, что с `debounce` в `methods`).

Сложность: O(1) по времени и памяти.
:::
