# Каскад, специфичность, наследование и custom properties

> **Коротко.** Для каждого свойства каждого элемента браузер собирает все подходящие объявления, а каскад (cascade) сортирует их по критериям: origin и `!important`, контекст shadow DOM, атрибут `style`, каскадные слои `@layer`, специфичность, близость `@scope`, порядок появления. Каждый следующий критерий проверяется только при равенстве предыдущих. Если победителя нет, значение берётся по наследованию или из начального значения. Дальше значение проходит стадии specified → computed → used, и наследуется именно computed value. Custom properties тоже наследуются, а `var()` подставляется на этапе computed value. Поэтому неподходящее значение не откатывается к прошлому объявлению, а делает свойство invalid at computed-value time.

**Связанные темы:** [Стили в компонентах: scoped, CSS Modules, `v-bind()` в `<style>`](../vue/styles.md), [Design system и UI-kit](../architecture/design-systems.md), [Конвейер рендеринга: layout, paint, composite](../browser/rendering-pipeline.md), [DOM API и observers](../browser/dom.md), [Масштабирование фронтенда](../architecture/scaling-frontend.md), [Семантический HTML и мультимедиа](./semantic-html.md)

## Теория

Фрагменты проверены в Chromium 159 (Playwright 1.65, headless): страница через `page.setContent`, значения через `getComputedStyle`. Спецификации — CSS Cascading and Inheritance Level 5 и 6, Selectors Level 4, CSS Custom Properties Level 1, CSS Properties and Values API Level 1, CSS Values and Units 4 (Editor's Drafts, сверено 2026-11-22). Поддержка в браузерах — по MDN browser-compat-data 8.1.10 (2026-11-19).

### Стадии значения

Каскад — часть шага **Style** (recalc style) в [конвейере рендеринга](../browser/rendering-pipeline.md). Спецификация описывает путь значения так:

| Стадия | Что происходит | `font-size: 1.2em` | `width: 50%` |
| --- | --- | --- | --- |
| **declared** | все объявления, которые прошли фильтрацию: правило подходит к элементу, условия `@media`/`@supports` истинны, синтаксис верен | `1.2em` (и другие кандидаты) | `50%` |
| **cascaded** | победитель каскада; его может не быть | `1.2em` | `50%` |
| **specified** | defaulting: нет победителя — наследование или начальное значение; CSS-wide keywords (`inherit`, `initial`…) раскрываются здесь | `1.2em` | `50%` |
| **computed** | относительное делается абсолютным, насколько это возможно без layout: `em` → `px`, URL → абсолютный, `var()` подставлен | `19.2px` (при 16px у родителя) | `50%` |
| **used** | досчитано после layout | `19.2px` | `200px` |
| **actual** | подогнано под устройство: округление, доступные шрифты | `19px` | `200px` |

Два вывода, о которых спрашивают:

- **Наследуется computed value.** `width: inherit` у ребёнка элемента с `width: 50%` даёт `50%` от своего родителя, а не пиксели родителя: блок 400px → `section` 50% (200px) → `p { width: inherit }` получил 100px. По той же причине `line-height: 1.5em` при `font-size: 10px` наследуется как `15px` и ребёнку с `font-size: 20px` строки слипаются, а безразмерный `line-height: 1.5` наследуется числом и даёт ребёнку 30px.
- **`getComputedStyle` возвращает resolved value**, а не всегда computed. Для `width`, `height`, `margin`, `top` и ещё нескольких свойств на отрисованном элементе это used value (`200px` вместо `50%`), для остальных — computed. У элемента с `display: none` layout нет, и `width` вернётся computed-значением.

Отдельно от стадий — **фильтрация при разборе**. Объявление с неверным синтаксисом (`color: 20px`) выбрасывается парсером, как будто его нет. Поэтому `color: red; color: 20px` даёт красный: работает предыдущее объявление. Так устроен CSS-приём «сначала запасное значение, потом новое».

### Порядок сортировки каскада

Каскад сортирует объявления для одного свойства одного элемента по критериям в порядке убывания приоритета (Cascade 6):

1. **Origin и importance** — источник объявления и `!important`.
2. **Context** — дерево, из которого пришло объявление (shadow DOM).
3. **Атрибут `style`** — объявления, привязанные прямо к элементу.
4. **Layers** — каскадные слои `@layer`.
5. **Specificity** — специфичность селектора.
6. **Scope proximity** — близость корня `@scope`.
7. **Order of appearance** — порядок в документе: последний выигрывает.

Это не сумма баллов. Критерий ниже по списку не может перевесить критерий выше: `#a.b p.x` в слое проиграл `p` без слоя, потому что слои сравниваются раньше специфичности.

### Origin и `!important`

Объявление приходит из одного из трёх **origins**: user-agent (стили браузера по умолчанию), user (настройки пользователя), author (стили страницы). Плюс отдельные «источники» для анимаций и переходов. По убыванию приоритета: transitions → important UA → important user → important author → animations → normal author → normal user → normal UA.

`!important` **переворачивает** порядок origins. Обычные стили автора сильнее пользовательских, а важные стили пользователя сильнее важных стилей автора. Смысл — доступность: пользователь, которому нужен крупный шрифт или контраст, может перебить любую страницу. Анимация `@keyframes` перебивает обычное объявление, но не `!important`: в Chromium `p { color: red }` проиграл анимации, а `.imp { color: blue !important }` её перебил.

> [!NOTE]
> `!important` не часть значения, а флаг объявления. У custom property `--c: red !important` важно само объявление `--c`, а в `var(--c)` подставится просто `red`.

### Context: shadow DOM

Если объявления пришли из разных деревьев (документ и shadow root), то для обычных объявлений побеждает **внешний** контекст, а для `!important` — **внутренний**. Проверено: `:host { color: red }` внутри shadow root проиграл `x-el { color: blue }` снаружи, а с `!important` с обеих сторон выиграл внутренний `:host`. Так компонент задаёт значения по умолчанию, которые страница может переопределить, и с помощью `!important` может закрепить то, что переопределять нельзя. Что именно проникает через границу shadow root — в [«DOM API и observers»](../browser/dom.md).

### Атрибут `style`

Объявления из атрибута `style` сильнее объявлений из правил той же важности, и этот критерий стоит **перед** слоями и специфичностью. `style="color: blue"` выиграл у `#t#t#t { color: red }`. `style="color: blue !important"` выиграл у `!important` в слое, хотя важные объявления в слоях обычно сильнее неслоёных. А обычный `style` проиграл любому `!important` автора: важность сравнивается раньше.

> [!NOTE]
> Старая формула «inline-стили — это специфичность (1, 0, 0, 0)» описывает результат, но не модель. В Selectors 4 специфичность трёхкомпонентная (A, B, C), а атрибут `style` — отдельный шаг каскада.

### Каскадные слои `@layer`

Слой — именованная группа правил с явным приоритетом. Порядок слоёв задаётся **первым упоминанием**, поэтому его объявляют одной строкой в начале: `@layer reset, vendor, base, components, utilities;`. Сторонний CSS кладут в слой при импорте: `@import url("datepicker.css") layer(vendor);`. Полная схема — в «Примерах».

Правила сравнения:

- Для обычных объявлений побеждает **более поздний** слой, независимо от специфичности.
- **Неслоёные стили** образуют неявный последний слой и сильнее любого слоя. Поэтому стили, которые ещё не перенесены в слои, перебивают слоёные.
- Для `!important` порядок обратный: побеждает **ранний** слой, а неслоёный `!important` слабее любого слоёного. Проверено: `@layer base { p { color: red !important } }` выиграл у `#t { color: blue !important }`.
- Вложенные слои (`@layer a { @layer x { … } }`, имя `a.x`) упорядочены внутри родителя, а собственные правила родителя без вложенного слоя — последние в нём.
- `@layer { … }` без имени создаёт анонимный слой. Каждый такой блок — отдельный слой, дописать в него нельзя.

Зачем это нужно: специфичность перестаёт быть оружием. Сторонний CSS с `#app .dp-header .dp-title` кладётся в `layer(vendor)` и проигрывает простому `.title` из `base`. Утилиты в последнем слое перебивают компоненты без `!important`.

> [!WARNING]
> `!important` внутри стороннего слоя (`vendor`) после переворота **сильнее** ваших `!important` в более поздних слоях. Из стилей автора его перебьёт только `!important` в ещё более раннем слое или в атрибуте `style`.

`@layer` и `revert-layer` поддерживаются с Chrome 99, Firefox 97, Safari 15.4.

### Специфичность

Специфичность селектора — тройка (A, B, C), которая сравнивается покомпонентно, без переноса разрядов: **A** — ID-селекторы, **B** — классы, атрибуты и псевдоклассы, **C** — типы и псевдоэлементы. `*` и комбинаторы не считаются.

`ul li.red` — (0, 1, 2), `#nav a:hover` — (1, 1, 1). Одиннадцать классов не перебьют один ID. Повтор того же селектора считается: `.btn.btn` — (0, 2, 0), этим приёмом поднимают специфичность без изменения смысла.

Особые псевдоклассы:

- `:is()`, `:not()`, `:has()` берут специфичность **самого специфичного** аргумента, даже если элемент совпал с другим. `:is(p, #nope)` на `<p>` без id — это (1, 0, 0), и он выиграл у `p.c`. `p:not(#nope)` — (1, 0, 1).
- `:where()` всегда (0, 0, 0). На нём строят сбросы и стили библиотек, которые легко переопределить.
- `:nth-child(2n of .item)` — один псевдокласс плюс самый специфичный аргумент.
- В обычном списке `#nope, p { … }` каждый селектор считается отдельно, и берётся тот, что совпал. Здесь — `p`.
- **CSS Nesting** заворачивает родителя в `:is()`: правило `#nope, .a { & p { … } }` — это `:is(#nope, .a) p` со специфичностью (1, 0, 1). Проверено: оно выиграло у `.a p.c`.

Подробно о самих селекторах — в теме «Селекторы, псевдоклассы и псевдоэлементы».

### `@scope` и близость

`@scope (.card) to (.content) { img { … } }` ограничивает правила поддеревом: от корня `.card` до границы `.content`. Селекторы внутри **не получают** специфичность корня: `@scope (#hero) { p {} }` — это (0, 0, 1), как `:where(#hero) p`. `:scope` внутри даёт (0, 1, 0), `&` — ноль.

Новый критерий каскада — **scope proximity**: при равной специфичности побеждает правило, корень которого ближе к элементу по числу шагов вверх по дереву. Проверено на вложенных темах: `<div class=light><div class=dark><p>` — правило `@scope (.dark)` выиграло у `@scope (.light)`, хотя стоит раньше. Близость стоит **после** специфичности: `div p` (0, 0, 2) выиграл у `@scope (#hero) { p }`.

`@scope` поддерживается в Chrome 118, Firefox 146, Safari 26.4 (в Safari 17.4–18.6 тоже была поддержка, в 26.0–26.3 — частичная). Scoped-стили Vue — другой механизм: переписанный селектор с атрибутом `data-v-*`, который **повышает** специфичность. Подробно — в [«Стилях в компонентах»](../vue/styles.md).

### Порядок появления

Последнее по документу объявление выигрывает. `@import` подставляется на место правила, `<link>` и `<style>` идут в порядке документа, атрибуты `style` — после всех таблиц. Для SPA это значит, что порядок CSS-чанков задаёт сборщик и меняется при code splitting. Два правила одинаковой специфичности из разных чанков могут поменяться местами между страницами. Слои снимают эту зависимость.

### Наследование и CSS-wide keywords

Если победителя каскада нет, **наследуемое** (inherited) свойство берёт computed value родителя, а ненаследуемое — начальное значение (initial value) из таблицы определения свойства. Наследуются в основном текстовые свойства: `color`, `font-*`, `line-height`, `letter-spacing`, `text-align`, `visibility`, `cursor`, `direction`, все custom properties. Не наследуются свойства блока: `margin`, `padding`, `border`, `background`, `width`, `display`, `position`, `opacity`, `transform`. Наследование идёт по flat tree: слотированный элемент наследует от `<slot>`, а не от родителя в light DOM.

| Ключевое слово | Что делает | `display` на `<div>` |
| --- | --- | --- |
| `inherit` | computed value родителя | как у родителя |
| `initial` | начальное значение **свойства**, не стиль браузера | `inline` |
| `unset` | `inherit` для наследуемых, `initial` для остальных | `inline` |
| `revert` | откат к предыдущему origin: для автора — к стилям user/UA | `block` (из UA) |
| `revert-layer` | откат к предыдущему слою; если слоя нет — как `revert` | значение из прошлого слоя |
| `revert-rule` | как будто текущего правила нет | значение из прошлого правила |

`all` сбрасывает сразу все свойства, кроме `direction`, `unicode-bidi` и custom properties. `all: unset` на `<h1>` даёт `display: inline` и унаследованный размер шрифта. `all: revert` возвращает браузерные 32px и `display: block`. Для сброса оформления кнопки лучше подходит `revert`: `initial` и `unset` выбрасывают и стили браузера, которые нужны (у `<div>` пропадает `display: block`). `revert-rule` — новинка Cascade 5 (Chrome 148, Firefox 150, Safari 27). Вместе с `if()` (Chrome 137, Safari 27.3, в Firefox нет) он позволяет условно «выключить» объявление.

> [!WARNING]
> Элементы форм в стилях браузера не наследуют шрифт и цвет: у `<button>` при `body { color: rgb(1, 2, 3) }` цвет остался чёрным. Отсюда строка любого reset: `button, input, select, textarea { font: inherit; color: inherit; }`.

### Custom properties

Custom property (`--name`) — обычное наследуемое свойство с почти любым значением. Парсер проверяет только общую грамматику, а значение хранится **последовательностью токенов** до подстановки.

**Подстановка — на этапе computed value**, на каждом элементе отдельно. `var(--x)` берёт computed value `--x` **этого** элемента, а значения в `var()` внутри custom property подставляются там, где эта custom property объявлена. Отсюда главная ловушка:

```css
:root { --base: 10px; --double: calc(var(--base) * 2); }
.box  { --base: 20px; width: var(--double); }   /* 20px, not 40px */
```

`--double` вычислен на `:root` как `calc(10px * 2)` и унаследован уже готовым. Переопределение `--base` на `.box` его не трогает. Производное значение надо объявлять на том элементе, где меняется исходное: `.box { width: calc(var(--base) * 2) }`.

**Fallback.** `var(--x, fallback)` использует второй аргумент, если `--x` имеет **guaranteed-invalid value**: не задана, сброшена `initial`, попала в цикл. Fallback может содержать запятые (`var(--font, Inter, sans-serif)`) и другие `var()`. Пустое значение `--x: ;` — валидное пустое значение, а не «нет значения». Fallback не сработает, а подстановка даст пустоту.

**Invalid at computed-value time (IACVT).** Парсер не знает, что подставится в `var()`, поэтому объявление с `var()` принимается всегда. Если после подстановки значение не подошло свойству, откатиться к прошлому объявлению уже нельзя: каскад закончился. Свойство ведёт себя как `unset`:

```css
body { color: green; }
p    { --c: 20px; color: red; color: var(--c); }  /* green: inherited, not red */
```

Для ненаследуемого `background-color` тот же приём дал `transparent`. Циклы (`--one` ссылается на `--two`, а `--two` на `--one`) делают обе переменные guaranteed-invalid. В этом случае у `var(--one, 33px)` срабатывает fallback.

**Каскад для custom properties тот же:** слои, специфичность, `!important`. Поэтому темы и переопределения компонента работают через обычные селекторы.

### `@property`

Регистрация превращает custom property в «настоящее» свойство с типом, наследованием и начальным значением:

```css
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}
```

Что меняется:

- **Тип проверяется на этапе computed value.** Неподходящее значение даёт IACVT, и свойство получает `initial-value`, а не наследование и не пустоту. `--c: 20px` при `syntax: '<color>'` дал синий из `initial-value`.
- **`inherits: false`** отключает наследование: значение у `div` не дошло до вложенного `p`, там остался `initial-value`. Для токенов, которые задаются только на корне компонента, это защищает от случайного наследования внутрь вложенных компонентов.
- **Подставляется computed value**, а не токены: `--x: 8em` при `font-size: 10px` у зарегистрированного `<length>` даёт в `var(--x)` `80px`. У незарегистрированного — `8em`, который пересчитается на месте подстановки.
- **Анимируемость.** Незарегистрированная custom property при `transition` меняется скачком: в Chromium анимация вообще не создалась, значение сразу стало `180deg`. Зарегистрированная `<angle>` интерполируется: на середине перехода `--angle` была `90deg`. Так анимируют градиенты, которые сами по себе не интерполируются.
- `initial-value` обязан быть **computationally independent** (`10px` можно, `3em` нельзя) — иначе правило невалидно.

`@property` поддерживается в Chrome 85, Firefox 128, Safari 16.4; из JS — `CSS.registerProperty()`. Регистрация глобальна для документа, в том числе для shadow DOM.

> [!WARNING]
> В текущем Editor's Draft дескрипторы `syntax` и `inherits` необязательны, и есть короткая форма `@property --c <color>: blue;`. В Chromium 159 правило без `inherits` или без `syntax` игнорируется целиком, а короткая форма не поддерживается. Пишите оба дескриптора.

Тип проверяется только на этапе computed value, поэтому `@supports (--c: 1em)` истинно даже для зарегистрированной `<color>`.

### Темизация через каскад

Тема — это переопределение custom properties в поддереве. Компоненты ссылаются на семантические токены (`.card { background: var(--bg) }`), а `[data-theme=dark] { --bg: rgb(17 17 17) }` меняет их значения. Наследование доставляет значение до каждой карточки внутри `[data-theme=dark]`, а карточка снаружи остаётся светлой. Альтернатива без дублирования — `color-scheme: light dark` и `light-dark(white, rgb(17 17 17))`: функция выбирает значение по used color scheme элемента. `.d { color-scheme: dark }` переключил её на тёмный вариант (поддержка: Chrome 123, Firefox 120, Safari 17.5). Почему темы строят на трёх уровнях токенов и как избежать мигания при SSR — в [«Design system и UI-kit»](../architecture/design-systems.md).

> [!TIP]
> Разделяйте публичные и приватные переменные компонента: `--btn-bg` — API для потребителя, `--_bg: var(--btn-bg, var(--accent))` — внутренняя. Потребитель задаёт `--btn-bg` на любом предке, и специфичность при этом неважна.

Цена переменных на корне — пересчёт стилей: смена custom property на `<html>` заставляет пересчитать стили всего поддерева, которое её наследует. Часто меняемые значения (координаты, прогресс) ставят на конкретный элемент. Пример с `v-bind()` во Vue — в [«Стилях в компонентах»](../vue/styles.md).

## Примеры

### Архитектура стилей на слоях с темой и анимируемым токеном

```html
<style>
  @layer reset, vendor, base, components, utilities;
  @import url("datepicker.css") layer(vendor);

  @property --accent-h {
    syntax: '<number>';
    inherits: true;
    initial-value: 250;
  }

  @layer reset {
    *, *::before, *::after { box-sizing: border-box; margin: 0; }
    button, input { font: inherit; color: inherit; }
  }

  @layer base {
    :root {
      color-scheme: light dark;
      --bg: light-dark(white, rgb(17 17 17));
      --fg: light-dark(rgb(17 17 17), rgb(238 238 238));
    }
    [data-theme="dark"]  { color-scheme: dark; }
    [data-theme="light"] { color-scheme: light; }
    body, [data-theme] { background: var(--bg); color: var(--fg); }
  }

  @layer components {
    .btn {
      /* public API: --btn-bg; private: --_bg */
      --_bg: var(--btn-bg, oklch(60% 0.15 var(--accent-h)));
      background: var(--_bg);
      color: white;
      transition: --accent-h 200ms;
    }
    .btn:hover { --accent-h: 300; }
    .toolbar .btn.btn-primary { padding: 8px 16px; }
  }

  @layer utilities {
    .p-0 { padding: 0; }   /* beats (0, 3, 0) from components */
  }
</style>

<div data-theme="dark">
  <button class="btn btn-primary p-0">Save</button>
  <button class="btn" style="--btn-bg: crimson">Delete</button>
</div>
```

Что здесь происходит:

- Порядок слоёв задан первой строкой, поэтому `.p-0` с (0, 1, 0) перебивает `.toolbar .btn.btn-primary` с (0, 3, 0). Утилитам не нужен `!important`.
- Сторонний `datepicker.css` с любой специфичностью проигрывает `base` и `components`: его слой раньше.
- `oklch(…var(--accent-h))` вычисляется на самой кнопке, поэтому `:hover` на ней меняет цвет. Если бы цвет был собран в `:root { --accent: oklch(…) }`, `--accent-h` на кнопке ничего бы не изменил.
- `--accent-h` зарегистрирован как `<number>`, и переход по нему плавно меняет оттенок. Переход `background-color` здесь бы тоже сработал, но через токен можно анимировать любое число свойств сразу, в том числе градиенты.
- `--bg` не зарегистрирована, поэтому `light-dark()` подставляется токенами и вычисляется на том элементе, где стоит `var(--bg)`, по его `color-scheme`. `[data-theme]` только задаёт схему поддерева и сам получает фон темы.
- Кнопка «Delete» переопределяет публичную переменную через `style`. Внутренний `--_bg` подхватывает её без правки CSS компонента.

Проверено: у кнопки «Save» `padding` стал `0px`, правило из подключённого в `vendor` CSS с `#app .btn` не применилось, фон `[data-theme="dark"]` — `rgb(17, 17, 17)` при светлой схеме страницы, через 100 мс из 200 `--accent-h` равен `290.12` (переход с функцией `ease`).

## Вопросы с интервью

::: details Как браузер выбирает значение свойства, если несколько правил конфликтуют
Каскад сортирует все подходящие объявления для свойства элемента по критериям, каждый следующий — только при равенстве предыдущих. Первым идёт origin и важность: transitions, важные UA, user, author, animations, обычные author, user, UA. Дальше контекст shadow DOM (обычные — внешний, важные — внутренний), атрибут `style`, каскадные слои, специфичность, близость `@scope`, порядок появления. Если после сортировки нет ни одного объявления, наследуемое свойство берёт значение родителя, ненаследуемое — начальное. Важно, что это лексикографическое сравнение, а не сумма баллов: правило в раннем слое не спасёт никакая специфичность.
:::

::: details Почему !important переворачивает порядок источников и слоёв
Чтобы `!important` всегда означал одно и то же: «закрепить значение у того, кто стоит раньше». Для origins это гарантия пользователю: важные пользовательские стили (крупный шрифт, контраст) сильнее важных стилей страницы. Для слоёв так же: базовый слой может закрепить `!important` то, что более поздние слои и утилиты не перебьют. Неслоёный `!important` при этом слабее любого слоёного. Следствие для практики: `!important` в слое сторонней библиотеки, который подключён рано, сильнее ваших `!important` в поздних слоях.
:::

::: details Как считается специфичность и как на неё влияют is, where, not и has
Тройка (A, B, C): ID; классы, атрибуты и псевдоклассы; типы и псевдоэлементы. Сравнивается покомпонентно, без переноса: один ID сильнее любого числа классов. `*` и комбинаторы не считаются. `:is()`, `:not()` и `:has()` берут специфичность самого специфичного аргумента, даже если элемент совпал с другим: `:is(p, #x)` — это (1, 0, 0) для любого `p`. `:where()` даёт ноль, поэтому на нём пишут сбросы и стили библиотек, которые должны легко переопределяться. CSS Nesting заворачивает родителя в `:is()`, и `#a, .b { & p {} }` получает ID-специфичность даже для `.b p`. Атрибут `style` в специфичности не участвует: это отдельный шаг каскада выше неё.
:::

::: details Зачем нужны каскадные слои и почему неслоёные стили сильнее слоёных
Слои дают явный приоритет групп правил, который проверяется раньше специфичности. Порядок задаётся первым упоминанием, обычно строкой `@layer reset, vendor, base, components, utilities;`. Сторонний CSS кладётся в слой через `@import … layer(vendor)` и перестаёт выигрывать за счёт длинных селекторов, а утилиты в последнем слое перебивают компоненты без `!important`. Неслоёные стили — неявный последний слой. Это сделано для постепенного перехода: старый CSS без слоёв продолжает перебивать новый, ничего не ломается. Для `!important` порядок обратный, как и у origins.
:::

::: details Чем computed value отличается от used value и что возвращает getComputedStyle
Computed value — значение после раскрытия ключевых слов и перевода относительных единиц в абсолютные там, где это возможно без layout: `em` → `px`, URL → абсолютный, `var()` подставлен. Проценты ширины остаются процентами. Именно computed value наследуется, поэтому `width: inherit` даёт ребёнку проценты, а `line-height: 1.5em` наследуется готовыми пикселями, в отличие от безразмерного `1.5`. Used value досчитывается после layout: `50%` → `200px`, `auto` → длина. `getComputedStyle` возвращает resolved value: для геометрических свойств отрисованного элемента это used value, для остальных — computed. Значение у элемента с `display: none` будет computed.
:::

::: details Что наследуется и чем inherit, initial, unset и revert отличаются
Наследуются в основном текстовые свойства (`color`, `font`, `line-height`, `visibility`, `cursor`) и все custom properties. Свойства блока (`margin`, `padding`, `border`, `background`, `display`) не наследуются. `inherit` берёт computed value родителя, `initial` — начальное значение свойства из спецификации (у `display` это `inline`, а не `block` браузера). `unset` работает как `inherit` или `initial` в зависимости от свойства. `revert` откатывает к предыдущему origin: для стилей автора это стили браузера, поэтому `<div>` остаётся блочным. `revert-layer` откатывает к предыдущему слою. `all` применяет ключевое слово ко всем свойствам, кроме `direction`, `unicode-bidi` и custom properties.
:::

::: details Когда подставляется var() и что такое invalid at computed-value time
`var()` подставляется на этапе computed value, на каждом элементе отдельно. Берётся computed value custom property этого элемента, а `var()` внутри самой custom property подставляется там, где она объявлена. Поэтому производная переменная на `:root` не реагирует на переопределение исходной в поддереве. Парсер не может проверить объявление с `var()` и принимает его. Если после подстановки значение не подходит свойству, к прошлому объявлению уже не вернуться. Свойство становится invalid at computed-value time и ведёт себя как `unset`: `color: red; color: var(--size)` даёт унаследованный цвет, а не красный. Fallback `var(--x, …)` срабатывает только при guaranteed-invalid value: переменная не задана, `initial` или цикл.
:::

::: details Что даёт @property по сравнению с обычной custom property
Тип, начальное значение и управление наследованием. Тип проверяется на этапе computed value: неподходящее значение даёт `initial-value`, а не пустоту или наследование. `inherits: false` ограничивает переменную элементом, где она задана. В `var()` подставляется computed value (`8em` → `80px`), а не токены. Главное на практике — анимируемость: зарегистрированный `<angle>` или `<color>` интерполируется в `transition` и `@keyframes`, и через него анимируют градиенты. Незарегистрированная переменная меняется скачком. Регистрация глобальна для документа. В Chromium правило без `syntax` или `inherits` игнорируется, хотя в черновике спецификации они уже необязательны.
:::

## Задачи

### 1. Какого цвета текст · легко

```html
<style>
  @layer base, theme;
  @layer theme { #title { color: red; } }
  @layer base  { h1 { color: green !important; } }
  h1.title { color: blue; }
</style>
<h1 id="title" class="title" style="color: orange">Hello</h1>
```

Какого цвета заголовок? Что изменится, если убрать `!important`?

::: details Решение и разбор
Зелёный. Origin и важность сравниваются первыми: `!important` автора сильнее любого обычного объявления автора, в том числе атрибута `style`. Слои, специфичность и порядок для него уже не важны.

Без `!important` — оранжевый. Атрибут `style` проверяется раньше слоёв и специфичности. Если убрать и `style`, выиграет `h1.title` (синий): неслоёные стили сильнее слоя `theme`, хотя `#title` специфичнее. Проверено в Chromium: зелёный, оранжевый, синий.
:::

### 2. Найдите баг: hover не меняет оттенок · средне

```css
:root {
  --hue: 250;
  --accent: hsl(var(--hue) 70% 50%);
}
.btn { background: var(--accent); }
.btn:hover { --hue: 330; }
```

При наведении кнопка не меняет цвет. Почему и как исправить?

::: details Решение и разбор
`var(--hue)` внутри `--accent` подставляется на `:root`, где объявлен `--accent`. Кнопка наследует уже готовое `hsl(250 70% 50%)`, и `--hue` на кнопке в нём ничего не меняет. Проверено: на `.btn:hover` `--hue` равен `330`, а цвет фона остался прежним.

Исправление — собрать цвет там, где меняется исходное значение. Если `--accent` нужен как общий токен, его переобъявляют на компоненте, и подстановка происходит на кнопке:

```css
:root { --hue: 250; }
.btn { --accent: hsl(var(--hue) 70% 50%); background: var(--accent); }
.btn:hover { --hue: 330; }
```

Чтобы смена оттенка была плавной, `--hue` регистрируют через `@property` с `syntax: '<number>'` и добавляют `transition: --hue 200ms`.
:::

### 3. Почему текст стал чёрным · средне

Дизайн-система разрешает темам переопределять `--brand`. Одна тема по ошибке задала размер:

```css
body { color: black; }
.link { color: blue; color: var(--brand); }
.theme-x { --brand: 16px; }
```

Почему ссылка внутри `.theme-x` чёрная, а не синяя? Как сделать, чтобы при неверном значении компонент получал осмысленный цвет?

::: details Решение и разбор
Объявление `color: var(--brand)` парсер принимает, оно вытесняет `color: blue` уже при разборе. После подстановки `16px` не цвет, и свойство становится invalid at computed-value time. Оно ведёт себя как `unset`, то есть `inherit` для `color`: ссылка унаследовала чёрный от `body`. Приём «запасное значение строкой выше» с `var()` не работает.

Решение — зарегистрировать токен:

```css
@property --brand {
  syntax: '<color>';
  inherits: true;
  initial-value: blue;
}
.link { color: var(--brand); }
```

Теперь неверное значение `--brand` даёт его `initial-value`, и в `var()` подставится синий. Проверено: с регистрацией ссылка синяя. `var(--brand, blue)` здесь не поможет: fallback срабатывает только для guaranteed-invalid value, а `16px` — обычное значение незарегистрированной переменной.
:::

### 4. Сверстайте темизируемую кнопку для UI-kit · сложно

Нужна кнопка библиотеки, которую подключают в чужие приложения:

- стили библиотеки не должны перебивать стили приложения, даже если у приложения селекторы проще;
- приложение может поменять цвет кнопки на любом предке без увеличения специфичности;
- у библиотеки есть тёмная тема по `[data-theme="dark"]` на любом предке;
- приватные переменные кнопки не должны быть видны её содержимому (иконкам и вложенным компонентам);
- неверное значение от приложения не должно делать кнопку «невидимой» случайным образом.

::: details Решение и разбор
```css
@property --_ui-btn-bg {
  syntax: '<color>';
  inherits: false;
  initial-value: rgb(37 99 235);
}
@property --_ui-btn-fg {
  syntax: '<color>';
  inherits: false;
  initial-value: white;
}

@layer ui {
  :where(.ui-btn) {
    --_ui-btn-bg: var(--ui-btn-bg, var(--ui-accent, rgb(37 99 235)));
    --_ui-btn-fg: var(--ui-btn-fg, white);
    background: var(--_ui-btn-bg);
    color: var(--_ui-btn-fg);
    border: 0;
    padding: 0.5em 1em;
    font: inherit;
  }
  :where(.ui-btn:hover) {
    --_ui-btn-bg: color-mix(in oklch, var(--ui-btn-bg, var(--ui-accent, rgb(37 99 235))), black 15%);
  }
  :where([data-theme="dark"]) {
    --ui-accent: rgb(96 165 250);
  }
}
```

Приложение:

```css
@layer ui;                          /* library layer goes first */
@import url("ui-kit.css") layer(ui);

.danger-zone { --ui-btn-bg: crimson; }   /* any ancestor */
.ui-btn { padding: 0; }                  /* simple selector wins */
```

Разбор:

- **Слой.** Всё в `@layer ui`, а приложение объявляет этот слой первым или вообще пишет без слоёв. Неслоёный `.ui-btn` приложения выигрывает у слоя библиотеки, какой бы ни была специфичность. Библиотека не может решить это за приложение: порядок слоёв задаёт тот, кто первым их упомянул. Поэтому дополнительно все селекторы обёрнуты в `:where()`, и специфичность библиотеки нулевая даже без слоёв.
- **Публичный API** — `--ui-btn-bg`, `--ui-btn-fg`, `--ui-accent` с fallback. Наследование доставляет их с любого предка, специфичность потребителя не важна.
- **Приватные** `--_ui-btn-*` вычисляются на самой кнопке и зарегистрированы с `inherits: false`: содержимое кнопки их не видит, `var(--_ui-btn-bg)` внутри иконки даст начальное значение, а не фон кнопки. Тип `<color>` превращает неверное значение (`--ui-btn-bg: 12px`) в `initial-value`, то есть в фирменный синий, а не в IACVT с прозрачным фоном. Регистрация глобальна для документа, поэтому имена с префиксом библиотеки.
- **Тема** меняет только `--ui-accent` в поддереве. Явный `--ui-btn-bg` приложения сильнее темы, потому что стоит первым в цепочке fallback.
- `!important` в библиотеке не нужен. В раннем слое он стал бы непробиваемым для приложения.
:::
